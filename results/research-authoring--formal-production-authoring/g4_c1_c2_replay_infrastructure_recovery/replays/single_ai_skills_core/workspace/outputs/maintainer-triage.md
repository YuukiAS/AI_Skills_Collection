# 候选插件回放维护分诊

该说明提出的是发布前回放的证据要求：必须证明子运行时实际使用了候选插件。可能的实现责任层是 Bridge Kit 的插件回放运行时；AI Skills Maintainer 负责中央候选插件的维护合同及证据验收。当前材料足以作责任分诊，尚不足以确认具体缺陷或宣布修复、发布完成。

**来源与边界。** [维护说明](../inputs/01-single_ai_skills_core_input.md)第 3 行明确要求预发布插件被子运行时实际消费，并将交付物限定为有明确范围的路由回执。说明未提供插件标识、候选版本或哈希、运行记录、公开来源链接。本次只核对所提供文本；未独立验证其公开出处，也未运行回放。工作区未提供中央仓库 TODO、维护看板政策、回放实现或测试，故未完成去重和现行实现核查。

**责任判断。** 已安装 `ai-skills-core` 的 `maint/SKILL.md` 中 “Production Consumption Diagnosis” 要求区分安装身份、实际加载、路由和测试忠实度；静态源码或生成一致性不能证明正常入口消费。其 `bridge/SKILL.md` 的 “Boundary” 明确将插件回放运行时及运行时源码变更交由 Bridge Kit。因此，建议由 `GPT_Codex_AI_Bridge_Kit` 的运行时维护者定位实现，AI Skills Maintainer 配合核验候选身份与消费证据；该归属仍需以实际 helper 的源码位置确认。无需交给领域写作插件，也不应在 AI_Skills 内复制一套回放运行时。

**分诊结论。** 暂按待核实的基础设施维护反馈处理，保留 `NEW`，不直接晋升为 `PROMOTE_NOW`。现有维护规则已覆盖“实际消费”的要求，应先查执行链，再决定是否缺能力。当前不能在 `not_loaded`、`stale_install`、`consumer_not_routed`、`unfaithful_test`、`execution_noncompliance` 或 `capability_gap` 中作确诊。问题涉及过程证据，尚无产品产物质量失败的证据。

**建议的最小后续核查。** 先读取责任仓库的现行合同、已有 TODO 和相关测试，复用已有条目。随后在获授权的有界回放中收集路由回执，建议至少关联：候选插件标识及内容哈希、回放与子运行时身份、实际加载的插件来源、触发的技能或路由、对应证据位置。用同一次运行把候选身份与实际消费关联起来；仅有安装成功、退出码为零或执行者自述不够。具体回执字段应沿用现有合同，不据此另建 schema。若确认需要修改运行时，交回该层 Planner/Critic 冻结范围，再做原失败回放及无关回归。
