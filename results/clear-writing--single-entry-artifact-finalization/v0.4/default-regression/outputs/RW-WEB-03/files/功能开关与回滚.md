功能开关不能替代回滚方案，因为它能控制接下来的请求走哪段代码，却不会自动撤销之前已经写入的数据，也不会把数据库结构改回原样。回滚方案需要解决的是：出了问题以后，怎样让代码、数据和数据库结构重新配合，恢复可用的服务。关闭开关可以是其中一步，但不能单凭这一步判断恢复已经完成。

可以把功能开关想成路口的指示牌：把车辆引回旧路，能阻止后续车辆进入新路，却不会把已经运到目的地的货物搬回去。应用里已经写下的账单数据，就像这些已经送达的货物。

**场景一：新搜索排序只改变读请求。** 它改变的是搜索结果的排列顺序，旧排序代码仍然存在，关闭开关后也不会留下新的持久化数据，也就是不会留下需要另行撤销的存储记录。若新排序出了问题，建议先关闭开关，让后续搜索回到旧排序，再确认实际请求确实使用旧排序、结果恢复到预期。按已知条件，这里可以优先用开关恢复旧行为；但输入没有提供关闭后的验证结果，因此还不能说服务已经恢复。

**场景二：新结算流程已经写入新账单字段，并执行了数据库迁移。** 字段是账单中保存某项信息的位置，数据库迁移则可能改变这些信息的存储结构。即使关闭新流程，已经写入的信息和已经改变的结构仍然存在。旧版本能否正确处理它们，决定了切回去后能否继续正常结算。

这里建议先确认怎样安全停止新流程继续写入，并验证旧版本能否读取迁移后的账单数据，再决定是否切回旧流程。如果关闭开关会立即把请求交给旧版本，就不能把“直接关掉”当成已验证的安全操作。需要恢复数据时，还应先完成恢复演练，确认已有账单如何保留、如何恢复，再执行相应操作。

目前只知道迁移脚本执行成功。这说明迁移跑完了，并不能说明旧版本兼容新字段，更不能说明数据一定能恢复。输入明确指出兼容性尚未验证、恢复演练尚未完成，也没有说明关闭开关后结算请求具体会怎样处理。因此，目前不能确定场景二能否直接切回旧版本，也不能确定该采用哪一种数据恢复方法；这些都需要验证后才能决定。
