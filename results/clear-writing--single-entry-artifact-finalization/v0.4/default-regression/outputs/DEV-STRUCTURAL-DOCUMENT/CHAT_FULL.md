# Clear Writing 调用策略与 Web 验证方案 v0.2

Clear Writing 希望让采用它的 ChatGPT Project 持续提供清楚、易读的最终回答，同时保证代码、命令、日志等精确输出不被改动。v0.2 提议由 Project 设置规定何时使用 Clear Writing，再由实际选中或加载的现有技能完成相应写作处理。没有 Project 策略时，平台按相关性自动选择插件的能力仍可测试，但不再承担主要入口的承诺。

这份设计的日期为 **2026-10-18**，状态为 `PLANNER_REVISION_FOR_CRITIC`，适用对象是 `writing-style / Clear Writing`。它仍是待 Critic 复核的提案：不重做六技能架构，不修改已经通过独立评审的生产候选版本，也不授权执行 Web 测试、修改真实 Project 设置或发布新版本。

## 一、调用策略解决什么问题

“要求使用插件”“平台实际加载插件”和“插件改善了回答”是三个不同问题，需要分别规定、分别取证。

| 层次 | 负责的事情 | 不能据此声称的事情 |
|---|---|---|
| Project 调用策略 | 规定哪些最终回答应尝试使用 Clear Writing | 不能证明平台已经选择或加载技能 |
| 平台激活 | 实际选择插件或读取具体技能的完整指令 | 不能仅凭插件被选中，就断定某个技能已完整加载 |
| Clear Writing 的处理行为 | 在具体技能实际被使用后，按职责改写文字或保护精确内容 | 不能仅凭最终文字好看，就断定改善来自插件 |

v0.2 据此确定三项边界：自然语言及混合型最终回答纳入 Project 调用策略，纯精确输出免于强制激活；多轮测试 W1 只证明策略下的行为可靠性；插件相对 Project 设置本身的额外价值，必须由严格配对的 W2 对照测试证明。

### 平台能力的适用时点

2026-10-18 对 OpenAI 官方资料的再次核对，与 v0.1 及 Critic 的平台现实检查结论一致，未发现会改变三个待处理问题判断的新事实：

- **Skills in ChatGPT**：安装后的技能可以在模型认为有帮助时自动使用。
- **OpenAI Developers Skills**：模型先看到技能名称和描述等元信息；请求匹配或用户直接调用后，才读取完整技能指令。
- **Plugins in ChatGPT**：插件可以因相关请求自动使用，也可以被用户直接选择或提及。
- **Projects in ChatGPT**：Project 指令仅在对应 Project 内有效，并覆盖全局自定义指令；Project 记忆模式会影响会话历史的可见范围，进而可能影响后续回答。

这些能力支持按相关性选择技能，但不构成公开承诺的“每条回答都调用技能”机制。当时未发现普通 ChatGPT Web 中可公开依赖、在每条回答发送前运行的技能收尾机制，也没有每轮都提供加载凭证的保证。因此，自动选择、Project 指令和技能加载不能当作同一种机制。

## 二、哪些回答使用 Clear Writing

### 自然语言和混合回答

采用 Clear Writing 的 Project，拟要求每条面向用户的自然语言最终回答使用合适的现有写作技能。若最终回答同时包含自然语言解释和机器内容，也适用这一策略。

这里的机器内容包括 JSON、YAML、代码、命令、日志、字段、路径和状态等需要精确保留的内容。混合任务中的解释可以由匹配的技能处理，机器内容必须保持精确，不能为了统一风格而改写。

Project 设置只表达调用策略，不复制 Clear Writing 的内部规则。它不负责具体技能分工中的专业判断，不直接重写语言，不模拟未安装或未加载的 Clear Writing，也不能声称某一轮已经真实加载插件。

### 六个现有技能的职责

当平台实际选中、直接调用或明确使用了某个 Clear Writing 技能后，继续按现有分工处理：

| 任务 | 负责技能 |
|---|---|
| 普通解释、诊断、建议和任务结果说明 | `response-clarity` |
| 正式中文文档、README、报告，以及 Markdown/PDF 成稿的最终语言检查 | `chinese-prose` |
| 中文或中文为主的科研技术材料，在忠实保留内容的前提下进行结构重写 | `scientific-rewrite` |
| 英文科学写作 | `scientific-prose` |
| 产品界面的标签、提示等短文案 | `product-ui-copy` |
| 事实、精确内容及其他保真要求的保护 | `writing-fidelity` |

`response-clarity` 不得越权接管其他写作技能的任务。本设计不新增第七个协调技能，也不新增路由器或状态机。

### 纯精确输出免于强制激活

若用户只要求纯 JSON、YAML、代码、命令、原始日志、逐字文本或其他精确机器输出，应直接返回要求的内容。这些任务不属于“每轮调用”策略的强制对象，不需要为了证明调用经过而加载写作技能。

没有加载任何写作技能，不能记成 Clear Writing 自己执行了 `BYPASS_EXACT`。免于激活与“已加载技能主动跳过处理”是不同事实。

如果用户显式选择 `@Clear Writing` 或插件，同时要求纯精确输出，仍须开展保持输出不变的压力测试。测试通过只能证明显式选择插件没有污染输出；若当前产品界面无法证明具体技能的完整指令已经加载，就不得声称“loaded-skill bypass PASS”。将来若 Web 界面支持直接调用具体技能，并能观察完整指令加载，可以增加诊断，但不新增发布验收关口。

### Project 设置中的最小桥接指令

若 Critic 最终批准设计，未来 Web 测试执行包中的桥接指令应保持最小范围：

> 对每条面向用户的自然语言最终回答，以及自然语言与机器 payload 混合的最终回答，如果当前 Clear Writing 可用，则使用其合适的现有 writing skill；pure JSON/YAML/code/command/raw log/verbatim/exact machine output 不为此强制调用 Clear Writing，直接保持精确原样。不要模拟、重建或复制 Clear Writing 内部规则。

这段指令只用于测试和正常入口的调用策略，不等于 Clear Writing 的实现，不复制六技能规则，也不证明插件已被实际使用。正式 W2 对照测试中，两组必须使用完全相同的桥接指令字节。本轮不得将它写入任何真实 Project 设置。

## 三、为什么选择这套方案

产品目标是让普通最终回答的阅读质量持续受益，同时不破坏精确机器输出。v0.2 比较了以下方案：

| 方案 | 决定与原因 |
|---|---|
| A：继续以无桥接指令的自动选择为主要入口 | 不采纳。官方能力只支持在相关或有帮助时自动使用，不能承担每轮调用的主要承诺。 |
| B：连纯精确输出也强制调用 Clear Writing | 不采纳。现有六技能没有协调者承担这项职责，纯精确任务也不应仅为证明调用而加载写作流程；否则容易把未加载误报为加载后的旁路。 |
| C：Project 策略覆盖自然语言和混合回答，纯精确输出免于激活，加载后的处理仍由现有技能负责 | 采纳。在不新增协调技能的前提下，覆盖用户需要阅读的最终内容。 |
| D：使用已知存在混杂因素的 W2 备选测试作为发布证据 | 不采纳。此类测试只能用于诊断，不能证明改善来自插件。 |

比较范围还包括把全部规则复制进 Project 设置。v0.2 选择的是 Project 调用策略加严格配对的增量验证，桥接指令不得复制内部规则。

设计从产品目标、平台现实、替代方案、反证和执行条件五方面检查可行性，尤其防止三类假通过：没有加载技能却声称完成加载后旁路；W1 文字表现良好就声称证明插件因果作用；W2 存在记忆、会话或插件可用性混杂，却声称完成严格配对比较。

## 四、Web 测试分别要证明什么

Web 验证保持 `W0 -> W1 -> W2 -> W3` 的顺序。W0 检查安全边界，W1 检查多轮行为，W2 检查插件增量，W3 只做自动发现诊断。以下均为未来执行包应满足的设计要求，本轮不执行。

### W0：调用策略是否安全

W0 分成自然语言／混合回答安全测试，以及显式选中插件后的纯精确输出压力测试。

**W0-A：自然语言与混合回答。** 在冻结的候选版本下，使用明确要求 Clear Writing 的 Web 请求，覆盖以下九类情况：

1. 普通技术解释。
2. 复杂科研解释。
3. 陌生方法或包含多重下标的对象。
4. 确有必要的长回答。
5. 临时改用英文及随后恢复默认语言。
6. 完整、可执行的提示词或合同。
7. 确实需要分支判断的流程。
8. 解释与 JSON、YAML、代码或日志混合的回答。
9. 命令、路径、字段、状态、提交和产品名等精确身份。

通过必须同时满足：任务进入正确的现有写作技能；`response-clarity` 不越权；混合回答的机器内容精确保留；长答不被机械压短；临时语言覆盖不污染后续默认语言；原有四组保持不变测试仍然成立。

**W0-B：显式选中插件后的纯精确输出。** 可以使用 `@Clear Writing` 或当前界面提供的明确插件级选择方式，至少覆盖纯 JSON、纯 YAML、纯代码、原始日志／逐字文本，以及精确命令／机器内容。

通过要求输出的字节内容等价：不能加自然语言前言，不能装饰、解释或重排字段、代码，插件选择本身不能污染精确输出。

若界面只能证明选中了插件，不能证明具体技能完整指令已加载，结论只能是：

`PLUGIN_SELECTION_DOES_NOT_CONTAMINATE_EXACT_OUTPUT`

不得将其写成“loaded-skill bypass PASS”。

W0 失败后，必须停止 W1/W2，不修改 Project 设置。应交回 Planner/Critic，仅针对现有六技能的元信息或合同边界做最小修复，不能默认新增协调技能。

### W1：Project 策略能否让多轮行为持续可靠

W1 要回答的是：用户不必每轮手动 `@` 时，Project 调用策略能否让多轮最终行为持续符合 Clear Writing 的目标合同。它不再尝试证明 Project 设置能强制每轮加载插件。

推荐测试序列至少包括：

| 序列 | 检查重点 |
|---|---|
| 普通解释 → 纯精确 JSON → 普通解释 | 精确输出豁免后能否恢复普通写作行为 |
| 中文 → 临时英文 → 恢复中文 | 临时语言要求是否只作用于指定范围 |
| 短回答 → 必要的长回答 | 是否按任务需要调整长度 |
| 解释 → 可执行提示词／合同 | 是否保留可执行性与完整性 |
| 某一写作技能任务 → 下一轮无关的普通回答 | 技能选择是否错误延续到后续轮次 |
| 混合回答 → 下一轮纯精确输出 → 普通回答 | 能否正确切换处理方式 |

通过要求多轮行为持续满足技能分工、跳过处理、语言恢复和不错误延续前轮行为的要求。纯精确输出的激活豁免不能影响下一轮普通 Clear Writing 行为；临时英文只能影响明确指定的范围；某个写作技能不能错误占用后续无关任务。

界面若提供调用或加载证据，必须记录；若没有证据，不能用模型自述“我用了 Clear Writing”代替。

W1 通过只支持：

`PROJECT_POLICY_BEHAVIOR_RELIABILITY=PASS`

它不单独支持：

`PLUGIN_LOADED_EVERY_TURN=PASS`

即使行为通过，没有加载证据也不得将结论升级为插件因果作用。W1 失败则表明 Project 策略作为正常入口不可靠，必须停止进入 W2 的发布结论验证。

### W2：插件是否带来可归因的稳定增量

W2 是唯一负责证明“Clear Writing 插件相对 Project 设置本身是否有稳定额外价值”的发布关键关口。测试必须严格配对：除插件候选版本的可用性／实际使用外，两组不得存在其他实质差异。

#### 运行前冻结测试条件

必须预先冻结并记录以下内容：

- 实验组与对照组 Project 设置的精确字节。
- ChatGPT 产品界面或运行入口。
- 模型。
- 实际插件及发布版本身份。
- Project 记忆模式。
- 会话隔离结构。
- 任务集。
- 任务顺序策略。
- 尝试预算。
- 评分标准。
- 提供给 Reviewer 的输入。
- 停止条件。

#### 两组的共同条件与隔离要求

两组必须使用完全相同的 Project 设置字节、ChatGPT 界面、模型、预先冻结的任务集、任务顺序策略、尝试预算、评分标准和评价程序。每组都必须使用全新、隔离的会话上下文。

任何一组都不得读取另一组的输出、会话或 Project 历史。如果使用 ChatGPT Project，必须冻结并记录记忆模式，测试结构必须防止两组互相污染。实验组会话不能成为对照组可引用的 Project 历史，反之亦然。

#### 两组唯一允许的实质差异

| 组别 | 条件 |
|---|---|
| 实验组（treatment） | 冻结的 Clear Writing 候选版本可用；必须提供实际可用性或使用证据，证据强度按当前界面真实能提供的能力记录。 |
| 对照组（control） | Clear Writing 候选版本不可用；仅保留与实验组完全相同的 Project 设置字节；不复制任何技能正文，也不允许看过实验组输出后人工补规则。 |

唯一允许的实质变量是 **Clear Writing 候选版本的可用性／实际使用**，即 availability / consumption。

测试不得挑选最好输出，不得反复尝试直到成功，不得中途修改评分标准，不得看完一组后修改另一组任务，不得改变任务顺序策略，不得使用不同模型或界面，不得将插件正文复制到对照组，也不得把 Project 设置自身的改善归因给插件。

#### 通过条件与不确定结论

实验组必须在多个预先冻结的任务族上，表现出稳定、可读且可归因于插件可用性／实际使用的增量，同时不能牺牲 W0 中纯精确输出、混合回答和长回答的控制要求。

如果对照组已经同样好，不能为了“证明插件有用”而修改评分标准。此时应报告：

`PLUGIN_INCREMENT_NOT_PROVEN`

必须停止发布，交回 Planner 重新判断产品定位。

如果当前 ChatGPT 产品界面无法合法建立严格配对条件，应报告：

`W2=INCONCLUSIVE`

同样必须停止发布。任何已知存在混杂因素的备选方案只能标记为 `DIAGNOSTIC_ONLY`，不能替代 W2 通过，也不能声称已经证明插件增量价值。

### W3：没有桥接策略时，插件能否被发现

保留原有 A/E 自动选择实验，但它只回答三个问题：技能元信息是否容易被发现；没有 Project 策略时模型能否按相关性触发插件；Project 策略是否提高行为可靠性或可用性。

W3 不是发布关键关口，不证明每轮调用，不替代 W1，也不替代 W2 的插件增量验证。如果 W0/W1/W2 均通过，W3 自动选择能力较弱不阻塞以 Project 策略为入口的产品方案，但必须记录可发现性限制。

## 五、G7：用全新任务验证泛化能力

G7 保留为最终的全新任务泛化验收。它要验证冻结调用策略在未见任务上是否仍然有效，不能用开发期间已经影响机制或评分标准的样本代替。

### 开始前必须冻结的身份和条件

至少冻结以下十三项：

1. 冻结生产候选版本的提交。
2. 实际 Web 插件及发布版本身份。
3. Project 桥接指令的精确字节。
4. ChatGPT 产品界面或运行入口。
5. 模型。
6. Project 记忆模式。
7. 会话隔离策略。
8. 尝试预算。
9. 全新任务集。
10. 任务顺序策略。
11. W0/W1/W2 的评分标准。
12. Reviewer 输入。
13. 停止条件。

运行期间，只要其中任一身份或条件发生变化，就不能把结果拼成同一个 G7 最终批次。

### 全新任务必须同时满足的要求

G7 应检验技能分工是否正确，自然语言和混合回答是否便于阅读，纯精确输出是否按约定免于激活，混合回答的精确内容是否受到保护。还要检验临时语言覆盖及恢复、写作技能切换、内容保真与无语义漂移，以及插件增量价值是否满足既定评分标准。

以下样本永久排除在全新任务集之外：

- `KR-WEB-01..09`。
- 原四组保持不变测试。
- W0、W1、W2 的任务。
- W2 诊断性备选方案的任务。
- 任何开发期间见过、并用于修改机制或评分标准的样本。

## 六、各项验证如何影响发布

v0.2 不新建 G8/G9，只修改原 G1 的发布判定含义。完整验收关系如下：

| 关口 | v0.2 的含义 | 是否为发布关键条件 |
|---|---|---|
| G0 | 分发与候选版本身份 | 是 |
| G1a | W0 自然语言／混合回答安全，以及显式选中插件后的精确输出压力测试 | 是 |
| G1b | W1 Project 策略下的多轮行为可靠性 | 是 |
| G1c | W2 严格配对的插件增量验证 | 是 |
| G1d | W3 无桥接策略时的可发现性诊断 | 否 |
| G2 | 已知回答可读性问题的回归验证 | 是；当前候选版本已 PASS |
| G3 | 内容保真与精确输出保护 | 是；W0 补充显式选择和混合回答证据 |
| G4 | 现有写作技能职责分工不退化 | 是 |
| G5 | 领域使用方的职责边界 | 保持原定义 |
| G6 | 多轮行为与语言恢复 | 是；主要由 W1 提供证据 |
| G7 | 冻结策略下的全新任务泛化 | 是 |

### 失败后的处理规则

| 观察结果 | 结论及后续动作 |
|---|---|
| W0 精确输出被污染 | 显式选择、现有技能元信息或实现边界存在安全缺口。停止 W1/W2，交回 Planner/Critic 做最小范围修复，不修改 Project 设置，不默认新增协调技能。 |
| W1 行为不稳定 | Project 策略不能稳定产生目标多轮行为。停止，检查桥接指令、界面与插件可用性、记忆和上下文条件；不能自动归咎于 `response-clarity`。 |
| W1 行为通过，但没有插件加载证据 | 只可报告 `PROJECT_POLICY_BEHAVIOR_RELIABILITY=PASS`，不得声称证明插件因果作用。 |
| W2 无法构造严格配对条件 | 报告 `W2=INCONCLUSIVE`，停止发布，不能用存在混杂因素的备选方案替代。 |
| W2 对照组与实验组同样好 | 报告 `PLUGIN_INCREMENT_NOT_PROVEN`，停止发布，交回 Planner 重新判断产品定位；不能改变评分标准。 |
| W3 自动选择较弱 | 若 W0/W1/W2 通过，不阻塞 Project 策略入口；记录可发现性限制。 |

| 问题 | 提案中的关闭方式 |
|---|---|
| CW-IP-01：纯精确输出的职责冲突 | 每轮强约束只覆盖自然语言和混合最终回答；纯精确输出免于激活。W0 只证明显式选择插件不污染精确输出，没有具体技能加载证据就不声称加载后旁路，也不新增协调技能。 |
| CW-IP-02：多轮行为与插件因果作用混淆 | W1 仅证明 Project 策略下的多轮行为可靠性；加载证据有则记录，无则不猜。W1 单独通过不证明插件因果作用，这部分由 W2 负责。 |
| CW-IP-03：对照测试不够严格 | W2 强制设置字节、界面、模型、任务、顺序、预算和标准一致，使用全新隔离上下文，冻结记忆模式并防止两组污染；插件可用性／实际使用是唯一实质差异。无法合法配对则 `W2=INCONCLUSIVE` 并停止发布，混杂备选仅供诊断；G7 的冻结身份同时补齐。 |

下一次 Critic 应优先检查：CW-IP-01 是否由激活豁免和精确输出压力测试的结论边界正确解决；CW-IP-02 是否由 W1 的行为结论与 W2 的因果职责正确解决；CW-IP-03 是否由严格配对、防污染措施和不确定即停止发布的规则正确解决。

还须确认这些改动没有破坏已认可的方向：以 Project 策略为正常入口，保持 `W0 -> W1 -> W2 -> W3`，W3 仅作诊断，保留全新任务 G7，六技能架构不变，生产候选版本不变。
