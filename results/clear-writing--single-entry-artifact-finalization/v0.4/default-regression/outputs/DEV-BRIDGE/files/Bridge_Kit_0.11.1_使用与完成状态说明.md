**Bridge Kit 0.11.1 可以作为日常协作工具使用，但要把“产品已有可用能力”“正式发行已经完成”和“你的机器已经装对并跑通”分开判断。** 这四份文档支持的结论是：主要功能已经有明确入口和运行边界，0.11.0 有正式发行记录，0.11.1 是针对进度通知的修复补丁。它们不足以证明你当前机器运行的就是正式 0.11.1，也没有提供与 0.11.0 同等明确的 0.11.1 发行目标及完整验收记录。因此，我不会把它判断为“仍然只有设计、不能用”，也不会说“所有环境、所有功能都已验证完成”。日常从机器策略和 Lite 开始用是合理的；长期运行、通知和外部复核需要各自配置并满足授权条件。

本文依据你提供的 `YuukiAS/GPT_Codex_AI_Bridge_Kit` 在 `ba9013b9fbbd242e51b09f9d09291f417df17652` 对应的 README、QUICKSTART、CHANGELOG、AGENTS 完整本地副本。以下是对这些文档的综合解释，没有联网核验远端分支、读取其他规格或实际启动 Bridge Kit。文中的操作命令供理解和后续使用，本轮没有执行安装、邮件发送或外部同步。

**现在的架构：先选协作方式，再按需要加运行和辅助能力。**

Bridge Kit 的基本作用是把 GPT 的规划、Codex 的执行和后续复核落实到项目文件中。任务和证据保存在仓库或明确的机器本地状态里，下一次会话能够从这些材料接着做，不必依赖某个聊天窗口记住整个项目。

它分三层，层与层之间各有职责：

| 层级 | 管什么 | 你需要做什么 |
|---|---|---|
| 机器层：Machine Policy | 当前 Codex 身份的长期规则、常用安全操作、授权边界 | 每个 `CODEX_HOME` 分别安装和验证一次 |
| 项目层 | 默认 Lite，以及按需安装的 Review、Control、Persistent Run、Overleaf、复核工具等 | 每个项目只安装实际需要的能力 |
| 任务层 | 某一次工作要做什么、按什么方案执行、结果怎样、由谁判断通过 | 为具体工作建立任务及结果文件 |

这里最容易混淆的是：**协作工作流只有 Lite、Review、Control 三种；长期运行、通知、论文同步和视觉/文本复核是配套能力。** 例如，你可以用 Lite 完成一个长任务，再加 Persistent Run 保证前台执行进程在断线后继续运行；不需要仅仅因为任务要跑一夜，就改成最重的 Control。

三种工作流的区别，在于需要多强的独立判断：

- **Lite：普通工作默认选它。** GPT 写任务单，Codex 执行并保存结果，需要时再交给 GPT 复核。它适用于修 bug、开发功能、整理文档、常规重构，也可以承载较大实现；规模本身不决定要不要升级流程。
- **Review（Reviewed Mode）：需要独立规划和复核时使用。** GPT 规划者先冻结方案，Codex 按方案实现，GPT 复核者再看真实差异、测试和结果。默认最多两轮复核：第一轮要求修改时允许一次自动返修，第二轮仍未通过就转人工决定。监视器负责机械推进，不替代规划者或复核者的判断。
- **Control（Controlled Mode）：错误通过的代价很高时使用。** 规划者决定目标，审查者检查合同及最终闭环，控制器负责路由，验证者建立冻结要求对应的验证依据，执行者负责实现。它还保存稳定的审查对象和最终独立检查，适用于需要严格证明完成条件的科研、生产、安全或迁移任务。

命令名没有跟显示名称一起改：机器策略仍用 `ai-bridge host ...`，Review 用 `ai-bridge reviewed-handoff ...`，Control 用 `ai-bridge agent-flow ...`。看见这些旧名称，不代表装的是旧架构。

辅助能力分别解决不同问题。Persistent Run 管进程的断线存活；进度系统报告阶段、完成比例和有根据的预计时间；Notifier 发送已经成立的事实；Overleaf Bridge 只同步论文目录；Visual Review 和 Text Review 生成供复核者使用的证据。这些组件都不能因为“进程还活着”“邮件发出了”或“外部接口返回成功”就替原任务宣布完成。

**0.11.1 的实际修复很集中，主要架构变化来自 0.11.0。**

如果你已经在用 0.11.0，升级到 0.11.1 最直接的收益是：长期任务的进度邮件不再因为小幅进展频繁发送，也不会因为观察过于频繁而一直等不到定时邮件。

这次修复把两个时间点分开记录：一个是“最近一次观察到进度”，另一个是“上一次逻辑投递”。普通 count/fraction 变化只更新进度记录；是否到了定时通知时间，要从上一次逻辑投递算起。

举一个说明行为的例子：假定通知间隔是 60 分钟，10:00 有一次逻辑投递，之后每 5 分钟更新一次普通进度。新的行为不会每 5 分钟发一封，也不会每次更新都把下一封邮件往后顺延；到通知间隔满足时，下一次适用的观察可以触发定时投递。这只是对规则的示例，不是本轮实测记录。

阶段切换、进入停滞/阻塞/失败状态、运行终止以及预计完成时间发生重大变化，仍然可以提前通知。预计时间从已知变成 `UNKNOWN`，或从 `UNKNOWN` 变成已知，都算重大变化。已知预计时间的变化门槛保持为：变化至少达到“15 分钟”和“此前剩余时间的 25%”中的较大者。默认通知间隔为 60 分钟，非测试配置不得低于 15 分钟。

0.11.1 没有更换 ETA 算法，也没有改变进程寿命合同；邮件传输失败后，不会把下一次进度观察偷偷变成自动重试。CHANGELOG 还记录了受控时间的通知间隔回归、ETA 状态切换回归、传输失败不影响主任务的回归，以及保留 Persistent/Lite 终态通知去重。另两项工作是关闭历史上由 Bridge 负责的短期待办，并同步用户文档。**关闭旧待办不等于实现未来 Program Run，也不等于替其他项目的负责人完成工作。**

如果你是从 0.10 或更早版本过来，0.11 系列还有下面这些更重要的变化：

| 变化 | 解决的问题及使用含义 |
|---|---|
| 执行前绑定准确上下文 | Lite、Review、Control 的 Bridge 管理执行入口绑定仓库、工作树、分支、提交及必需来源文件的精确版本，避免在错误位置或不匹配的任务材料上启动执行者 |
| 写入项目规则前检查容量 | Lite/core、Persistent Run、Overleaf 共用写入前检查和串行事务，按 Codex 实际指令字节上限计算；超限或检测到外部冲突时不改项目，托管标记外的原始字节保持不变 |
| 持久运行结构简化 | 每次运行明确对应一个完整哈希命名的 tmux 会话、一个监督进程、一份绑定记录和一个子进程，便于判断是否已有运行、是否存在冲突 |
| 进度与恢复规则明确 | 支持原子进度更新、保守 ETA、明确的恢复分类；遇到陈旧或不完整状态，不擅自重启、接管或猜测任务结束 |
| 通知配置统一到机器 | 使用一份机器私有配置，项目不再各复制一套秘密；Lite、Review、Control、Persistent 共用发送能力，发送失败不改变业务结论或主进程 |
| 自动通知接入 Clear Writing | 每次逻辑投递至多尝试一次表达整理，保真或调用检查失败就退回确定性文本，不反复请求模型；手工 `send`、`send-test` 保持原行为 |
| 增加受限的分支入站同步 | `host sync-current-branch` 支持干净、已跟踪、同名远端的非 `main` 当前分支，只允许快进；分叉或配置不符时停止 |

同时，0.11.0 明确移除了实验性的 app-server 阅读/显示路径、`codex_progress_thread`、生产用双向工作树交换、跨工作流事件总线，以及项目本地通知传输配置的权威地位。它们不能再作为“当前应该有的能力”来理解。现在的运行和进度查询不依赖常驻 Codex 对话或专门的进度显示线程。

从更早历史看，Overleaf、视觉复核、私有文本复核、生产插件回放、Review 首次工作树创建和首次发布，都已经在此前版本出现。0.11.1 没有重新引入这些功能；这一补丁是在已有产品之上修正通知行为。

**平时怎么用：先把最常见的一条路径跑顺。**

我的建议是，普通项目采用“机器策略 + Lite”，把其他组件留到需要时再加。安装源应是正式 `release` checkout；README 明确说，较新的开发分支 HEAD 不会自动成为正式发行目标。`pip install -e` 使用的是你指定目录中的源码，所以仅看版本名称不够，还要确认该目录的来源。

一次性的本机安装和身份检查可以按文档入口进行：

```bash
pip install -e /path/to/GPT_Codex_AI_Bridge_Kit
ai-bridge host install
ai-bridge host status
ai-bridge host validate
```

Machine Policy 管理当前 `$CODEX_HOME` 下的 `config.toml`、`AGENTS.md` 和 `rules/ai-bridge-global.rules`。如果你有多个 `CODEX_HOME`，要分别配置。`host status/validate` 会报告实际可执行文件、导入源码和版本、源码提交及工作树状态、本地正式发行引用和安装元数据；它们提供诊断，不会自动联网更新运行环境。

每个真实项目再初始化一次：

```bash
ai-bridge init --target /path/to/project
ai-bridge validate --target /path/to/project
```

进入项目根目录直接运行 `ai-bridge` 也是文档提供的初始化方式。默认不覆盖同名模板；`--force` 是明确要求更新模板时才考虑的选项。项目初始化不会自动修改你的 `CODEX_HOME`，也不会自动装齐所有可选功能。

日常协作只需要记住三个动作：

1. 让 GPT 读取 `AGENTS.md` 和 `prompts/CHATGPT_RULES.md`，把本次要做的事写入 `prompts/tasks/repo--fix-ci.md`。
2. 让 Codex 读取 `AGENTS.md`、`prompts/AGENT_RULES.md` 和任务单，按授权执行，把结果写入 `results/repo--fix-ci/result.md`，文件产物放在同一结果目录，并写 `MANIFEST.md`。
3. 把任务单、结果、产物索引和必要产物交回 GPT，写 `review.md`，判断继续、停止、补证据、请求人工授权或开下一张任务。

如果使用 Bridge 管理的 Lite 执行入口，命令是：

```bash
ai-bridge task run \
  --target /path/to/project \
  --task-key repo--fix-ci
```

这个入口在创建 Codex 子进程前检查绑定的执行上下文与必需来源。它不会让“任务文件写了某种授权”自动变成当前用户对外部传输、付费调用或资源申请的批准。

文件放置也有清楚分工：执行任务放 `prompts/tasks/`，运行结果和文件产物放 `results/<task_key>/`；暂时不执行的想法、会议记录和研究笔记放 `docs/notes/`；需要长期复用的论文和报告知识放 `docs/wiki/`，维护索引与日志。这样 GPT 不会把每一份笔记都误当成需要立即交给 Codex 的任务。

需要独立复核时，再安装 Review：

```bash
ai-bridge reviewed-handoff install --target /path/to/project
ai-bridge reviewed-handoff validate --target /path/to/project
```

具体任务可以用 `task init` 建立。如果需要全新的任务专用分支和工作树，文档另有 `task bootstrap`；它按任务键派生 `reviewed/<task_key>` 和同级工作树，仍需要精确范围的用户授权。首次发布入口 `task publish-first` 只接受第一份 REQUEST/CURRENT 元数据提交和尚不存在的同名 GitHub HTTPS 远端分支，不能拿它发布任意源码提交。已有任务恢复则使用绑定任务材料的 `materialize-worktree`。这些入口不是让代理自行决定分支策略的通行证。

Review 的本地 watcher 可以在方案冻结或需要返修时启动执行者，但外部 GPT 的规划/复核仍然要通过对应安排返回。正常等待不应变成失败，更不能为了结束会话而伪造通过或宣布不可恢复阻塞。运行中的 watcher 如果加载的是旧源码，状态查询会报告需要重启；更新磁盘源码不代表正在运行的进程已经切换到新版。

**长期任务、邮件和论文协作，分别按需要接入。**

如果任务已经交给 Slurm 等调度器，或由脱离终端的服务负责寿命，不必再因“要跑一夜”套一层 tmux。只有前台进程或编排进程确实需要在 Codex、SSH、终端断开后继续执行，且没有其他运行主体负责它时，才安装 Persistent Run：

```bash
ai-bridge persistent-run install --target /path/to/project
ai-bridge persistent-run validate --target /path/to/project
ai-bridge persistent-run prompt kickoff \
  --target /path/to/project \
  --goal prompts/tasks/repo--long-run.md
```

最后一条命令只生成启动授权文本，不会启动进程。用户发送包含 Goal SHA-256 和准确启动命令的授权后，才按合同启动。已有兼容运行再次启动不会多开一个子进程；遇到陈旧绑定、会话不匹配或监督进程丢失，先用 `recover` 分类，不能直接删状态重跑。只有符合 `SAFE_TO_CLOSE_STALE` 的情况才能显式关闭陈旧状态，而且这不代表目标完成。

进度需要项目真实提供。没有进度就返回 `UNKNOWN`；子进程存在、心跳更新，都不是工作已完成的证据。count/fraction 的 ETA 至少需要同阶段、同总量的三个有效点，跨度至少十分钟，以近期正向速率估算。进度回退、阶段或总量改变、间隔过大都可能重新积累数据。因此刚启动看不到 ETA 是正常行为，不应靠猜测填一个时间。

邮件通知默认关闭。需要时，每台机器配置一次权限为 `0600` 的 `~/.ai-bridge/private/notifier.env`，然后用 `notifier validate/status` 检查；有既存私有配置来源时可用 `private sync --profile notifier`，旧项目配置有显式迁移入口。正式传输目前是 Gmail SMTP 587、STARTTLS 和 App Password。任务或合同还需要明确启用通知。`send-test` 要在明确授权真实发信后执行，成功只表示 SMTP 服务器接受，不保证已进收件箱。

自动通知会尝试使用已安装的 Clear Writing；整理失败时继续走确定性文本发送。邮件的职责是让你知道发生了什么，不负责给任务判定通过。即使通知失败，任务也不应被停止或回滚；传输结果不明时，重试需要明确接受重复投递的可能。

论文协作使用 Overleaf Bridge 时，Codex 仍在整个科研仓库工作，Bridge 只把指定的 `paper/manuscript` 之类论文目录投影到机器本地镜像，再同步给 Overleaf。典型日常顺序是：本地修改、编译检查、提交，再查 `overleaf status` 并 `push`；合作者在 Overleaf 改稿后，则 `pull`、看差异、重新编译、提交。拉取不会自动提交或推送 GitHub；双边修改会拒绝自动覆盖。每台机器各自连接，令牌交给 Git 凭据工具管理。

README 在 Overleaf 示例中出现了 `git push origin main`，但同一份 README 的机器策略章节和 AGENTS 明确保留原始 push 的审批边界。因此不能把这个示意步骤理解成新增授权。符合条件的已有同名 GitHub HTTPS 分支，可以用 `host publish-current-branch`；其他情况仍按相应授权执行。

图片、PPT 或私有全文必须独立检查时，再安装视觉或文本复核。视觉复核默认经 GitHub Actions 调用 OpenAI 图像输入；私有文本先在本地加密，Actions 临时解密，再以 `store=false` 调用 OpenAI 并保存绑定输入身份的证据。加密和不存储选项不等于没有外部传输，安装功能也不等于授权上传。它们是可选的证据来源，普通任务不必一律启用。

**为什么我认为主体已可用，却不能替 0.11.1 宣布所有交付都完成。**

支持“主体已可用”的依据并不只是 README 写了一个版本号。四份文档对三层架构、三种工作流、安装入口、运行状态、失败恢复、秘密配置和完成责任有相互对应的说明。CHANGELOG 还明确记录：0.11.0 在 C1–C6 和最终 Persistent 正常入口评估后，通过 `refs/heads/release` 正式分发，目标提交为 `391ff889ad156540727da168fb608c5f37dbbdfc`。这足以支持“文档记录了正式发布的 0.11 基线”，不能再把整个系列描述成未落地方案。

0.11.1 的变化也足够具体：它描述了原有通知计时的两个问题、修复后的行为、没有改变的 ETA/进程合同，以及新增回归类型。它不是一句笼统的“提升稳定性”。但本轮读到的是发布说明，没有读到测试实现、运行日志或远端 CI 结果，不能把其中的回归记录说成我亲自重跑通过。

正式分发还要单独判断。README 称当前补丁为 0.11.1，QUICKSTART 也按该补丁讲解；CHANGELOG 有 2026-10-20 的 0.11.1 条目，并提到对齐正式 0.11 分发。可是明确写出 `release` 目标提交的条目仍是 0.11.0。AGENTS 又规定，正式分发及版本收口由 `AI_Skills_Collection` 的 `ai-skills-core:bridge-kit-maintainer` 负责，本仓库不能在该负责人完成前自称分发完成。**这留下的是 0.11.1 正式分发的证据缺口，不是它一定未发布的证明。**

你指定的来源提交也不能自动补上这个缺口：它固定了“我们读的是哪份文档”，不自动证明它就是正式 `release` 指向，更不证明每台机器已经同步。后续若要判断某台机器是否已经正常使用 0.11.1，需要核对实际安装身份、正式发行目标和所用功能的运行证据。本轮按你的范围只解释文档，没有做这项环境验收。

**真正没有做的事情，要与主动删除的功能和待配置事项区分。**

| 类别 | 当前边界 | 对你的影响 |
|---|---|---|
| 明确未实现 | Program Run 不在当前短期范围 | Bridge 不会自主找下一任务、生成下一 Goal 或自动串联整个任务计划 |
| 历史路线未获当前材料确认 | 0.7.0 把 Project State Bridge 标为未来路线；所给后续记录没有宣告它实现 | 不能把它算进 0.11.1 的现有能力，也无法仅凭这四份文件列出其最新剩余计划 |
| 已主动移除 | app-server 阅读/显示路径、专用进度线程、双向工作树交换、跨工作流事件总线 | 不应再等它们作为 0.11.1 的补齐项，也不应靠旧设计恢复这些入口 |
| 有意不自动化 | 陈旧运行自动接管/重启、自动取消或扩资源、Overleaf 实时同步、凭进程状态宣布完成 | 异常时需要证据和明确操作；工具不会为了“自动继续”替你做高风险决定 |
| 需使用者配置 | 各 Codex 身份的机器策略、项目可选层、通知配置、Overleaf 连接、外部复核服务及授权 | 产品有入口，不代表新机器和新项目无需配置就全部能用 |
| 本轮材料不足以确认 | 0.11.1 的准确正式发行目标、当前机器版本、当前运行的 watcher、实际端到端结果 | 这些不能报告为已验证，也不能反过来当成已知产品缺陷 |

CHANGELOG 说历史 Bridge 短期待办已关闭，我会保留这个来源结论；但它没有在这四份文件里展开逐项清单，所以不能据此编造“所有历史问题都已逐项核验”的说明。AGENTS 中对发布责任和验收的严格规定也不是“版本还没完成”的直接证据，它规定的是宣布完成必须满足什么条件。

对你的实际决策，我建议这样把握：**把 0.11.1 当作已有 0.11 产品上的通知修复补丁，按正式发行来源安装，从机器策略和 Lite 开始日常使用。需要独立复核、断线运行、通知或论文协作时再逐项接入。若你要的是能自主持续生成和推进下一批任务的系统，当前版本仍不提供；若你要的是可靠组织一次已明确授权的 GPT–Codex 协作，文档已经给出了可使用的产品路径。**
