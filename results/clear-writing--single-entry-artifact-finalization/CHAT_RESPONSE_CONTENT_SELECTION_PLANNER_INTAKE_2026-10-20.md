## 1. 用户真正要解决的事

用户明确手动选择 Clear Writing 后，希望 ChatGPT 在**普通聊天回答**中自然、连贯、清楚地回答问题。详细任务应充分解释功能、方法、证据和必要限制，但不把后台调查过的所有实现排除项、运行日志、审计记录或审查术语自动复制给用户。用户不接受再靠频繁修改 Project setting、Planner/Critic 规则、追加同义写作禁令或增加一批回归样本宣称问题已解决；要求定位真实的内容进入正文机制并用正常调用证明改进。

这不是“所有回答越短越好”，也不要求绝对零失误。实际目标是：显式调用 Clear Writing 后，类似严重退化不应再频繁发生；技术上确实需要详细推导或复现步骤的任务仍必须充分完整。

## 2. 已观察到的失败、证据边界

1. 真实负例：Bridge Kit 0.11.1 完成汇报。用户希望详细了解是否完成、主要架构、新增能力如何使用、为什么可信、还有什么。实际答复却形成24个编号章节、1128行，并大量展示内部审计过程。典型段落逐项罗列“没有 daemon / 数据库 / 第二状态机 / 长期 Codex session / app-server progress thread / watcher hierarchy”。这些明细可以作为设计审查证据，但对该次用户的完成判断及正常操作没有相应增量；“Persistent Run 只负责进程断线存活，不引入新的中央运行工作流”即可保留其必要用户含义。
2. 原 Bridge 线程报告，其**实际工具轨迹**显示最终回复生成前读取了已安装的 `response-clarity` 与 `writing-fidelity`，并将调查结论记录至 `docs/plugin-todos/writing-style.md`，提交 `de460300f55b5617654dd50b2a5cfec9ab89a094`，Issue #13 评论 `6293997950`、`6294277450`。本登记没有独立取得原线程完整内部工具轨迹，也不声称证明了网页插件选择动作的内部路由因果链；能够确认的是用户看到的劣质输出以及原线程已经做出的、可供 Planner 复查的调查记录。
3. `skills/writing/core/response-clarity/SKILL.md` 现有规则已要求结论先行、削减无意义内部过程、按语义成段、核心问题回答完成后停止。项目设置同样要求中文自然解释。因此不能直接归因为“缺少少用列表／减少英文／避免日志”的规则。
4. 当前0.6候选的 `packaging/chatgpt/writing-style/clear-writing/SKILL.md` 对 `CHAT_RESPONSE` 已有单入口与 `response-clarity` 路由，但尚未在进入正文组织前，显式区分“支持判断的证据池”与“用户要求阅读的交付内容”。这是一个**可检查的合同缺口和最有依据的修复假设**，尚未由0.6正常网页入口试验证明。
5. `writing-fidelity` 保护的是任务要求保留的事实、限制及精确字符串；不能把“内部检索到的每项事实都必须写给用户”作为该技能的真实要求。其是否具体放大了此次错误，现有证据不足以独立确认。

## 3. 供 Planner 独立判断的最小修复方向

在现有0.6单入口中，**先做普通聊天的读者问题与内容纳入判断，再由现有专业路线组织措辞和保真**。建议优先审查 `CHAT_RESPONSE` 任务分解，而不是另建服务或追加一组同义规则。

建议的私有工作顺序（是模型应遵循的流程指令，不是假装存在的强制拦截器）：

- 从当前用户请求确定问题、回答种类、详细程度、真实交付物和必要行动，不把上一阶段调查范围误认为用户要求的展示范围；
- 领域分析与检索可以充分进行，但进入用户正文的内容须对回答问题、解释正常使用或机制、改变可信度与风险判断、交代限制或明确行动有具体作用；用户**明确要求**的推导、参数、证明、实现细节和复现信息必须保留；
- 没有当前读者价值的内部测试设施、被否决架构清单、重复的“不是什么”、机械状态堆叠，只保留在内部证据或必要的精确定位资料中；不是根据某个禁词自动删除；
- 普通聊天仍调用 `response-clarity`；`writing-fidelity` 负责保护已经选定的有用事实、公式、版本、权限、状态、命令和行动边界，不负责强迫输出全部背景资料；
- 输出前对完整答案检查“有没有回答原问题、解释是否够深、是否漏掉必须交代的证据与下一步、是否有无法说明用户价值的展开”。不设固定字数、段落数、标题数、英文比例。

Planner 必须比较：只依赖现有 `response-clarity`、调整单入口的内容选择顺序、以及仅增加最终自检三者为何不同；解释选定方案如何在**现有正常插件入口**实际被消费，并明确证据局限。纯 Skill 的步骤仍由模型遵循，没有网页发送前强制拦截权；不得把“新增最终化合同”宣传成不可绕过的发送前审核机制。

## 4. 怎样识别真修复，而不是测试凑通过

将 Bridge 完成汇报作为**已知回归**，不作新鲜留出样本；对完整真实最终答复进行语义验收，不能只统计字符或搜索黑名单。至少覆盖三种相反要求：

- 复杂技术项目完成汇报：材料有大量内部实现与验收证据，用户要求“详细说明为什么已完成”。应完整说明完成状态、关键功能、正常使用、可信证据和真正剩余项，但不自动展开放弃的内部架构与逐条审计流水。
- 受阻的阶段汇报：应保留真实失败与安全边界，直接说出下一责任方、需修事项、是否需要用户动作及可复制交接；不要把“请寻找某种执行环境”当成有用下一步。
- 用户确实要求详细算法、公式、验证方法或实现设计：必须保留证明、参数、条件和具体技术细节，避免为了简短而造成实质遗漏。

属于当前修复的结果应映射到现有普通聊天与完整产物质量 Gate，是否需改变 G2 等由 Planner 按当前 Gate 方案检查，不机械新增顶层 Gate。修改后先完成便宜的已知回归与不应改变场景，随后同一冻结候选从真正 ChatGPT Web 正常入口显式选择 Clear Writing 验证；高成本或新鲜验证不能被重跑已见输入替代。用户最终阅读完整产物；不能以 Skill 自述“我执行了检查”替代质量证据。
