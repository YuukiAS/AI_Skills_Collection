# Clear Writing 真实 Web 已知回归库 v2

本文件只冻结可迁移的“好在哪里 / 坏在哪里”。不复制私人科研原文，不保存 DII 项目科学答案。以下全部样本已经暴露，永久属于 known regression / positive control，禁止作为 G7 fresh/unseen。

## KR-WEB-01 — 长回答把真正判断淹没

类型：负例。  
已有对应：原 RW-WEB-01。

坏在哪里：
- 开头已经给出有用判断，随后被大量章节、列表、机器字段、重复边界淹没；
- 面向人的解释与可复制机器交付物混在一起；
- 后文不断重新分类同一结论，读者必须反复判断“这是新信息还是重复”。

通过标准：
- 先给结论、意义、是否需要动作；
- 后续只有在增加新证据、新决策或用户明确要求的细节时才继续；
- 机器字符串保持精确，但与解释层分开。

## KR-WEB-02 — 伪澄清、建议漂移和自我检讨代替回答

类型：负例。  
已有对应：原 RW-WEB-02。

坏在哪里：
- 先排除用户没提出的解释，却不定义真正对象；
- 建议发生变化，却不说明新证据或原判断为何退出；
- 用户批评表达质量时，回答转去重新研究领域问题或长篇反省自己。

通过标准：
- 直接回答真正对象、判断和依据；
- 推荐变化必须绑定新证据或纠正的前提；
- 写作反馈就审写作本身，不用空泛道歉或心理揣测代替分析。

## KR-WEB-03 — 具体解释、真实例子和证据边界

类型：正例。  
已有对应：原 RW-WEB-03。

好在哪里：
- 先给具体选择或结论；
- 用日常情境或具体场景建立直觉；
- 解释因果关系；
- 把建议方向与尚未验证的事实分开。

保护要求：
- 不得把 Clear Writing 修成固定短答；
- 必要例子、因果解释和不确定性必须保留。

## KR-WEB-04 — 伪结构化降低信息密度

类型：负例。  
已有对应：原 RW-WEB-04。

坏在哪里：
- 简单线性关系被展开成大代码框、逐行箭头或树状结构；
- 为了说明“这些内部东西不用管”，先迫使读者处理一串内部名词；
- 普通中文解释被不必要的英文标签打断。

通过标准：
- 结构只有在真实降低阅读成本时才使用；
- 简单关系优先自然段或紧凑一行；
- 真正分支、执行步骤、命令和机器内容仍允许结构化。

## KR-WEB-05 — 研究综合自动膨胀成方案文档

类型：负例。  
已有对应：原 RW-WEB-05。

坏在哪里：
- 来源综合已经完成，回答却继续追加共同点、组件、架构、实验和再次总结；
- 来源共同结论与助手进一步建议混在同一确定性叙事里；
- 每个局部都“有结构”，整篇却重复重建结构。

通过标准：
- 先说来源共同支持什么、哪里真正不同、当前是否要动作；
- 助手建议与来源共识分层；
- 用户没要求方案设计时，不自动扩成架构 memo；
- 问题回答完就停止。

## KR-WEB-06 — 科研解释一句一段、标题与公式碎片化

类型：负例。  
来源：2026-10-16 DII 普通 Web 科研解释反馈。

坏在哪里：
- 同一个概念、因果链或局部推导被拆成大量单句段落；
- 连续解释被十几个小标题切碎；
- 短定义、一步公式和一句结论各自占块，导致滚动和重新进入上下文的成本过高；
- 每句话单独看都清楚，但整篇像“卡片流”。

本轮新修复要求：
- 相邻句子共同完成一个完整语义/推理单元时，应组成自然段；
- 标题、列表和独立展示公式只在提供真实导航、比较或推导价值时拆开；
- 最终输出要做整篇碎片化检查，而不是只审每句话；
- 不得实现成固定段落长度、标题上限、行数或公式数量阈值。

## KR-WEB-07 — 中文科研解释退回普通英文概念栈

类型：负例 + 边界回归。  
来源：2026-10-16 DII Markdown 与 2026-10-17 follow-up。

坏在哪里：
- 普通概念用 `memory`、`audit`、`benchmark`、`patient structure`、`feature memory` 等英文承担核心论证；
- 来源论文是英文，被错误当成保留英文的理由；
- 用户已经要求“说人话、少非必要英文”后仍复发，说明需要最终整篇语言层检查。

现有合同应保护的边界：
- 正式模型/方法名、稳定缩写、代码/机器字符串、检索身份可以保留；
- 普通推理概念优先自然中文；
- 不新增禁词表或英文比例规则。

本轮用途：
- 主要作为 runtime regression 验证，不扩大生产修复范围；若当前合同仍失败，再由 Reviewer 判断是否属于两个冻结缺口的直接后果。

## KR-WEB-08 — 复杂科研方法解释的正向深度样本

类型：正例。  
来源：2026-10-15 DII 方法解释，用户明确认可。

好在哪里：
- 先给一句可复述的方法主线；
- 用真实强基线对照解释“为什么需要新方法”，不靠“现有方法不足”的空话；
- 把多个研究想法分别落到算法角色；
- 先建立“切线 + 非线性偏离”这类直觉，再进入正式方法和公式；
- caveat 贴着结论，明确何时现有方法可能更合适；
- 中文主体稳定，只保留正式方法名和必要身份。

保护要求：
- 新增段落规则不能破坏这种长而清楚的解释；
- 不得为了紧凑删掉真实对照、直觉、证据边界或停止条件。

## KR-WEB-09 — 三方案对比正例 + 术语/数学对象首次解释反例

类型：混合样本。  
来源：2026-10-16 DII 三方案比较及原始研究文档阅读反馈。

正例好在哪里：
- 每个方案先有一句自然中文定义，再讲细节；
- 三个方案各自用连续段落，最后才用一个紧凑比较表；
- 最终建议建立在比较结果上，没有再次复述全部内容。

反例坏在哪里：
- 陌生术语直接以 `provenance`、`halo`、`tile`、`estimand` 等身份出现，却没解释它在这里是什么、为什么需要；
- 多重下标对象直接进入公式，读者不知道对象层级、各下标角色、已知/估计状态、近似对象和后续用途；
- 数学正确不等于读者知道“这个量算出来以后拿来做什么”。

本轮新修复要求：
- 新方法、陌生术语或数学对象第一次出现时，先给不越权的 reader mental model：它是什么、处于什么层级/单位、为什么需要、后面拿来做什么；
- 多重下标首次出现时解释下标角色，或明确引用已经建立的定义；
- 再给正式术语/公式，并紧接说明结果如何进入下一步；
- 如果上游 domain reasoning 没有提供足够信息，明确指出对象定义不足，不得猜科学含义。

## 继续保留的 should-not-change

所有修复仍必须通过以下四组控制：

1. 用户明确要求完整 report / executable prompt / contract 时保持完整；
2. 真正有分支、层级或逐步执行价值的流程允许结构化；
3. 纯 JSON/YAML/code/raw log 等精确机器输出旁路 Clear Writing；
4. 正式产品名、方法名、稳定缩写、命令、路径、字段和精确机器字符串原样保留。

## 本轮判定原则

- 9 组样本全部参与回归，但只有 KR-WEB-06 与 KR-WEB-09 的两个 Reviewer 缺口授权新增生产规则；
- KR-WEB-01..05 证明旧能力不能退化；
- KR-WEB-07 验证现有中英文边界是否真的被 runtime 消费；
- KR-WEB-03、08、09 的正向部分共同防止“清晰 = 越短越好”；
- 不允许按 DII 名词硬编码；
- 不允许词数、段落数、标题数、英文比例、公式数量或关键词 grep 作为定性 PASS oracle。
