功能开关能控制接下来的请求是否使用新功能，却不会自动撤销新功能已经造成的变化。因此，它可以是回滚方案的一部分，但不能替代整个方案。

可以把功能开关想成一个路口的指示牌：关闭开关，相当于让后来的车走旧路；已经开过去的车不会因此自动回来。在应用里，“已经发生的变化”可能是写入了新的账单数据，或改动了数据库结构。数据库迁移就是调整数据库结构或数据的过程。回滚方案需要说明，出了问题后怎样让代码、数据和数据库结构重新配合，恢复可用的服务；只换回旧代码，也未必能做到这一点。

**场景一：新搜索排序只影响读取。** 这里旧排序代码仍然存在，新排序不会留下需要撤销的持久化数据，也就是长期保存的数据。如果需要撤回新排序，应先关闭开关，让后续搜索请求回到旧排序，再检查实际请求是否已使用旧逻辑、搜索结果是否恢复正常。在输入给定的条件下，关闭开关是直接的恢复手段；不过，输入没有提供关闭后的实际验证结果，所以还不能声称服务已经恢复。

**场景二：新结算流程已写入新账单字段，并执行了数据库迁移。** 此时应先确认关闭开关后的旧流程能否处理当前的数据和数据库结构，不能直接认定切回旧版就安全。如果正在发生故障、需要立即阻止影响扩大，应先暂停受影响的新结算入口或写入；如果关闭开关会自动把请求交给尚未验证的旧流程，就不能把“关开关”当作已确认安全的止损办法。接下来应验证旧版本的兼容性，并完成数据恢复演练，再据此决定怎样恢复服务。

例如，一笔账单已经按新格式保存，关闭开关不会把它自动改成旧格式。旧代码也许能正常处理，也许会报错或误读；这些只是可能性，输入没有证明其中任何一种已经发生。迁移脚本执行成功，只说明迁移已执行成功，不能证明旧版本仍能读取新字段，也不能证明数据能按预期恢复。目前还不能确定旧版是否兼容、数据恢复是否可行，以及恢复需要多久，因此不能承诺“一关开关就能安全回滚”。
