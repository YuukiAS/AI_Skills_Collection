# 050 round-4 clean replay and observability contract

## Purpose

Round 3 demonstrated a process defect in addition to the remaining style defect. The same long-lived Codex context that maintained `writing-style` also generated and self-reviewed the smoke candidates. The smoke manifests additionally carried semantic role labels derived from the rejected document. This makes context contamination a plausible source of repeated reader-facing terminology and makes the current self-declared Chinese reader PASS insufficient as product evidence.

This round must separate three things that were previously mixed together:

1. plugin maintenance;
2. production generation;
3. validation/review evidence.

No new product architecture is authorized. The current host-Codex heavy rewrite architecture remains selected.

## A. Clean production replay is mandatory evidence

A style smoke is not valid production evidence unless it is generated by a fresh isolated `ai-bridge plugin-replay` child using the installed `writing-style` plugin.

The replay child may receive only:

- the clean generic task file `CLEAN_PRODUCTION_REPLAY_TASK.md`;
- the exact frozen private smoke source file.

Do not stage into the child:

- 050 PLAN/REQUEST/CURRENT;
- STYLE_REJECT analyses;
- previous smoke candidates;
- repair prompts;
- semantic smoke role labels;
- expected answers;
- vocabulary examples from prior rejection.

The production replay child must use an ephemeral Codex runtime with memories disabled and network disabled, as enforced by Bridge Kit `plugin-replay`.

The outer maintenance Executor may inspect diagnostics, but it must not hand-edit the replay candidate.

## B. Smoke identity must be opaque to the writer

Public evidence may retain `SMOKE-A`, `SMOKE-B`, `SMOKE-C` and source hashes/ranges.

Semantic role labels used for bookkeeping must not be injected into the writer context. The generation child should not receive labels such as `checkpoint-...`, `method-comparison-...`, or `next-experiment-...` that paraphrase source vocabulary or prime a preferred wording.

## C. Chinese reader pass must stop being self-certification

The current contract is insufficient if the validator only checks that a host-authored JSON says `PASS`.

For the terminal Chinese pass, mechanically enumerate visible Latin-script spans from the assembled candidate outside protected formula/code/path/citation material. The host must classify every enumerated span occurrence as one of:

- `exact_identity`: byte-exact identity genuinely needed for an algorithm, dataset, metric, package, API, command, path, citation, or other externally identifying formal name;
- `useful_recognition`: an English technical identifier useful at first use, with a natural Chinese explanation in reader-facing context;
- `ordinary_reasoning`: organization, inference, comparison, qualification, transition, or ordinary descriptive language that should be expressed naturally in Chinese.

Rules:

- classification coverage must be complete for the mechanically enumerated spans;
- `exact_identity` must be supported by the protected-name/literal ledger or another explicit identity reason; it cannot be used as a catch-all for convenient English wording;
- `ordinary_reasoning` occurrences must be absent from the final candidate after the terminal pass;
- `useful_recognition` may remain only when the reader-facing passage supplies the Chinese meaning/context needed to understand it;
- do not implement a banned-word list.

## D. Preserve pre-pass and post-pass artifacts

The terminal reader pass must be observable as a real transformation or a justified no-op.

Private local stage evidence should preserve at least:

- assembled candidate before the Chinese reader pass;
- Chinese reader-pass findings/classification;
- final candidate after the pass;
- post-pass semantic/exact verification for any touched content.

The public receipt may expose only hashes/counts/statuses, never private prose.

If pre-pass and final hashes are equal, the pass may still be valid, but its findings must show why no repair was required. A bare `PASS=true` is not sufficient evidence.

## E. Stage receipts must represent real artifacts

Do not represent several conceptual stages as independent outputs when they are merely different names pointing to the same aggregate JSON file.

At minimum, unit semantic audit evidence, global assembly evidence, Chinese reader-pass evidence, and final candidate identity must be distinguishable in the private stage package and public hashes.

The receipt proves artifact identity/dataflow, not prose quality. Human style judgment remains authoritative.

## F. Reader Plan must be capable of affecting global organization

Do not require reordering for every input. However, when the Reader Plan claims structural reorganization, the stage evidence must show the actual bundle/order/morphology choice that affected the candidate.

The validator should not treat a Reader Plan as meaningful merely because a schema exists. It should be able to report:

- source order;
- planned reader order;
- final reader order;
- non-contiguous bundle count;
- information-shape changes;
- whether the final assembly consumed those choices.

## G. Do not regress the working fixes

Keep all already-established protections:

- host Codex owns semantic/writing stages;
- no OpenAI/Terra generation dependency;
- no source-copy Meaning Card fallback;
- no project-specific phrase repair;
- no raw literal/token-dump repair;
- inline-critical material cannot be appendix-only;
- formulas remain atomic protected spans;
- structural rewrite preserves the evidence graph rather than source position;
- light polish and fidelity-only routes remain unchanged.

## H. Round-4 decision logic

First, freeze production code and run a clean isolated replay of SMOKE-A without changing the plugin.

If that clean replay is materially better than round 3, record context contamination as confirmed and avoid unnecessary style-rule expansion. Still implement the observability/self-certification hardening above because it is a real process defect.

If the clean replay still has the same reader-facing failures, implement only the bounded terminal-pass/English-span and observability hardening above, rebuild/update the installed plugin through the canonical repository path, then rerun clean isolated A/B/C from the same frozen implementation.

Do not add another project-specific rule layer. If clean isolated replay plus the strengthened terminal gate still fails human style review, return to Planner with the isolated artifacts and stage evidence rather than continuing unbounded repair loops.
