4. Home：before → proposed result
首页当前能读懂，但有一个核心问题：状态、行动提示和品牌式短句重复解释同一件事。
当前页面表达
  • 首批同学加入中 / 首批同學加入中
  • 只开放注册 / 只開放註冊
  • 先把资料准备好 / 先把資料準備好
  • 先把自己说清楚；轮次开放后，再由你决定是否参加。
  • 不是刷资料，而是在合适的时候认真认识一个人。
插件第一反应
保留品牌、资格、主要 CTA、四步流程和隐私边界。把“当前可做什么”集中放在 CTA 附近；流程区只说明步骤，不再继
续写口号。
建议方向
  • 把状态改成一处清楚说明：目前只开放建立账户和填写资料；轮次开放后仍需主动报名。
  • 删除“不是刷资料……”这类标语，而不是再写一句更漂亮的标语。
  • 创建账户 / 建立帳戶 可以 KEEP，但公开 /register 现在 404，必须先由产品方确认入口状态。

5. How it works：before → proposed result
这个页面的结构是对的：它确实在解释流程。但部分标题像内部任务名，部分正文把政策说明压进产品页。
当前页面表达
  • 验证学生使用范围 / 驗證學生使用範圍
  • 轮次开放后自主报名 / 輪次開放後自主報名
  • 最多收到一位介绍 / 最多收到一位介紹
  • 没有合适介绍也是正常结果，不代表你被拒绝。
插件第一反应
这里不能只润色“好听”
          。它先确认四个用户任务：验证邮箱并声明资格、填写资料、轮次开放后主动报名、双方同意后才
显示联系方式。
建议方向
  • 验证学生使用范围 改成“验证邮箱并声明学生身份与年龄”，同时保留 @Link 不是大学身份认证的边界。
  • 最多收到一位介绍 改成“每轮最多介绍一位对象”。
  •“没有合适介绍也是正常结果”可以保留含义，但语气需要更像给用户的解释，不像系统判定。

6. Privacy / Terms：哪些能改，哪些不能改
隐私和条款页的最大问题不是文风，而是公开页面暴露了内部阶段和未决法律状态。
可以直接改的文案
 • 把 解除使用你的账户这类不自然搭配改成人能理解的删除或停用后果。
 • 把 资格边界 / 使用范围这类内部词改成用户能感知的资格、登录或可见范围。
不能直接改的文案
 • 正式法律审批仍需项目负责人和外部法律顾问确认。
 • 它不是法律意见，也不代表外部法律审批已完成。
 • 系统按已冻结的产品合同进行周期式匹配。
 • 质量边界 / 品質邊界。
这些不是“句子不自然”那么简单。插件正确做法是升级给产品、法律或隐私负责人确认：公开页到底应该披露什么，哪
些状态尚未准备好，哪些承诺不能写。

7. Support / Register / Login
Support 页面方向正确：告诉用户能登录时先用产品内设置、屏蔽、举报和删除功能；不能登录时用公开邮箱；紧急情况不
要依赖 Meet at CU。
可以改得更自然
  • 如你无法登录、需要隐私或删除支持，或需要回报无法在产品内处理的安全问题，可以电邮 support@cuhkdate.com。
  • 建议简体写成：如果你无法登录、需要隐私或删除方面的帮助，或需要反馈无法在产品内处理的安全问题，可以发
    送邮件至 support@cuhkdate.com。
需要确认事实
  • 不会向对方公开你的身份 比隐私页的范围更宽。应确认是“不在产品界面显示”，还是更强的身份保护承诺。
  • 目前介绍相关页面 不是一个用户能直接找到的入口名。没有登录态证据时，不能编造按钮位置。
Register/Login 当前公开路由为 404。插件没有把旧审计里的注册/登录文案拿来假装当前仍可见，这是正确边界。

8. zh-Hans 与 zh-Hant-HK 分开判断
这次候选没有把两种语言当成机械简繁转换。
zh-Hant-HK 可以保留的自然表达
  • 私隱
  • 電郵
  • 支援
  • 封鎖
  • 舉報
  • 上載
  • 建立帳戶
这些不需要为了统一被改成另一套语域。
两种语言都需要处理的内部词
  • 使用范围 / 使用範圍
  • 产品合同 / 產品合同
  • 质量边界 / 品質邊界
  • 正常结果 / 正常結果
zh-Hans 更明显的问题
电邮、回报、支持路径在简体产品界面里不够自然；这些需要按简体用户语感改，不应直接沿用香港繁体思路。

11. 为什么不是逐句润色，也为什么会升级
例子 1：首页状态重复
首批同学加入中、只开放注册、先把资料准备好、现在可以创建账户并完成资料都在解释当前阶段。逐句润色会让页面更
顺，但仍然重复。正确处理是合并位置和角色。
例子 2：How it works 标题层级
页面名、导航名和正文主标题都在讲“如何运作”
                     。这不是把“如何运作”改成“使用流程”就结束，而是要确认哪些是导
航、哪些是正文标题、哪些是浏览器标题。
例子 3：Privacy / Terms 内部阶段眉题
第一批真实用户前不是语言不自然，而是不应当作为公开页视觉眉题出现。这里应删除或换成成熟公开页结构，不是换个
更圆滑的说法。
下面这几类情况必须升级，不能靠一句更顺的文案解决。
例子 1：注册入口
页面说可以创建账户，但公开 /register 当前 404。插件不能自行决定“暂停注册”或“加入候补名单”
                                                     ，只能把入口状态
交给产品 owner。
例子 2：法律审批状态
正式法律审批仍需项目负责人和外部法律顾问确认不能被改成“已完成法律审核”，也不能为了好看直接删掉。公开条款
效力需要法律/产品决定。
例子 3：删除与保留
少量最小化记录可能保留说明有保留事实，但没有明确类别、期限、用途和备份处理。Product UI Copy 可以指出问题，不
能承诺“立即永久删除”
          。

17. 与 2026-09-26 历史 150 条审计对照
这一页是第二阶段结果：旧审计只在第一阶段盲测冻结后读取，用来做回归对照，不改第一阶段原始判断。
旧审计共 150 条：A 53、B 72、C 15、D 10。当前公开抓取里，118 条仍可见：109 条是精确字符串，9 条是旧表合并行在
当前页面拆成多行但内容仍在。5 条已改变或本次未见。27 条来自 Register/Login；当前公开 /register 与 /login 两种语
言都是 404，所以不可比较。
对仍可见的 118 条，第一阶段盲测表现如下：

                         类型                            结果
                         A 类自然文案正确 KEEP               30 / 30
                         B/C 类问题被自己识别或页面级覆盖           64 / 78
                         B/C 类未单独点名、留给人工语气判断          14 / 78
                         D 类正确升级到产品/法律/信任边界           10 / 10
                         明显误改本来好的文案                         0
                         明显 material 漏诊                     0


旧审计 Most Important 20 Lines 中，盲测清楚发现 18 条，部分覆盖但需要产品语气判断 1 条，因当前 Register/Login 404 不
可比较 1 条。
最值得你人工看的分歧不是安全或法律边界，而是 B 类品牌语气：首页要不要保留“私密、低频”“不是刷资料”的宣言
感；
 “你的资料，不会变成公开名单”是否符合你想要的产品声线；以及简体是否要避开“电邮 / 回报 / 支持路径”这类偏
港式或翻译式表达。
