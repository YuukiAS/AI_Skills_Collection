功能开关决定接下来的请求是否使用新功能；回滚方案则要说明，出了问题以后，怎样让代码、数据和数据库结构重新处于能正常配合工作的状态。因此，关闭开关可以是回滚方案中的一步，但不能替代整个方案。

可以把功能开关想成道路入口的栏杆：放下栏杆能阻止后面的车进入，却不会把已经进去的车送回来。软件也是如此：关闭新功能，不会自动撤销它已经写入的数据，也不会恢复它已经改变的数据库结构。数据库迁移，就是对数据库结构等内容做调整；迁移执行成功，并不意味着旧代码还能使用调整后的数据库。

两个场景应该分别这样处理：

- **新搜索排序：需要恢复旧排序时，先关闭功能开关，再检查请求是否确实回到旧排序、搜索是否正常。** 已知这次变化只影响读请求，旧排序代码仍在，而且关闭开关后不会留下新的持久化数据，也就是不会留下需要另外处理的已保存数据。因此，关闭开关有条件成为恢复旧行为的直接办法。输入没有提供实际关闭后的验证结果，目前还不能说恢复已经成功。
- **新结算流程：先控制新增影响，并核实旧代码与现有数据、数据库结构的兼容性，再决定如何回退。** 如果正在发生故障，应先阻止更多请求进入有问题的新流程；但如果关闭开关会把请求送到旧流程，就不能直接认定这样做安全，必要时应暂停受影响的结算入口。随后要验证旧版本能否读取新账单字段、能否在迁移后的数据库上正常工作，并完成数据恢复演练，再据此制定和执行回退步骤。

第二个场景中，新账单字段已经写入，数据库迁移也已执行。即使关掉开关，这些变化仍然存在。旧版本可能能够兼容，也可能无法正确处理，现有信息还不能确定。我们目前只知道迁移脚本执行成功；兼容性尚未验证，数据恢复也尚未演练，因此不能据此宣称“可以安全回滚”，也不能假定直接切回旧版本或撤销迁移就能解决问题。
