功能开关不能替代回滚方案，因为它只能控制接下来的请求是否进入新代码，不能自动撤销新代码已经造成的变化。回滚方案则要说明：出了问题后，怎样让代码、数据和数据库结构重新处于能够配合工作的状态，并验证服务已经恢复。

可以把功能开关想成水龙头：关上它能阻止水继续流出，但已经流到地上的水仍然需要处理。类似地，关闭新结算流程，并不会自动清除已经写入的账单字段，也不会把数据库结构改回原样。因此，功能开关可以是回滚方案中的一个步骤，但不能包办整个恢复过程。

**场景一：新搜索排序只影响读取，可以先关闭开关，恢复旧排序。** 输入已经说明，旧排序代码仍然存在，新排序只改变读请求，关闭后不会留下新的持久化数据，也就是需要长期保存的数据。在这个范围内，没有额外的新数据需要撤销。关闭后应检查实际搜索请求是否已经使用旧排序，以及原来的问题是否消失。输入没有提供关闭后的验证结果，所以现在能确定的是处理顺序，还不能说服务已经恢复。

**场景二：新结算流程已经改变数据，先控制新增影响，再验证能否安全退回旧版本。** 如果正在发生故障，应先阻止更多请求进入有问题的新流程。但这里不能直接照搬场景一：如果关闭开关会立即让旧结算代码接手，就需要先确认旧代码能否处理现有数据；尚未确认时，应考虑暂时暂停受影响的结算入口，避免把请求直接交给未经验证的旧流程。

接下来，要验证旧版本能否读取新增账单字段、能否在迁移后的数据库结构上正确工作，并完成数据恢复演练，再根据结果决定如何恢复。数据库迁移是对数据库结构等内容的调整；“迁移脚本执行成功”只说明这一步执行成功，不代表旧版本仍然兼容，也不代表数据能够恢复。例如，旧代码可能忽略新增字段后仍能正常工作，也可能因结构或字段含义变化而处理失败；这两种情况目前都不能排除。

因此，场景二目前还不能确定：关闭开关后旧流程是否可用、直接回退代码是否安全，以及数据恢复是否可行、需要多久。输入明确说兼容性尚未验证、恢复演练尚未完成，不能把这些条件当作已经满足，也不能据此宣布“随时可以回滚”。
