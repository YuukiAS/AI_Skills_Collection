## 背景与当前结论

当前只记录问题、可选设计和验证方法；**不创建产品、不修改既有插件运行行为、不启动 Reviewed Handoff、不发布版本**。

用户的核心诉求是：AI 能够持续承担判断责任。允许一轮没有可发表的科研方案，也允许发现错误后纠正；不能在用户提出质疑时立即改口，或机械认错后继续没有依据地作出相反结论；更不能把形式完整的流程、下一轮提示词和模型投票当成科学进展。

当前倾向于**优先复用 AI_Skills_Collection 中已有的技能、现有 GitHub 和必要的轻量检查**，不重新开发 Codex App、独立智能体平台或数据库。是否需要新增独立技能、纳入 `workflow-core`、添加 Codex 钩子或新增 MCP，须由实际能力缺口和对抗评估决定，不能预先锁死。

## 真实失败案例（2026-10-24，DII）

用户提供的 14:00—14:03 对话出现三个连续问题：

1. 14:00：AI 表示 DII 本轮应重新发现值得解决的医学影像研究问题，将“复用多院异质历史标注、以较少专家工作建立共同分割模型”降为可选方向；没有给出相对过去确定研究起点的新增科学依据。
2. 14:01：用户指出此前已有同一个历史标注方向的决定。AI 立即改称“应该从上述问题出发，不是彻底推倒重找问题”；没有发生对应的文献、实验或逻辑证据更新。
3. 14:03：AI 承认前两次立场切换不是研究判断，但仍在没有实质新增依据的情况下重新宣布原问题应被保留，并开始规划三模型研究轮次和审查流程。

此处**不能仅根据对话断言 DII 科学上应保留或废除历史标注问题**。能确认的是：AI 未区分历史讨论、用户明确冻结的研究目标、研究候选以及已获证据支持的科学判断；在质疑压力下给出了相互冲突的确定结论。用户要求解决的正是这种跨任务可重现的判断失稳，而非替 DII 在本文件中选题。

另一个失败是解决方案过度设计：首次答复提出自建完整决策平台及数据库，未先考察现有技能、插件和 GitHub 能力，也未证明额外工程成本值得；用户明确指出没有精力重新开发 Codex App。

## 要解决的行为缺陷

- **迎合式反转**：用户表露不同意见，即被当成足以推翻原判断的依据。
- **空洞认错**：承认先前没有证据，却立刻给出新的确定结论；缺少真正的复核动作。
- **错误坚持**：反向风险同样重要，不能为了“保持一致”而拒绝有效反例或正确纠错。
- **依据与权限混乱**：混用“用户要求”“曾经讨论”“模型建议”“可验证事实”“实验结果”。
- **目标漂移**：局部公式、漂亮的方法、下一轮流程取代原本要解决的研究问题，未经说明就改变成功标准。
- **流程代替判断**：生成完整计划、报告或测试通过，不等于完成真正的科学判断。
- **过度工程化**：为了修复语言模型行为，先让用户维护另一套客户端、数据库与状态系统。

这不是写作风格问题，`writing-style` 不应承担科学判断或任务权限裁决。

## 初步设计原则（假说，尚未验证）

### 1. 最小化、可跨任务复用

优先检查 `workflow-core` 对复杂任务的来源和验收约束，以及 `project-thread-handoff` 对既有决策及来源恢复的能力。先区分是规则缺失、技能没有被真正加载、模型违背已有规则，还是宿主平台不能在普通聊天中强制调用技能。不要仅为新名称创建顶级技能或插件。

建议的最低配是：**一份针对有依据判断与纠错的技能规则、一小组真实多轮回归案例，以及在现成宿主支持时才添加的可执行拦截**。保持现有 GitHub 文件为正式项目判断的来源，避免第二套决策数据库和第二套任务状态机。普通即时问答不强制写入持久记录，长期且高影响的判断才需要保存来源。

### 2. 判断必须能正确分类

对长期任务，至少分清：
- **用户明确目标／授权边界**：由用户明确更改，AI 不可暗中替换。
- **事实与实验结果**：需追溯到原文、运行结果或原始文件；被新的可核查证据推翻时修订。
- **模型的科学推断或建议**：可因新证据、发现既有推理错误、重新审查重要前提而修订；不必强行要求每次都有一篇新论文，但必须说明具体改变了哪条理由。
- **开放假说、待决事项**：允许暂不决定；不应冒充已获认可的结论。
- **历史助理表述**：不是独立证据，也不自动代表用户批准的决定。

质疑应触发复核。复核后可能坚持、修订、撤销或暂不判断；不能把“用户质疑强烈”本身当成证据，也不能因留痕而阻断正确的纠错。

### 3. 插件、MCP 与宿主强制检查的边界

- **技能／插件**：最适合先定义工作方法和小范围评测；若宿主不调用或模型不执行，软约束会失效。
- **已有 GitHub 连接**：可保存和回读正式项目材料、决策及差异；不是聊天回答的全局拦截器。
- **Codex 钩子与仓库检查**：若目标 Codex 版本和运行入口确实支持，可在关键输出或提交处增加轻量校验；只能覆盖被挂接的执行路径，不能保证所有语义判断正确。
- **MCP**：主要用于补充可被调用的读取／修改／核验能力；若已有连接满足需求，不另建 MCP。MCP 本身通常也不能强制拦截任意普通聊天回答。
- **独立客户端或模型接口代理**：仅在确实需要跨所有客户端强制拦截，且较轻方案在严格测试后达不到目标时再论证；目前不建议。

关于具体 Codex Hook 事件、拦截语义、各 ChatGPT／Work／Codex 宿主的调用保证与安装能力，**实施前必须核查当时的官方文档和真实运行路径**；不以本笔记推定已有全局强制力。

### 4. 不制造新的流程依赖

单个质疑优先做有针对性的检查，不自动创建新一轮多人投票、全面审查或多模型辩论。新增模型调用必须能够提供独立证据或实质性推理增益；多个模型重复同一假设不是独立证明。对于真正缺证据的科研争议，允许清楚报告未决，并给出能改变判断的最小证据需求；用户不应反复充当 AI 的裁判。

## 怎样验收有效性

先冻结原始失败对话作为**已知回归样例**，另建未曝光给开发者的测试集。比较同一模型在原生对话、仅提示词、技能加载、技能加可执行校验等条件下的表现；记录额外耗时、成本与有效工作完成度，不以“更啰嗦”冒充“更可靠”。

最少覆盖以下双向情形：

1. **错误质疑**：用户以不同措辞及不同压力强度反驳正确结论，AI 应能坚持并说明依据。
2. **正确纠错**：用户指出可核查错误，AI 应能接受并精确修正，不能变成机械固执。
3. **无新增证据**：重复反问不得造成无理由反复改口或反复认错。
4. **真正规则变化**：用户明确改变目标、时间或约束时，应合法更新行动路线。
5. **历史决定非授权**：此前助理的建议不得假冒用户决定或科学事实。
6. **长期目标漂移**：持续检查研究目的与评价标准是否被局部数学、美观或流程悄悄替换。
7. **证据不足**：允许不给方案，但必须交代已核查范围、剩余关键不确定性和停止／继续依据。
8. **跨项目与新线程**：检查来源恢复是否准确、是否滥用旧记忆，以及是否能从仓库重新验证。

主要指标：无依据立场反转率、正确纠错接受率、错误坚持率、研究目标漂移率、错误完成声明率，以及每完成一个有效决策的时间与模型调用成本。验收阈值应在试验前确定，不得运行后按结果改动；不能只优化其中一个指标。

可用外部学术研究作为机制与评测设计参考，但不能把已发表的总体结果冒充本仓库插件的实际效果；论文来源、实验结论和适用边界需在正式设计前独立复核。

## 暂定实施顺序（需要后续单独授权）

1. **差距核查**：看现有 `workflow-core`、`project-thread-handoff` 和当前宿主能力实际能做到什么；查同类 TODO，避免重复创造技能。
2. **先建评测，不先建平台**：用用户实际失败对话和双向纠错测试设定可观察基线；保证不能简单靠永远拒绝更改而通过。
3. **最小改动验证**：优先新增／修订最小技能行为，只有确有价值才加 Codex 钩子或便宜的 GitHub 校验。
4. **按失败机制升级**：区分技能未触发、来源丢失、证据误读、判断失稳、目标漂移；只有既有能力确实不能覆盖且效果增益值得成本时，才研究新 MCP。
5. **停止条件**：达不到预先验收的双向正确性就不宣称“解决”；改善已足够则停止加组件，不因架构完整性继续开发。

## 风险与边界

- 一个技能插件无法强制影响所有普通 ChatGPT 回复；仅凭提示词不能承诺彻底消除迎合。
- 钩子可检查文件、来源和操作边界，但不能凭正则表达式判定任意科学论证对错。
- “每次改判断必须有新外部论文”是过强的约束；发现原推理缺陷同样可能合理纠错。
- 过重记录和审查会使探索失去效率；应只对高影响、长期或正式交付的判断增加必要手续。
- 这份笔记是**问题与候选方案存档**，不是已经验证的产品方案，也不是开发许可。此前聊天中出现过的“测试通过”说法不构成本仓库生产环境证据。
