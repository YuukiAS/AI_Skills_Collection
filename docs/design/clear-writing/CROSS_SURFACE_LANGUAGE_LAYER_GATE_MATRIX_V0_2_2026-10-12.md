## G0：真实分发和最终身份一致

证明对象：正式候选的六个技能与支持文件真实进入 Codex 正式安装和 ChatGPT 用户私有插件，而非只存在于 GitHub、模型上下文或临时路径。

证据：源提交、`scripts/codex_marketplace_config.json` 中 `writing-style` 条目、六个源目录与生成六份技能的清单、Codex 官方 Marketplace 插件载荷、清单/内容核对、Plugin Creator 真实个人插件创建结果与当前版本/发行身份、ChatGPT Web 新会话可见技能和插件身份；真实安装/恢复记录分平台保存。仅测试候选包的创建与安装不能替代自动使用效果（G1）。

同时检查源中需要执行帮助脚本的技能在真实 ChatGPT Web 是否具有必要运行条件。只有包装成功或文件可见时，不能宣称该技能的重型完整流程在网页端可用；若不支持，必须标出实际受影响的表面与能力，并返还架构/执行评审裁定，不得默认做隐式功能降级。

硬失败：插件不可安装、生成版落后于源、正式源有两份、网页包并非候选、只有 Codex 可用却声称双端正常、用户插件未实际安装、现有五技能被意外省略、私有 ID/URL 泄漏到公共仓库。

## G1：无 `@` 正常入口及候选增量

目标：用户在 Project 内、Project 外或 Codex 自然工作任务中，不必每次点名 Clear Writing，第一条完整回答就满足场景需求；新增插件相对持久指令本身有可观察增量。

冻结条件：同一用户/工作区、相关可用模型、任务族、语言合同、评审标准和事先限定的尝试次数；安排自然直接与间接请求、边界负例、跟进任务。比较以下有 Project 条件：

| 条件 | 配置 | 证明什么 |
|---|---|---|
| A | 已安装候选，维持同一 Project 基础语言合同，无额外激活桥 | 插件在普通项目设置下能否独立改善 |
| B | 已安装候选，维持同一合同，加一次性简短激活桥 | 更强的可行入口 |
| C | 无新候选／上一版本但具相同项目合同和激活桥 | 排除“仅项目短指令有效”的伪增量 |
| D | 明确 `@Clear Writing` | 诊断技能能力，不计自动入口 |

无 Project：在固定个性化自定义指令下做有/无候选的成对比较，并验证当前消息语言覆盖下一轮可恢复。对照设置必须通过受支持、获授权、可恢复的机制建立；如果当前个人环境不能可靠启停候选或隔离版本，则该对照报告 `INCONCLUSIVE`，不得主张候选因果效果，也不得把同一个会话的“先试一次、后试一次”当盲对照。

Codex：正式安装新会话/新任务，普通软件解释、文稿与领域消费者不能只有显式技能名才成功。必须附录正向、反向与近似触发记录，记录技能实际选择与必要时产生的差异。

硬失败：B 未通过首答或 B 与 C 无稳定增量却宣称自动终审；只有 D 通过；直接源注入代替正式安装；评审只看模型自述而不看真正回复。A 可靠成功时，B 里的额外桥应降为可选。**没有增量时必须返回 Planner 简化，而不是强行认定“技能通过”。**

## G2：自然目标语言与人能读懂的完整首答

输入覆盖：科研/统计解释、CUHK Date 类型的架构判断（以公开安全等价内容，不复制私有对话）、服务器故障与英文日志、代码项目运行状态、生活简短建议，以及读取大量英文仓库资料后同一回复给人的结论。

由具备完整内容的独立审阅者检查：第一段是否回答用户最关心的结论及实际影响；普通工程/管理概念是否自然中文化；来源标签是否仅在检索/定位必要处出现；是否把机器字段、重复流程和日志转为经过消化的推理；列表/换行是否因信息结构而存在；是否在必须精确保留时保留正式名字。

硬失败：普通英文词串堆砌、每句话一段、内部状态替代分析、强制三段式、纯关键词消除而语义变差、因为短而省掉真正必要的条件。只有文本简短或“英文字符减少”不构成 PASS。

## G3：跨语言/安全/机器语义保真

审查带有事实、作者归因、源的观察与推断、科研公式/引用、许可/权限边界、机器标识、产品删除/付款/隐私后果及未完成状态的输入，对源结论与最终表述进行逐命题检查。

保留：数值、单位、符号、定理状态、因果与否定、条件、比较、证据强度、未授权与已授权、当前与未来、用户删除/拒绝的内容，以及主机、字段、路径、命令、协议值等真正需要逐字定位的字符串。纯 JSON/YAML/代码/原始日志/逐字内容必须保持用户要求的机器协议；混合任务只处理解释文字。

硬失败：任何受保护语义被改写，未完成变完成、可选变必须、来源假设变确定结论，或纯机器输出被添加解释。不能因输出流畅而豁免。

## G4：现有写作技能兼容和专业完整成稿

用正式 Clear Writing 安装入口覆盖：中文轻量修稿、英文科研表达、已有中文/中文主导科研技术长文的重度保真结构重写、只做保真核查、无改动应原样保持的案例、完整技术报告/必要 PDF 渲染、公式表格及合法代码。

必须从候选正常路线产生完整文稿或实质被消费的片段，并检查来源保真、全文结构、必要的复现细节、语言与真实渲染。对已有 `scientific-rewrite` 的含义映射—读者计划—中文实现—整篇组织—保真主链，只验证有无回归，不另起重型架构。

硬失败：旧五项功能丢失、轻量任务误入重写、普通解释抢走中文成稿、参考材料的作者未来计划变成当前执行命令、合法公式/代码被删除、整篇成稿仍像内部备忘录。**Research Authoring 不作本轮消费者或验收项。**

## G5：领域消费和真实渲染

至少审查以下不同真实使用形态，使用合规公开安全样本或经授权的只读实际项目材料：

- Frontend Design：已有前端内容架构把产品状态、用户行动、文字角色和受保护后果交给 `product-ui-copy`；正常入口确实消费它；审阅实际宽屏与窄屏/必要原生界面渲染，确认文字长度、语义与相邻信息合理。后端纯数据负例不进入界面文案路线。
- Presentations：已有 `chinese-prose`、`scientific-prose`、`writing-fidelity` 接口保持；用完整一套自然演示请求产生最终候选并检查实际渲染、页面信息层级、引用/科学结论和可编辑要求；不能用单页片段宣称整套效果。
- Codex 普通代码/统计/服务器任务：向人汇报结论与动作时表达自然；源码、机器日志、性能数值与未经授权操作语义原样保留。

硬失败：相关能力仅在静态文字说明中存在、一个技能被“读了”但实际输出没受它影响、界面文字更自然却改错后果、幻灯片文案更顺却挤爆页面/改科学结论、原有入口回归、数据后端误触发界面写作。仅测试候选脚本不算真实入口。

## G6：长会话、语言模式及不应改变

冻结 ChatGPT 的多轮序列：新项目会话→一般解释→阅读大量英文材料→普通跟进→纯机器内容→本轮英文/双语/繁体覆盖→下一轮恢复基础语言合同。无 Project 会话另跑相同原则。Codex 测试简单回复、英文科研文稿、香港地区 UI、中文论文/公式、未要求润色时的纯机器输出。

硬失败：英文 Project 被误中文化、一次语言覆盖污染未来、机器输出被改、长会话后恢复大量普通英文和机械换行、无关简短问题被夸大成报告。持久规则与技能调用功效必须分开归因。

## G7：最终候选不可拼接的独立验收

在生产候选、ChatGPT 个人插件归属/版本和 Codex 正式载荷已经确认、G0–G6 的既有回归及代表性完整产物经审阅后，再执行不可用于继续调优的冻结未见任务。样本按失败族与风险设最小覆盖，不因“标准矩阵有 8 Gate”固定每 Gate 一个或增加重复次数。冻结清单至少记录：

`FINAL_CANDIDATE_COMMIT`、`CODEX_PLUGIN_PAYLOAD_HASH`、`WEB_WRAPPER_PACKAGE_HASH`、`WEB_CURRENT_RELEASE_ID`、`TARGET_SURFACE`、`FROZEN_TASKS`、`ASSIGNMENT_AND_MAX_ATTEMPTS`、`REVIEW_RUBRIC_VERSION`、`REVIEWER_ROLE`。

注意同一最终候选的不同正式包可以是格式适配，但每项正式技能正文和支持文件必须核对同一冻结源，不能旧 Web 版和新 Codex 版分别拼证据。真实 ChatGPT Web 首答、项目内外、完整报告、真实 UI、整套幻灯片、来源保真、语言与纯机器反例是不同证据来源；独立评审要拿到实际全文与可打开渲染。

硬失败：最终候选更改后沿用旧 PASS、只挑成功回复、替换未见题、把开发回归改称新题、来源不完整、跨不同候选组装“所有 Gate 通过”。基建故障与产品故障分开归因，基础设施恢复不允许改源、任务、评分或无限重试。

## 结论的严格等级

- `DIRECT_TOOL_ONLY`：只有显式调用通过，不能宣传普通自动表达层；
- `BRIDGE_ONLY_SUFFICIENT`：仅持久语言指令与桥已经等效，不得宣传新技能增量；
- `INSTALLED_SKILL_WITH_BRIDGE_REQUIRED`：B 稳定通过并且相对 C 证明额外效果，桥为必要部署前提；
- `INSTALLED_SKILL_WITHOUT_BRIDGE_RELIABLE`：A 稳定通过，且相对无候选证明额外效果，桥可选；
- `NORMAL_ENTRY_UNSUPPORTED`：实际表面无法安装、自动触发或无法完成有证据的正常入口，整体跨表面能力不可宣称完成。

只有同一最终候选在适用的 G0–G7 上满足通过标准、独立 Reviewer/必要 Critic 没有阻断问题、用户按正式交付范围接受时，才可宣布对应产品范围完成。架构/执行包审查 PASS 都不等于这些产品能力已实际通过。
