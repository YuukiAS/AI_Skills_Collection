## 1. 产品承诺：把内容变成读者能理解和使用的交付物

Clear Writing 不是插件架构说明专用工具，也不是把最终一句话润色一下。它处理普通问答、科研和数学解释、技术说明、比较与建议、执行进展与交接、已有文稿改写、正式中文终稿、英文科研表达、产品界面文字，以及上述任务中必须保持精确的代码和机器内容。

用户在 ChatGPT 或 Codex 明确选用 Clear Writing 后，应得到与当前问题和读者需求相称的表达：该简短时直接回答，该解释时补足直觉和因果，该给完整证明和复现时保留深度。需要写入 GitHub 的文件是独立交付物，必须实际得到全文处理，不能由聊天说明代替。

共同流程是：确认交付目标和内容边界；选择并组织读者必须理解的信息；用正确专业路线写成完整文本；对照问题与来源审校；交付同一份已审文本。它是现有原生技能的工作流程，不引入第二模型、服务器、发送拦截器或常驻审校系统。

## 2. 边界：本线程负责什么，另一线程负责什么

| 事项 | 决定者 | Clear Writing 的职责 |
|---|---|---|
| 项目默认语言、角色权限、执行授权、下一责任方、审查与恢复规则 | AI Research Stack 设置、Planner/Critic 合同及任务负责人 | 使用已经确定的事实与交接决定，表达清楚，不另定规则 |
| 科学事实、统计结论、算法正确性、证据是否足以发布 | 领域工具和任务负责人 | 保持主张、条件、限制和证据强度，不编造支持材料 |
| 新论文/研究报告的贡献、实验选择、论证设计；幻灯片叙事与视觉布局 | Research Authoring、Presentations 等领域负责人 | 消费其已确定的内容简报，处理措辞、局部解释、衔接与保真 |
| 普通聊天该回答哪些问题、如何让读者理解；已有文本获授权后的清晰改写 | Clear Writing 现有专业路线 | 对读者内容选择和组织承担明确责任，不只换词 |

本轮不修改项目设置、Planner/Critic 角色合同、Bridge Kit、Slurm 或 CAT-TRACE 研究事实。中断时下一角色由现行工作流决定，Clear Writing 负责把这个已确定决定及完整交接说清楚；不能为写出漂亮结尾擅自选择新任务或授权。用户明确要求完整审计时，审计证据就是正文的一部分；不能以“内部材料”为由删除。

## 3. 对前一方案的必要修正：能力不能只留在 ChatGPT 包装里

上一方案规定六项专业路线的正文不变，新增内容选择只放进 ChatGPT 单入口。这能改善网页入口，却不能使直接调用现有专业技能的 Codex 自动获得同一改善；还会产生包装层与专业路线两份重叠的写作规则。

本版明确改变这一冻结决定，待独立审查：保留六项专业能力和 Codex 六入口，但允许在其既有职责内修正唯一源文。普通回复的内容选择、解释组织和全答复审校归回 `response-clarity`；跨产物的保真和最终文本绑定归 `writing-fidelity`；正式长文继续用已有 `scientific-rewrite` 的意义组织和读者计划，以及 `chinese-prose` 的全文表达终审。ChatGPT 包装仅识别对象、选择/组合路线与报告逐对象状态，不再独立维护一份普通聊天写作规则。

这不是新增第七项能力，也不是否定现有规则已经写过正确原则。要替换的是“先生成一大段结果，再在末尾提醒自然表达”的消费顺序：在现有专业路线的实际工作步骤中，先做任务与读者内容选择，再生成与审校全文。重复条款要合并，不在文件末尾继续叠加同义要求。

## 4. 一套写作工作方式，按任务采用不同深度

### 4.1 先分清目标和编辑权限

本轮可以同时有聊天说明、行内文档、GitHub文件、界面文案和机器内容。它们是当前任务内临时识别的对象，不建立数据库或持久登记系统。

每个对象先确定读者、用途、语言、用户具体问题、需要的深度、材料是否齐全、允许的修改幅度，以及必须保留的主张/公式/引用/命令。单纯润色保留已约定结构；授权结构重写可改变顺序但不删必要意义；摘要允许范围收缩但必须标明摘要；新文稿先取得足够的已核实依据，缺事实不靠润色补造。

### 4.2 分析材料不自动成为正文

普通聊天的领域分析可以充分读取资料。正文纳入的信息必须直接回答问题、解释必要机制、改变可信度或风险判断、保留关键限制、支持操作与复现，或属于用户明确要求展开的细节。

实际写作前，应能说清每段要让读者理解什么。它可以围绕判断、比较、因果、推导、操作步骤或后续决定组织，不要求所有内容都套“问题—机制—证据”模板。比较建议先给选择依据，简短状态先给结果和必要行动；陌生方法先讲用途、对象和关系，再用合适的例子/公式解释。方法解释不等于必须讲故事，完整证明也不能被比喻代替。

具体例子和数值必须来自材料或明确标记为示意。未知变量意义不能猜。关键局限紧随相应结论。正文不承担内部执行历史的展示义务；但必要版本、路径、命令和操作状态不得被随意删改。

### 4.3 现有专业路线各负其责

| 交付类型 | 唯一专业路线 |
|---|---|
| 普通解释、比较、建议、进展、完成和交接答复 | `response-clarity`，必要时结合 `writing-fidelity` |
| 已有中文正式文稿的润色与全文终审 | `writing-fidelity` + `chinese-prose` |
| 已有中文长技术/科研材料的结构重写 | `writing-fidelity` + `scientific-rewrite`，由 `chinese-prose` 完成表达和终审 |
| 英文科研写作 | `writing-fidelity` + `scientific-prose` |
| 产品界面文字 | `writing-fidelity` + `product-ui-copy` |
| 纯精确机器输出 | 不改写；混合任务只处理自然语言部分 |

新论文的研究论证规划不因此归 Clear Writing。一般说明文的新建可以依据用户给定材料完成；涉及领域新主张或实验选择时，先由相应负责人确定再写。文档完成后附带的聊天说明另走普通回复路线。

### 4.4 全文审校，不以首段自然代替整篇合格

审校分别回答三件事：是否回答完整的问题、读者能否顺着理解、内容是否保真。逐句无错不等于整篇有用；有公式和例子也不等于解释到位。要检查概念第一次出现的对象/层级/用途、相邻段落的关系、证明或操作前置条件、必要限制、普通英文与精确标识的区别，以及结尾是否重复已完成的结论。

发现表达问题先在当前任务内返修完整候选；涉及事实冲突交回领域判断，不擅改结论。候选被实质修改后，先前审校不自动覆盖新文本。日常模型自检不称为独立审查；发布验收另由已有独立机制检查完整来源和完整最终产物。

## 5. GPT 与 Codex 怎样实际消费同一能力

ChatGPT 保持唯一顶层 `clear-writing`，按对象读取并应用打包的六条路线。Codex 保持当前六项可直接调用能力和 `codex-writing-style` 组合；自然插件请求按已有描述选路线，领域插件直接调用相应技能也能得到相同的新语义。不得要求用户每次指出内部技能名称才能触发改善。

允许修改的唯一源与职责如下：

- `skills/writing/core/response-clarity/SKILL.md`：重整现有 Workflow，使内容选择、读者问题组织、表达、整篇覆盖/保真检查发生在正确阶段；保留短答、必要长答、混合内容和不越权边界。只在这里保存普通回复的微型正反示范，不在包装层另维护副本。
- `skills/writing/core/writing-fidelity/SKILL.md` 及新增 `references/final-delivery.md`：统一保真要求与已审全文的交付合同；明确整体审校对象、返修使审校失效、各宿主实际读写路径及准确的未完成状态。新引用是交付协议，不是另一套写作规则。
- `skills/writing/core/chinese-prose/SKILL.md`：仅整理其已有全文终审与最终候选交接，确保不把差异片段或回执当终稿；不复制普通聊天的内容选择算法。
- `skills/writing/core/scientific-rewrite/SKILL.md`：仅对接已有完整候选和交付引用；意义图、读者计划、helper及保真机制保持。不另造重写器。
- ChatGPT `packaging/chatgpt/writing-style/clear-writing/SKILL.md`：保留唯一入口和对象路由；删除独立的普通回复内容规则副本，要求实际消费上面的专业源文与交付引用。
- `scripts/build_clear_writing_chatgpt_wrapper.py`：保留确定性包装与两项允许的路径投影，纳入新增支持引用；安全支持真实 ZIP/tar.gz 旧归档。Codex 生成器和 profile 由现有正式生成流程更新，不手改生成文件。

`scientific-prose`、`product-ui-copy` 没有新增语义，只验证与整体路由和保真兼容。六项能力没有删除、合并或改名；变的是职责内的消费顺序，所有源改动必须进入同一个新候选。新示范仅用脱敏通用文字，不打包私有 CAT-TRACE 原文或 Slurm 配置。

## 6. 为什么写入 GitHub 的文件会是可以交付的终稿

信任不能只依赖一句“用了 Clear Writing”，而要同时成立三个条件：内容任务正确完成、全文表达确实经过审校、仓库实际保存的就是那一份全文。

**读取与范围。** 修改既有文件时取得真实完整 UTF-8 源文与 repo/可写分支/路径/blob 身份；截断时分段读完，不以摘要或旧聊天代替。只读请求不写文件。新建文件要有明确授权的目标路径、用途与完整依据，先确认目标不存在。

**完整候选。** 正式文件不是聊天答案的副产物。按文件本身的类型选择完整路线，形成可直接独立阅读的完整文本；本来要求只改一处时仍检查其与全文的衔接，不借全文终审擅自扩大编辑范围。写前对照来源/授权资料检查事实、公式、条件、版本、引用和权限，再检查全文是否自然、解释连贯、标题有用、普通英文是否需要中文化。任何一个内容检查未完成，都不把候选作为已完成终稿写入。

**交付与同一性。** ChatGPT 使用现有 GitHub 工具。既有文件写前复查源blob，`update_file`带原blob条件写入完整候选；新文件使用`create_file`非覆盖创建，确认路径仍不存在、写前分支头与返回提交父提交的关系，不能把事后检查宣传成不可绕过事务。写后从真实目标读取全文，与已审候选逐字核对。保存来源、候选与提交/回读关系供评审。

Codex 的本地工作区写入同样先形成已审全文，写后读回实际文件；任务明确要求推送 GitHub 时，按已有目标仓库授权与发布入口提交/普通推送，再回读远端精确提交的目标全文。没有推送权限只交付本地文件并说明实际状态，不把本地完成写成已上 GitHub；不新增通用推送器或改变 Branch/Host 策略。

审过的全文不在上传步骤自由重新生成。确因事实变更而改正文，重新检查后才提交。读取、内容审校、写入和回读分别有证据；哈希只证明版本，不证明文章写得好。最终消息分别说明聊天结果与每个文件的实际完成情况，不打印内部状态表代替解释。

## 9. 实施与恢复边界

实现顺序：批准范围内源文重整→现有生成/路径投影/确定性ZIP→安全ZIP/tar.gz恢复输入→已有开发回归和完整产物自查→必需CI与独立实施审查→冻结同一个源提交及两端分发身份→Phase C真实前置→G1到G5→原Critic最终评估前检查→唯一G6→正式版本收口。

每个正式Web任务一次产品答案；只有没有产生模型答案的基础设施故障允许原输入一次重试。产品失败不reroll、不换题。修改源或评价口径会使受影响旧证据失效；使用过的fresh样本转成已知回归。
