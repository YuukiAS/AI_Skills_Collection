## 1. 产品承诺：把内容变成读者能理解和使用的交付物

Clear Writing 不是插件架构说明专用工具，也不是把最终一句话润色一下。它处理普通问答、科研和数学解释、技术说明、比较与建议、执行进展与交接、已有文稿改写、正式中文终稿、英文科研表达、产品界面文字，以及上述任务中必须保持精确的代码和机器内容。

用户在 ChatGPT 或 Codex 明确选用 Clear Writing 后，应得到与当前问题和读者需求相称的表达：该简短时直接回答，该解释时补足直觉和因果，该给完整证明和复现时保留深度。需要写入 GitHub 的文件是独立交付物，必须实际得到全文处理，不能由聊天说明代替。

共同流程是：确认交付目标和内容边界；选择并组织读者必须理解的信息；用正确专业路线写成完整文本；对照问题与来源审校；交付同一份已审文本。它是现有原生技能的工作流程，不引入第二模型、服务器、发送拦截器或常驻审校系统。

## 2. 边界：本线程负责什么，另一线程负责什么

| 事项 | 决定者 | Clear Writing 的职责 |
|---|---|---|
| 项目默认语言、角色权限、执行授权、下一责任方、审查与恢复规则 | AI Research Stack 设置、Planner/Critic 合同及任务负责人 | 使用已经确定的事实与交接决定，表达清楚，不另定规则 |
| 科学事实、统计结论、算法正确性、证据是否足以发布 | 领域工具和任务负责人 | 保持主张、条件、限制和证据强度，不编造支持材料 |
| 新论文/研究报告的贡献、实验选择、论证设计；幻灯片叙事与视觉布局 | Research Authoring、Presentations 等领域负责人 | 消费其已确定的内容简报，处理措辞、局部解释、衔接与保真 |
| 普通聊天该回答哪些问题、如何让读者理解；已有文本获授权后的清晰改写 | Clear Writing 现有专业路线 | 对读者内容选择和组织承担明确责任，不只换词 |
| GitHub 或本地文件实际读写、Git 发布与平台权限 | 宿主工具及目标仓库规则 | 只交付审过的候选、核对实际目标，不自行扩大权限 |

本轮不修改项目设置、Planner/Critic 角色合同、Bridge Kit、Slurm 或 CAT-TRACE 研究事实。中断时下一角色由现行工作流决定，Clear Writing 负责把这个已确定决定及完整交接说清楚；不能为写出漂亮结尾擅自选择新任务或授权。用户明确要求完整审计时，审计证据就是正文的一部分；不能以“内部材料”为由删除。

## 3. 对前一方案的必要修正：能力不能只留在 ChatGPT 包装里

上一方案规定六项专业路线的正文不变，新增内容选择只放进 ChatGPT 单入口。这能改善网页入口，却不能使直接调用现有专业技能的 Codex 自动获得同一改善；还会产生包装层与专业路线两份重叠的写作规则。

本版明确改变这一冻结决定，待独立审查：保留六项专业能力和 Codex 六入口，但允许在其既有职责内修正唯一源文。普通回复的内容选择、解释组织和全答复审校归回 `response-clarity`；跨产物的保真和最终文本绑定归 `writing-fidelity`；正式长文继续用已有 `scientific-rewrite` 的意义组织和读者计划，以及 `chinese-prose` 的全文表达终审。ChatGPT 包装仅识别对象、选择/组合路线与报告逐对象状态，不再独立维护一份普通聊天写作规则。

这不是新增第七项能力，也不是否定现有规则已经写过正确原则。要替换的是“先生成一大段结果，再在末尾提醒自然表达”的消费顺序：在现有专业路线的实际工作步骤中，先做任务与读者内容选择，再生成与审校全文。重复条款要合并，不在文件末尾继续叠加同义要求。

## 4. 一套写作工作方式，按任务采用不同深度

### 4.1 先分清目标和编辑权限

本轮可以同时有聊天说明、行内文档、GitHub文件、界面文案和机器内容。它们是当前任务内临时识别的对象，不建立数据库或持久登记系统。

每个对象先确定读者、用途、语言、用户具体问题、需要的深度、材料是否齐全、允许的修改幅度，以及必须保留的主张/公式/引用/命令。单纯润色保留已约定结构；授权结构重写可改变顺序但不删必要意义；摘要允许范围收缩但必须标明摘要；新文稿先取得足够的已核实依据，缺事实不靠润色补造。

### 4.2 写作前先定读者任务，不把证据池直接展开成正文

现有0.5入口被读取仍可能产生差回答的原因是：`response-clarity`先确认一个已有“known result”，再决定回复类型和措辞；此时模型可能已经把所读审计事实排列成正文，之后的语言检查只能局部优化，难以取消错误的叙事骨架。修复重点不是更多禁词，而是**在草稿成形前**改变选择与组织的对象。

`response-clarity` 的唯一canonical Workflow 需要按真实任务执行：

1. **定位答案任务**：按最新用户提问确定本次实际要回答的疑问、受众、允许的详细程度、输出类型，以及需不需要实际行动或机器原文。不要把查了多少文件、测试或历史方案当作应写多少内容的依据。
2. **分离两个信息集合**：领域工具已核实的事实/来源构成证据池；正文只选择直接回答问题、建立必要机制与数学理解、影响完成/可信度/风险判断、保留实质限制、支持行动/复现，或用户明确要求展开的内容。用于内部推理的事实仍可用于核实，不自动获得正文段落。
3. **形成理解顺序**：在动笔前，明确每个主要内容单元准备回答哪个读者问题，以及读者必须先知道什么。科研方法按需建立对象层级与具体数量/假设例子，再解释公式和条件；工程机制按需解释原风险、机制如何影响风险、用户实际效果及证据。不是固定“每段四问”，短状态不造故事，完整审计和证明不删必要细节。
4. **形成连续答案**：按已选的读者理解顺序撰写段落。一个因果链不拆成低信息量代码框和一串单句段落；真正需要比较、步骤、公式或机器字节时保留表格、列表和精确内容。

这是一份仅在当前模型推理中使用的轻量读者问题安排，不落库、不输出额外计划、不调用第二模型。事实、科学结论和任务决策由原领域owner承担，Clear Writing只组织**已得到支持**的结论的读者表达。

### 4.3 现有专业路线各负其责

| 交付类型 | 唯一专业路线 |
|---|---|
| 普通解释、比较、建议、进展、完成和交接答复 | `response-clarity`，必要时结合 `writing-fidelity` |
| 已有中文正式文稿的润色与全文终审 | `writing-fidelity` + `chinese-prose` |
| 已有中文长技术/科研材料的结构重写 | `writing-fidelity` + `scientific-rewrite`，由 `chinese-prose` 完成表达和终审 |
| 英文科研写作 | `writing-fidelity` + `scientific-prose` |
| 产品界面文字 | `writing-fidelity` + `product-ui-copy` |
| 纯精确机器输出 | 不改写；混合任务只处理自然语言部分 |

新论文的研究论证规划不因此归 Clear Writing。一般说明文的新建可以依据用户给定材料完成；涉及领域新主张或实验选择时，先由相应负责人确定再写。文档完成后附带的聊天说明另走普通回复路线。

### 4.4 第二阶段不是“我已经检查过”，而是重新阅读独立完整候选

完成正文后，当前模型要**离开最初的生成顺序**，以最新用户问题和整个候选为两个明确检查对象。不能照着撰稿时列出的组件清单自我肯定，而要从读者角度实际回答：

- **任务覆盖**：用户问的每个问题具体由候选的哪一部分回答？如果结论不清楚、关键下一步缺失或限制漏了，改正文。
- **理解障碍**：全文首次出现的关键对象是什么、属于哪个层级、为什么在此处需要它？读者能否理解相邻论证、公式、因果或步骤如何连接？若需要读者自行补推理或反复返回前文，改正文。
- **价值筛选**：有没有整段主要陈列“审查过哪些组件、排除了哪些方案、测试了多少项目”，却不改变用户理解、判断或行动？有则删去、合并或移至用户明确要求的详细审计部分。
- **表达与保真**：普通英文和内部状态是否抢占正文，是否机械单句成段、重复否定/总结？修掉表达问题时仍须保护事实、条件、数字、数学符号、引用、权限和精确机器字符串。

这一步的实际产物是**返修后的完整回答**，不是“审阅通过”的自述或给用户看的长评价表。若改动了重要内容，重新检查被影响的全文，不能仅修第一屏后继续发送。源文或事实有不一致时交领域判断，不靠语言补造证据。

这属于**同一GPT的一轮分工明确的编辑过程**，不是第二个独立模型。普通用户不用多开对话。独立于生成任务的判断只存在于原正式发布Gate的审阅：审阅者必须能看到完整问题、来源和最终文本并可给质量FAIL。纯Skill不是发送前不可绕过的拦截器，因此“步骤写了”不是产品PASS；必须用正常入口的整篇答复证明它真实改善了结果。

## 5. GPT 与 Codex 怎样实际消费同一能力

ChatGPT 保持唯一顶层 `clear-writing`，按对象读取并应用打包的六条路线。Codex 保持当前六项可直接调用能力和 `codex-writing-style` 组合；自然插件请求按已有描述选路线，领域插件直接调用相应技能也能得到相同的新语义。不得要求用户每次指出内部技能名称才能触发改善。

允许修改的唯一源与职责如下：

- `skills/writing/core/response-clarity/SKILL.md`：**替换**旧版先按known result写完再检查措辞的Workflow：先明确本轮用户问题、读者理解依赖与可展示事实，再生成全文，最后以原问题为判据进行整篇返修。只在此处保存普通聊天的微型正反示范，不能在总入口复制第二份。
- `skills/writing/core/writing-fidelity/SKILL.md` 及新增 `references/final-delivery.md`：只集中完整来源与最终候选的**事实/条件覆盖、正文实际版本绑定与工具前后身份**，规定实质返修使旧候选审校无效。具体自然中文表达质量归 `chinese-prose`，普通聊天内容价值归 `response-clarity`，避免多处重复标准。
- `skills/writing/core/chinese-prose/SKILL.md`：仅整理其已有全文终审与最终候选交接，确保不把差异片段或回执当终稿；不复制普通聊天的内容选择算法。
- `skills/writing/core/scientific-rewrite/SKILL.md`：仅对接已有完整候选和交付引用；意义图、读者计划、helper及保真机制保持。不另造重写器。
- ChatGPT `packaging/chatgpt/writing-style/clear-writing/SKILL.md`：保留唯一入口和对象路由；删除独立的普通回复内容规则副本，要求实际消费上面的专业源文与交付引用。
- `scripts/build_clear_writing_chatgpt_wrapper.py`：保留确定性包装与两项允许的路径投影，纳入新增支持引用；安全支持真实 ZIP/tar.gz 旧归档。Codex 生成器和 profile 由现有正式生成流程更新，不手改生成文件。

`scientific-prose`、`product-ui-copy` 没有新增语义，只验证与整体路由和保真兼容。六项能力没有删除、合并或改名；变的是职责内的消费顺序，所有源改动必须进入同一个新候选。新示范仅用脱敏通用文字，不打包私有 CAT-TRACE 原文或 Slurm 配置。

## 6. GPT 写入 GitHub 的实质质量路径

**具体承诺**：同一轮 ChatGPT 用户显式选择Clear Writing并授权修改/创建GitHub UTF-8文本文件，模型应在实际写入前形成并处理**整篇目标文档**，而不是只把聊天解释写得自然，或对源文件仅做字符串替换、段落拼接。内容保真、读者质量和写入身份三个问题分别成立后，才能把实际仓库文件称为终稿。

### 6.1 正确决定文档编辑深度

先取得用户要求、真正完整的源文/授权依据和目标repo/branch/path。确定这次是：

- **局部修订/普通润色**：保护用户未授权改变的事实和结构，但**在全文环境**检查修改区的语气、术语和上下文；只需要改机器字符串时，不为证明调用而强行改写正文。
- **明确授权的长技术/科研材料结构重写**：实际使用既有`scientific-rewrite`的来源锚点、意义图、读者计划、中文实现、装配、保真与返修；再由`chinese-prose`完成整篇中文读者终审。不能以只做`chinese-prose`普通句子润色替代结构重写，也不能用摘要代替保留重要命题的全文。
- **新建文本**：先取得明确目标读者、用途和足够的已核实内容依据。领域科学结论由原owner决定，不因为要“写成篇”就补造研究事实。

如当前ChatGPT宿主不能访问完整源文、无法实际消费需用的路线/支持文件或无法完成整篇写作，不能跳成低配语句替换后宣称同等质量；该对象维持未完成、保留已形成的草稿和确切缺口，正式G3不得PASS。需要执行机械helper的重路线是否能在真实Web中完成，须在正式变更Personal Plugin前用合法的只读/无副作用工具能力核查；不能等发布后才发现调用路径不存在。

### 6.2 同一个GPT真正执行两次不同的文本操作

**第一次：生成完整候选**。按实际编辑深度形成一份可直接阅读的目标文件全文，不是只生成补丁、要点、审校清单或局部片段。为长重写按现有意义图/读者计划整理来源命题及读者依赖关系。

**第二次：把整个候选当作外部读者拿到的文章重新检查。** 这不是再次重复“文字自然吗”。模型必须从头到尾检查全文是否回答文档用途、概念首次出现的定义是否充分、每节的作用是否清楚、论证/公式/限制是否正确连贯、非必要英文/内部状态是否仍然支配叙事、原来源重要命题有无遗漏/改变。发现具体问题必须**实际重写对应部分并重新形成完整候选**，再对受影响全文复查；不能只输出“检查了”的状态。

两次操作由相同GPT在同一请求中执行，不要求用户追加提示词或手工校对。它依靠已选专业路线的具体读者任务与来源保真标准，不用第二模型和新服务。但两次模型操作也不能靠隐藏推理自述给Gate证明：正式审阅仍必须独立判断**最终真实文档**是否已具备这两类质量。

### 6.3 只有已审候选才进入真实写入工具

修改既有GitHub文件：写前复核原blob身份未变，调用现有`update_file`时把**这份候选全文**作为content并带当前blob SHA；新建文件：明确有权写的branch/path与目标不存在状态，使用原有`create_file`非覆盖创建，记录返回commit并核对实际提交。**不得在工具参数中另生成一套未审正文**，也不得在没有足够源文时根据聊天摘要补造文件。

写后必须重新fetch目标文件**全文**，核对repo/branch/path、blob/提交及返回内容与已审候选一致；再把实际保存的整篇文件作为读者读一次。内容如果仍然生硬、缺必要解释或丢失重要限制，不能用内容哈希相同证明“文档已审完”。属于原授权与版本安全范围内的返修，可形成新的完整候选，再经同样审查和版本条件写入；若无法合法补救，则明确说明文件已写入但**尚未达到终稿要求**，不要以完成状态掩盖失败。

ChatGPT的文件工具来自用户已经连接的GitHub入口，Clear Writing本身不创造账号权限。Codex的本地文件操作先写入审过的内容并实际回读；若用户授权推送GitHub，还必须通过原仓库Git规范提交/推送并从远端精确提交回读，不能以本地文件等同GitHub完成。两端专业写作内容共享canonical源，实际工具调用权限仍由各宿主承担。

### 6.4 一次请求多个交付对象

聊天与GitHub文件应各自按相应路线完成并审查。文件全篇正确不自动保证聊天说人话；聊天回答漂亮也不能证明文档符合读者要求。最终给用户的回复只需自然说明实质修改、文件确实保存的位置和验证状态；内部候选/检查细节只在任务确实需要时提供。

整个流程既不增加强制人工审批，也不引入新的提交审查服务器。真正独立的质量判断放在**发布前G3/G4独立完整产物审阅**，不可用普通GPT自审替代。正常用户能否获得合格文稿，必须由同一新版候选在真实ChatGPT完整任务中直接证明；只看Skill源码或模型声称加载一概不算。

## 7. 现有成果、旧批准与 Phase C

## 9. 实施与恢复边界

实现顺序：批准范围内源文重整→现有生成/路径投影/确定性ZIP→安全ZIP/tar.gz恢复输入→已有开发回归和完整产物自查→必需CI与独立实施审查→冻结同一个源提交及两端分发身份→Phase C真实前置→G1到G5→原Critic最终评估前检查→唯一G6→正式版本收口。

每个正式Web任务一次产品答案；只有没有产生模型答案的基础设施故障允许原输入一次重试。产品失败不reroll、不换题。修改源或评价口径会使受影响旧证据失效；使用过的fresh样本转成已知回归。

live更新后任一终止性产品失败或基础设施重试耗尽导致无法继续，停止发布并按原forward restore恢复0.5行为的0.6.1分发档案；保持same identity、expected release、精确existing-file删除列表和完整回读。工具不可用时如实记录待恢复，工具恢复后的唯一动作是恢复，而不是继续Gate。冻结语义内普通缺陷留原Codex修；需改产品、归属、权限或验收定义才回Planner/Critic。
