## 1. 实现目标

在现有 Clear Writing 插件 `writing-style` 内新增技能：

```text
reader-layer-finalization
```

实现后，用户在目标 ChatGPT Web 表面安装 Clear Writing，并在需要高可靠性的 Project 中完成一次短桥配置后，应能直接提出科研、工程、统计、前端或管理问题；第一条完整回答已经执行当前语言合同、自然段落组织、机器内容分层和语义保真，不需要每个 thread 再追加“说中文”“不要英文”“先说结论”或 `@Clear Writing`。

这个目标是可重复、可观察的高可靠行为，不是平台级绝对保证，也不声称存在独立第二次模型调用。

## 2. 冻结职责

### 2.1 新技能负责

- 解析当前回复的目标语言和输出模式；
- 在领域语义形成后识别受保护内容；
- 把普通来源英文、内部标签和日志框架转化为自然目标语言；
- 组织结论、动作、证据和机器细节；
- 合并机械碎片、重复状态和无真实结构的列表；
- 将精确机器内容与解释正文分层；
- 核对事实、条件、权限、证据强度、完成状态、不确定性和精确标识；
- 对纯机器输出、逐字内容和临时语言覆盖正确绕过或切换。

### 2.2 新技能不负责

- 研究新事实或改变领域结论；
- 判断模型、定理、网络、权限、代码或设计是否正确；
- 创建引用、补证据、升级结论或推定授权；
- 编辑长期 Project instructions；
- 把另一个技能调用作为必需运行步骤；
- 通过外部服务进行第二次重写。

### 2.3 现有能力保持

- `chinese-prose` 继续负责中文文档和段落的具体成稿方法；
- `writing-fidelity` 继续负责广义内容保真原则；
- `scientific-rewrite` 继续负责既有长文的结构化重写；
- Research Authoring、统计、前端、Server+VPS 等领域能力继续拥有专业语义；
- PIE 只可能在核心能力成立后，作为一次性短桥配置消费者，不是本能力负责人。

## 3. 正式源设计

建议正式源：

```text
skills/writing/core/reader-layer-finalization/
├── SKILL.md
├── references/
│   ├── activation-language-and-bypass.md
│   ├── protected-semantics-and-exact-identities.md
│   └── full-answer-counterexamples.md
└── evals/
    └── cases.json
```

文件名可按仓库当前生成体系调整，但必须保持：

- `SKILL.md` 在被加载后具有完整、紧凑的运行合同；
- 不依赖运行时技能链；
- 引用文件只承载边界和反例，不建立新状态机；
- 测试输入用于回归，不实现关键词评分；
- `skills/writing/core/` 是正式源，生成插件快照不是反向事实来源。

### 3.1 触发与绕过

技能元数据应围绕“已经形成内容的最终用户阅读层”描述，不写成无边界的“每次回答都必须使用”。应在以下情况匹配：Project 或当前用户偏好声明最终阅读层；用户要求解释、判断、总结、审查结论、计划或其他完整读者输出；任务读取英文来源、日志或内部文档；用户明确调用 Clear Writing。

纯 JSON/YAML/CSV/XML、纯代码或补丁、单条命令、原始日志、逐字引用、严格转录和其他机器专用协议必须进入绕过模式。混合任务只重写解释层。

### 3.2 语言优先级

```text
当前消息明确要求
> 当前 Project 的持久语言与输出合同
> 当前会话仍有效的明确约定
> 用户或工作区默认偏好
```

当前消息覆盖只影响当前回复，不写回长期设置。

### 3.3 受保护语义

至少包括事实、数值、公式、引用、归因、否定、比较、因果、条件、结论强度、证据强度、不确定性、限制、必须/可选、允许/禁止、授权/未授权、安全、隐私、权限、时间、完成状态、用户纠正/删除/拒绝/接受，以及需要复制、执行、搜索或唯一定位的精确标识。

### 3.4 阅读层实现

- 先给用户实际结论、是否需要动作和下一步；
- 普通概念使用目标语言，不因来源英文而保留；
- 来源标题、阶段和内部字段只在用户任务本身讨论它们时出现；
- 段落按信息结构，而不是按字段或每句话换行；
- 列表只用于真实并列或步骤；
- 同一结论不以多套状态重复；
- 裸日志、路径、提交和内部审计不能代替已经消化的判断；
- 必要机器内容单独呈现，并由正文说明其意义；
- 不使用固定段数、固定模板、禁词表或英文比例。

### 3.5 精确字符串

保留与翻译依据语义角色，而不是字符类型。仓库、分支、提交、路径、文件名、命令、代码、配置键、协议值、端口、主机名、服务名、正式产品/方法/模型/数据集，以及用户需要复制、执行、搜索或唯一定位的字符串，按需要原样保留。普通推理和来源标签应自然本地化；确需定位时，以目标语言为主、原字符串附属出现一次。

### 3.6 最后核对

发送前在内部检查来源英文、内部标签、机械换行、重复状态、结论顺序、机器内容分层和受保护语义。该检查不得以状态块输出，也不得声称发生了独立第二次调用。

### 4.2 目标 ChatGPT Web 分发

当前已认证个人 ChatGPT 中存在多个私有技能型插件，但没有独立 Clear Writing。后续实现必须明确完成以下一条受支持路线：

- 将同一 `writing-style` 候选作为个人私有技能型插件创建或更新；或
- 在真实工作区目录中安装同一候选，并记录适用的安装策略与权限。

不得把 Research Authoring 内附带的 `chinese-prose`/`writing-fidelity` 当成跨 Project Clear Writing 已安装的证据。不得只修改仓库文件而省略 ChatGPT Web 安装候选。

### 4.3 短激活桥

候选包提供一条正式参考，但不自动修改真实 Project：

```text
发送面向用户的解释性正文前，使用已安装的 Clear Writing 完成最后阅读层。按本 Project 的语言与格式合同表达，只改措辞和信息组织，不改事实、数值、条件、权限、安全、证据强度、不确定性、完成状态、时间关系或精确标识。本条消息明确要求其他语言、双语或纯机器内容时，仅对本次切换或跳过。
```

只有用户另行授权试点 Project 后，才能写入。短桥只配置一次，不复制完整技能文本，不扩写成 C11 的长基线。

### 4.4 Project 外兜底

可以提供同等长度的全局 Custom Instructions 建议，但必须说明 Project instructions 会覆盖它；它不是跨 Project 强制层，也不能在候选未安装或未触发时被描述为已经消费技能。

## 5. 验收条件设计

### 5.1 静态与生成检查

保护技能目录、元数据、引用和测试文件的合法性；正式源与生成快照一致；插件保持单一身份；没有新 MCP、钩子、连接或接口密钥；版本与变更记录在正式发布时按政策闭环。静态检查不能证明产品通过。

### 5.2 开发回归

覆盖 C5–C11、普通来源英文、内部治理字段、状态块、机械换行、裸日志、精确路径/主机/端口、完成状态、必须/可选、允许/禁止、用户已拒绝/删除的决定、临时语言覆盖、英文/双语 Project 和机器专用绕过。C5–C11 只能算已知回归，不能重新标为未见样本。

### 5.3 候选安装

从不可变提交生成候选，安装或升级到明确账户/工作区，记录可见插件版本、技能清单、源提交、包身份和新会话边界。不得把本地读取 `SKILL.md`、Codex 钩子或源注入当作普通 Web 证据。

### 5.4 四条件对照

冻结相同任务和评审标准，比较：

```text
A = 候选已安装，无短桥
B = 候选已安装，有短桥
C = 不含候选技能的上一版本或禁用候选，有同样短桥
D = 明确 @Clear Writing
```

B 是目标正常入口，C 是提示词基线，A 判断短桥能否降为可选，D 只做诊断。若 B 相对 C 没有稳定增量，不能发布新增技能；若仅 D 通过，不能宣称普通入口成立。

### 5.5 真实完整回答

在 AI Research Stack、Server+VPS、CAT-TRACE、前端/Figma/代码、英文 Project、双语 Project、临时语言覆盖和纯机器输出中审查首答。用户 prompt 不提技能、不重复语言要求。必须看完整回答和命题级保真，不看单句、关键词比例或自检声明。

### 5.6 多轮稳定性

测试 fresh 首轮、跟进、读取大量英文材料、机器输出轮次、临时英文覆盖后的恢复，以及长会话。用户需要再次提醒即为当前正常入口失败。

### 5.7 冻结最终批次

Critic 在进入最终评估前冻结未见样本、条件分配、最大尝试次数、评审标准和候选提交。冻结后禁止换题、挑赢家、补样本冲淡失败或修改技能。基础设施故障、产品失败和评审误判分别归因。

### 5.8 独立审查

独立 Reviewer 同时审查阅读质量、语义保真、精确标识、语言模式、机器绕过、正常入口、候选依赖和平台边界。若产品界面不显示技能调用记录，只能形成候选依赖的可观察证据，不得宣称证明内部调用顺序。

## 6. 实施阶段

### 阶段 0：Critic 冻结

输入：本 `v0.2` 提案、执行方案和验收矩阵。输出只能是 `PASS` 或 `REVISE`。Critic 不直接修改设计，也不启动实现。

### 阶段 1：表面与分发预检

在写正式技能前确认目标 ChatGPT Web 表面、账户/工作区资格、个人或工作区插件分发路线、安装权限、可见技能清单和可用证据。若目标表面无法运行技能型插件，立即返回 Planner。

### 阶段 2：正式技能源

创建技能、引用和回归输入，落实语言、结构、受保护语义、精确标识和绕过合同；保持职责窄，不改其他领域语义，不预先改版本。

### 阶段 3：插件打包

纳入 `writing-style` 生成包，更新必要清单和生成测试，形成不可变候选。若出现第二产品身份、动态技能链或额外服务依赖，停止。

### 阶段 4：安装与明确调用诊断

安装到目标 ChatGPT Web，核对候选身份；用 D 条件检查基本能力、边界和机器绕过。此阶段不计正常入口通过。

### 阶段 5：获批短桥试点与对照

只有用户另行授权后，在专门验收 Project 或获批真实 Project 写入短桥，执行 A–D 对照。若短桥必须扩成大型模板，或 B 相对 C 没有增量，返回 Planner。

### 阶段 6：多领域普通 Web 验收

执行完整首答、跨语言、机器绕过和多轮测试。不得依赖第二轮纠正，不能用开发回归代替未见样本。

### 阶段 7：独立综合审查

Reviewer 对不可变候选和完整证据给出通过或返修。关键入口失败立即停止，不以“多数时候可以”掩盖。

### 阶段 8：版本与发布收口

仅在所有阻断性验收通过且用户另行批准发布后，决定下一个两段插件版本，更新 `docs/plugin-changelogs/writing-style.md`、Marketplace 配置和生成清单，完成安装/升级/新会话回放。合并和发布仍是单独授权动作。

### 阶段 9：可选下游适配

核心能力成立后，才评估 PIE 是否在创建或整理 Project instructions 时保留短桥，以及既有 Project 的一次性迁移。不得命名为 C12，不得重新打开 C11，也不得在本方案中自动创建后继任务。

## 7. 失败归因

| 失败 | 主要归因 |
|---|---|
| 目标 Web 无法安装候选 | 分发/表面资格 |
| 候选安装错误或缓存旧版本 | 打包/安装身份 |
| 明确调用也失败 | 技能产品缺陷 |
| B 失败、D 通过 | 正常入口/元数据/平台路由缺陷 |
| B 与 C 无差异 | 新技能增量价值未证明；返回 Planner 简化 |
| 触发后仍泄漏来源英文或状态块 | 阅读层产品缺陷 |
| 语言自然但事实、权限、状态漂移 | 语义保真缺陷，阻断 |
| 精确标识被改写 | 精确身份缺陷，阻断 |
| 英文/双语 Project 被错误中文化 | 语言模式缺陷，阻断 |
| 机器专用输出被加解释或改字段 | 绕过缺陷，阻断 |
| Codex/本地通过而普通 Web 失败 | 错误表面证据 |
| 测试通过而完整回答失败 | 评估缺陷与产品缺陷 |

不得把关键入口失败统一归因于“模型随机性”。

## 8. 安全、隐私与权限

新技能不新增外部数据传输、MCP、第三方托管或账户连接；不放宽工具写入、确认和授权规则；不因压缩而删除安全、隐私、权限或不可逆操作边界。真实验收材料涉及私人仓库、账户、主机和网络时，证据包必须最小化暴露。
