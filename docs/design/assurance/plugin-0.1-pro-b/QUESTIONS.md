# Design Assurance 与 Delivery Assurance 插件 0.1：待决定问题

这些问题会改变正式入口、打包或 D5 的实现方式，D3 无权替设计负责人或用户决定。除此之外，状态、调度、角色卡、修订、冻结合同、验收治理、证据和 0.1 范围已经给出可实施设计。

## 1. 两个新插件怎样进入已经用满的 Codex Marketplace？

**为什么必须问：** 当前 `scripts/codex_marketplace_config.json` 把 `marketplacePluginBudget` 设为 10，现有顶级插件也正好有 10 个。直接增加 `design-assurance` 与 `delivery-assurance` 会超过当前发布预算；删除、合并或替换现有入口都属于新的产品决定，不能由实现者自行处理。

**选项：**

1. 把预算提高到至少 12，同时审查生成器、Marketplace 展示和安装体验是否仍成立。
2. 另行决定合并或移除某个现有顶级插件，为两个新入口腾出名额。
3. 0.1 先保留两个独立插件的完整源实现与生成包，做直接安装和正常入口验收，但暂不列入 Marketplace。
4. 把 Design Assurance 与 Delivery Assurance 合成一个 Marketplace 插件、内部保留两套技能。这会改变用户已经认可的“双插件”产品决定，除非用户明确改需求，否则不应采用。

**推荐：** 保留两个独立插件身份，不删除或合并现有入口。若 D1 尚未完成扩容影响审查，先采用选项 3；完成两个最终候选包并如实标为“可直接安装、尚未上架”。只有 D1 证明扩大预算不会破坏现有安装、展示和发布合同，且用户批准后，再采用选项 1。

**未决定时的边界：** 实现可以完成源技能、配置候选、生成包和直接安装验证，但不得把超预算配置合入正式 Marketplace 发布，也不得声称两个插件已经上架。

**决定者：** D1 提案；改变顶级插件组合、Marketplace 预算或双插件产品决定时由用户批准。

## 2. “规划端一份 `SKILL.md`”是两个插件共享一份，还是每个插件各有一份？

**为什么必须问：** 流程 0.1 第 10 节使用单数“一份 `SKILL.md`”，但 Design Assurance 与 Delivery Assurance 分别由 D1、X1 统筹。若各复制一份完整规则，后续很容易漂移；若两个生成插件打包同名技能，运行时又可能出现名称冲突或发现歧义。

**选项：**

1. 一个权威 `assurance-planning/SKILL.md`，两个插件都从同一源打包。
2. `design-assurance-planning/SKILL.md` 与 `delivery-assurance-planning/SKILL.md` 两个薄入口，共享同一组 `references/`、schema 和模板。
3. 两个插件各维护完整独立规则。

**推荐：** 语义上采用选项 1；若真实安装探针证明同名技能不能安全共存，则采用选项 2。选项 3 会制造两个流程版本，不采用。

**未决定时的默认实现：** 先建立一个权威源和两个可生成的薄入口方案；在真实安装探针后只保留不会冲突的形式。

**决定者：** D1；若用户希望两个入口的呈现方式不同，可由用户决定界面偏好，但不能改变共享语义。

## 3. D5 的 Asteria Blueprint 检查器怎样进入 0.1？

**为什么必须问：** D5 必须运行 Blueprint 检查器。Asteria-Blueprint 已有成熟的 v3 schema、跨引用验证和冻结规则，但它当前是另一个仓库中的实现，不是 AI_Skills_Collection 已发布依赖。现场要求用户另行检出仓库会使正常入口不稳定；重新写一个低配检查器又会丢失成熟规则。

**选项：**

1. 运行时依赖固定提交的 Asteria-Blueprint 仓库。
2. 选择性移植固定提交的 schema、必要验证入口和代表性规则测试，并保留来源、许可、上游提交和差异检查。
3. 只在插件里重写少量字段检查。

**推荐：** 采用选项 2。只移植 D5 必需的内容，不复制 Asteria 的界面、渲染器或其他产品功能；用同一组正反例比较上游与移植结果，防止低配重写。若许可或依赖边界阻止移植，再退回选项 1，并把固定提交和安装前置写进正常入口。

**未决定时的边界：** 不得声称 D5 已可用；可以完成其他源文件，但冻结功能不能发布。

**决定者：** D1。若涉及改变 Asteria-Blueprint 的职责归属或发布方式，应由对应仓库负责人共同确认。

## 4. GPT Work 的“直接使用 `SKILL.md`”要求自动发现，还是接受精确路径显式读取？

**为什么必须问：** 已有资料支持 OpenAI 技能使用 `SKILL.md`，但本轮没有证据证明 GPT Work 会自动扫描任意 GitHub 仓库的 `skills/` 目录。把 Codex 的生成目录或 Claude Code 的 `.claude/skills/` 规则直接推断为 GPT Work 自动发现，会形成虚假入口承诺。

**选项：**

1. 0.1 只要求提示词给出仓库、完整提交和 `SKILL.md` 路径，GPT Work 完整读取后执行。
2. 0.1 必须提供 GPT Work 自动安装、发现和触发。
3. 先显式读取，后续取得官方或真实平台证据后再升级自动发现。

**推荐：** 采用选项 3。0.1 的正式承诺是精确路径显式读取；自动发现单独作为后续能力门，只有真实平台入口通过后才写入产品说明。

**未决定时的默认实现：** 按选项 1 交付，不声称自动安装或隐式触发。

**决定者：** D1；只有用户明确把“无需提示的自动触发”作为首版必需体验时，才需要用户改变 0.1 范围。
