# Assurance 0.1 冻结说明

2026/11/13，D1 撰写。按设计第 6.4a 节的固定格式写成；冻结前与设计一起交 D6 核对。

## 1. 一句话结论

批准后，X1 会按这份设计做出两个插件：**Design Assurance** 负责从需求到冻结设计，**Delivery Assurance** 负责从冻结设计到签发成品。任何时候，你都能从当前状态拿到下一条完整提示词：发给谁、在哪开对话、写回哪里。

## 2. 你这次在做的决定

批准就等于同意以下取舍。前四条是你之前明说过的，后面几条是设计者替你定的默认做法。

- **规划端角色都在 GPT 上跑，每个角色每轮只转交一次。** 代价是你每轮要手动发几条，但不会再有一次发几十条的情况。
- **D8 复述每轮只开一个新对话，一次读完所有待读段落。** 这比每段换一个新读者的独立性弱，是为了让你只发一条而接受的取舍。
- **网页端打包放进 0.1**，沿用 thread handoff、thread instruction 已经测通的方法，不另造。
- **插件市场上限调到 12 个插件、32 个技能**，两个新插件直接进市场，旧插件一个不删。
- （默认）**状态全部存成仓库里的文件**，不建中央服务、不常驻后台。好处是简单、可追溯；代价是不能自动推送提醒，要你或负责人去读状态。
- （默认）**新流程只对你明确选用的任务生效**，已有任务不自动迁移。
- （默认）**只改错字一类的小修不需要你重新批准**，但每次都要事前告诉你、事后给差异，并重跑结构检查。凡是改变含义的修改，都要重新过关卡、重新请你批准。
- （默认）**这个插件自己的实施由 GPT Work 极高担任 X1**，Claude 只负责机械地启动 Codex。插件本身的通用规则仍允许 Claude 或 GPT Pro 当负责人。
- **被放弃的方案：** 每段换一个新读者做复述（需要你发几十条，已否决）；先只做直接安装包、以后再进市场（多一轮过渡，已否决）；网页端推迟到 0.2（你已测通，没必要推迟）。

## 3. 做完时你会看到什么，你自己怎么验

这是插件，做完后你会看到：

- **在 Codex 里：** 插件市场多出两个插件，各有一个执行技能，只接负责人明确派发的工作。没有派发时，它会说缺什么，不会自己动手。
- **在 Claude Code 和 GPT Work 里：** 告诉负责人“继续这个任务”，它读当前状态，给出下一步和完整提示词。
- **在 ChatGPT 网页端：** 上传插件包，新开一个对话，它能读规则、给出下一条提示词，并在有仓库连接时写回指定分支。它会如实说明自己不能运行本地脚本。

**你自己怎么验：** 拿一个公开、安全的示例任务，从需求开始走一遍：派设计 → 过四道关卡 → 你批准 → 交付 → 修一次验收程序 → 签发。中途故意制造几种错误，看它是否拦住：
- 拿过期的状态去派发；
- 验的是 A、交的是 B；
- 偷偷放松验收标准；
- 拿不到原始证据却想签发。

拦住了才算通过，出错时应该明确告诉你“无法判断”，而不是写成通过。

## 4. 验收器

一共 **67 个**，都是必须通过的。其中 54 个检查正常功能，13 个专门检查出错时的处理。按测的功能分成 6 类：

| 类别 | 个数 | 测什么 |
|---|---:|---|
| 任务状态与交接 | 8 | 一个任务只有一份当前状态；换人接手、写入中断、状态损坏后都能恢复，并且不会两人同时改；修订会事前、事后告诉你；三项衡量数据能从记录里重建 |
| 派发与提示词 | 3 | 按当前状态选对角色和档次；生成的提示词不依赖上下文，换一个新对话也能直接开工；某个角色用不了时如实报告，不让别的角色顶替自审 |
| 13 个角色各自的职责 | 15 | 每个角色（D1–D8、X1–X5）用对档次、只读该读的材料、交回该交的东西，不越权，例如设计者不能自己冻结、X5 只给意见不签发 |
| 从需求到冻结 | 18 | 澄清需求；四道关卡缺一不可，不能拿不同版本各过一项拼起来；冻结合同的九项都写清楚；冻结说明按固定格式，由 D6 核对；你没批准就不能冻结 |
| 从冻结到签发 | 13 | 修验收程序时不能改掉“什么算完成”；验收器要用正例、坏例、缺证据的例子校准过；签发的必须是当前最终成品；拿不到原始证据就是“无法判断”；签发后发现新问题能暂停、维持或撤回 |
| 打包与安装 | 10 | 规则只有一个来源，各端读到的是同一份；两个 Codex 包安装后入口正确、资源齐全；网页端包按上面三件事真实验收；市场预算调整到 12/32 且旧插件不受影响 |

**需要真实环境或专人才能验的：**
- **真实宿主：** 跨端读同一份规则（Claude Code、GPT Work、ChatGPT 网页端）、Codex 真实安装后调用、网页端上传后新开对话，都必须在真实环境里实际操作，不能只看文件。
- **X5 专业判断：** 签发前对提示词质量、责任链这类没有标准答案的问题，由 X5 给意见，X1 最终决定。
- **需要你本人：** 批准冻结；授权费用或账号；状态恢复时遇到涉及冻结、批准、签发的冲突。

其余检查读文件、跑脚本就能完成。

## 5. 需要下载或安装的大件

**没有超过 100 MB 的。** 需要装的只有三个小的程序库（JSON 格式检查、两个哈希规范化库，各自不到几 MB），以及这两个插件自己的包。Claude Code、GPT Work、Codex 和 ChatGPT 网页端你都已经有了，不需要重新安装。

## 6. 不能降级的

- 不能用“文件都在”、旧版本、同一个对话自己审自己、“缺证据就算过”来代替真实验收。
- 无法判断必须写成无法判断。
- 签发必须对应当前最终成品，旧安装包、验过的另一个版本都不行。
- 原有 10 个插件、30 个技能一个不删，也不能变差。
- 规则正文只有一个来源，Codex、GPT 和网页端都读这一份，不能各写一套。

## 7. 实现者可以自己定的

文件内部怎么写、脚本细节、模板措辞、测试怎么组织，以及设计里没有限定的其他普通实现细节。

## 8. 权限、费用、时间

- **只改 AI_Skills_Collection 仓库**，它是公开的，不放任何私有项目内容。
- **不改 Blueprint 仓库**，只按固定版本调用它的检查器。
- **不加外部服务，不加自动付费调用。** 如果要用付费模型，次数和预算要在第一次调用前另行请你授权。
- **时间：** 设计里没有定工期，由 X1 接手后估计。

## 9. 这次不做的

自动新开或恢复对话、自动发消息、后台定时运行、任务看板界面、中央数据库或服务、旧任务自动迁移。这些留到 0.2 以后，等真实任务证明需要时再加。
