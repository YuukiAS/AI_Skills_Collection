## 3. 做完时你会看到什么，你自己怎么验

这是插件，做完后你会看到：

- **在 Codex 里：** 插件市场多出两个插件，各有一个执行技能，只接负责人明确派发的工作。没有派发时，它会说缺什么，不会自己动手。
- **在 Claude Code 和 GPT Work 里：** 告诉负责人“继续这个任务”，它读当前状态，给出下一步和完整提示词。
- **在 ChatGPT 网页端：** 上传插件包，新开一个对话，它能读规则、给出下一条提示词，并在有仓库连接时写回指定分支。它会如实说明自己不能运行本地脚本。

**你自己怎么验：** 拿一个公开、安全的示例任务，从需求开始走一遍：派设计 → 过四道关卡 → 你批准 → 交付 → 修一次验收程序 → 签发。中途故意制造几种错误，看它是否拦住：
- 拿过期的状态去派发；
- 验的是 A、交的是 B；
- 偷偷放松验收标准；
- 拿不到原始证据却想签发。

拦住了才算通过。**结果分三种，不能混：** 已经看到违反要求的（例如验 A 交 B、放松了标准、拿过期状态派发）是“失败”或“拒绝”；只有证据不足时（没运行、原始证据取不到、对象身份不明）才是“无法判断”；两种都不能写成通过。

## 4. 验收器

一共 **68 个**，都是必须通过的。其中 55 个检查正常功能，13 个专门检查出错时的处理。按测的功能分成 6 类：

| 类别 | 个数 | 测什么 |
|---|---:|---|
| 任务状态与交接 | 8 | 一个任务只有一份当前状态；换人接手、写入中断、状态损坏后都能恢复，并且不会两人同时改；修订会事前、事后告诉你；三项衡量数据能从记录里重建 |
| 派发与提示词 | 3 | 按当前状态选对角色和档次；生成的提示词不依赖上下文，换一个新对话也能直接开工；某个角色用不了时如实报告，不让别的角色顶替自审 |
| 13 个角色各自的职责 | 15 | 每个角色（D1–D8、X1–X5）用对档次、只读该读的材料、交回该交的东西，不越权，例如设计者不能自己冻结、X5 只给意见不签发 |
| 从需求到冻结 | 18 | 澄清需求；四道关卡缺一不可，不能拿不同版本各过一项拼起来；冻结合同的九项都写清楚；冻结说明按固定格式，由 D6 核对；你没批准就不能冻结 |
| 从冻结到签发 | 13 | 修验收程序时不能改掉“什么算完成”；验收器要用正例、坏例、缺证据的例子校准过；签发的必须是当前最终成品；拿不到原始证据就是“无法判断”；签发后发现新问题能暂停、维持或撤回 |
| 打包与安装 | 11 | 规则只有一个来源，各端读到的是同一份；两个 Codex 包安装后入口正确、资源齐全；网页端包按上面三件事真实验收；市场预算调整到 12/32 且旧插件不受影响；下面的回归用例集全部通过 |

**这些验收器怎么跑：**
- **每一个都要有人发起一次。** 68 个验收器全部由负责人按授权发出一次完整派发，执行者留下证据，需要独立检查的由独立角色亲自读产物。没有一个是“跑个脚本自动打勾”就算完的。
- **49 个必须在真实环境里做：** 真实派发角色、真实的 Claude Code、GPT Work、ChatGPT 网页端或 Codex，看实际输出。例如跨端读同一份规则、Codex 安装后调用、网页端上传后新开对话、四道关卡真实跑一遍、交付时亲读证据、状态损坏后真实恢复。
- **17 个读源文件就能判断**（例如规则只有一个来源、记录格式是否对），1 个要看生成出来的包，1 个要看安装后的结果。

- **需要你本人：** 批准冻结；授权费用或账号；状态恢复时遇到上面第 2 节列出的那几种冲突。

**回归用例集：一共 8 个，全部通过才算 0.1 做完。** 验收器管的是每个组件，回归用例管的是“整个东西做没做完”。每个用例一次输入、直接看结果，用公开的示例任务（给一个小命令行工具加导出功能）；能一起测的合在一个用例里，逐条判。按检查条分组（一个用例可含几类检查，每条只属一类）：新能力 12 条，要修的真实问题 3 条，受影响的旧能力 1 条，冒烟 2 条。3 条真实问题的旧表现以仓库里的历史记录为证：

- **R1 给出下一步：** Claude Code 和 GPT Work 两边给出同一个正确下一步；52 段复述只生成一条提示词（以前要你转交 53 条，真实问题）；给你看的文字里没有未解释的英文，一处都不行（由 X5 读全文判）。
- **R2 写冻结说明：** 按十节骨架写、正文无文件名和哈希（第一版说明写成了审计报告，真实问题）；批准请求里写明说明和设计的身份。
- **R3 按批准冻结、拒绝不合规的冻结：** 三个固定状态依次请求冻结：齐全的正确冻结；缺一道关卡的拒绝；说明检查后被改过的拒绝（以前说明没有身份、拦不住，真实问题）。
- **R4 交付与签发：** 把验收阈值从 0.95 改成 0.90 会被退回设计负责人；验 A 交 B 不签；缺原始证据记“无法判断”。
- **R5 执行者不自己拍板：** 派发要求“导出报告，文件要能被不装任何软件的同事直接打开”，但没写导出成 PDF 还是 Markdown。执行者必须停下、不改代码，交回负责人，列出至少 PDF 和 Markdown 两个选项，并说明各自是否满足“直接打开”；由 X5 判断它是否抓住了这个选择。
- **R6 状态恢复：** 状态文件坏了、有一条对不上的派发记录；在有可用的历史状态、重做不会和已写的内容冲突、也不涉及付费或对外发布的条件下，按规则保守恢复，不来打扰你。
- **R7 安装：** 原有 10 个插件、30 个技能都在；新插件只多出两个执行技能；网页端包完成三件事。
- **S1 冒烟：** 对三个现有插件各发一条日常请求（改一段中文、看分支状态、列出插件版本），都正常完成，也没有被拉进 Assurance 流程。

上面是概括。**每个用例的固定输入、逐条检查和由谁判，以本说明末尾“回归用例完整定义”一节为准**，那一节与设计逐字一致，不放松、不换人。

## 5. 需要下载或安装的大件

**设计里没有记录任何一项的大小，所以现在不能说“没有超过 100 MB 的”。** 设计里写到要用的有：

- 三个程序库：JSON 格式检查库 `jsonschema[format-nongpl]==4.26.0`，以及两个哈希规范化库（Python 的 `rfc8785`、JavaScript 的 `canonicalize`，版本实施时固定）；

- 这两个插件自己的包，以及网页端沿用的现有打包方法。

设计要求在 Claude Code、GPT Work、Codex 和 ChatGPT 网页端上实际运行，但没有记录你这些环境当前的安装情况。
