## 阻塞问题

### 1. 角色启用、独立性与不可用入口处置披露不完整

冻结说明第 2 节已经正确写出主要宿主、模型档次、派发者、用户手工转交角色和大部分角色职责，但“哪些角色每次必跑”只明确列出 D2 与 D5–D8，漏了设计中同样必跑的 D1、X1、X2。它也没有完整披露 Blueprint 第 2.1 节的独立性规则：D2/D3 每次独立设计新开，D6 每轮新开且不继承负责人上下文，D7 每轮新开且只拿 Blueprint 与无设计暗示的运输说明，X3 首次独立新开且不继承 X2 的解题过程，X5 每次独立裁判新开且不看实现过程。D8 的单线程合批新对话规则已经写清。

规定入口不可用时，Blueprint 的规则是：缺少满足档次、独立性或工具能力的入口，就生成给该入口的完整提示词并等待，不自动降档，也不让负责人冒充。当前冻结说明只在验收器概述中写“如实报告，不让别的角色顶替自审”，没有把“等待”和“不得降档”完整披露。

这会影响用户对必跑工作量、角色独立性和宿主故障时实际行为的批准。关闭条件：D1 按 Blueprint 与用户认可流程补全这些角色信息，不新增角色、不改变触发条件。

### 2. 0.1 明确不做的能力漏了三项

Blueprint 的 0.1 范围明确把以下九类能力留到 0.2 或以后：跨宿主自动新建/恢复线程、自动发消息、后台调度、任务看板界面、中央数据库或服务、隐藏用例基础设施、通用验收器平台、所有项目预设适配器、历史任务自动迁移。

冻结说明第 9 节只写了其中六类，漏掉“隐藏用例基础设施”“通用验收器平台”“所有项目预设适配器”。这是七类固定清单第 7 类的直接漏写，会使用户误解 0.1 的批准范围和完成标准。

关闭条件：D1 把这三项按 Blueprint 原意补入“不做的”范围，不扩大或缩小 0.1。

### 3. 回归用例概括段有三处不等价改写

末尾“回归用例完整定义”中的 8 个用例、固定输入、检查条、分组、判定者和旧表现依据与 Blueprint 一致；问题出在前面的用户概括段。

R2 的概括写“第一版说明写成了审计报告，真实问题”，Blueprint 实际记录的旧表现依据是：提交 2965b008 的第一版冻结说明正文以哈希开头，缺验收器数量和下载说明，以及对应的决定记录。“写成审计报告”在 Blueprint 中没有依据。

R3 的概括写“以前说明没有身份、拦不住”，Blueprint 的旧表现依据是“说明原本没有身份，无法证明用户看到的就是检查过的那份”。“拦不住”把证据不足强化成已经证实的拦截失败。

R6 的概括说在“不涉及付费或对外发布”时按规则恢复、“不来打扰你”，但 Blueprint 的固定输入还要求该派发“不涉及向他人发消息”。省掉这一条件会把无需询问用户的恢复边界写宽；正式表格后面虽然写对了，前面的实质承诺仍然与设计不等价。

关闭条件：D1 将三处概括改成与正式定义等价的文字，或删去会改变语义的概括，只保留准确正式定义。
