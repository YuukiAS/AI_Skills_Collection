# D6 用户代理追问第 16 轮：冻结说明检查结果

## 结论

阻塞问题总数：**2**。

### 阻塞问题 1：普通执行角色的模型档次被写弱

冻结说明第 2 节把 D4、D5、D7 和 X2 的普通实现写成“由 Codex 跑”。Blueprint 在 `shared/dispatch` §2.1 以及四张角色卡中固定的是 **Codex 高**，并同时规定找不到满足档次的入口时只能等待，不能自动降档。因此省掉“高”不是普通措辞简化，而是把可接受的执行档次放宽了。

为什么影响用户批准：用户只读冻结说明时会得到“任意 Codex 档次都可以”的较弱承诺，和实际 Blueprint 的固定档次不同。

关闭条件：D1 只修改冻结说明，把 D4、D5、D7 和 X2 普通实现明确写为“Codex 高”，并保留现有“不降档”规则；Blueprint 无须改变。说明字节发生变化后，按 Blueprint 规则仅重做冻结说明的四项 D6 检查，不重做逐组件追问。

### 阻塞问题 2：“已回答的问题不再重复问”漏掉了重新打开的条件

冻结说明第 2 节写“你已经回答过的不再重复问”。Blueprint 的 `design/clarify` §6.1 更精确：只有同一选择的**已有回答仍然有效**时才直接引用；如果新事实推翻了该回答的适用前提，必须保留旧答，写明重新打开的原因和影响，再处理新的用户决定。

为什么影响用户批准：当前说明把条件性规则写成了无条件保证，会让用户低估后续可能需要再次确认的工作量，也改变了哪些事情必须重新找用户的边界。

关闭条件：D1 在冻结说明中补上“已有回答仍有效”这一条件，以及“新事实使原回答前提失效时会重新打开并说明原因和影响”的例外；Blueprint 无须改变。说明改动后同样只重做冻结说明四项检查。
