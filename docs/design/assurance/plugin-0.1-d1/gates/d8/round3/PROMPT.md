# D8 读者复述：第 3 轮（合批）

开一个全新的 GPT 对话，推理强度调到最高，把 `---` 下面的全部内容贴进去。

---

你是一位读者，帮忙检查一组说明文字能不能被人读懂。你此前没有看过这个项目的任何材料。

项目一句话简介：这是一套给 AI 协作用的插件流程：先把需求设计成一份可冻结的蓝图，再按冻结的蓝图交付成品，并由负责人核对证据后签发。

下面有 10 个单位，每个单位是流程中某一步的说明，顺序已经随机打乱。请逐个处理，并遵守两条规则：
- **每个单位只依据它自己的文字理解。** 不要用其他单位的内容补全信息，也不要猜测前后步骤。
- 不要读取任何仓库文件或网页。

对每个单位，用你自己的话分五点复述：
1. 这一步在做什么；
2. 它拿到什么；
3. 它交出什么；
4. 为什么要这样做；
5. 出错时会怎样。

然后列出读不懂或拿不准的地方：哪个词或哪句话，困惑是什么。不要评价文字好坏，也不要提修改建议。

## 写回

把结果写到 GitHub 仓库 `YuukiAS/AI_Skills_Collection` 的分支 `gates/assurance-0.1-d1`，文件路径为 `docs/design/assurance/plugin-0.1-d1/gates/d8/round3/RESULT.json`。文件内容是一个 JSON 数组，每个单位一项，字段如下：

```json
[{"subjectId": "<单位编号>", "round": 3, "paraphrase": "<五点复述>", "confusions": ["<每条一个，没有就留空数组>"]}]
```

另在数组外层不要加任何内容。只写这一个文件，不要读取、修改或删除仓库里的其他文件，不要切换分支。提交后回读确认。如果没有写入权限，就把 JSON 直接回复在对话里。

最后用一两句中文说明：写入是否成功，有多少个单位存在读不懂的地方。

## 单位

### 单位 1（编号 `ws-dispatch`，类别：正常走查）

```text
这一步：决定下一角色
这一步在做什么：负责人按固定的优先顺序检查各条件：先处理状态冲突，再处理用户决定、进行中的角色、返修、必跑角色（流程规定每次都要跑的角色）、条件角色（满足条件才启用的角色，如现实核查、独立验收），最后是冻结或签发；只给出一个下一动作。
拿到什么：拿到当前状态、角色和澄清结束后的任务书；先按既定优先顺序选择下一动作。
交出什么：生成设计或核查事实的角色（两位独立设计者和现实核查）绑定任务书；检查设计的角色（四道冻结关卡）绑定内容快照（设计文件除版本历史以外全部内容的哈希）；交付工作绑定有效的冻结对象。需要用户转交的规划端角色在 GPT 网页端运行，每个角色每轮转交一条；执行端在设计阶段由设计负责人（D1）派发，在交付阶段由交付负责人（X1）派发，次数不限。
为什么要这样：第一次独立设计开始时还没有设计稿；共同任务书提供需求、决定和事实，同时避免给设计者共同的设计基线。
出错会怎样：任务书换版就把旧版结果标为过期并交设计负责人判断；提前核查事实时也先写只含待核实问题的任务书。
```

### 单位 2（编号 `wr-gates`，类别：正常走查）

```text
这一步：完成四道冻结关卡（结构检查、用户代理追问、冷读、读者复述）
这一步在做什么：负责人在冻结前用草稿检查（Blueprint 检查器中不要求已有版本历史的模式）检查结构，并收集同一设计上的追问、冷读和复述。
拿到什么：拿到同一内容快照（设计文件除版本历史以外全部内容的哈希）的四项关卡结果、读者复述关卡（D8）本轮新 GPT 对话的逐单位复述，以及记录中的读者隔离字段 `reader_isolation`（合批时取值 `single-thread-batch`）。
交出什么：设计负责人逐项比对原意与复述，全部正确时本轮合批就是有效通过，不另设单位例外。读错则改写，下一轮新对话只重读改动及与改写单位属于同一步骤或同一失败路径的单位。
为什么要这样：每轮新对话合批降低逐步换人的独立性，但这是用户为可操作性接受的取舍，冻结说明要如实写明。
出错会怎样：有单位读错就改写后进入下一轮新 GPT 对话，不复用旧文字或旧对话的通过记录。
```

### 单位 3（编号 `fail-role-step-1`，类别：失败处理）

```text
这一步：发现与传递异常
这一步在做什么：当前角色保留异常事实并交给下一接收者。
拿到什么：拿到的异常是：角色规定的模型档次（例如需要用户转交的规划端角色用 GPT 最高推理，执行端用 Codex）或新开的对话或线程不可用，或者派发缺少必要材料定位。
交出什么：交出原始事实、对象身份和受影响范围。
为什么要这样：问题必须落到负责处理的人，不能在转交时被写成成功。
出错会怎样：证据仍不足时保留无法判断并说明恢复所需条件。
```

### 单位 4（编号 `wr-owner`，类别：正常走查）

```text
这一步：接收交付责任
这一步在做什么：新交付负责人亲读冻结包并确认接收。
拿到什么：拿到冻结合同、授权记录和三个哈希（内容快照、语义、完整文件）。冻结后如果做过小修，还拿到每次小修的继承记录：写明小修前后的哈希、改了哪些字段、为什么含义不变；这些记录把获批时的语义哈希一路连到当前的语义哈希。
交出什么：核对完整冻结文件的哈希后确认接收，得到清楚的实施范围、必需角色和交回路径。
为什么要这样：设计与交付需要分开负责人并保留返修接缝。
出错会怎样：合同矛盾或缺关键决定时按规定回原负责人。
```

### 单位 5（编号 `fail-recovery-step-1`，类别：失败处理）

```text
这一步：停止并恢复状态
这一步在做什么：任何角色发现当前状态文件丢失、损坏或与远端不符，立即停下，只把现象报告当前阶段负责人。
拿到什么：拿到状态文件不存在、无法解析、检查未通过或修订号与远端最新提交不符的实际现象。
交出什么：负责人从历史最后一个通过检查的状态恢复，只补登有原始记录支撑的事件，写新的状态和不可变恢复记录。通过检查并从远端回读后才恢复派发；无有效历史状态先交用户确认。
为什么要这样：事件日志需要与派发、结果、冻结和签发等原始记录逐条对照，不能凭记忆选择一个状态。
出错会怎样：不知道当前阶段就报告设计负责人（D1）。恢复冲突指事件日志和原始记录对不上，或者无法判断某个变化是否已经发生；负责人不自行选择，涉及冻结、批准或签发的交用户决定。
```

### 单位 6（编号 `fail-role-whole`，类别：失败情形整体收场）

```text
这一步：整体收场说明
这一步在做什么：负责人说明整个失败情形怎样结束及谁继续处理。
拿到什么：这次出现的情况是：角色规定的模型档次（例如需要用户转交的规划端角色用 GPT 最高推理，执行端用 Codex）不可用，无法新开对话或线程，或者派发缺少必要的材料位置。
交出什么：用户最终看到：下一角色还缺入口或材料，这一步暂停；已保留实际状态和缺项清单，补齐后由负责人重新派发。
为什么要这样：受影响部分必须有明确收场，同时保留仍可继续的工作。
出错会怎样：必要的 GPT 对话、执行端入口或材料仍不具备时保留缺项，不冒充角色已经执行或复述已经通过。
```

### 单位 7（编号 `wr-contract`，类别：正常走查）

```text
这一步：核对冻结合同的九项内容（能力范围、入口与最终对象、成败与无法判断、证据、禁止替代、旧功能、控制例、变更权、授权边界）
这一步在做什么：设计负责人（D1）核对设计是否包含九项明确完成语义。
拿到什么：拿到用户要求、完整设计和关键开放问题。
交出什么：得到九项完成约定明确的受审设计。用来判断含义是否改变的语义哈希，从同一份内容快照（设计文件除版本历史以外的全部内容）出发，只删去进度、运行和出处字段，其余全部参与计算，包括九项以外节点里的具体设计。
为什么要这样：没有完成定义就无法判断后续产物有没有做到。
出错会怎样：定义内容、走查或失败处理有缺口时先补设计，不能因为不在九项合同节点内就忽略。
```

### 单位 8（编号 `wb-planning`，类别：正常走查）

```text
这一步：确定读取来源
这一步在做什么：入口明确给出固定的源仓库提交（指定的版本，读取规则时不随最新改动变化），或者运行插件的工具（宿主，如 Claude Code、Codex 或 GPT 网页端）可读的插件包的根目录（安装后包内文件的起点）。
拿到什么：拿到同一规划正文与支持资源的实际定位。
交出什么：Claude Code 和 GPT Work 实际读取同一固定来源的规划正文、角色卡和模板，得到可以跨宿主核对的同源读取方式。
为什么要这样：文件格式相同不代表任意包目录都自动可见。
出错会怎样：资源根未确认时不声称完整加载。
```

### 单位 9（编号 `ws-prompts`，类别：正常走查）

```text
这一步：交出完整消息
这一步在做什么：负责人把派发展开成可直接复制的提示词。Claude 担任负责人时直接派发执行端，GPT 担任时生成完整提示词交用户转交给 Codex。
拿到什么：拿到确切仓库、分支、任务书位置与身份、读限、写入目录和角色卡。
交出什么：用户拿到需要转交的规划端角色本轮的一条完整提示词；读者复述在一个新的 GPT 对话里合批处理本轮全部单位。对话随机逐个作答，每单位只依据自身文字，由设计负责人逐项判断。
为什么要这样：新接收者不应靠旧聊天猜授权和产出。
出错会怎样：缺材料先补齐；读错则改写，下一轮只把改过单位和与改写单位属于同一步骤或同一失败路径的单位交一个新 GPT 对话重读，仍只转交一条。
```

### 单位 10（编号 `fail-role-step-2`，类别：失败处理）

```text
这一步：识别问题并交回
这一步在做什么：负责人在此处核对异常并采取合同允许的处理。
拿到什么：拿到的异常是：角色规定的模型档次（例如需要用户转交的规划端角色用 GPT 最高推理，执行端用 Codex）不可用，无法新开对话或线程，或者派发缺少必要的材料位置。
交出什么：得到明确收场：下一角色还缺入口或材料，这一步暂停；负责人记录实际状态和缺项，补齐后再派发，不写成已经执行。
为什么要这样：问题必须落到负责处理的人，不能在转交时被写成成功。
出错会怎样：缺的是工具入口，由负责人换到该角色规定的工具（宿主，如 Claude Code、Codex 或 GPT 网页端）；缺的是材料，由负责人补齐材料位置后重新派发。
```
