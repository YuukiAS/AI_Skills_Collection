# D8 读者复述：第 7 轮（合批）

开一个全新的 GPT 对话，推理强度调到最高，把 `---` 下面的全部内容贴进去。

---

你是一位读者，帮忙检查一组说明文字能不能被人读懂。你此前没有看过这个项目的任何材料。

项目一句话简介：这是一套给 AI 协作用的插件流程：先把需求设计成一份可冻结的蓝图，再按冻结的蓝图交付成品，并由负责人核对证据后签发。

下面有 8 个单位，每个单位是流程中某一步的说明，顺序已经随机打乱。请逐个处理，并遵守两条规则：
- **每个单位只依据它自己的文字理解。** 不要用其他单位的内容补全信息，也不要猜测前后步骤。
- 不要读取任何仓库文件或网页。

对每个单位，用你自己的话分五点复述：
1. 这一步在做什么；
2. 它拿到什么；
3. 它交出什么；
4. 为什么要这样做；
5. 出错时会怎样。

然后列出读不懂或拿不准的地方：哪个词或哪句话，困惑是什么。不要评价文字好坏，也不要提修改建议。

## 写回

把结果写到 GitHub 仓库 `YuukiAS/AI_Skills_Collection` 的分支 `gates/assurance-0.1-d1`，文件路径为 `docs/design/assurance/plugin-0.1-d1/gates/d8/round7/RESULT.json`。文件内容是一个 JSON 数组，每个单位一项，字段如下：

```json
[{"subjectId": "<单位编号>", "round": 7, "paraphrase": "<五点复述>", "confusions": ["<每条一个，没有就留空数组>"]}]
```

另在数组外层不要加任何内容。只写这一个文件，不要读取、修改或删除仓库里的其他文件，不要切换分支。提交后回读确认。如果没有写入权限，就把 JSON 直接回复在对话里。

最后用一两句中文说明：写入是否成功，有多少个单位存在读不懂的地方。

## 单位

### 单位 1（编号 `fail-freeze-explanation-whole`，类别：失败情形整体收场）

```text
这一步：冻结说明缺口的收场
这一步在做什么：用户追问角色对照设计检查冻结说明，发现影响用户决定的内容漏写、增加未承诺内容、验收器的总数和各类个数与设计不一致，或单项超过 100 MB 的下载或安装遗漏时，交回设计负责人改写。说明在检查之后只要有改动，原来对说明的检查就失效。
拿到什么：拿到按固定格式（结论、你在做的决定、做完时看到什么和怎么验、验收器、单项超过 100 MB 的下载或安装、不能降级的、实现者可自定的、权限费用时间、这次不做的、与上次批准相比的变化）写的冻结说明和同一份受审设计。
交出什么：设计负责人收到具体缺口，按固定骨架改写。用户追问角色在冻结前对新说明重做四项检查，结果写明说明文件的原始字节哈希；设计未变时不必重做逐组件追问（即用户代理追问角色站在用户角度，对设计中每个组件逐个追问是否有答案）。
为什么要这样：冻结说明是用户批准前唯一要读的东西，漏写会使用户在没看到的情况下批准。
出错会怎样：问题未解决时保持缺口，交回设计负责人，不把说明已经通过检查写进记录。
```

### 单位 2（编号 `ws-prompts`，类别：正常走查）

```text
这一步：交出完整消息
这一步在做什么：负责人把派发展开成可直接复制的提示词。Codex 档次在 Claude 负责人时直接派发、GPT 负责人时交用户转给 Codex；GPT Work 极高档次必须由用户在 GPT Work 转交，不得改用 Codex 或降档，X4 写明专业档次或所用专门插件；需要用户转交的执行端角色每角色每轮最多一条。
拿到什么：拿到确切仓库、分支、任务书位置与身份、读限、写入目录和角色卡。
交出什么：用户拿到需要转交的角色（含规划端和需要用户转交的执行端）本轮的一条完整提示词；读者复述在一个新的 GPT 对话里合批处理本轮全部单位。对话随机逐个作答，每单位只依据自身文字，由设计负责人逐项判断。
为什么要这样：新接收者不应靠旧聊天猜授权和产出。
出错会怎样：缺材料先补齐；读错则改写，下一轮只把改过单位和与改写单位属于同一步骤或同一失败路径的单位交一个新 GPT 对话重读，仍只转交一条。
```

### 单位 3（编号 `wr-freeze`，类别：正常走查）

```text
这一步：批准具体设计
这一步在做什么：设计负责人先按固定十节骨架（结论、你在做的决定、做完时看到什么和怎么验、验收器、单项超过 100 MB 的下载或安装、不能降级的、实现者可自定的、权限费用时间、这次不做的、与上次批准相比的变化）给用户冻结说明，说明已由用户追问角色对照设计检查漏写、多写、验收器的总数和各类个数是否与设计一致，以及单项超过 100 MB 的下载或安装有没有遗漏；检查结果、批准请求、用户批准和冻结记录都写同一个说明文件的原始字节哈希。用户先批准四道冻结关卡（结构检查、用户代理追问、冷读、读者复述）共同通过的内容快照（设计文件除版本历史以外全部内容的哈希），再由设计负责人用 Blueprint 的冻结命令（给设计文件追加一条版本历史）追加首个版本。
拿到什么：拿到按固定格式写成并经用户追问检查的冻结说明、获批快照、四项有效关卡结果、用户答复和追加一条版本历史（内容快照本身不变）后的完整文件；读者复述关卡（D8） 合批已经设计负责人逐项判断正确。
交出什么：设计负责人对完整输出运行冻结档检查（Blueprint 检查器中要求已有版本历史的严格模式），核对获批快照未变后才写冻结记录，同时保存内容快照的哈希、语义哈希（去掉进度和出处字段后的设计内容的哈希）、完整文件的哈希和冻结说明原始字节的哈希。
为什么要这样：追加历史不改变获批内容、冻结说明也未改动时，原关卡和批准继续有效；冻结档复验只是机械确认，不需要重新批准。
出错会怎样：D8 尚未判断全部正确时先改写并下一轮重读；冻结档不通过或快照改变则不写冻结记录，交回设计负责人。冻结说明有漏写或多写等缺口时交设计负责人按固定格式改写，说明改动后由用户追问角色对新说明重做四项检查，设计未变不重做逐组件追问（即用户代理追问角色站在用户角度，对设计中每个组件逐个追问是否有答案）。
```

### 单位 4（编号 `fail-role-step-1`，类别：失败处理）

```text
这一步：发现与传递异常
这一步在做什么：当前角色保留异常事实并交给下一接收者。
拿到什么：拿到的异常是：角色规定的模型档次（例如需要用户转交的规划端角色用 GPT 最高推理，执行端按档次表用 Codex 或 GPT Work 极高，X4 依派发记录使用专业档次或现有专门插件）或新开的对话或线程不可用，或者派发缺少必要材料定位。也包括将 GPT Work 极高的执行角色改用 Codex 或降档、X4 未写明专业档次或所用专门插件、需用户转交的角色同轮被要求转交多条。
交出什么：交出原始事实、对象身份和受影响范围。
为什么要这样：问题必须落到负责处理的人，不能在转交时被写成成功。
出错会怎样：证据仍不足时保留无法判断并说明恢复所需条件。
```

### 单位 5（编号 `fail-role-whole`，类别：失败情形整体收场）

```text
这一步：整体收场说明
这一步在做什么：负责人说明整个失败情形怎样结束及谁继续处理。
拿到什么：这次出现的情况是：角色规定的模型档次（例如需要用户转交的规划端角色用 GPT 最高推理，执行端按档次表用 Codex 或 GPT Work 极高，X4 依派发记录使用专业档次或现有专门插件）不可用，无法新开对话或线程，或者派发缺少必要的材料位置。也包括将 GPT Work 极高的执行角色改用 Codex 或降档、X4 未写明专业档次或所用专门插件、需用户转交的角色同轮被要求转交多条。
交出什么：用户最终看到：下一角色还缺入口或材料，这一步暂停；已保留实际状态和缺项清单，补齐后由负责人重新派发。
为什么要这样：受影响部分必须有明确收场，同时保留仍可继续的工作。
出错会怎样：必要的 GPT 对话、执行端入口或材料仍不具备时保留缺项，不冒充角色已经执行或复述已经通过。
```

### 单位 6（编号 `ws-dispatch`，类别：正常走查）

```text
这一步：决定下一角色
这一步在做什么：负责人按固定的优先顺序检查各条件：先处理状态冲突，再处理用户决定、进行中的角色、返修、必跑角色（流程规定每次都要跑的角色）、条件角色（满足条件才启用的角色，如现实核查、独立验收），最后是冻结或签发；只给出一个下一动作。
拿到什么：拿到当前状态、角色和澄清结束后的任务书；先按既定优先顺序选择下一动作。
交出什么：生成设计或核查事实的角色（两位独立设计者和现实核查）绑定任务书；检查设计的角色（四道冻结关卡）绑定内容快照（设计文件除版本历史以外全部内容的哈希）；交付工作绑定有效的冻结对象。需用户转交的规划端角色在 GPT 网页端，每角色每轮转交一条；执行端由设计负责人（D1）或交付负责人（X1）按阶段与档次派发：Codex 档次在 Claude 负责人时直接派发、GPT 负责人时交用户转给 Codex，GPT Work 极高档次由用户在 GPT Work 转交且不得改用 Codex 或降档，X4 按记录选专业档次或指定插件宿主；需用户转交的执行端角色每角色每轮最多一条。
为什么要这样：第一次独立设计开始时还没有设计稿；共同任务书提供需求、决定和事实，同时避免给设计者共同的设计基线。
出错会怎样：任务书换版就把旧版结果标为过期并交设计负责人判断；提前核查事实时也先写只含待核实问题的任务书。
```
