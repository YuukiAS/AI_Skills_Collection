## 3. 阻塞问题

### B1：跨宿主计算内容哈希时，以哪一种唯一的 JSON 字节表示为准？

**涉及节点和字段：**

- `state.terminal.mechanism` 的“三个身份”与任务书身份定义；
- `freeze.terminal.mechanism` 第 6.5 节中的 `snapshot_sha256`、`semantic_hash`；
- `clarify`、`dispatch`、`prompts` 对 `brief_sha256` 的约定；
- `record-check` 对上述身份引用的检查，以及 `q-inheritance` 对哈希相等和继承链的核验。

**问题：** 蓝图规定按“规范化 JSON（键排序、UTF-8、无多余空白）”计算哈希，并要求派发方、接收方和记录检查使用同一规则，但没有唯一确定序列化字节。例如，同一个解析后的对象可以写为 `{"x":"中"}`，也可以写为 `{"x":"\u4e2d"}`；两者都可使用 UTF-8、满足键排序和无多余空白，却会得到不同的 SHA-256。这里的例子只是说明协议歧义，没有运行计算。

**为什么阻塞：** 这不是函数拆分或库名选择。上述哈希决定用户批准的是哪个对象、角色是否可以接收派发、小修是否可继承批准、证据是否仍对应冻结对象。两个端都遵守现有文字，仍可能将同一对象判断为身份冲突。执行者需要替设计方补一个跨端可观察的接口规则，才能确定身份检查的验收预期。受阻的是身份计算及其消费者；记录布局等独立部分可以继续细化，但不能据此宣称整条链已经可按确定语义实现。

**可能的选项：**

- 指定一个完整的 JSON 规范化标准及版本，并约定适用的数据范围，所有端按同一标准计算；
- 指定一个有固定版本的共用规范化实现，要求所有身份生产者和检查者调用它，以其输出字节为准，并提供跨端相同的输入／字节／哈希对照例；
- 在蓝图中完整写出自己的字节规则，包括字符串转义、键排序、数值表示和散列输入是否含结尾换行等，再允许各端独立实现。

需要设计方确定的是身份协议或唯一权威实现，不是要求设计方选语言、拆函数或编写代码。`bundle_sha256` 已明确按完整文件原始字节计算，不属于这一缺口。
