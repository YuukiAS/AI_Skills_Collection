## 1. 拟开工顺序

这里的实现顺序以完成既定冻结和执行授权为前提。蓝图明确保留 `versions: []`，且尚未通过全部关卡；本次冷读不构成冻结或实施许可。

| 顺序 | 拟做的工作 | 蓝图依据（节点 id） |
|---|---|---|
| 1 | 先核对受审快照的 D5 草稿档、D6、D7、D8 结果和用户批准；追加版本历史后运行 D5 冻结档，确认获批内容未变，再形成冻结记录。由另一个 X1 长期线程实际读取接收，D1 最后一次状态提交切换写权，X1 回读确认。 | `gates`、`freeze`、`writer`、`role-X1`；固定检查器接入见 `q-checker`。 |

| 5 | 从唯一源生成两个 Codex 插件，配置两个不同的执行技能名及显式调用策略；把规划正文和共用资源随包复制。将市场预算调整为 12 个插件、32 个技能，保留原 10 个插件、30 个技能。网页端由 X2 查明并复用两个既有插件包的打包方法，记录来源。 | `source-layout`、`execution-package`、`planning-entry`、`q-capacity`、`web-later`。 |

## 2. 已经明确的接缝

| 组件之间 | 输入 | 输出及接收规则 |
|---|---|---|
| 任务入口 → 共用状态 | 明确的仓库、分支、任务标识和绑定目录；已有状态先读。 | 两个插件使用同一 `STATE.json`，默认位于 `docs/assurance/<task_id>/`。状态是当前事实，事件日志只追加审计与恢复线索，不能反向覆盖状态。见 `state`。 |
| D1 澄清 → D2/D3/D4 | 不可变任务书，包含需求及出处、用户决定、事实、开放事项和读限。 | `based_on.brief_sha256` 绑定整份任务书；D2/D3 读同一任务书且互不读设计产物。提前做 D4 核查也先有问题任务书。换版后旧结果标为 `stale`，交 D1 判断仍有效范围。见 `clarify`、`dispatch`、`role-D2`、`role-D3`、`role-D4`。 |
| 调度 → 提示词 → 执行角色 | 有效状态、角色档次、阶段绑定对象、读写边界及产出要求。 | 七级优先顺序取首个成立条件，可并行角色明确组成批次；每个角色仍有独立完整提示词。`prepared` 与实际 `sent` 分开登记。设计阶段由 D1 派执行端，交付阶段由 X1 派执行端。见 `dispatch`、`prompts`。 |
| 派出角色 → 负责人 | `RESULT.json`、自然中文说明及实际产物；附派发编号、绑定身份、实际读写和未运行项。 | 派出角色不写状态。负责人核对后采纳，重复相同结果幂等，不同结果保留冲突版本；写状态前重读基线，写后回读。见 `writer` 及各 `role-*` 节点。 |
| Blueprint → 四关卡 → 冻结 | D5–D8 检查同一受审 `snapshot_sha256`；用户批准该快照。 | 首次冻结按五步进行，追加历史后再做 D5 冻结档；`freeze.json` 引用九项语义、四关卡、批准与授权，不复制第二份可变完成标准。见 `gates`、`freeze`。 |
| 三类内容身份与文件身份 | `snapshotOf` 内容快照、按清单删字段后的语义对象、完整任务书，以及冻结输出文件。 | `snapshot_sha256` 绑定受审和批准对象；`semantic_hash` 用于语义定义和小修继承核验；`brief_sha256` 绑定任务书。这三个按 JCS 规范化后计算。`bundle_sha256` 对完整冻结文件原始字节计算，供存档和 X1 接收核对。见 `state`、`freeze`、`dispatch`。 |
| D1 → X1 | 冻结文件、冻结记录、批准、关卡和授权；如有小修，还包括完整继承链。 | X1 写实际接收记录，D1 核对后同时切换 `phase` 与 `state_writer`。交付期间 D1 仍决定设计修订，状态由 X1 按原样登记。见 `writer`、`freeze`、`role-X1`。 |
| 验收作者 → 校准 → X1 审定 | 验收资产版本与差异、冻结准则、独立来源的预期和正/坏/缺证例。 | 同一个验收实现实际产生 `passed/failed/unknown` 校准结果。X1 审查所有验收资产变化；改变完成定义须退 D1，不能在交付端批准。见 `acceptance`、`calibration`。 |
| X2 候选提案 → X1 当前候选 → 证据 | 源码集合、最终对象、构建安装记录、运行器环境、数据参数及候选身份。 | 只有 X1 选择当前候选；证据绑定候选、冻结条款、资产版本、实际观察对象和原始记录。内容变化产生新候选，实际受影响证据失效，不能拼接不同候选的通过部分。见 `candidate`、`evidence`。 |
| 偏离 → 返修或设计退回 | 冻结要求、实际差异、原因、原始证据和影响范围。 | 普通程序、环境和一般缺证留在 X1 同一任务；只有五类原因退原 D1，并暂停影响范围及依赖闭包。小修也须满足六项条件、留下继承记录及新 D5 结果；大改重过关卡和批准。见 `deviation`、`revision`、`q-inheritance`。 |
| 当前证据 → 签发与撤回复核 | 同一最终候选的完整必需证据、角色结果、授权和约定的用户验收。 | X1 亲读后只对整个冻结范围签发。签发后有新事实，先暂停声明并保留原引用；维持则恢复，撤回则清空当前引用、标记指定证据过期并返修或退回设计。旧签发不改写，新签发用 `supersedes` 关联。见 `sign`、`evidence`。 |
| 源层 → 各宿主包 → 实际验证 | 四个源入口及一份共用规则、角色卡、模板和结构定义。 | Codex 每包只暴露一个执行技能，规划资料另放 `planning/`，资源不借包外文件。规划端按固定源提交或已确认完整包根读取。网页端复用既有打包方法，X4 留三项原始对话证据，X1 签发。见 `source-layout`、`planning-entry`、`execution-package`、`web-later`。 |

只读记录检查的边界也已明确：`record-check` 接收任务根、记录种类和文件，输出 `assessment/errors/unresolved/checked_files`；退出码 0、1、2 分别表示结构及可检查引用合规、确定错误、无法完成检查。它不写状态、不派发、不执行记录中的命令，也不代替语义判断或真实能力验收。

## 3. 阻塞问题

**本轮未发现需要设计方再决定的阻塞问题，共 0 项。** 因而没有待列的互斥设计选项。

以下事项仍需实际执行或核验，但蓝图已经给出了处理合同，不另计为设计阻塞：

- **尚未冻结。** `gates`、`freeze` 和 `minimum` 已规定完整前置顺序以及冻结前禁止实现的边界。缺少本轮实际关卡、批准或接收证据时按该顺序推进，不能把本报告当开工授权。
- **上游检查器是否实际可用。** `q-checker` 已固定提交和入口，并明确 Assurance 不改上游；不可访问或检查未完成就记无法判断，交 D1 处理。本轮不去验证，也不把“已指定依赖”当“本设计已通过检查”。
- **网页端既有打包方法的具体定位。** `web-later` 明确由 X2 在仓库及实际包中查明来源后复用；找不到或不能复现就经偏离流程交 X1，禁止另造替代方式。这是已有指派的事实查找，不要求冷读者补选技术方案。
- **D8 的独立性和复读方式。** `dispatch`、`role-D8`、`q-checker` 已规定每轮一个新 GPT 对话合批、随机逐单位作答、保留 `single-thread-batch` 和文字身份，由 D1 逐项判断；返修轮重读改动及受影响单位，冻结说明披露该方式。无需另定是否逐单位另派独立读者。
- **通用负责人规则与本插件自身实施的安排。** `dispatch` 和 `role-X1` 已单列本插件自身的安排：D1 为 Claude，X1 为 GPT Work 极高，Claude 只做机械启动 Codex 的运输。该特定安排与面向其他任务的通用角色规则有明确适用范围，无需执行者自行更换负责人或档次。
- **运行环境、费用或私有资料尚未取得。** `contract-authorization`、`prompts`、`evidence` 已规定同范围授权复用、变化另行处理，以及缺项和缺证不得假称成功。具体任务的授权值由其实际派发提供，不由本插件预先替所有任务开放资源。

## 4. 实现自由度

以下事项可由执行者在已定合同内选择，不需要设计方另作产品决定：

- 模块、函数和内部类型怎样拆分，变量如何命名，重复的模板或身份核验逻辑怎样复用；保留既定入口、文件字段含义和角色写权。
- 如何把已明确的记录字段和约束表达为 JSON Schema，怎样组织本地预注册结构、诊断信息和只读检查代码；不改变已定记录种类、退出码及三态含义。
- `rfc8785`、`canonicalize` 的具体依赖版本，蓝图明确留到实施时固定；各端仍须通过规定的规范化字节和哈希对照例，不能自选另一种序列化语义。
- 在既定角色读限内，怎样按需加载共用文件、角色卡和模板，怎样组织源码与生成器接线；源和副本的一致性、技能名称、自包含资源以及容量预算已经固定。
- 代表性控制例的具体内容、文件命名和组织方式，以及与实际改动范围相称的回归覆盖。数量按能力覆盖确定，但每个关键验收必须真实运行三类控制例，预期不得取自当前候选输出，也不能删减必需宿主观察。
- 验收脚本、选择器、解析器、运行器和报告生成的具体代码。其准入、修改分级、等价依据和重验仍受 `acceptance` 约束；实现自由不包括自行改变阈值、方法真实度或完成定义。
- 自然中文提示词和报告的具体措辞、排版及错误呈现，只要保留全部必需定位、边界、角色合同、写回和未运行说明，不夹带对独立角色的答案暗示。
