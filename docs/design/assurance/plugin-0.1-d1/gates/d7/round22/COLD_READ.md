# D7 冷读

本次判断只依据当前目录的 `blueprint.json`，包括节点内嵌的合同、角色卡、回归用例、走查和失败处理。没有打开其中引用的其他文件或网页，没有运行探针，也没有实施插件。

## 1. 拟开工顺序

这里列的是满足冻结与授权条件后的实施顺序。蓝图当前 `versions` 为空；本次冷读不能代替其他关卡、用户批准或 X1 接收。

1. **先完成设计进入实施的关卡。** 由 D1 收敛设计及九项合同，D5 草稿档、D6、D7、D8 对受审对象完成检查；冻结说明另交 D6 对照检查，再取得用户批准。随后追加冻结历史、跑 D5 冻结档、确认获批快照未变，才写冻结记录。新 X1 实际读取并接收后，D1 最后一次状态提交同时切换阶段与写者，X1 回读确认。依据：`contract`、`gates`、`freeze`、`writer`、`role-X1`。冻结前仅做允许的现实核查和材料整理，不开始插件实现。
2. **实施共用协议和运输基础。** 先做任务定位、状态与事件格式、角色结果和派发格式、身份计算、只读记录检查，再接入冲突、写入不明和状态恢复规则。它们是两个插件共同使用的基础，先做好才能让后续工作从同一状态出发。依据：`state`、`writer`、`record-check`、`dispatch`、`prompts`、`source-layout`。
3. **实施设计端。** 接入澄清分类、不可变任务书、独立设计的读限、四关卡、冻结说明、用户批准及冻结交接；同时接入小修继承、大改重审和前后告知。依据：`clarify`、`role-D1` 至 `role-D8`、`contract` 及其九个子节点、`gates`、`freeze`、`q-checker`、`revision`、`q-inheritance`。
4. **实施交付端。** 接入 X1 接收、X2 实现、按条件启用 X3/X4/X5、验收资产审定和三类校准，再完成候选选择、原始证据登记、偏离、设计退回、签发及撤回复核；衡量记录从真实事件生成。依据：`role-X1` 至 `role-X5`、`acceptance`、`calibration`、`candidate`、`evidence`、`deviation`、`sign`、`metrics`。
5. **生成并验证跨端产物。** 从源层生成两个自包含执行包，落实 12 个插件、32 个技能的预算并保护旧能力；规划端按固定来源读取同源规则。网页端先定位并复用既有打包方法，再由 X4 在真实网页端验收。依据：`source-layout`、`planning-entry`、`execution-package`、`q-capacity`、`web-later`。
6. **完成实际能力验收再签发。** 先做记录检查和校准，再验证真实宿主及正常入口。按合同生成示例文件，由 X1 在首次运行前逐条核对、记录哈希后固定；执行六类能力矩阵及 R1–R7、S1 八个回归用例。开发中按失败和影响范围重跑；最终候选固定后完整跑一遍，全部通过且签发清单满足，才由 X1 签发。依据：`minimum`、`capability-check`、`contract-regression`、`sign`。

以上四个内部实施工作包的先后，直接来自 `minimum.terminal.mechanism` 第 10.1 节；不另设角色或后台调度服务。

## 2. 已经明确的接缝

| 接缝与节点 | 输入 | 输出及接收规则 |
|---|---|---|
| 任务定位与写入：`state` → `writer` | 固定任务目录、仓库、分支、状态修订号、文件身份和分支头 | 一份权威 `STATE.json`；写入前校验基线，写入后同分支回读。事件追加到 `history/events.jsonl`，不取代状态。派出角色不写状态。 |
| 记录检查：`record-check` | 指定任务根、记录种类、记录文件和包内本地结构 | 输出 `assessment/errors/unresolved/checked_files`；退出 0 表示结构及可检查引用合规，1 表示确定错误，2 表示无法完成检查。入口只读，不作语义批准或执行记录中的命令。 |
| 调度与提示词：`dispatch` → `prompts` | 当前有效状态、固定优先级、角色档次、读写范围及绑定对象 | 一个下一动作或明确可并行的批次；每角色有完整提示词和独立派发记录。准备、实际发送、返回和采纳分别登记，不把准备当执行。 |
| 澄清与独立设计：`clarify` → `role-D2` / `role-D3` / `role-D4` | 不含设计倾向的不可变任务书及 `brief_sha256` | 绑定任务书的设计或事实结果。D2、D3 使用同一任务书且互不读取本轮对方产物；任务书换版后旧结果标 `stale`，交 D1 判断仍有效的范围。 |
| 设计与关卡：`contract` → `gates` | 九项语义完整的 Blueprint 及 `snapshot_sha256` | D5–D8 的原始结果、覆盖和有效性。D7 只读 Blueprint；D8 每轮新 GPT 对话合批，保留逐单位文字身份和原样复述，由 D1 判断。 |
| 关卡、批准与冻结：`gates` → `freeze` | 有效关卡、用户批准、经 D6 检查的冻结说明、授权定位 | 冻结包及 `freeze.json`。`snapshot_sha256` 绑定获批内容，`semantic_hash` 用于定义内容与继承核验，`bundle_sha256` 绑定完整文件，`explanation_sha256` 绑定说明原始字节；用途不混用。 |
| 设计与交付：`freeze` → `role-X1`，经 `writer` 交接 | 冻结包、批准、授权及 X1 实际接收记录 | D1 完成最后一次带基线的状态提交后，X1 回读并取得状态写权。交付中 D1 仍决定设计修订，X1 原样登记，不代改设计决定。 |
| 验收实现与准入：`role-X2` / `role-X3` → `calibration` → `acceptance` | 验收实现、独立预期、正例、危险坏例、缺证例及实际差异 | 同一验收实现的三类运行证据和 X1 审定记录。语义变化交 D1；未审定的提案不能替换正式验收引用。 |
| 候选、证据与签发：`candidate` → `evidence` → `sign` | X1 选定的候选、源码与最终对象身份、正常入口观察、必要专业结果 | 绑定同一最终候选的原始证据和十三项签发核对。失败、未知或过期的必需项均阻止签发；0.1 只对整个冻结范围一次签发。 |
| 偏离与设计退回：`deviation` → `revision` → `role-D1` | 冻结要求与实际差异、原始证据、影响节点及依赖闭包 | 普通实现或环境问题留 X1；命中五类设计退回条件才交原 D1。暂停受影响范围，未受影响的获准工作继续。 |
| 恢复：`state`、`writer`、`record-check` | 最后有效历史状态、后续事件及不可变原始记录 | 普通冲突固定作保守处置，相关派发记 `stale`，原记录保留；重派须披露已有写入。涉及批准等权威事实、不可安全重派或无有效历史基线时交用户。检查及远端回读后恢复未暂停范围。 |
| 打包与真实验收：`source-layout` → `planning-entry` / `execution-package` / `web-later` → `capability-check` | 同一规则源、固定来源或确认可读的包根、既有生成器和网页打包方法 | 两个执行技能及网页端规划包。各宿主分别留真实证据；网页端无写权限时如实给出应写内容，这是明定分支，不能声称已写回。 |

角色结果的共同接口也已给定：`RESULT.json` 保存派发身份、绑定对象、实际读写、输出定位、发现、未运行项和时间；自然中文说明交给指定负责人。它不是角色自行宣布总体冻结或交付的凭据。

## 3. 阻塞问题

**未发现必须由设计方另作决定的阻塞问题，共 0 项。** 因而没有需要列举选项的未决项。

以下事项已有明确处理方式，不另计为阻塞问题：

- **示例文件尚未生成。** `contract-regression.terminal.mechanism` 第 6.3a 节和 `capability-check.terminal.mechanism` 第 10.2a 节已区分职责：D1 写定关键输入、期望和尺子，X2 生成机械文件，X1 运行前核对并固定。不能把文件尚不存在本身算成设计缺口，也不能借生成文件改动已定语义。
- **新插件没有旧版本。** 同两节点已允许用指定的公开历史原始记录证明旧表现；已有可运行旧版本时仍须实际复现。历史记录未取得时不能声称已证明修复。
- **网页端方法或能力尚未实际核实。** `web-later` 已指定查找、复用和真实验收职责；找不到或不能复现就申报偏离，不能另造替代方法。网页端无本地终端、无仓库写权时的边界也已明确。
- **运行时可能出现新授权或设计问题。** `contract-authorization`、`deviation` 和恢复规则已指定停止范围、接收方及决定权；这不要求实现者现在预先发明答案。实际出现的问题仍须按合同处理。

R6 是按第 1.3a 节验证普通恢复的用例，其“不找用户”不能被实现成覆盖该节例外的通用规则；涉及权威事实、无法安全重派或找不到有效历史基线时，仍执行正文规定的用户决定路径。

## 4. 实现自由度

以下可以由执行者在合同内自行决定：

- 模块、函数、类和变量怎样组织，内部辅助文件怎样拆分；保持既定入口、记录字段含义和角色写权。
- JSON Schema、模板、只读检查和错误报告的内部实现方式；不改变规定的格式、退出结果、引用边界和无副作用要求。
- 为 JCS 选择并固定所指定库的具体版本，组织跨端对照例；规范化规则及哈希覆盖范围已定，不由实现者另选。
- 示例记录的编号、时间、路径和机械文件组织，以及不影响检查含义的示例细节；R1 的 52 个单位、R3 的三个场景、R4 的阈值及候选错配、R5 缺少的格式选择、S1 的三条请求等关键条件必须保持。
- 将脚本可判的检查写成何种运行器和断言，怎样保存原始输出和汇总；专业或真实宿主判断仍交合同指定的角色。
- 按源层规则组织支持文件、复制映射和包内引用；保持规划副本与源字节一致、两个执行技能名称唯一、资源自包含和市场预算。
- D8 合批的随机排序实现、运输材料的排版和结果索引方式；不改变逐单位只依自身文字作答、每轮新对话及 D1 逐项判断的要求。
- 在冻结标准内安排调试和等价维修，提出验收资产修改；正式准入仍由 X1 审定，语义改变仍交 D1。

普通实现自由度不包括自行选择产品行为、改验收题目或尺子、换不可替代方法、降角色档次、扩大权限资源，或缩小冻结范围来取得通过。
