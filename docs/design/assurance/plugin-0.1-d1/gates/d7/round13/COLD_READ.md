# D7 冷读

本次判断依据为 `blueprint.json` 内的节点、字段、连接、走查和失败处理。外部资料的可访问性、检查器运行和宿主能力仍由蓝图规定的实际检查取得证据。

## 1. 拟开工顺序

| 顺序 | 工作与交回结果 | 蓝图依据 |
|---|---|---|

## 2. 已经明确的接缝

### 当前状态、写者与记录检查

- `state` 接收明确的任务、仓库、分支、任务标识和绑定目录，输出唯一 `STATE.json`。事件追加到 `history/events.jsonl`，各角色的原始产物留在各自目录。
- `writer` 接收状态修订号、文件身份、分支头和角色返回，核对基线后提交并回读。重复结果幂等，同一派发的不同结果保留冲突。设计阶段由 D1 写状态，交付阶段由 X1 写状态。
- `record-check` 接收任务根、记录种类及记录文件，只读检查结构和已声明引用。退出值为 0、1、2，分别对应检查合规、确定错误、检查无法完成，JSON 输出含 `assessment,errors,unresolved,checked_files`。
- 状态丢失、损坏、检查失败或与远端修订不符时，`state`、`writer` 和 `fail-recovery` 给出了停止、历史基线、事件与原始记录核对、冲突处置、恢复记录、检查和远端回读的顺序。无有效历史基线时已有交用户确认的路线。

### 派发、角色与结果采纳

- `clarify` 由 D1 形成不可变的 `design/briefs/<brief_version>.json`。D2/D3/D4 的 `based_on.brief_sha256` 绑定整个任务书，D2、D3 读取同一事实和需求基线，保留独立设计边界。
- `dispatch` 从有效状态按七级优先顺序选下一动作，`prompts` 将角色、档次、线程、读写范围、输入定位、写入测试和写回要求展开成完整消息。准备与实际发出分别登记为 `prepared` 和 `sent`。
- 角色交回带 `dispatch_id,based_on,actual_reads,actual_writes,outputs,findings,unrun` 等字段的 `RESULT.json` 和中文说明。负责人核对身份与有效范围后采纳，任务书换版后的旧结果标记为 `stale`。
- D5–D8 绑定受审 `snapshot_sha256`。D7 只读 Blueprint 及最小运输封套。D8 每轮一个新的 GPT 对话合批复述，记录 `reader_isolation: single-thread-batch`，由 D1 逐单位判断，读错后按规定范围在下一轮新对话重读。
- 需要用户转交的 D2/D3/D6/D8/X5 在 GPT 网页端运行，每角色每轮最多一条提示词。D1/X1 使用各自长期线程，负责人宿主及 Claude/GPT 两种执行端派发方式已写明。

### 冻结身份与交付接收

- `freeze` 将用户批准和四关卡绑定到 `snapshot_sha256`，将冻结输出文件绑定到 `bundle_sha256`，用 `semantic_hash` 及合格小修继承链核验交付依据。内容哈希采用 JCS 规范化字节，完整文件哈希采用原始文件字节。
- `freeze.json` 保存九项合同的节点或字段定位、关卡、批准、授权及三个身份。X1 读取冻结包，核对完整文件身份并写接收记录。D1 核对后切换状态写者，X1 回读后承担状态维护。
- 交付期间 D1 继续负责设计修订、设计关卡和新冻结记录，X1 按原样登记这些决定。`revision`、`q-inheritance` 已规定小修条件、字段级差异、批准继承与大改重新过关卡的边界。

### 候选、验收、证据与签发

- X2 向 `candidate` 提交候选提案，X1 选定当前候选。记录连接源码集合、最终对象、构建安装过程、运行器、环境、数据和参数，内容改变产生新候选。
- `calibration` 接收验收资产及独立来源的正例、危险坏例、缺证例，实际调用同一验收实现。`acceptance` 将资产差异、分类、等价依据和校准交 X1 审定，完成语义变化交 D1 决定。
- `evidence` 将观察绑定到候选、冻结合同、判据、验收资产和受测对象，保存原始定位、三态结论及适用边界。对象或关键条件变化后，受影响证据失效并重验。
- `deviation` 接收每次 X2 交回的偏离核对。普通返修由 X1 组织，五类设计问题回原 D1，暂停范围及继续范围明确记录。
- `sign` 接收当前候选、逐项证据、角色结果、偏离处置及用户验收，X1 亲读并核对十三项清单后，对整个冻结范围签发。签发后新事实触发复核，维持与撤回的状态变化、不可变记录和新签发的 `supersedes` 关系均已规定。

### 同源分发与能力验收

- `source-layout` 向现有生成器提供四个源技能目录和共用资源映射。两个生成插件各暴露一个执行技能，规划正文随包保存，源与副本按字节核对。
- `planning-entry` 接收固定源提交或已确认可读的完整包根，加载同源正文、角色卡和模板。`execution-package` 向安装后的正式执行入口提供角色资源和派发要求。
- `capability-check` 接收同一最终规则集和安装对象的真实观察，覆盖正常链、危险坏例、缺证例、恢复和旧能力。`metrics` 从实际问题、退回、修订和告知记录去重汇总三项衡量。

## 3. 阻塞问题

未发现需要设计方补充决定、且会影响产品行为、科研或验收语义、接口、权限或资源边界的阻塞问题。

阻塞问题数量为 **0 项**。

角色宿主与转交方式、D8 合批通过条件、按角色绑定的输入身份、首次冻结顺序、写权交接、修订继承、整份签发及状态恢复，均有内嵌规则可据以实施。后续实际任务中的用户授权、检查器可访问性和运行环境，由既定入口检查和停止路线处理。

## 4. 实现自由度

- **代码组织。** 在既定入口、职责和输入输出含义下，决定函数拆分、模块内部组织、变量名、数据结构和错误汇总方式。依据为 `minimum`、`contract-changes`。
- **记录检查的内部写法。** 决定 JSON Schema 的分文件与 `$defs` 复用、错误排序、引用检查遍历方式，以及共用校验逻辑的复用。记录字段、枚举、路径边界、三态和只读性质按 `record-check` 实现。
- **身份与文件操作的工程实现。** 在仓库内唯一、不可变和幂等要求下选择记录编号生成方式，组织 Git 基线检查、提交、回读和故障注入。身份算法、写权和重试上限依 `state`、`writer`、`freeze` 的既定规则。
- **规范化库的具体版本。** `state`、`freeze` 已指定 Python 使用 `rfc8785`、JavaScript 使用 `canonicalize`，具体版本在实施时固定，并以共享对照例验证各端字节一致。
- **实现与校准接线。** 选择运行器内部结构、解析和报告实现，设计覆盖既定能力的具体控制例。预期结果依据冻结语义和独立参考，验收资产按 `acceptance`、`calibration` 交 X1 审定。
- **材料的表达与布局。** 在完整提示词、角色读限、必要字段和自然中文要求内安排段落、表格及报告呈现，按 `prompts`、`source-layout` 的同源规则组织正文和资源。

## 5. 结论

就设计语义而言，可以按上述顺序组织实施，尚需设计方补充裁决的阻塞问题为 **0 项**。

当前候选的实际开工前置步骤是完成四关卡、用户批准、冻结档复验、冻结记录及 X1 接收和写权交接。插件实现随后按 `minimum` 的四个工作包推进，能力结论由 `capability-check` 规定的实际验收取得。
