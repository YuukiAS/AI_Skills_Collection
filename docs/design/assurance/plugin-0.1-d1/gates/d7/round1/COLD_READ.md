# D7 冷读

本次只依据 `blueprint.json`。没有读取其引用的规格、仓库、网页或其他材料，没有运行探针，也没有修改蓝图。下文把蓝图中的流程当作待实现的产品合同，不把其中“尚未实现”“尚未运行”本身算成设计缺口。

## 1. 拟开工顺序

以下是解决相应阻塞问题后的实施顺序。阻塞只限制相关工作，不要求已经明确的部分全部停工。

1. **先落实共用文件协议。** 实现唯一任务定位、状态结构、角色返回、事件日志、单写者交接、冲突与重复返回处理，再提供只读记录检查。依据：`state`、`writer`、`record-check`。这一层提供后续所有派发和结果采纳的共同基础。
2. **实现调度与完整提示词。** 把固定优先级、角色档次、线程规则、读写范围、实际发送与仅准备的区别落到角色卡及模板中，同时接入修订告知与衡量记录。依据：`dispatch`、`prompts`、`revision`、`metrics`、`role-D1` 至 `role-D8`、`role-X1` 至 `role-X5`。
3. **实现设计端，并接通上游检查器。** 完成澄清分类、九项合同定位、D5–D8结果与有效范围、批准冻结和交接。先补定下文关于语义哈希、上游工作边界和首次冻结顺序的决定，再实现相关判定。依据：`clarify`、`contract`及其九个子节点、`gates`、`q-checker`、`freeze`、`q-inheritance`。
4. **实现交付端。** 完成候选提案与选择、验收资产审定、三类校准、证据绑定、偏离与五类退回，再实现X1亲读和十三项签发检查。依据：`acceptance`、`calibration`、`candidate`、`evidence`、`deviation`、`sign`。
5. **生成两插件，并从真实入口验证完整任务。** 共用资源只维护一份；用现有生成机制形成两个包，落实12插件、32技能预算和旧能力保护，再验证两个规划宿主与安装后的执行入口。依据：`source-layout`、`planning-entry`、`execution-package`、`q-capacity`、`capability-check`。这也遵循`minimum`规定的四个内部工作包顺序；`web-later`只交说明。

## 2. 已经明确的接缝

| 接缝及节点 | 输入 | 输出与责任边界 |
|---|---|---|
| 任务定位 → 状态（`state`） | 明确的任务、仓库、分支、任务编号和已绑定目录 | 同一任务的两个插件使用同一`STATE.json`；未知用`null`，已知空集合用`[]`。聊天只是状态快照。 |
| 角色返回 → 负责人采纳（`writer`、各角色卡） | `dispatch_id`、基线状态修订、设计或候选身份、实际读写及结果定位 | 负责人核对后采纳；重复结果幂等，冲突保留，过期结果不能覆盖当前决定。派出角色不改权威状态。 |
| 当前状态 → 下一步消息（`dispatch`、`prompts`） | 有效状态、已作出的条件选择、角色卡和实际宿主能力 | 给出角色、档次、线程方式及完整提示词；只有实际发送或转交确认才由`prepared`变为`sent`。不自动跨宿主发送。 |
| 独立设计 → 汇总（`role-D2`、`role-D3`、`role-D4`、`role-D1`） | 共同需求与事实基线；独立设计者互不读本轮对方产物 | D1收到原稿、问题和来源，负责取舍与完整Blueprint；D4提供事实，不替代完整验收。 |
| 关卡 → 冻结 → 交付接收（`gates`、`freeze`、`writer`、`role-X1`） | 同一受审对象的有效关卡、九项语义、实际批准和授权 | 不可变设计及冻结记录交给另一个X1线程。X1先实际接收，D1最后一次状态写入切换写权，X1回读后才写。首次冻结的对象关系仍见问题3。 |
| 验收作者 → X1审定（`role-X2`、`role-X3`、`calibration`、`acceptance`） | 验收实现、差异、独立预期和三类实际校准 | X1审定资产版本；X3按科研数值、统计、安全或弱验收重写条件启用。改变完成语义交D1。 |
| 候选 → 证据 → 签发（`candidate`、`evidence`、`sign`） | X1选定的最终对象、准入验收资产、正常入口的原始观察和必要专业结果 | 证据分`passed/failed/unknown`并记录有效性；未运行是`unknown`。X1亲读并逐项签发，不能拼接不同候选各自通过的部分。 |
| 设计退回 → 原D1（`deviation`、`revision`、`writer`） | 五类退回原因、原始证据、影响闭包和所需决定 | X1登记并暂停受影响范围；D1保留设计权，交付阶段的状态仍由X1写。无关且获准的工作继续。 |
| 源文件 → 安装包（`source-layout`、`planning-entry`、`execution-package`） | 固定源提交或确认可读的完整包根、复制映射 | 两包各暴露一个名称唯一的执行技能，规划正文作为资料；副本与源字节一致，不借其他包补资源。 |

## 3. 阻塞问题

### 问题1：语义哈希究竟覆盖哪些权威内容，怎样排除非语义说明？

**涉及节点与字段：** `freeze.terminal.mechanism`第6.3、6.4节的`nine_item_refs`、`semantic_hash`；`contract-*`各节点的`terminal.mechanism`；`revision`、`q-inheritance`的小修判定。

**问题：** 蓝图规定对九项引用内容做规范化JSON后计算SHA-256，同时要求只覆盖语义、不覆盖错字所在的说明文字。但九项承诺目前大量写在自然语言的`terminal.mechanism`及验收条款中，尚未规定哪些字段或片段组成权威投影、哪些说明可以排除，以及怎样保证引用没有遗漏分散在其他节点中的义务。

例如，同一段文字中既有正常入口和禁止替代，也有解释句。直接哈希整段，解释中的错字修复也可能改变哈希；自行抽取“语义”，又可能漏掉会改变义务的文字。键排序和去空白不能解决这个区别。

**开工影响：** 不能据此实现可靠的小修继承与交付派发核验。执行者选择投影范围，会实际决定哪些变化必须重新批准，属于验收和批准语义。

**可能的选项：** 由D1显式固定完整的字段或片段引用及排除边界，程序只做机械取值；或规定结构化的九项权威表示与正文之间的对应关系，由其提供确定投影。无论采用哪种，都需说明义务覆盖及修改后的复核责任。这里不要求增加第二份可独立修改的合同。

### 问题2：上游检查器改造由哪项工作承担，冻结前允许实施到哪里？

**涉及节点与字段：** `q-checker.outputs.result`、`q-checker.terminal.mechanism`；`minimum.terminal.mechanism`第10.1节；`role-X2.terminal.mechanism`；`dispatch.terminal.mechanism`中的`X1-intake`、`X2-implement`进入条件。

**问题：** 两档检查、三态结果和“在Blueprint维护源修改，不复制检查器”的方向已经裁决。但`minimum`仍明确写着“D5适配需要的上游工作由D1决定范围，不交给X2临场猜”，文件没有给出这一范围。还需明确：上游改造是本实施任务的一部分，还是必须另行交付的前置依赖；若属于本任务，允许修改哪个维护源、哪些接口与资源范围，由谁派发和接收。

这里还有启动顺序需要绑定：上游完成前D5只能是无法判断，四关未过不能冻结，而X2的正常实施入口要求已冻结合同；与此同时，`minimum`允许继续实现其他部分。蓝图没有说明这些冻结前的实现工作依据哪份有效实施合同，以及这一许可的确切范围。

**开工影响：** 不能开始上游改造，也不能自行把“可以继续其他部分”解释成绕过冻结的通用实施许可。该决定会改变跨仓库写入边界与实施准入条件。已经明确的材料整理和不依赖该接缝的准备工作不必全部等待。

**可能的选项：** 把上游两档检查作为独立前置任务，由D1交付确定版本后本任务只接入；或把上游改造纳入当前任务，明确其维护源、受限工作范围、实施依据和验收接口，并说明冻结前准备与正式实施的界线。

### 问题3：首次冻结时，批准、历史追加和冻结档检查分别绑定哪个对象？

**涉及节点与字段：** `gates`、`q-checker`的`terminal.mechanism`；`freeze.terminal.mechanism`中的`blueprint_ref`、`blueprint_sha256`、`gate_refs`、`user_approval`；`state`中的`blueprint.frozen_ref`；`sign`清单第1项；顶层`versions`。

**问题：** 冻结前草稿可以是`versions: []`，D5用草稿档；冻结时及以后要用保留完整历史要求的冻结档。另一边，四关必须覆盖待批准对象，用户批准内容版本后才生成不可变快照和冻结记录。

第一次真实冻结必然要产生历史。若把历史追加进获批Blueprint，该JSON的内容身份会变化；若快照原样保留空历史，又需要说明冻结档究竟检查哪一个文件，以及它怎样认可外部真实历史。蓝图没有给出这两类对象的明确关系，也没有说明冻结档D5结果怎样接入原先已通过的草稿档记录。

**开工影响：** 不能确定首次冻结输出、批准对象绑定和D5有效性核验的实现。执行者自行决定“历史变化不影响批准”或换一个对象通过检查，会改变批准与验收语义。这不是把尚未取得批准本身算作问题，而是缺少实现批准流程所需的对象规则。

**可能的选项：** 将获批正文身份与真实冻结历史分开保存，并明确冻结档检查两者的关联；或把含历史的Blueprint作为最终对象，明确内容批准、真实历史生成、最终确认与冻结档复验的阶段和身份绑定。两种路径都须保留真实历史，不能预填通过或虚构批准。

## 4. 实现自由度

以下事项可以在现有合同内由执行者决定，不计入阻塞：

- 函数、模块、变量和内部辅助类型怎样拆分、命名；既定源目录内的普通文件组织方式。
- 在已规定字段、空值、枚举和跨记录身份语义内编写Schema、模板及错误报告；不自行增减产品义务。
- 临时文件、原子写入和内部索引等机械实现，只要保持单写者、基线检查、幂等、回读与最多一次机械重试的规则。
- 在既定可并行范围内安排批次、组织测试代码和选择具体样例；保持独立角色、新读者、独立参考及关键验收的三类实际校准。
- 在合同允许的方法范围内选择日志、解析器、选择器与运行器接线；正式验收资产变更仍交X1审定，不能自行改阈值、总体或证据真实度。
- 提示词的自然中文措辞和报告排版，只要完整保留任务定位、角色、档次、读限、写回、告知和真实执行边界。
- 按已决定的源层与复制映射扩展生成器、调整容量断言并组织相称回归。12插件、32技能以及保留旧10插件、30技能已经确定，无需再选。
- D3可选判据的操作化及D4具体事实核查安排已有负责人和边界；本轮D3已启用。X3/X4/X5的职责、触发原则及缺入口时不降档的处理也已明确。

## 5. 结论

**尚不能在无需设计方补充决定的前提下，按既定完整语义开工。阻塞问题共3项。**

共用协议、角色卡和打包方案已有足够明确的基础，可以准备不依赖未决项的部分；语义哈希、上游检查器改造及首次冻结接缝需要D1补定后，才能据此完成相关实施和验收。0.1仍须交付完整任务链，不能把这些部分暂缺改称整体完成。
