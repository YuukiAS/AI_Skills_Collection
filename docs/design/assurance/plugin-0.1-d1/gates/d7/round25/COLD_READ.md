## 3. 阻塞问题

**本轮发现 0 个阻塞问题。**

以下事项已有明确责任和处理路线，可以按合同推进。

- **示例文件的具体落盘。** `contract-regression.terminal.mechanism` 与 `capability-check.terminal.mechanism` 已将关键输入、期望和尺子交 D1 写定，将机械文件生成交 X2，并要求 X1 首次运行前核对、记录哈希。R5 的格式选择缺口、S1 的三条固定请求及 R6 的安全恢复条件都有具体描述。执行者可以据此构造文件。
- **回归统计。** `capability-check` 已明确 8 个用例、18 条检查，分别为新能力 12 条、真实问题 3 条、受影响旧能力 1 条、冒烟 2 条。分组按检查条计，同一用例可以覆盖多类。
- **新插件的旧表现。** `contract-regression` 和 `capability-check` 已允许以公开历史原始记录证明，并给出相应记录定位与所证明的旧表现。后续执行仍须取得并核对这些记录。
- **既有网页打包方法的取得。** `web-later` 明确由 X2 查找来源并复用，找不到或无法复现时申报偏离给 X1。执行者无需自行选一套替代产品方案。
- **网页端写权限。** `web-later` 已明确有权限时写回指定分支，无写权限时如实给出内容，并保留实际边界与原始对话。
- **外部依赖和资源事实。** `q-checker` 给出上游检查器固定提交，`record-check` 给出记录检查依赖及版本，`contract-authorization` 规定授权边界与大件下载规则。后续取得失败、证据不可访问或实际需要新授权时，有对应停止和接收路线。

这些路线仍可能在实际执行时暴露新事实，届时按已定的返修、偏离或设计退回规则处理。
