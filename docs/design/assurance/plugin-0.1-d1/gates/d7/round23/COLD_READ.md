# D7 冷读检查

本次只以当前目录的 `blueprint.json` 为设计依据。没有读取外部规格、历史回答、其他目录或网页，没有运行环境或产品探针，也没有修改蓝图。下文判断的是设计是否足以支持实现，不代表任何关卡、安装或运行验收已经通过。

## 1. 拟开工顺序

蓝图明确禁止冻结前实现插件。因此，下面是设计问题关闭、规定关卡通过、用户批准并完成冻结交接后的实施顺序，不是本次开始实施的许可。

1. **核对冻结对象和责任交接。** 按 `gates`、`q-checker`、`freeze` 核对同一受审快照的四关卡、用户批准、说明身份和冻结档结果。按 `writer`、`role-X1` 完成两个长期线程之间的实际接收；D1 最后一次状态写入同时切换阶段与写者，X1 回读后接手。不能把可编辑草稿当实施合同。
2. **先做共用文件协议和运输。** 按 `state`、`writer`、`record-check` 实现状态结构、单写者规则、不可变记录、只读检查和恢复约定；按 `dispatch`、`prompts`、各 `role-*` 节点生成角色资源和完整派发。先把后续模块共同使用的身份、输入输出和写权接通。
3. **再做设计端。** 按 `clarify`、`role-D1` 至 `role-D8`、`contract` 及其子节点、`gates`、`freeze` 实现澄清、任务书、独立设计、四关卡和冻结交接。按 `revision`、`q-inheritance` 接入小修继承、大改重审及实际告知记录。
4. **随后做交付端。** 按 `candidate`、`acceptance`、`calibration`、`evidence`、`deviation`、`sign` 及 `role-X1` 至 `role-X5`，接通候选提案、验收资产审定、三类校准、原始证据、返修或设计退回、唯一签发和签发后撤回复核。按 `metrics` 从已有事件重建三项衡量。
5. **生成各端包，再做真实验收。** 按 `source-layout`、`planning-entry`、`execution-package`、`q-capacity` 复用生成器和同源资源，将预算调整到 12 个插件、32 个技能并保留原有能力。按 `web-later` 复用既有网页端打包方法；按 `capability-check` 完成实际宿主观察、三类校准及 R1–R7、S1 回归，最后由 X1 亲读证据、核对十三项清单并签发。

这个顺序与 `minimum.terminal.mechanism` 的四个内部工作包一致。固定提交的 Blueprint 检查器是外部前置依赖，实施只接入，不改上游；网页端既有方法找不到或不能复现时走偏离流程，不自行换方法。

## 2. 已经明确的接缝

| 接缝与节点 | 输入 | 输出与责任边界 |
|---|---|---|
| 当前事实与状态写入：`state` → `writer` | 绑定的任务目录、目标分支、状态修订号、文件身份及预期分支头 | 设计阶段仅 D1、交付阶段仅 X1 写 `STATE.json`；写前核对、写后回读。日志只追加，不能代替当前状态。派出角色只交自己的结果。 |
| 澄清到独立设计：`clarify`、`prompts` → `role-D2`、`role-D3`、`role-D4` | 不含设计倾向的不可变任务书、原话出处、既有决定、事实及读限 | 派发绑定 `brief_sha256`；D2、D3 互不读本轮对方产物。换版后旧结果保留、标过期，由 D1 判断剩余适用范围。 |
| 调度到实际工作：`dispatch` → `prompts` → 各角色 | 有效状态、固定优先级、角色档次、线程规则、允许材料和写入范围 | 自包含提示词及独立派发记录；准备与实际发送分开登记。需要用户转交的角色每轮最多一条，专业档次不能用 Codex 或降档替代。 |
| 角色返回到负责人：各 `role-*` → `writer`、负责人 | 派发编号、依据身份、实际读写、产物定位、发现与未运行项 | `RESULT.json` 和自然中文说明；负责人核对后采纳。同一派发同一结果幂等，不同内容保留冲突，不以最后写入者为准。 |
| 记录检查：`record-check` | 指定任务目录、记录种类、记录文件及包内预注册结构 | 只读报告 `assessment,errors,unresolved,checked_files`；退出值 0、1、2 分别表示可检查项符合、确定错误、无法完成检查，不写状态或执行记录内命令。 |
| 设计审查到冻结：`contract` → `gates` → `freeze` | 同一快照的九项语义、D5–D8 结果、经 D6 对照的冻结说明和用户批准 | 四关卡先通过、用户再批准、追加冻结历史、D5 冻结档确认、最后写 `freeze.json`。说明变动使说明检查失效；不必在 Blueprint 未变时重做逐组件追问。 |
| 冻结到交付：`freeze` → `role-X1`、`writer` | 冻结包、批准、授权与四个不同用途的身份 | 快照身份绑定批准；说明身份绑定用户所读说明；完整文件身份用于存档和接收；语义身份用于交付派发与小修继承。X1 实际读取并交回接收记录后才切换状态写权。 |
| 修订到继续工作：`revision`、`q-inheritance` → `dispatch` | 字段级差异、九项比较、实际前后告知、新 D5 结果及必要批准 | 小修须满足至多两个既有节点等全部窄条件，完整继承链可沿用原批准；大改重跑关卡并重新批准。只暂停受影响节点及依赖工作。 |
| 验收实现到正式证据：`role-X2`／`role-X3` → `calibration` → `acceptance` → `evidence` | 验收资产版本、独立期望、正例／危险坏例／缺证例及原始运行结果 | X1 审定后才能用作正式验收。校准结果不能代替当前最终成品从正常入口得到的直接证据。 |
| 候选到签发：`candidate` → `evidence` → `sign` | X1 选定的当前候选、源码及最终对象身份、有效验收资产、实际观察、必要专业角色结果 | 证据逐项绑定候选和冻结义务，结果为通过／失败／无法判断；X1 亲读后对整个冻结范围签发，不能拼接不同候选的通过部分。 |
| 偏离到设计修订：`deviation` → `revision`、`role-D1` | 预期与实际差异、原始证据、已尝试的合同内处理及影响范围 | 普通实现或环境故障留在 X1；命中五类设计退回条件才交 D1。交付期间 D1 仍负责设计决定，状态由 X1 原样登记。 |
| 唯一源到分发：`source-layout` → `planning-entry`、`execution-package`、`web-later` | 固定源版本、明确资源根、复制映射及实际包身份 | 两个执行技能独立命名，规划资料不额外计技能数；各包自包含、正文同源。网页端无写权时如实给出内容是明确允许的验收分支。 |

D8 的合批方式、每轮新对话、逐单位只依据自身文字、D1 逐项判断及 `single-thread-batch` 标记均已写明；这里没有待执行者选择的读者隔离方案。

## 3. 阻塞问题

### B1. S1 第一条请求的固定正文尚未给出，不能确定这条冻结用例的实际输入

**涉及节点与字段：** `capability-check.terminal.mechanism` 第 10.2a 节 S1 的“输入”，同节点 `terminal.acceptance` 的 S1 条目及 `validators[id=v-regression-set].method.description`；约束依据为 `contract-regression.terminal.mechanism` 第 6.3a 节“用例写到多细”。

**问题：** S1 第一条请求仍写作“把下面这段话改得更通顺：〈固定的一段 200 字左右中文说明文字〉”。要润色的实际文字没有内嵌，也没有给出固定输入的定位。这里的尖括号内容究竟应由 D1 补成正文，还是允许 X2 自行写一段？

**为什么阻塞：** 合同明确把关键输入内容留给 D1 决定，X2 只把已定描述转成机械文件。S1 同时要求输出不出现“冻结、派发”等用语；输入本身是否含这些词、是否讨论 Assurance，会直接影响这一判据与正常润色任务能否同时成立。自行选择输入内容，会改变固定冒烟用例实际覆盖什么，不能只按文件生成细节处理。X1 事后核对、记录哈希，也不能补出合同未给出的输入选择。

**可能的选项：**

- D1 在 Blueprint 内给出完整正文，X2 原样做成样例文件。
- D1 给出同一固定正文的明确版本与定位，并明确其作为用例输入的身份。
- 设计方明确授权执行者按具体内容约束生成这段文字，并说明与输出禁词判据的关系；这是对现有固定输入约定的补充。

本问题不要求 D1 决定样例文件名、编号或序列化方式，只要求确定送给被测插件的实际文字或其明确生成边界。

### B2. R6 的“不找用户”缺少成立所需的恢复和安全重派前提

**涉及节点与字段：** `capability-check.terminal.mechanism` 第 10.2a 节 R6 的“输入”和“看什么”，同节点 `terminal.acceptance` 的 R6 条目及 `validators[id=v-regression-set].method.description`；对照 `state.terminal.mechanism`、`writer.terminal.mechanism` 第 1.3a 节第 2、4、6 步，以及 `state.validators[id=v-fail-recovery]`。

**问题：** R6 只给出“状态无法解析、日志记已返回、结果文件不存在”，随后要求恢复、重派，并因不涉及冻结等四类记录而“不找用户”。该场景是否还明确保证：存在有效历史基线，原派发已有写入可查清且与重派不冲突，重派不会重复不可撤回的外部后果？

**为什么阻塞：** 总恢复合同不仅把冻结、批准、签发、撤回冲突交用户，还规定“保守处置做不了”时交用户，找不到有效历史状态时也须用户确认。因此，“不涉及四类记录”本身不足以推出“不找用户”。符合 R6 已列输入的场景，仍可能必须请求用户决定。执行者若自行补成安全、可恢复的场景，就替设计方选择了影响权限和验收结果的前提；若把“不找用户”实现成普遍规则，又会违反恢复合同。

**可能的选项：**

- 把 R6 限定为有有效历史基线、原写入可列明且可安全重派的普通冲突，写明相关场景条件，保持当前“不找用户”的期望。
- 让 R6 明确覆盖不同恢复条件，按总合同分别判定自动保守恢复或交用户决定，并同步写定检查条与分组。
- 若意图让 R6 成为恢复规则的例外，明确例外的适用范围和授权依据，并同步修改总恢复合同。

这里不是要求预先填死提交号或修订号的具体数值；这些可以机械生成。缺的是决定走哪条恢复路线的场景条件。

## 4. 实现自由度

- 模块、函数和类如何拆分，内部变量名、局部辅助函数、错误报告的排列方式，只要不改变已定接口、三态和接收方，可以自行决定。
- 在已定类型、字段和空值规则下编写 JSON Schema、模板和验证代码，选择本地结构注册与遍历的内部组织方式；不能借此增加联网取结构或执行记录内命令的能力。
- JCS 已明确，Python 使用 `rfc8785`、JavaScript 使用 `canonicalize`；具体版本按合同在实施时固定，逐字节对照例的文件组织可自行决定。不能改成自行发明的规范化算法。
- 按已定用例语义生成示例状态、编号、无业务含义的文件名、时间和可核对哈希。无需设计方逐个手写 JSON 字节，但不能自行补入会改变判定分支的前提或尚未给出的关键输入。
- 在生成器既有机制内组织复制配置、构建辅助代码和检查脚本，保持两个执行技能名称、预算、自包含资源及源与副本一致性。
- 对已定规则编写普通验收实现和运行器接线，由 X1 审定。X3、X4、X5 的条件和职责已经写清，不能把选择代码组织方式扩成选择是否启用必需角色。
- 根据合同安排开发期间失败项及受影响项的重跑顺序；最终候选必须完整运行回归集，此后改代码须再完整运行，不能自行缩减。
- 在不改变含义和读取边界的前提下组织中文提示词与报告，使英文术语得到解释；D8 已读文字、冻结说明身份及小修限制仍按既定规则处理。

网页端方法的查找和复现已有责任人及失败路线，依赖大小未知已有如实记录和授权规则，运行环境缺失已有补证或停止路线；这些不另算设计阻塞。缺少本轮真实运行证据，也不等于设计必须再作一个选择。

## 5. 结论

**当前不能认定已具备按既定语义完整开工的条件，共有 2 个阻塞问题。** 两项都集中在必需回归用例的输入与成立前提，而非普通代码细节；需设计方补定后再核对。

其余主要组件、角色分工、身份绑定、冻结与交付接缝已有可执行约定。本结论不表示这些约定已实际实现或验收；即使上述问题关闭，仍须完成蓝图规定的冻结和交接，才能开始插件实现。
