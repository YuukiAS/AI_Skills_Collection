# D7 冷读记录

本次判断仅依据当前 `blueprint.json` 中的需求、节点、接口、内嵌合同、走查和失败路径。结论是设计层面具备按既定语义组织实施的条件，阻塞问题共 **0 项**。实际插件实现的启动时点仍受蓝图规定的批准、冻结和交接顺序约束。

## 1. 拟开工顺序

### 1.1 先完成实施前的流程条件

1. **由 D1 固定受审对象并关闭关键问题。** 以九项合同检查能力、正常入口、最终对象、三态结果、证据、禁止替代、旧能力、变更权和授权范围。首次独立设计和现实核查使用不可变任务书，已有设计的关卡使用受审快照。依据 `clarify`、`contract` 及其九个子节点、`state`、`dispatch`。
2. **取得同一快照的四关卡结果及冻结说明检查。** D5 使用固定提交的草稿档，D6 逐组件追问并对照冻结说明，D7 冷读，D8 每轮在一个新 GPT 对话中合批复述。D1 收集真实结果，改动后按影响更新有效范围。依据 `role-D5` 至 `role-D8`、`gates`、`q-checker`、`freeze.terminal.mechanism` 第 6.4a 节。
3. **按五步顺序冻结并交接。** 四关卡对同一 `snapshot_sha256` 通过后请用户批准，再追加冻结版本，运行 D5 冻结档，核对获批快照后写 `freeze.json`。X1 在独立长期线程实际读取并接收，D1 最后一次状态提交切换写者，X1 回读后进入交付。依据 `freeze`、`writer`、`role-X1`。本插件自身的负责人安排采用蓝图明定的 D1 为 Claude、X1 为 GPT Work 极高、Claude 机械启动 Codex 的分工。

### 1.2 冻结交接完成后实施

4. **先实现共用协议、模板和只读记录检查。** 建立四个源入口的框架、一份共用规则源、状态与记录结构、十三张角色卡、完整提示词模板，以及 `check_records.py`。落实按角色绑定身份、单写者、幂等采纳、远端回读和恢复规则。各端内容哈希使用 JCS，附跨语言字节与哈希对照例。依据 `minimum` 第 10.1 节的第一个工作包，以及 `source-layout`、`state`、`writer`、`record-check`、`prompts`。
5. **接通设计端。** 实现澄清分类、共同任务书、独立设计派发、汇总、四关卡记录、冻结说明、冻结及小修继承。接入蓝图指定的 Blueprint 检查器提交 `c05edcf51bc93f8be82180fd4ad28a250937f195`。依据 `dispatch`、`design-roles`、`clarify`、`gates`、`contract`、`freeze`、`q-checker`、`q-inheritance`。
6. **接通交付端。** 实现 X1 接收与派发、候选提案和选择、验收资产五级变更、三类校准、证据绑定、偏离及五类设计退回、十三项签发清单、整份签发撤回复核和衡量记录。依据 `delivery-roles`、`acceptance`、`calibration`、`candidate`、`evidence`、`deviation`、`sign`、`revision`、`metrics`。
7. **生成两端分发包。** 用既有生成器生成两个 Codex 插件，每个暴露一个名称唯一的执行技能，复制同版本规划资料与完整共用资源，把市场预算调整为十二个插件、三十二个技能。网页端由 X2 查明并复用 thread handoff、thread instruction 的既有打包方法。依据 `source-layout`、`execution-package`、`planning-entry`、`q-capacity`、`web-later`。
8. **在稳定最终候选上完成真实验收。** 先做记录结构、来源及已知回归检查，再完成 Claude Code、GPT Work、安装后 Codex 和真实 ChatGPT 网页端的规定观察。安全相关验收交 X3，提示词与责任链的专业判断交 X5，网页端三项观察交 X4。X1 亲读成品和原始证据后决定签发。依据 `capability-check`、`calibration`、`role-X3` 至 `role-X5`、`sign`。

上述四个实施工作包的前后顺序取自 `minimum`。包内函数、模块和具体编码次序由执行者安排。

## 2. 已经明确的接缝

| 接缝及节点 | 输入 | 输出与接收规则 |
|---|---|---|
| 任务定位与状态，`state`、`writer` | 任务、仓库、确切分支、绑定目录、当前状态修订及文件身份 | 同一任务共用一份 `STATE.json`。设计期由 D1 写，交付期由 X1 写。状态变化追加事件并经同分支回读确认 |
| 共同任务书到独立设计与核查，`clarify`、`prompts`、`role-D2` 至 `role-D4` | 不可变任务书中的需求出处、已有决定、事实、开放事项和读限，派发绑定 `brief_sha256` | D2、D3 交完整独立候选，D4 交事实与原始观察。任务书换版后旧结果标 `stale`，由 D1 判断仍可支持的范围 |
| 派发到角色返回，`dispatch`、`prompts`、各角色节点 | 角色、档次、会话方式、依据身份、读写范围、完整提示词、预期产物和接收者 | 角色返回 `RESULT.json` 与自然中文说明，列实际读写、产物身份、发现和未运行项。负责人核对后采纳，派发状态区分准备、实际发送、返回和采纳 |
| 记录到只读检查，`record-check` | 指定任务目录、记录种类、记录文件及包内本地结构 | 输出 `assessment/errors/unresolved/checked_files`。退出值 0、1、2 分别表示结构及可检查引用合规、确定错误、检查无法完成 |
| 受审设计到四关卡，`contract`、`gates`、`role-D5` 至 `role-D8` | 同一 `snapshot_sha256`，以及各角色允许读取的材料 | 结果带受审身份、覆盖与有效性。D7 只看 Blueprint，D8 保留逐单位原文、文字身份、真实复述和 `single-thread-batch` 标记，判断交 D1 |
| 批准到冻结交接，`freeze`、`writer`、`role-X1` | 四关卡、用户对具体快照的批准、授权定位及冻结档结果 | 不可变冻结 Blueprint、`freeze.json`、X1 实际接收记录。`snapshot_sha256` 绑定批准对象，`bundle_sha256` 核对冻结文件原始字节，`semantic_hash` 用于定义内容与继承核验 |
| 修订到后续派发，`revision`、`q-inheritance`、`dispatch` | 新旧设计、字段级差异、九项合同对照、受影响节点、告知及关卡记录 | 小修满足全部条件后以完整继承链启用新值，大改重新过关卡和批准。编辑中的草稿期间，未暂停工作继续绑定原有效冻结对象 |
| 实现到验收资产准入，`role-X2`、`role-X3`、`calibration`、`acceptance` | 冻结语义、验收资产提案、差异、独立参考及正坏缺证例的实际结果 | X1 审定资产版本。X2 默认编写，科研数值、统计、安全相关或弱验收需换人重写时启用 X3。正式引用的替换以 X1 审定为前提 |
| 候选到证据和签发，`candidate`、`evidence`、`sign` | 源码集合、最终对象、构建安装映射、运行器、数据参数及正常入口的原始观察 | X1 选择当前候选，证据逐项绑定候选及准则。签发覆盖整个冻结范围，十三项全部满足后形成可回读的签发记录 |
| 偏离到返修或设计退回，`deviation`、`revision`、`writer` | 每次交回的偏离核对、实际事实、原始证据及需要决定的内容 | 普通实现和环境问题交原交付角色处理，五类设计问题交 D1。暂停影响范围及依赖工作，交付期的状态仍由 X1 登记 |
| 中断到状态恢复，`state`、`writer`、`record-check` | 最后有效历史状态、后续事件和对应不可变记录 | 新状态与 `recovery/<recovery_id>.json`。普通冲突固定采用 `stale-redispatch`，重派提示词列出已有提交和文件。须用户决定的冲突隔离进 `paused_scopes`，其余范围经检查回读后恢复 |
| 同源规则到分发与宿主观察，`source-layout`、`planning-entry`、`execution-package`、`web-later` | 固定源提交或已确认完整包根、复制映射及最终包身份 | 两个自包含 Codex 包和网页端规划包。规划正文副本保持字节一致。各宿主分别留下实际读取和使用证据，网页端还须生成下一条提示词并按权限写回或给出内容 |

签发后的新事实有独立接缝。`sign`、`evidence` 和 `state` 已规定先进入 `X1-review-release` 暂停声明，X1 写 `upheld` 或 `revoked` 的不可变记录。撤回后清空当前签发引用、使指定证据失效并返修，新签发以 `supersedes` 关联被撤回签发。

以下几处已具备足够明确的处置规则。

- `state.terminal.mechanism` 第 1.3a 节已经规定恢复冲突的默认结果、原始记录保留、重派时披露已有写入，以及交用户决定的边界。涉及冻结、批准、签发、撤回，或原写入冲突、不可撤回外部后果时，执行者有明确的暂停和移交路径。
- `dispatch`、`role-D8`、`gates` 和 `contract-fidelity` 已明确接受每轮新对话合批复述，D1 逐项判断，全部正确即有效通过。返修轮处理改动及相关单位，保留每个单位最近有效的文字身份和复述。
- `state`、`freeze`、`revision`、`q-inheritance` 已给出内容哈希的规范化规则、三个身份各自用途及小修继承条件，执行者可以据此实现身份核验。
- `web-later` 已把网页端打包和三项真实观察纳入 0.1，并把既有方法的查找、来源记录和复用交给 X2。查找失败或无法复现时申报偏离给 X1，处置路径已经确定。

实际仓库写入定位、线程定位、既有打包方法的具体来源、宿主可用性、执行授权和真实验收记录，须按蓝图规定在派发与执行时取得。蓝图已经规定取得责任、缺项结果及接收方，这些执行条件有明确处理路径。

## 4. 实现自由度

- **代码组织。** 在规定入口和职责内选择函数拆分、变量名、模块组织、JSON Schema 的复用方式和错误收集实现。`minimum`、`record-check` 已固定外部职责和检查结果。
- **规范化依赖版本。** 按 `state`、`freeze` 规定，实施时固定 Python `rfc8785`、JavaScript `canonicalize` 的具体版本，并用规定的对照例检验。JCS 算法及哈希覆盖范围已经固定。
- **模板展开方式。** 可选择怎样组合公共运输要求、角色卡与本次输入，怎样展示中文诊断和结果索引。`prompts` 已规定正式消息所需内容、独立角色读限和完整性要求。
- **记录编号生成。** 可选择满足任务内唯一、不可覆盖及幂等要求的编号生成办法。派发、结果、修订、候选和证据之间的绑定规则按 `state`、`writer`、`dispatch`、`candidate` 执行。
- **写入与回读的代码实现。** 在实际授权支持的工具范围内实现普通 Git 提交或带身份校验的文件接口，选择内部封装方式。基线核对、单写者、有限重试、响应不明先回读和冲突保留已有明确规则。
- **验收实现及控制例构造。** 按 `contract-controls`、`calibration`、`capability-check` 选择具体公开安全样例、运行接线和原始记录组织方式，覆盖规定能力与真实危险坏例。专业角色触发条件、独立参考及正坏缺证结果已有规定。
- **等价的交付内维修。** 按 `acceptance` 提交路径、选择器、解析器或运行器的维修提案，附对应差异、校准和当前候选重验，由 X1 审定。
- **生成与校验的内部安排。** 在既有生成器和已定复制映射内组织资源复制、字节一致性检查及回归运行。十二插件、三十二技能的预算、旧能力保护和两个执行技能的名称已经固定。
- **衡量汇总的呈现。** 可选择汇总排序和排版，从原始事件计算三项记录。问题去重、五类退回归因、未知归因单列和真实前后告知的计数含义按 `metrics` 执行。
