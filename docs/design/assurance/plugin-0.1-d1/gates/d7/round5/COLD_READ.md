3. **实现共享协议、模板和运输检查。** 先建立状态、任务书、派发及结果的记录结构，再接入只读记录检查、基线回读、冲突和幂等规则，随后生成完整提示词及事件记录。这是两插件共同依赖的部分，不另建服务。依据：`state`、`writer`、`record-check`、`dispatch`、`prompts`、`metrics`。

5. **实现交付端。** 接入候选提案与 X1 采用、验收资产五级分类、三类校准、三态证据、偏离与设计退回，再实现整份签发及签发后的复核、维持和撤回。依据：`role-X1` 至 `role-X5`、`acceptance`、`calibration`、`candidate`、`evidence`、`deviation`、`sign`。
6. **生成两插件并验证真实入口。** 按源层映射生成自包含包，预算调整为 12 插件、32 技能；保留原有 10 插件、30 技能。先做记录结构和受影响的回归，再在稳定最终候选上取得两个规划宿主、安装后 Codex 入口及所需独立角色的真实证据，交 X1 亲读签发。网页端本轮只写后续打包说明。依据：`source-layout`、`planning-entry`、`execution-package`、`q-capacity`、`capability-check`、`web-later`。

## 3. 阻塞问题

### B1：`brief_sha256` 的哈希输入是什么？

**涉及节点与字段：**

- `clarify.terminal.mechanism`：任务书文件及其字段定义。
- `state.terminal.mechanism`、`dispatch.terminal.mechanism`：D2/D3/D4 使用 `based_on.brief_sha256` 绑定任务书，并据此处理换版与过期。
- `prompts.terminal.mechanism`、`role-D2`、`role-D3`、`role-D4`：把该身份交给不同执行者。
- `writer.terminal.acceptance`：返回时核对 `based_on.brief_sha256`。
- `record-check.terminal.mechanism`：核对任务书记录及已声明身份引用。

**问题：** 蓝图已经规定谁创建任务书、何时创建、写哪些内容、怎样换版，以及哪些角色绑定它，但没有像另外三个身份那样定义 `brief_sha256` 的计算输入。它究竟是任务书文件原始字节的 SHA-256，还是完整任务书 JSON 规范化后的 SHA-256？如果是后者，应明确采用哪套规范化规则及覆盖范围。

**为什么阻塞：** 这是派发方与接收方共享的身份接口，不只是哈希函数怎样封装。同一 JSON 值仅改变缩进、键顺序或末尾换行，文件字节哈希会改变，规范化内容哈希则可以不变。任务书不可变的要求限制了写入行为，却没有替双方选定校验表示。D1、两个规划宿主及只读检查器若各自按不同表示计算，就可能拒收同一任务书；反过来，也会对哪些变化算身份变化作出不同判断。执行者不能在没有共同规则的情况下，把其中一种接收语义写进正式提示词和检查器。

**可能的选项：**

- 对持久保存的任务书完整文件原始字节计算 SHA-256；接收方取得同一字节对象后核对，格式变化也改变身份。
- 对任务书完整 JSON 内容按明确的规范化规则计算 SHA-256；明确所有字段是否全部参与，并让派发、返回核对和记录检查共用此定义，格式变化不改变身份。

本项需要 D1 补定共同规则，不需要冷读者代选。它阻塞共享身份协议及其下游派发、核验接口的定稿；不意味着其他已定规则都要重新设计。

## 4. 实现自由度

- **代码组织。** 可以自行拆函数、命名变量、组织内部模块和复用辅助函数；无需把每个流程节点实现成独立服务或程序。依据：`minimum`、`contract-changes`。
- **规则源的内部编排。** `source-layout` 给的是建议源路径；可以在保持入口名称、资源根定位、源与副本一致、自包含包和生成机制等承诺的前提下安排文件。不能据此新增市场技能、服务或后台调度。
- **结构检查的内部实现。** 可以决定如何封装已选 `jsonschema`、遍历已声明引用、排列错误信息和组织测试夹具；依赖版本、只读边界、记录种类、三态退出含义及既定字段语义按合同执行。B1 的哈希输入不归入这一自由度。
- **提示词的自然表达。** 可以调整不改变含义的句式和排版，按角色裁剪允许材料；必须保留实际定位、完整职责、独立读限、写入测试、写回和接收方，不能为了简短删掉权限或验收条件。依据：`prompts`、各角色卡。
- **合同内的验收实现。** X2 可选择日志、选择器、解析器、运行器接线等具体写法；变更按 `acceptance` 分类并由 X1 审查，需要时重新校准和重验。这是已有授权机制，不要求设计方预选所有代码细节。
- **控制例的具体构造与数量。** 可按能力覆盖选取样本和组织运行，遵守独立预期、三类实际校准、修复样例转为已知回归和最终候选直接验收等要求，不另造固定样本数或零退回门槛。依据：`calibration`、`capability-check`、`metrics`。
- **条件角色的逐任务判断。** D1 按已定条件决定 D3/D4，X1 按已定条件安排 X3/X4/X5并记录依据；这是蓝图已分配的职责。本轮已经启用的 D3、必跑的 D5–D8 和实际命中的专业角色不能被实施者省掉。依据：`dispatch`。

本次未把“插件还没实现、验收还没运行、当前尚未获批冻结”另算成设计问题；这些已有明确的前置条件和后续路径。也没有把宿主是否实际支持某项能力当场猜成答案，后续应按蓝图取得真实证据。

## 5. 结论

**尚不能按整份既定语义直接进入插件实现；阻塞问题共 1 项，即 B1。** 补定任务书身份的计算规则后，仍应先完成蓝图规定的关卡、批准、冻结和写者交接，再按四个内部工作包实施。当前没有冻结不是第二项设计歧义，也不能由本次冷读替代批准。
