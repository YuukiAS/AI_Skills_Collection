2. **实现共用文件协议、模板与运输检查。** 先建立状态、任务书、派发、结果、事件和恢复记录的结构，接入内容规范化与身份计算，再实现只读记录检查、单写者校验、重复返回和写入不明的处理。随后组织完整提示词与角色资源。依据节点为 `minimum`、`state`、`writer`、`record-check`、`dispatch`、`prompts`、`source-layout`。
3. **实现设计端完整链路。** 接入澄清分类、独立设计任务书、角色读限、四关卡、冻结说明、冻结记录及小修批准继承。Blueprint 检查器按指定提交调用。依据节点为 `clarify`、`design-roles`、`contract`、`gates`、`q-checker`、`freeze`、`revision`、`q-inheritance`。
4. **实现交付端完整链路。** 依次接入候选提案与 X1 选定、验收资产变化审查、三类校准、证据绑定、偏离与五类设计退回、亲读签发和签发后复核。衡量记录从真实事件及原始记录生成。依据节点为 `delivery-roles`、`acceptance`、`calibration`、`candidate`、`evidence`、`deviation`、`sign`、`metrics`。

## 3. 阻塞问题

### B1 普通恢复冲突由谁裁决，什么条件下可以恢复派发

**涉及位置**

- `state.terminal.mechanism` 的第 1.3a 节第 4、5 步，以及 `state.interface.boundaries`。
- `writer.terminal.mechanism` 的第 1.3a 节第 4、5 步。
- `record-check.terminal.mechanism` 对恢复记录的检查边界。
- `dispatch.terminal.mechanism` 中相同的恢复规则。
- 失败路径 `fail-recovery.handling`。

**需要设计方决定的问题**

恢复时，事件与不可变记录对不上，或无法判断某个变化是否已发生，都要列为恢复冲突。合同明确写了“负责人不能自行选择”，并规定涉及冻结、批准、签发的冲突交用户决定。对于其余冲突，合同没有指定裁决者、合法处理方式，以及冲突尚未解决时能否恢复部分派发。

例如，历史有效状态中某次 D4 派发仍在进行，之后事件日志声称已经返回，但对应结果记录缺失，且现有材料无法查明结果是否真正交回。这已符合恢复冲突定义，却未必涉及冻结、批准或签发。此时由谁决定保留待返回、作废后重派，或继续等待，蓝图没有给出依据。

**为什么阻塞实施**

共享协议必须实现这条已承诺的恢复路径。将普通冲突一律交用户、允许负责人作废并重派、或在冲突未解时恢复无关范围，会分别改变用户介入条件、负责人权限和恢复后的派发边界。执行者自行选定其中一种，就会补入流程决定。只读记录检查器也已明确不能替负责人选择冲突，因此检查通过与远端回读本身不能补足这一决定。

**可能的选项**

- 所有经核查仍无法解决的恢复冲突统一交用户，明确用户决定后才能恢复哪些范围。
- 按冲突种类指定有权裁决的角色，并列出其可作出的决定、所需证据和须升级给用户的情形。
- 允许对规定种类的普通冲突采用固定的保守处置，例如保留历史、使相关结果失效并受控重派，同时明确防止重复副作用的条件。
- 允许隔离未决冲突及其依赖范围，先恢复其余范围，并另行规定未决范围的裁决者与恢复条件。

以上选项可以组合。需要设计方明确权限与恢复条件后，执行者才能据此实现和验收。

## 4. 实现自由度

- 在既定目录、角色职责和输入输出含义内，自行选择函数拆分、模块组织、变量名及内部数据结构。`minimum` 已给出四个内部工作包，`source-layout` 已给出源层与生成层职责。
- 将蓝图列出的字段、枚举、空值和引用约束写成具体 JSON Schema，选择可读的内部辅助字段和错误信息组织方式，遵守 `record-check` 的只读、路径和三态边界。
- 使用蓝图指定的 JCS 库，在实施时固定具体版本，组织跨端逐字节对照例。内容哈希的输入范围、规范化方法和完整文件哈希的算法已经由 `state`、`freeze` 明确。
- 在 `writer` 的基线比较、幂等、回读和重试上限之内，选择已有 Git 或 GitHub 写入接口及内部事务组织方式。B1 中缺失的冲突裁决权限仍需设计方补定。
- 在已经确定的角色、档次、线程、读限、写入范围和输出格式内，组织提示词与按职责加载的资源。规划端每角色每轮一条、D8 合批方式均已有合同。
- 按冻结能力选择具体正例、危险坏例、缺证例与代表性回归任务，并编写验收实现。控制例必须遵守 `calibration`、`contract-controls`、`capability-check` 的独立预期、覆盖和同一实现要求。
- 复用现有生成器，落实复制映射、资源根解析、构建记录和同源字节核对。市场预算、入口名称、规划资料位置及网页端方法复用要求已有决定。
- 由负责人在实际任务中落实具体派发编号、允许目录、线程定位、授权引用及资源记录。蓝图已经规定取得这些实际值和缺项时的处理职责。

## 5. 结论

**尚不能按无需补充设计决定的完整既定语义开工，阻塞问题共 1 个。** 缺口集中在普通恢复冲突的裁决权限和恢复派发条件。其余已明确部分可在完成冻结、交接并取得实际派发授权后，按上述顺序实施。

本结论是单文件设计冷读结果。蓝图中的实现状态、验收计划和外部依赖交付陈述均按其文字理解，实际运行结果仍待后续规定角色取得。
