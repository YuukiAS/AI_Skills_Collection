# D7 冷读

本次只依据 `blueprint.json` 判断，没有读取引用的规格、仓库、网页或其他材料，也没有运行探针或验收。下文的“明确”表示蓝图已经给出决定，不表示相关实现或外部前置工作已经由我验证。

## 1. 拟开工顺序

1. **先完成设计收敛与冻结，再进入插件实现。** 先由 D1 处理本文指出的启动问题；对稳定受审快照完成 D5 草稿档、D6、D7、D8，取得用户对该 `snapshot_sha256` 的批准，再追加冻结版本、运行 D5 冻结档，核对快照未变后写入含三个身份的 `freeze.json`。冻结前不开始插件实现。依据：`clarify`、`gates`、`freeze`、`minimum`。
2. **由新的 X1 线程接收冻结合同并交接写权。** X1 实际读取冻结包、批准与授权，核对 `bundle_sha256` 并写接收记录；D1 最后一次状态提交同时切换 `phase` 与 `state_writer`，X1 回读后才开始维护交付状态。依据：`writer`、`freeze`、`role-X1`。
3. **实现共用文件协议、记录检查和派发运输。** 先做唯一任务定位、状态模板与结构、结果记录、单写者冲突恢复、事件追加，再实现按条件生成下一步提示词与角色读写边界。这里须先有明确的首次派发身份规则，才能形成一致的 `dispatch`、`result` 结构及对应检查。依据：`state`、`writer`、`record-check`、`dispatch`、`prompts`；四个内部工作包的顺序依据 `minimum`。
4. **接上设计端完整流程。** 编写 D1–D8 角色资源、问题分类、九项合同定位、关卡接入和冻结记录；同时落实小修继承、大改重审、前后告知与暂停范围。Blueprint 检查器按蓝图指定的固定提交接入，不改上游。依据：`design-roles`、`clarify`、`contract` 及其九个子节点、`gates`、`q-checker`、`freeze`、`revision`、`q-inheritance`。
5. **接上交付端完整流程。** 编写 X1–X5 角色资源，串起候选提案与选择、验收资产审定、三类校准、原始证据、偏离和五类设计退回，最后接入整份签发、签发后复核与撤回。衡量记录从实际事件和原始记录重建。依据：`delivery-roles`、`candidate`、`acceptance`、`calibration`、`evidence`、`deviation`、`sign`、`metrics`。
6. **生成两个插件，再验证实际使用。** 从唯一源层生成包，把预算调整为 12 个插件、32 个技能，保留原有 10 个插件、30 个技能。随后在两个规划宿主及安装后的执行入口验证同一最终规则与对象，运行正例、危险坏例、缺证例及受影响的旧能力回归，由规定角色提供独立证据，X1 亲读后决定签发。网页端正式打包留待后续。依据：`source-layout`、`planning-entry`、`execution-package`、`q-capacity`、`capability-check`、`web-later`。

这些是获得冻结与实际执行授权后的实施顺序，不表示本次冷读已经开始其中任何工作。

## 3. 阻塞问题

### 1. 尚无 Blueprint 的新任务，首次设计派发绑定哪个对象？

**问题：** 0.1 支持从新任务澄清、派出独立设计者，再得到首份完整 Blueprint。但统一派发规则要求 D2–D8 都绑定“本次受审的 `snapshot_sha256`”，并检查受审文件确实是该快照。首份 Blueprint 尚未产生时，D2/D3 的首次派发，以及可能更早发生的 D4 现实核查，应绑定什么？如果必须先有一份 Blueprint，谁在何时建立它，它包含哪些允许交给独立设计者的内容？

**涉及节点与字段：**

- `state.terminal.mechanism`：`blueprint.draft_ref`、`blueprint.draft_revision`，以及“派发核验，按阶段绑定不同对象”中的 D2–D8 统一快照要求。
- `dispatch.inputs[context].description`、`dispatch.outputs[result].description`、`dispatch.terminal.mechanism`：设计角色的 `based_on` 绑定要求；第 2.3 节的 `D1-clarify`、`D2-D3-design`、`D4-reality` 进入条件；第 2.4 节派发记录形状。
- `freeze.terminal.mechanism` 第 6.5 节：D2–D8 均核对受审 `snapshot_sha256` 的规则。
- `clarify.outputs[result]`、`role-D2.terminal.mechanism`、`role-D3.terminal.mechanism`、`role-D4.terminal.mechanism`：澄清交出需求与事实，由独立设计者交完整 Blueprint，现实核查也可能在完整设计前发生。
- `prompts.terminal.mechanism`：必需身份不能留空，缺值不能输出“可直接执行提示词”。

**为什么阻塞：** “尚无批准”已经有明确处理——设计派发不查批准链；但“尚无受审 Blueprint”是更早的情况，当前规则没有给出对应绑定对象。照统一规则执行，会在首次独立设计前缺少必填身份；直接放行或把任务材料摘要填成 `snapshot_sha256`，又改变了该字段的对象含义。自行增加一份 D1 起草的设计作为强制前置输入，则会改变新任务的调用顺序和独立设计基线。这些选择影响派发接口、结果是否过期的判断和正常启动行为，不能仅作为函数拆分或序列化细节决定。

**可能选项：**

- 规定 D1 在首次派发前创建一份有固定内容范围的起始 Blueprint，明确它的创建时点、最低内容、身份及独立设计者可读范围；D2/D3/D4 绑定它。
- 区分“设计生成或事实核查”和“对既有设计进行检查”：前者绑定明确的任务输入或事实基线身份，后者绑定受审 `snapshot_sha256`；同步明确 `based_on` 与结果过期核验的规则。
- 将新任务入口明确限定为已经带有一份起始 Blueprint 的任务，并规定该输入要求。此选项会收窄当前从新任务澄清起步的入口，需要设计方明确决定。

这里不推荐选项。对于已经存在受审 Blueprint 的任务，这个问题不会触发；但不能据此视为新任务完整链已经明确。

## 4. 实现自由度

- **内部代码组织。** 可自行拆分记录加载、结构验证、引用核对、错误聚合、提示词渲染和身份计算函数，决定内部变量名及辅助模块；保持已定入口、字段含义、退出码与无副作用边界。依据：`record-check`、`prompts`、`minimum`。
- **建议路径下的内部组织。** 蓝图把部分源码位置列为建议，可以在正式实施范围内安排内部文件；须保持唯一源、明确资源根、自包含复制、规划正文与源字节一致及两个执行技能名称。不能借此改变外部入口或市场计数。依据：`source-layout`、`execution-package`。
- **等价的普通维修办法。** 日志、路径、选择器、解析器和运行器怎样修，可以由执行者提出；验收资产变更仍交 X1 审定，并按已定等级校准、重验。选择具体修法无需再决定产品标准。依据：`acceptance`、`revision`。
- **控制例的具体构造与组织。** 可按冻结能力选择具体样本、文件组织及运行顺序，不必为表格机械凑数量；必须保留独立预期、危险坏例和真实缺证例，同一验收实现实际运行，不能改变所验能力或用候选输出生成真值。依据：`contract-controls`、`calibration`、`capability-check`。
- **告知与提示词的具体中文措辞。** 可自然表达任务、影响和下一动作；已定角色、档次、读限、写回位置、必需告知内容及真实发送记录必须完整。依据：`prompts`、`revision`。
- **日常职责内的判断。** D1 可按既定条件决定一般任务是否启用 D3、D4并记录理由；X1 可按触发条件安排 X3/X4/X5、判断普通返修和证据影响范围。这些权力已经分配给角色，插件实现无需另创一套审批；也不能省略用户已启用或条件已触发的角色。依据：`dispatch`、`deviation`、`acceptance`。

不把容量、检查器归属、哈希覆盖范围、小修继承条件、整份签发、撤回权限或宿主不可用时能否降档列为自由度：这些已有明确决定。蓝图尚未冻结、验收尚未运行和实际执行仍须具备授权，也不各自计为设计问题；它们已有规定的关卡和处理路线。

## 5. 结论

**尚不能判定可以完全按既定语义开工，阻塞问题共 1 项：新任务在首份 Blueprint 产生前的派发身份与前置输入规则。**

其余主体接缝已足以排出实施顺序。设计方关闭这一问题后，仍须按蓝图完成四关卡、用户批准、冻结和 X1 接收，才进入插件实现；本次冷读不代表这些关卡或实际宿主验收已经通过。
