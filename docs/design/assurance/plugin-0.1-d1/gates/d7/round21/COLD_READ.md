# D7 冷读报告

本次判断仅依据 `blueprint.json`，包括各节点内嵌的合同。发现 **3 个阻塞问题**，均涉及本插件 0.1 回归验收的具体含义。共用协议、角色职责和打包方案已有明确的实施基础。

## 1. 拟开工顺序

以下是设计补定并完成冻结后的实施顺序。当前蓝图的 `versions` 为空，冻结前的工作范围由 `minimum`、`dispatch` 限定为 D4 现实核查和材料整理。

| 顺序 | 要做的事 | 蓝图依据 |
|---|---|---|
| 1 | D1 先关闭本报告中的设计问题，形成同一受审版本。取得 D5–D8 的有效结果，冻结说明经 D6 检查后交用户批准，再追加版本、运行冻结档检查、写冻结记录。 | `role-D1`、`gates`、`freeze`、`q-checker` |
| 2 | 独立的 X1 线程实际读取冻结包并写接收记录。D1 核对后在最后一次状态提交中切换阶段和写者，X1 回读确认。 | `writer`、`role-X1` |
| 3 | 按补定后的复现规则取得旧问题基线，然后实现共用文件协议、结构定义、模板、身份计算、只读记录检查、派发与结果运输。 | `minimum`、`state`、`writer`、`record-check`、`dispatch`、`prompts`、`contract-regression` |
| 4 | 接入设计端的澄清、独立设计、四关卡、九项合同、冻结与小修继承，复用指定提交的 Blueprint 检查器。 | `clarify`、`design-roles`、`contract`、`gates`、`freeze`、`revision`、`q-inheritance` |
| 5 | 实现交付端的候选、验收资产审查、三类校准、证据、偏离、退回、签发与撤回，并接入三项衡量。 | `delivery-roles`、`acceptance`、`calibration`、`candidate`、`evidence`、`deviation`、`sign`、`metrics` |
| 6 | 创建源入口与共用资源，通过现有生成器生成两个执行包，将预算调整为 12 个插件、32 个技能。网页端由 X2 查明并复用既有打包方法。 | `source-layout`、`planning-entry`、`execution-package`、`q-capacity`、`web-later` |

这与 `minimum.terminal.mechanism` 规定的四个内部工作包顺序一致。开发期按受影响范围复验，最终完整运行后再改代码，就重新完整运行用例集。

## 3. 阻塞问题

### 1. 回归用例的固定输入和部分判定尺子由设计方补齐，还是授权实施者制定

**涉及节点与字段**

- `contract-regression.terminal.mechanism` 第 6.3a 节，规定每个用例具有完整输入、预先写好的尺子，由 D1 在设计阶段写进合同，用例集随合同冻结。
- `capability-check.terminal.mechanism` 第 10.2a 节，以及 `inputs[context].description`、验收器 `v-regression-set.method`，规定使用预先保存的固定快照，完整运行 R1–R7、S1。

**还缺的决定**

当前八项用例给出了场景描述，尚未给出所称固定快照的内容或定位，也未明确实施者可以自行补定哪些验收输入。例如 R5 的“一处产品或科学选择”尚未指定，S1 的三个插件、三条日常请求及受保护的具体输出行为尚未固定，“人看输出是否正常”的判定尺子也未展开。

**为什么阻塞**

R5 选择什么缺口，会决定它是否真的要求设计方决定。S1 选择哪些请求、保护哪些表现，会决定旧能力回归覆盖。执行者若直接补齐这些内容，就同时制定了验收题目和部分判定标准。蓝图已将用例集的制定责任交给 D1，执行者目前无法判断这种补齐的授权范围，也无法区分正常实例化与改写冻结用例。

**可能的选项**

- D1 补齐固定输入、快照或明确定位，给出每条预期与尺子，随合同冻结。
- D1 明确允许实施者实例化的字段、必须保持的覆盖和判定规则，并规定实例化结果由谁在首次运行前确认和固定。

### 2. 本插件真实问题的旧表现，采用历史记录还是要求实施前重新复现

**涉及节点与字段**

- `contract-regression.terminal.mechanism` 第 6.3a 节，要求真实问题先在旧版本复现，复现不出来就不计入。
- `role-X2.terminal.mechanism`、`outputs[result].description`，要求 X2 动手修之前先跑旧问题用例并留下原始输出。
- `capability-check.terminal.mechanism` 第 10.2a 节开头及 `v-capability-check.method.description`，将旧版本定义为不用本插件的现行做法，并规定旧表现以设计过程中当时的记录为准。
- `v-regression-set.method.description` 再次要求实施前复现旧问题。

**还缺的决定**

R1、R2、R3、R5 标注的真实问题，究竟必须重新运行旧做法复现，还是允许用历史原始记录完成旧表现证明。如果允许历史记录，还需明确各检查条目对应哪份记录，以及该记录证明什么。

**为什么阻塞**

两种处理会直接影响用例能否计入和版本能否通过。执行者可能持有历史失败记录，却在重新运行旧做法时没有复现。同一结果按第 6.3a 节应排除，按第 10.2a 节又可能已满足旧表现依据。当前写法不足以确定这里是否有针对本插件的例外。

**可能的选项**

- 保持实施前重新复现的要求，固定可复现的旧做法、输入和运行边界，历史记录作为来源。
- 明确本插件哪些条目可以采用历史原始记录，给出对应定位和适用条件，并同步这些条目的角色要求与验收器要求。

### 3. R2 从已批准状态开始，却要求编写冻结说明，批准应覆盖哪一份说明

**涉及节点与字段**

- `capability-check.terminal.mechanism` 第 10.2a 节 R2，以及 `v-capability-check.method.description`，输入为“四道关卡齐全、用户已批准”的状态，随后要求 D1 写冻结说明并冻结。
- `freeze.terminal.mechanism` 第 6.4、6.4a、6.5 节，及 `inputs[context].description`，要求说明先经 D6 检查，用户批准与冻结记录绑定同一 `explanation_sha256`。
- `role-D6.terminal.mechanism` 规定说明改动后，原说明检查失效。

**还缺的决定**

R2 的输入是否已经包含经过 D6 检查、获得用户批准的完整说明，“写冻结说明”是否仅允许复现同一份字节。如果要在本次运行生成新说明，怎样在一次输入、一次输出的用例约束内取得对新说明的检查和用户批准。

**为什么阻塞**

预置用户批准只能覆盖具体的说明身份。新写说明与已批准说明字节不同，就不能直接完成冻结。若用例只读取或原样复现已有获批说明，它检验的又是获批对象的保存与冻结操作。执行者需要设计方确定 R2 要验哪种行为，才能写出正确的成功预期。

**可能的选项**

- 将说明生成与获批后冻结拆成两个单次场景，各自固定输入和预期。
- 保留一个场景，明确输入已含获批说明，限定本轮复现或使用同一字节，并据此明确 R2 的验收范围。
- 重新规定该场景的固定步骤及批准取得方式，同时说明它如何满足用例的单次执行约束。

R2 还应明确是首次冻结还是大改后冻结，以便确定第 6.4a 节第 10 项“和上次批准相比改了什么”的适用性。

## 4. 实现自由度

- 函数拆分、变量名、内部辅助模块和错误信息的具体组织，可在既定入口、字段含义和权限边界内自行选择。
- Python 的 `rfc8785` 与 JavaScript 的 `canonicalize` 具体版本，蓝图明确允许实施时固定。各端仍须通过规定的逐字节对照例。
- JSON Schema 的内部复用方式、错误汇总顺序和脚本内部结构可自行安排，须保持既定记录种类、必填语义、引用检查范围及退出码。
- 状态写入可使用蓝图允许的普通 Git 提交或带基线校验的文件接口，具体采用现有哪套工具可按授权环境确定，须满足单写者、冲突处理、幂等与回读要求。
- 在固定用例和尺子确定后，测试文件怎样组织、如何自动准备场景、怎样解析和保存输出，属于验收实现细节。
- 共用资源按职责拆分加载、生成器的具体接线及符合既有规范的维护元信息，可由实施者完成。
- 实际任务的仓库、分支、写入范围、线程定位与资源授权，是派发时按合同取得的输入。蓝图已给出缺项时的接收方和停止路线。
- 网页打包方法的来源查找已交给 X2，并有找不到或无法复现时的偏离路线，这项事实查找可以依合同执行。

## 5. 结论

**目前不能按完整既定语义直接开始插件实施，阻塞问题共 3 个。** D1 需补定回归输入与判据的制定边界、旧问题的复现依据，以及 R2 的说明与批准顺序。这些决定会影响正式验收，不能由实现者当作普通代码细节自行选择。

问题关闭后，实施可按第一节顺序推进。当前尚待完成的四关卡、用户批准与冻结属于蓝图已明确的开工门槛，未另计为设计歧义。
