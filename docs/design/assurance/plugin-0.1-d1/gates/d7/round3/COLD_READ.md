## 1. 拟开工顺序

1. **先补齐本文提出的两项决策，再完成冻结和交接。** D1 收敛设计，D5 草稿档、D6、D7、D8 对同一 `snapshot_sha256` 通过后，取得用户批准；追加首个版本，运行 D5 冻结档，确认快照未变，再写包含三个身份的冻结记录。新 X1 实际读取并接收，D1 最后一次状态提交切换写权。依据：`gates`、`freeze`、`writer`、`role-D1`、`role-X1`。冻结前不开始插件实现，这不是可由执行者豁免的条件。
2. **建立共用文件协议和运输基础。** 先完成任务目录、状态及记录结构、模板、修订基线比较、幂等采纳与回读，再接入只读记录检查入口。依据：`minimum` 规定的第一个内部工作包，以及 `state`、`writer`、`record-check`、`source-layout`。
3. **完成调度、提示词和角色资源。** 实现七级优先顺序、角色条件和派发批次，生成无空占位符的完整提示词；补齐十三张角色卡、修订告知与衡量记录。依据：`dispatch`、`prompts`、`design-roles`、`delivery-roles`、`revision`、`metrics`。
4. **接通设计端。** 完成澄清分类、九项合同定位、四关卡结果采纳、批准及冻结接入、小修继承核验。Blueprint 检查器只调用固定提交 `c05edcf51bc93f8be82180fd4ad28a250937f195`，不改上游。依据：`clarify`、`contract` 及其九个子节点、`gates`、`q-checker`、`freeze`、`q-inheritance`。
5. **接通交付端。** 完成候选选择、验收资产审定、三类校准、证据绑定、偏离申报、返修和设计退回，再完成十三项签发核对及签发后的暂停、维持、撤回和重新签发。依据：`acceptance`、`calibration`、`candidate`、`evidence`、`deviation`、`sign`、`writer`。
6. **生成两个插件，并验证真实使用。** 从唯一源生成自包含包，把容量调整为十二个插件、三十二个技能，保留原有能力。先做便宜的结构和已知回归检查，再用稳定最终候选验证两个规划宿主、GPT Work 专业执行角色和安装后 Codex 执行入口，完成实际任务链及必要专业检查。依据：`source-layout`、`planning-entry`、`execution-package`、`q-capacity`、`capability-check`、`contract-fidelity`、`contract-regression`。`web-later` 只交未来打包说明。

以上是条件满足后的实施顺序，不表示本次已经实施、冻结或取得执行授权。

## 3. 阻塞问题

### B1：语义哈希按列举字段计算，还是必须覆盖尚未列入的定义正文？

**涉及节点和字段：** `freeze.terminal.mechanism` 第 6.5 节；`revision`、`q-inheritance`、`dispatch`、`gates` 中重复的哈希规则及相关验收条款。实际承载定义但未被字段清单列入的部分包括各叶节点的 `terminal`，尤其 `terminal.mechanism`、`terminal.acceptance`、`terminal.retry`、`terminal.packages` 等；顶层 `failureQuestions` 也未列入。

**问题：** 规则一方面要求覆盖“整份设计的定义内容”，声称任何定义变化都会改变哈希；另一方面给出的机械投影只列了节点基础字段、验收器定义、需求、连接、走查和失败路径，没有列入 `terminal`。大量实际规则恰好写在那里，例如 `dispatch.terminal.mechanism` 的角色档次表、`state.terminal.mechanism` 的状态字段约束。执行者应以哪一条为准？遗漏字段中的规范性内容是否具有合同效力，怎样纳入核验？

**为什么阻塞：** 严格照字段清单实现，会漏检这些正文的变化；自行把它们加入，则改变已明确指定的哈希接口和批准继承依据。这不是函数怎么拆的问题，而是决定哪些变化能绕过重新审查。这里的例子来自字段清单与正文的直接对照，没有修改文件或运行哈希探针。

**可能的选项：**

- 补齐投影，将 `terminal` 中的定义字段及其他规范性字段明确纳入，并明确其排除项。
- 把所有合同义务移入已覆盖字段，规定未覆盖正文不承载独立义务，并在冻结检查中核对这种约束。
- 改为对完整内容快照作明确的排除式投影，统一规定哪些字段属于进度、运行或出处记录。

### B2：批准哈希核验究竟阻止哪些派发，设计检查与修订怎样合法推进？

**涉及节点和字段：** `dispatch.inputs[context].description`、`dispatch.interface.format`、`dispatch.terminal.mechanism` 和 `terminal.acceptance`；`freeze.terminal.mechanism` 第 6.5 节；`revision`、`q-inheritance` 的继承条件；`gates` 的首次冻结和大改关卡规则；`walkthroughs[walk-source].steps[ws-dispatch].expectedResult`。

**问题：** `dispatch` 的输入把冻结前禁令明确写成“不得派 X2 实施”，源码走查也说“派实施任务前”检查获批哈希；但通用核验条款写的是当前哈希必须等于获批值或沿完整继承链可达，否则“都拒绝派发”。它没有明确限定角色、阶段，以及“当前”指可编辑草稿还是本次派发绑定的冻结对象。需要设计方确定这一授权检查的适用范围。

**为什么阻塞：**

- 首次冻结前没有获批值，却必须先派 D2 和 D5–D8。
- 小修后的新哈希尚无完整继承记录，而该记录本身必须包含新的 D5 结果；若 D5 也受通用禁令限制，会形成循环。
- 大改必须先完成新设计关卡再重新批准，也不能预先满足旧批准的哈希相等条件。
- 交付中要求未受影响的获准工作继续。如果“当前”始终取正在修订的全局草稿，可能连这些工作也一并拒绝派发。

执行者必须决定什么时候允许不具备当前批准链的角色工作，以及继续工作应绑定哪个版本。这会改变派发权限和暂停范围，不能自行当作普通实现细节补上。

**可能的选项：**

- 将批准链检查限定于依据冻结合同开展的实施及交付工作；设计、现实核查和关卡派发按受审快照身份及各自权限检查。
- 保留通用派发检查，但明确首次设计、小修 D5、大改关卡等例外及其可执行动作和恢复条件。
- 明确区分可编辑设计与仍有效的冻结基线，逐派发绑定依据对象；设计检查使用受审对象，未受影响的交付使用其仍有效的冻结对象，并规定各自核验规则。

## 4. 实现自由度

以下事项可以在合同内自行决定，不另列为阻塞问题：

- 共用代码的模块、函数、变量名、内部数据结构和错误信息组织方式；不因此改变已指定的入口、输出字段、退出值或判断含义。
- 把已给出的记录形状落实为 JSON Schema，复用公共定义，设计对应模板及普通解析代码；不得自行增加产品义务或放松必填语义。
- 在既定标识约束下选择派发、结果、候选等编号的生成办法，以及模板的排版、解释措辞和文件内部组织。

- 在五级验收变更规则内维修路径、选择器、解析器或日志；所需审定、校准与受影响项重验不能省略。
- 按蓝图给定触发条件安排具体专业子任务、文件划分和最小调用接缝；不得降低固定档次、独立性或必需角色要求。
- 完成源文件和生成器配置的具体修改方式，以及受影响回归的组织；两个正式名称、自包含资源、源副本一致、十二／三十二容量和旧能力保护均已定。

缺少实际试跑环境、尚待用户授予具体资源权限或某项验收还没有运行，应按蓝图已有的取得、等待或无法判断路线处理；不能据此擅改方法，也不把这些未来运行条件重复算成新的设计选择。
