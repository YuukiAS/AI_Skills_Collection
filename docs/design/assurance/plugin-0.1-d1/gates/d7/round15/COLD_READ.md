## 2. 已经明确的接缝

| 接缝及节点 | 输入 | 输出及接收规则 |
|---|---|---|
| 任务定位，`state` | 用户明确的任务、仓库、分支、任务标识和已绑定目录 | 同一任务的两个入口读取同一份 `STATE.json`。状态修订递增，事件追加到 `history/events.jsonl`，状态写者按阶段唯一 |
| 状态采纳，`writer` | 当前状态修订、文件身份、分支头及角色返回 | 负责人核验后提交并回读。相同返回幂等，不同内容保留冲突，基线变化按受影响范围判断有效性 |
| 记录检查，`record-check` | 明确的任务根、记录种类、记录文件和包内结构 | 只读输出 `assessment/errors/unresolved/checked_files`。退出值 0、1、2 分别表示结构合规、确定错误、无法完成检查 |
| 任务书到独立设计，`clarify`、`role-D2`、`role-D3`、`role-D4` | 不可变任务书及 `brief_sha256`，包括需求、决定、事实和读限 | D2、D3 读取同一任务书并独立交稿，D4 交核查事实。任务书换版后旧结果保留并标为 `stale`，由 D1 判断可用范围 |
| 状态到派发，`dispatch`、`prompts` | 有效状态、固定优先级、角色条件、绑定对象和读写范围 | 完整提示词和派发记录。`prepared`、`sent`、返回及采纳分别记录，必需定位缺失时先补齐 |
| 角色到负责人，`role-D1` 至 `role-X5`、`writer` | 本轮完整派发及允许材料 | 各角色交自己的 `RESULT.json`、自然中文说明及产物身份，负责人读取后决定采纳；派出角色的状态写权受限 |
| 设计到关卡，`contract`、`gates` | 九项合同已定位的稳定 Blueprint 及 `snapshot_sha256` | D5–D8 的原始结果、覆盖和有效性。D7 只读 Blueprint，D8 逐单位复述并保留 `single-thread-batch` 标记 |
| 关卡到冻结，`gates`、`freeze` | 有效四关卡、已关闭的阻塞问题、用户对具体快照的批准 | 不可变 Blueprint 和 `freeze.json`。`snapshot_sha256` 绑定获批内容，`bundle_sha256` 绑定完整冻结文件，`semantic_hash` 支持定义内容及继承核验 |
| 设计到交付，`freeze`、`writer`、`role-X1` | 冻结包、批准、授权及适用的小修继承链 | X1 实际接收记录。D1 核对后切换状态写者，交付角色绑定有效冻结对象 |
| 验收作者到 X1，`role-X2`、`role-X3`、`calibration`、`acceptance` | 冻结语义、验收实现、独立预期及正坏缺证样例 | 原始校准结果和资产变更提案，X1 审定后用于正式验收。科研数值、统计、安全相关及弱验收重写按条件启用 X3 |

## 4. 实现自由度

1. **代码组织。** 可以决定函数拆分、内部模块、变量名、辅助类型和报错代码组织，同时保持规定入口、字段含义、三态结果及角色责任。
2. **结构定义的表达。** 可以选择 JSON Schema 的复用方式、本地注册表组织、错误路径的呈现和报告排序，落实已给字段、枚举、引用及路径边界。
3. **规范化库的具体版本。** `state`、`freeze` 明确允许实施时固定 Python `rfc8785` 和 JavaScript `canonicalize` 的版本，并要求规定的逐字节对照例通过。
4. **资源拆文件和加载组织。** 可以安排共用 Markdown、模板和角色资源的内部拆分及按需读取方式，保持角色读限、同源关系、确认后的资源根和完整派发内容。
5. **编号与文件组织细节。** 可以选用满足任务内唯一性、不可覆盖历史和重复返回幂等要求的编号生成方法，并细化蓝图标为建议的位置。对外约定的入口及记录引用保持可核对。
6. **等价的运输实现。** 可以在已获准的仓库工具能力内落实普通提交、文件 SHA 或预期分支头校验及回读机制，满足规定的基线核验、冲突处理和重试上限。
7. **校准及回归的具体实现。** 可以选择程序结构、夹具组织和样例构造方式。样例依据来自冻结语义及独立参考，覆盖规定能力、危险坏例、缺证和旧行为；X1 按既定规则审定验收资产。

这些自由度的边界由 `revision`、`acceptance`、`contract-changes` 给出。触及需求、接口含义、完成标准、不可替换方法或权限资源边界时，按既定设计修订或授权流程处理。
