# D7 冷读

本次只以 `blueprint.json` 为设计依据，没有读取外部规格、仓库或网页，没有运行探针、检查器或插件。以下判断回答“执行者是否还需要设计方补决定”，不证明蓝图已冻结、插件已实现或验收已通过。

## 1. 拟开工顺序

1. **先完成既定的冻结与交接，再开始插件实现。** 当前 `versions` 为空，文件明确仍是候选。按 `gates`、`freeze`、`q-checker`：D5 草稿档与 D6–D8 共同覆盖同一 `snapshot_sha256`，用户批准该快照，冻结命令追加历史，D5 冻结档核实内容未变，再保存三个身份与冻结记录。随后按 `writer`、`role-X1` 完成独立 X1 线程的实际接收及写权切换。这些是已规定的流程门槛，不是需要重新设计的选择。
2. **建立共用文件协议和运输检查。** 依据 `minimum` 的四个工作包顺序，先实现 `state`、`writer`、`record-check`、`dispatch`、`prompts`、`revision`、`metrics`：任务唯一定位、记录结构、身份算法、单写者、结果幂等、冲突与恢复、完整提示词和衡量记录。先使共用协议有可回读的输入输出，再接两个插件的具体流程。
3. **接入设计端。** 依据 `clarify`、`role-D1` 至 `role-D8`、`contract` 及其九个子节点、`gates`、`freeze`、`q-inheritance`：把澄清结果形成不可变任务书，支持独立设计交回与汇总，接入四关卡、批准、冻结和小修继承。Blueprint 检查器只接固定提交 `c05edcf51bc93f8be82180fd4ad28a250937f195`，不在本任务修改上游。
4. **接入交付端。** 依据 `role-X1` 至 `role-X5`、`acceptance`、`calibration`、`candidate`、`evidence`、`deviation`、`sign`：先打通验收资产审定和三类校准，再绑定最终候选与直接证据，处理返修、设计退回及整份签发后的复核、撤回。
5. **生成包并验证实际使用。** 依据 `source-layout`、`planning-entry`、`execution-package`、`q-capacity`、`capability-check`：从唯一源生成两个自包含包，调整为 12 插件、32 技能，保留原有 10 插件和 30 技能；先做便宜的结构和已知回归检查，再对稳定最终候选取得 GPT 网页端、GPT Work 专业执行任务和安装后 Codex 入口的实际证据。需要 X3/X5 的验收按既定条件派出。`web-later` 所述网页端正式打包留待后续。

## 2. 已经明确的接缝

| 接缝及节点 | 输入 | 输出与责任边界 |
|---|---|---|
| 任务定位 → 当前状态：`state`、`writer` | 已授权任务、仓库、分支、固定任务标识及绑定目录；已有状态的修订号、文件身份和分支头 | 两个入口读取同一 `STATE.json`。设计阶段 D1 写，交付阶段 X1 写；派出角色只交自己的结果。写入前校验基线，写后回读；事件日志不能覆盖当前状态。 |
| 澄清 → 独立设计与现实核查：`clarify`、`dispatch`、`role-D2`、`role-D3`、`role-D4` | D1 写出的不可变任务书，包含需求出处、用户决定、事实、开放事项和读限 | 派发及返回绑定整个任务书的 `brief_sha256`。D2/D3 取得同一任务书且互不读取对方设计；换版后旧结果标为 `stale`，由 D1 判断仍有效的范围。 |
| 调度 → 角色工作 → 采纳：`dispatch`、`prompts`、`writer` | 当前状态、固定优先级、角色档次与线程规则、读取和写入范围、适用身份 | 独立派发目录中的完整提示词与 `RESULT.json`/中文说明。`prepared` 不等于 `sent`，返回不等于采纳；负责人核对身份、实际读写和产物后登记。规划端每角色每轮一条用户转交消息，执行端按阶段负责人派发。 |
| 设计 → 四关卡 → 冻结：`contract`、`gates`、`freeze`、`q-checker` | 九项完成语义明确的设计、同一快照的关卡结果、用户实际批准及授权引用 | `freeze.json` 引用九项合同的位置、四关卡与批准，不复制另一份可变标准。`snapshot_sha256` 绑定受审和获批内容，`bundle_sha256` 绑定冻结输出原始字节，`semantic_hash` 用于定义内容核验和继承链。 |
| D1 → X1：`writer`、`freeze`、`role-X1` | 固定冻结包、批准、授权和 D1 交接记录 | X1 在不同线程实际读取并写接收记录；D1 核对后以最后一次状态写入同时切换阶段和写者，X1 回读后才开始写。交付中的设计修订仍由 D1 决定，当前状态由 X1 原样登记。 |
| 验收作者 → X1：`acceptance`、`calibration`、`role-X2`、`role-X3` | 验收资产版本和差异、冻结准则、独立参考、同一验收实现的正例/坏例/缺证例原始运行结果 | X1 的接受、拒绝或需设计决定记录。诊断、机械修复、等价方法及补充检查有各自条件；改变完成定义须回 D1，不能由验收作者自行准入。 |
| 候选 → 证据 → 签发：`candidate`、`evidence`、`sign` | X1 选定的来源集合、最终对象、构建安装身份、运行环境、数据参数及正式验收资产 | 证据明确 `passed/failed/unknown`、支持范围和有效性；签发映射到同一最终候选的原始证据。X1 亲读产物与关键原始观察，十三项条件满足后对整个冻结范围签发。 |
| 偏离 → 返修或设计修订：`deviation`、`revision`、`q-inheritance` | 实际与冻结要求的差异、原始证据、影响节点和依赖闭包 | 普通故障留在交付任务；五类设计退回交原 D1。小修须满足全部窄范围条件并留下完整继承链，大改重过关卡和批准；只暂停实际受影响的范围。 |
| 异常 → 停止、恢复或撤回：`state`、`writer`、`sign`；`fail-recovery`、`fail-revocation` | 状态丢失、损坏或身份不符，或签发后足以影响结论的新事实 | 状态恢复从历史有效基线与原始记录核对，不能凭日志或记忆选状态；无法核对时保持停止。签发后先暂停声明，再由 X1 决定维持或整份撤回，保留原签发历史，返修后的新签发引用被替代记录。 |
| 唯一规则源 → 各宿主：`source-layout`、`planning-entry`、`execution-package` | 固定源提交或已确认可读的完整包根、源技能与共用资源复制映射 | 两个唯一命名的执行技能及包内规划资料。规划副本与源逐字节一致，不借未安装包或源码目录补资源缺项；各宿主的实际读取和运行分别留证。 |

内容哈希的字节规则也已确定：三个内容哈希使用 RFC 8785 JCS 规范化后的 UTF-8 字节且不加结尾换行，完整文件哈希使用原始字节。`semantic_hash` 的字段排除清单和小修继承规则均已给出，执行者无需自行选择另一种摘要口径。

## 3. 阻塞问题

**本次未发现必须由设计方再决定的阻塞问题，共 0 项。**

以下几处需要按蓝图已有规则实施，没有列成新增问题：

- **当前未冻结。** `minimum`、`freeze` 已明确禁止冻结前实现，以及取得实施依据的顺序。缺少实际关卡、批准和交接记录是当前流程尚未完成，不能据此要求设计方再选择一种开工方式。
- **D8 的旧表述与现行规则。** `dispatch.terminal.mechanism` 第 2.1a 节明确取代旧的逐单位独立读者要求；`role-D8`、`gates` 采用每轮新 GPT 对话合批、逐项判断及 `single-thread-batch` 标记。不需要执行者在两套规则间另选。
- **恢复中的不确定性。** `state`、`writer` 的第 1.3a 节已经规定先停止、查历史、逐条核对原始记录；负责人不能自行选择冲突结果，涉及冻结、批准、签发的交用户，无有效历史状态也须用户确认。仍不能查明的事实不具备恢复派发条件，可以继续保持停止并报告缺项；这里不需要实现者发明自动胜出、自动补登或自动重发规则。
- **依赖或宿主能力尚未实测。** `q-checker` 固定了外部检查器身份，`planning-entry`、`capability-check` 规定实际宿主验证，`fail-role`、`fail-package`、`fail-missing` 给出了能力或证据不可得时的收场。冷读不把这些待取得的证据写成通过，也不以猜测其不可用来增设设计问题。

## 4. 实现自由度

- 在规定源层与生成层边界内，选择内部函数、模块、类、变量名和公共代码的拆分方式；不得因此新增角色、后台服务或第二份权威状态。依据：`source-layout`、`minimum`。
- 选择 JSON Schema 的内部组织、包内本地引用布局、错误收集和展示方式，前提是保留已定字段含义、枚举、路径边界、三态退出语义和只读性质。依据：`record-check`。
- 固定 `rfc8785`、`canonicalize` 的具体版本，组织共享对照例及调用封装；规范化算法、摘要输入和原始文件哈希口径不能自由替换。依据：`state`、`gates`、`freeze`。
- 选择满足基线比较、非强制更新和回读要求的具体读写实现；可以设计内部缓存或辅助函数，但不能扩大读写授权、放宽冲突处理或增加网络重试。依据：`writer`、`prompts`。
- 在完整消息必需内容和角色读限内安排提示词段落、模板复用与普通中文表述，不改变档次、独立性、每轮转交次数或派发责任。依据：`dispatch`、`prompts` 和各角色卡。
- 根据已定能力覆盖选择控制例的具体数据、测试文件名、测试组织及必要数量；样例预期必须来自冻结语义或独立参考，危险坏例和真实缺证例不能退化成只测字段格式。依据：`contract-controls`、`calibration`、`capability-check`。
- 选择日志、解析器、选择器、运行器接线等普通实现细节，并按既定验收资产变更分级交 X1 审查；这不赋予执行者改变阈值、证据真实度、不可替换方法或旧能力的权力。依据：`acceptance`、`contract-changes`。
- 从既有事件与原始记录计算和呈现三项衡量，选择内部去重实现与报告排版；未知归因仍须单列，不能自行新增发布阈值。依据：`metrics`。
