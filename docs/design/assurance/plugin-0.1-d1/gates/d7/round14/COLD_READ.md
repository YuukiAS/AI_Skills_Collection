## 2. 已经明确的接缝

### 当前事实、写权与派发

- `state` → `writer`：输入当前 `STATE.revision`、文件身份、目标分支头和角色返回。设计阶段由 D1 单写状态，交付阶段由 X1 单写；派出角色只写自己的结果。写前核对基线，写后从同一分支回读，重复返回幂等，冲突不按最后写入者获胜处理。
- `writer` → `dispatch` → `prompts`：输入已采纳结果、暂停范围、有效状态及角色条件；按七级优先顺序选首个成立条件，输出完整派发及 `prepared/sent/returned/accepted/stale/cancelled` 状态。准备提示词不代表已经发送。允许并行时，以明确的一批派发交出各角色独立提示词。
- `prompts` → 各角色 → 负责人：完整消息包含准确仓库、分支、写入范围、对象身份、读限、角色卡和写回要求；结果带 `dispatch_id`、`based_on`、实际读写、产物定位、发现与未运行项。负责人核对后才采纳。D7 只收 Blueprint 和最小运输说明，D8 不收答案，X5 不收实现过程或辩护摘要。

### 不同阶段绑定不同对象

| 接缝 | 绑定对象及规则 |
|---|---|
| `clarify` → D2/D3/D4 | D1 写不可变任务书 `design/briefs/<brief_version>.json`；派发绑定整个任务书的 `brief_sha256`。D2、D3 收同一任务书且互不读本轮对方产物。提前派 D4 也先写仅含待核实问题的任务书版本。换版后旧结果标 `stale`，由 D1 判断可继续支持的范围。 |
| `contract` / `gates` → D5–D8 | 绑定受审的 `snapshot_sha256`，首次冻结前不要求已有批准链。 |
| `freeze` → X1 → X2–X5 | X1 接收时核对完整冻结文件的 `bundle_sha256`；交付派发绑定获批的 `semantic_hash`，或经完整合格小修继承链到达的值。草稿不自动成为新的有效冻结对象。 |

`state`、`freeze` 和 `revision` 已给出身份算法：三个内容哈希使用 JCS 规范化后的 UTF-8 字节、不加结尾换行；完整文件的 `bundle_sha256` 使用原始字节。`snapshotOf` 的字段集合、`semantic_hash` 的排除清单和其余字段默认参与的规则均已列出，执行者无需自行决定哪些文字“算语义”。

### 冻结、交接与设计退回

- `gates` → `freeze`：同一受审快照上的四关卡有效、关键问题关闭，再取得用户批准；追加版本与冻结档检查通过后写 `freeze.json`。九项只保存节点/字段定位，不复制另一份可变完成标准。
- `freeze` → `writer` → `role-X1`：X1 先在独立长期线程读包并写接收记录，D1 再同时切换 `phase` 与 `state_writer`，X1 回读后才写状态。
- `deviation` → `revision` → `role-D1`：普通实现、环境与缺证问题留在 X1；命中五类设计退回条件才回原 D1。交付后 D1 仍写设计决定、修订、重开的关卡派发和冻结记录，由 X1 原样登记到状态。受影响范围暂停，其余已获准工作继续。
- `revision` / `q-inheritance` → 交付派发：小修须满足至多两个既有节点等全部窄范围条件，并保留差异、等价理由、新 D5 结果和告知记录；大改重跑四关卡并重新批准，不能借累计小修绕过。

### 验收、候选、证据与签发

- `role-X2` / `role-X3` → `calibration` → `acceptance`：验收实现与独立预期进入同一实现的正例、危险坏例和缺证例运行；X1 读取差异与原始校准记录后审定。X3 的强制触发条件与 X5 的专业判断条件分别明确。
- `role-X2` → `candidate`：X2 交候选提案，只有 X1 能选为当前候选；记录来源集合、最终对象、构建安装映射、运行器、环境和数据参数。内容变化产生新候选，旧记录保留。
- `candidate` → `evidence` → `sign`：证据绑定候选、冻结条款、验收资产、正常入口和实际观察对象；分别记录 `passed/failed/unknown` 与 `current/stale/rejected`。未运行为 `assessment:unknown`，另记 `execution_status:not-run`。X1 按十三项清单亲读后签发整个冻结范围，不能拼接不同候选的局部通过。
- `sign` 的后续复核：新事实出现时先暂停声明并保留原 `release_ref`；X1 写不可变的维持或撤回记录。撤回后清空当前签发引用、使指定证据失效，返修后新签发以 `supersedes` 指向旧签发，旧签发不改写、不删除。

### 检查、恢复、衡量与分发

- `record-check`：输入 `--task-root/--schema/--record/--format`，输出 `assessment/errors/unresolved/checked_files`。退出 0 是结构及可检查引用合规，1 是确定错误，2 是无法完成检查；它不写状态、不执行记录中的命令，也不替负责人判断语义。
- `state` / `writer` 的恢复：发现状态丢失、损坏、检查失败或与远端修订不符，先停止派发和写记录。负责人从历史有效状态、事件及不可变记录恢复；有冲突不自行选择，涉及冻结、批准、签发的交用户。恢复记录和新状态通过检查、远端回读后才恢复派发；没有有效历史则先交用户确认。
- `revision` / `deviation` → `metrics`：用真实问题、退回和告知记录去重统计，归因未知单列，通知模板生成不算实际告知；0.1 没有擅设“零追问、零退回”的发布阈值。
- `source-layout` → `planning-entry` / `execution-package`：四个源入口、一份共用规则和 13 张角色卡生成自包含包。两个新增可调用技能名称固定，包内 `planning/` 不增加市场技能数；规划副本与源字节一致，资源根须明确，不借其他版本补包。
- `web-later` → `capability-check` → X1：网页端打包属于 0.1，X2 查明来源后复用既有方法，找不到或无法复现就申报偏离，不另造方法。X4 在真实网页新对话中完成资源读取、正确下一条提示词及按权限写回或给出内容，保留原始对话，由 X1 签发。

## 4. 实现自由度

在冻结语义、已列字段含义及权限范围内，下列事项可以由执行者决定：

1. 模块和函数拆分、变量名、内部辅助类型、错误信息的具体排版，以及复用内部代码的方式。正常入口、对外记录和职责不随内部组织变化。
2. 将已定义字段落实为 JSON Schema 的具体写法、包内结构注册和检查逻辑的组织方式。依赖版本、Draft 2020-12、格式检查、只读边界及三态含义按 `record-check` 执行。
3. JCS 库的具体版本固定与调用封装。蓝图已指定 Python 和 JavaScript 所用库及跨端字节对照要求，规范化算法和身份覆盖范围不属于自由选择。
4. 在既定唯一性、幂等和历史保留要求内，选取派发、候选、证据等编号的生成方式；在建议布局内安排内部辅助文件。
5. 按已经明确的能力覆盖选取具体控制例、公开安全示例任务与必要回归样本，并编写普通验收实现。样例数量按覆盖确定，但不能因此省略必需角色、三类校准、真实宿主观察或旧能力保护。
6. 对合同内日志、路径、选择器、解析器和运行器作等价维修；是否能纳入正式验收仍由 X1 按五级变更规则审查，不能由代码作者自行准入。
7. 在不改变顺序依赖与读限的前提下安排内部工作项、整理报告索引，以及实施已明确允许的并行派发批次。

这些自由度不包含修改字段含义、哈希覆盖范围、角色档次、独立性要求、阈值、必需方法、宿主验收范围、写权、市场预算或费用权限边界。
