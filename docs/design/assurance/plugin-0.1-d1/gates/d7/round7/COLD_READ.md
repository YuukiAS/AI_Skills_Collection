## 1. 拟开工顺序

蓝图已经给出实施次序。下面先列实施前提，再列冻结后的工作；列出顺序不表示这些动作已经发生。

1. **先完成设计收敛、关卡、批准和冻结。** D1 收敛九项合同，D5 草稿档、D6、D7、D8 对同一 `snapshot_sha256` 检查。全部通过且关键问题关闭后，用户批准这个快照，再追加首个版本，对输出执行 D5 冻结档，确认获批快照未变，最后写入含三个身份的 `freeze.json`。依据：`role-D1`、`contract` 及其九个子节点、`gates`、`freeze`、`q-checker`。当前蓝图明确尚未冻结，不能直接安排 X2 实施插件。
2. **由独立 X1 接收并完成写权交接。** X1 实际读取冻结包、批准与授权，核对 `bundle_sha256` 并写接收记录；D1 最后一次状态提交同时切换 `phase` 和 `state_writer`，X1 回读后接管状态。依据：`writer`、`freeze`、`role-X1`。后续实施仍须有对应仓库、分支、写入范围和资源的实际授权。
3. **先做共用文件协议、模板和运输检查。** 落实唯一任务目录、状态与事件、任务书、派发和返回记录、身份计算、冲突恢复、角色卡与只读记录检查。先把普通正例、确定错误和缺证情形区分开，再接上规划入口。依据：`minimum` 的四个内部工作包，以及 `state`、`writer`、`record-check`、`dispatch`、`prompts`、`metrics`。
4. **再做设计端澄清、关卡与冻结接入。** 将共同任务书、独立设计返回、D1 汇总、D5–D8 派发及结果、用户批准、冻结和小修继承接成一条链。Blueprint 检查器只调用固定提交 `c05edcf51bc93f8be82180fd4ad28a250937f195`，不在本任务修改上游。依据：`clarify`、`role-D1` 至 `role-D8`、`gates`、`freeze`、`q-checker`、`revision`、`q-inheritance`。
5. **随后做交付端候选、验收、返修和签发。** X2 交候选及验收资产提案，验收作者完成三类校准，X1 审定资产并采用候选；按条件启用 X3/X4/X5，取得当前对象的直接证据。补齐偏离处置后，X1 亲读并按十三项清单签发；同时接入签发后暂停、维持或撤回的处理。依据：`role-X1` 至 `role-X5`、`acceptance`、`calibration`、`candidate`、`evidence`、`deviation`、`sign`。
6. **最后生成、安装并验证同一最终包。** 维护四个源入口与共用资源，通过现有生成器产生两个自包含插件；预算调整为 12 个插件、32 个技能，保留原有 10 个插件、30 个技能。两个规划宿主分别消费同源规则，Codex 从安装后的正式执行入口完成角色工作，再做六类能力验收和受影响旧能力回归。依据：`source-layout`、`planning-entry`、`execution-package`、`q-capacity`、`capability-check`、`contract-regression`。网页端只交后续打包说明，依据 `web-later`。

| 调度与角色执行 | 当前状态、角色条件及对应依据身份 → 角色、档次、线程安排、读写范围、预期产物、接收者和完整 `PROMPT.md`；准备只记 `prepared`，实际发送才记 `sent` | `dispatch`、`prompts` |

| 冻结与交付 | 冻结文件、批准、授权、关卡引用 → X1 实际接收；`snapshot_sha256` 绑定内容批准，`bundle_sha256` 核对完整存档，`semantic_hash` 核对交付依据。三种内容哈希的规范化规则及完整文件哈希的例外均已给出 | `state`、`freeze`、`writer` |

只读记录检查的接口也已明确：使用 Python、JSON Schema Draft 2020-12 和指定的 `jsonschema[format-nongpl]==4.26.0`，接受 `--task-root`、`--schema`、`--record`、`--format`，输出 `assessment/errors/unresolved/checked_files`；退出码 0、1、2 分别表示结构及可检查引用合规、确定错误、无法完成检查。它不作业务决定、不写状态，也不执行记录中的命令（`record-check`）。

## 3. 阻塞问题

**未发现需要设计方再作决定的阻塞问题，共 0 项。** 因此本节没有待裁决问题或选项。

以下几处容易被当成未决事项，但蓝图已经给出处理规则：

- **首次设计没有 Blueprint 时绑定什么：** `clarify`、`dispatch`、`prompts` 明确绑定不可变任务书及 `brief_sha256`；D4 提前核查也先取得仅含待核实问题的任务书版本。
- **跨端怎样得到相同内容身份：** `state`、`gates`、`freeze` 明确以 RFC 8785/JCS 的 UTF-8 字节计算内容哈希，不加结尾换行；`bundle_sha256` 单独按完整输出文件原始字节计算。库的具体版本留给实施时固定，并要求跨端逐字节对照。
- **尚无批准时如何派关卡、小修后批准是否有效：** `dispatch`、`freeze`、`q-inheritance` 区分受审快照与有效冻结对象；设计检查不查批准链，交付派发查有效对象，小修用完整合格继承链承接批准。
- **交付中退回设计是否打破单写者：** `writer` 已规定 D1 保留设计决定权，X1 原样登记设计决定、派发与新版本，D1 不直接改交付状态。
- **缺角色入口、资源、原始证据或检查器时怎么办：** `dispatch`、`record-check`、`q-checker`、`evidence` 已规定停止或无法判断的范围、接收者和恢复方式；不能自行降档、改上游、补造证据或替代正常入口。
- **能否部分签发、签发后如何撤回：** `sign` 明确 0.1 只对整个冻结范围签发和撤回；分批交付须在设计阶段拆成独立冻结任务，复核状态及不可变撤回记录也已定义。

当前尚待取得的真实关卡、用户批准、冻结、写权交接和运行授权，是蓝图已经规定的流程前提；它们不构成一组需要重新设计的选项。具体宿主是否可用、检查器能否运行、最终包是否通过验收，本轮没有验证；取得这些证据也不能由本报告代替。

## 4. 实现自由度

下列事项可以由执行者在合同内自行决定：

- 模块、函数、变量、辅助类如何拆分命名，以及内部数据结构和错误收集方式；不改变已经定义的记录字段含义、读写范围、退出码和职责。
- 将蓝图已经列出的字段与约束写成具体 JSON Schema、模板和角色资源的组织方式；普通辅助字段或文件的细化不能改变跨组件合同，也不能把未知值默认为成功。
- RFC 8785 实现库的具体版本固定与对照例的具体取值。蓝图已经指定 Python 使用 `rfc8785`、JavaScript 使用 `canonicalize`，并规定对照例至少覆盖中文、嵌套键排序和整数；无需重新选择规范化算法。
- 状态写入使用宿主现有 Git 或 GitHub 接口的具体适配代码，以及临时文件和回读代码的组织；必须保留基线核对、禁止强推、幂等和有界恢复规则，并服从实际授权。
- 依据既有生成机制细化源码文件布局和复制实现。建议目录不要求临场新增架构；唯一规则源、包内资源完整性、技能名称、市场数量和旧能力保护均须保持。
- 在能力覆盖范围内选择普通测试夹具、坏例内容、缺证注入方式及测试文件组织。样例数量可以按覆盖确定，但关键验收的三类真实校准、独立预期、必要 X3/X5 和同一最终候选要求不能自行取消。
- 完整提示词及中文说明的普通措辞与排版，以及衡量汇总的呈现方式；角色、档次、线程独立性、依据身份、读写清单、实际告知和证据边界必须保留。
- 四个内部工作包以内的低层开发先后与可独立进行的代码工作；蓝图规定的冻结前禁实施、先准入后采用、先接收后切写权、先取证后签发等依赖顺序不属于实现自由度。
