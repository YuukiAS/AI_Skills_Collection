# D7 冷读

## 1. 拟开工顺序

本报告的设计依据为当前 `blueprint.json`，包括其中内嵌的合同、角色卡、验收条款和走查。以下顺序沿用 `minimum.terminal.mechanism` 第 10.1 节的四个工作包，并展开各包的前置条件。

| 顺序 | 拟做的工作 | 蓝图依据与进入条件 |
|---|---|---|
| 1 | 先完成设计冻结与交接，核对实施范围和实际授权。 | `gates`、`freeze`、`writer`、`contract-authorization`。D5 草稿档、D6、D7、D8 覆盖同一受审快照，冻结说明经 D6 检查，用户批准后追加版本，再跑 D5 冻结档，生成冻结记录。X1 实际读取并接收，D1 提交写权切换，X1 回读确认。当前蓝图仍声明未冻结，`versions` 为空，因此当前可继续设计关卡和获准的现实核查，插件实施须等冻结交接完成。 |
| 2 | 建立共用文件协议、结构定义、模板和只读记录检查。 | `state`、`writer`、`record-check`、`source-layout`。先落实唯一任务目录、字段与空值、身份计算、单写者、幂等、冲突及恢复，再让记录检查覆盖规定的记录种类。正式实施还须按 `q-capacity` 加载既有维护插件。 |
| 3 | 实现派发规则、完整提示词和 13 张角色卡。 | `dispatch`、`prompts`、`design-roles`、`delivery-roles`。固定七级优先顺序，落实按角色绑定对象、实际宿主与档次、会话独立性、读写范围、准备与实际发送的区别。 |
| 4 | 接通设计端澄清、独立设计、四关卡、修订与冻结。 | `clarify`、`role-D1` 至 `role-D8`、`contract`、`gates`、`freeze`、`q-checker`、`q-inheritance`、`revision`。D5 接入固定提交的上游检查器，落实首次冻结五步、小修继承、说明身份及说明变动后的复查。 |
| 5 | 接通交付端的候选、验收资产、校准、证据、返修与签发。 | `role-X1` 至 `role-X5`、`acceptance`、`calibration`、`candidate`、`evidence`、`deviation`、`sign`、`metrics`。落实条件角色、五级验收变更、五类设计退回、十三项签发清单、签发后复核与撤回，以及三项衡量。 |
| 6 | 从源层生成执行包与网页端规划包。 | `source-layout`、`planning-entry`、`execution-package`、`q-capacity`、`web-later`。使用现有生成器，调整至 12 插件、32 技能预算并保留原有能力。X2 查明并复用既有网页端打包方法，记录来源。 |
| 7 | 先做便宜的结构与已知回归检查，再用稳定最终候选完成真实宿主验收。 | `capability-check`、`planning-entry`、`web-later`、`calibration`、`sign`。分别观察 Claude Code、GPT Work、GPT 网页端和安装后的 Codex 入口，运行所需控制例及回归，取得必要 X3/X4/X5 结果。X1 亲读最终产物与原始证据，逐项满足签发条件后交付。 |

## 2. 已经明确的接缝

| 组件接缝 | 输入 | 输出及接收约束 |
|---|---|---|
| 任务定位与状态写入，`state` → `writer` | 已确认的任务目录、仓库、分支、当前 `revision`、文件身份和分支头。 | 唯一 `STATE.json`。设计阶段由 D1 写，交付阶段由 X1 写。写前核对基线，写后回读。事件追加到 `history/events.jsonl`，状态事实以 `STATE.json` 为准。 |
| 记录与只读检查，`record-check` | 明确的任务根、记录种类、记录文件，以及包内预注册结构。 | `assessment/errors/unresolved/checked_files` 和退出码 0、1、2。分别表示检查完成且符合规则、存在确定错误、证据或依赖不足。入口只核对结构及已声明引用，语义决定交负责人。 |
| 澄清与独立设计，`clarify` → `role-D2` / `role-D3` / `role-D4` | D1 生成的不可变任务书，含带出处需求、已有决定、事实、开放事项和读限。 | 派发及结果绑定整个任务书的 `brief_sha256`。D2、D3 使用同一任务书且互不读本轮设计产物。任务书换版使旧结果变为 `stale`，D1 判断仍可支持的范围。 |
| 状态与角色派发，`dispatch` → `prompts` → 各角色 | 当前状态、成立的优先条件、角色档次、宿主、线程规则、材料定位及写入范围。 | 每角色独立的完整提示词和派发记录。实际发送后才记 `sent`。需用户转交的角色每轮最多一条，执行端按档次表进入 Codex、GPT Work 或指定插件宿主。 |
| 角色返回与采纳，各角色 → `writer` | 带 `dispatch_id`、`based_on`、实际读写、产物身份、发现和未运行项的结果。 | 负责人核对后登记有效结果。相同返回幂等，不同内容保留冲突。过期结果保留来源及适用边界。 |
| 设计与关卡，`contract` → `gates` | 九项合同已在蓝图中表达的稳定设计及 `snapshot_sha256`。 | D5–D8 结果绑定受审快照。D7 只收到蓝图及最小运输信息。D8 每轮新 GPT 对话合批，保留文字身份及 `single-thread-batch`，由 D1 逐单位判断。 |
| 批准、冻结与接收，`freeze` → `role-X1` → `writer` | 有效关卡、用户批准、冻结说明身份和授权依据。 | 冻结记录保存九项定位、关卡引用及四个身份。内容身份按 JCS 计算，完整冻结文件和说明按原始字节计算。X1 核对并实际接收后，D1 完成状态写权切换。 |
| 验收资产与正式采用，`role-X2` / `role-X3` → `calibration` → `acceptance` | 验收实现、版本差异、冻结准则、独立参考及正坏缺证例。 | 同一实现的实际校准结果与 X1 审定记录。X1 审定后才能替换正式验收引用。改变完成定义的提案交回 D1。 |
| 候选、观察与签发，`candidate` → `evidence` → `sign` | X1 选定的候选，包含来源集合、最终对象、构建安装映射、运行器、环境及数据参数。 | 对应同一最终候选的三态证据和逐项准则映射。必需项失败、未知或失效时保持未签发；满足条件后由 X1 对整个冻结范围一次签发。 |
| 交付问题与设计修订，`deviation` → `revision` → `role-D1` | 预期与实际差异、原始证据、影响节点及已尝试的合同内处理。 | 普通返修留在 X1；命中五类设计退回条件时回原 D1。受影响节点及依赖闭包暂停，其余获准范围继续。小修继承记录完整后才启用新有效冻结对象，大改须重新批准。 |
| 恢复与重新派发，`state` / `writer` / `record-check` | 历史有效状态、基线之后的事件及对应不可变记录。 | 新状态和不可变恢复记录。普通冲突采用既定的保守处置，相关派发标 `stale`，新编号重派并披露原有写入。冻结、批准、签发、撤回冲突或无法安全重派的情况交用户，暂停其影响范围。检查并远端回读后恢复其余派发。 |
| 同源分发与宿主观察，`source-layout` → `planning-entry` / `execution-package` / `web-later` | 固定来源的规划正文、共用资源、执行入口和复制映射。 | 两个自包含执行插件及网页端规划包。两个执行技能各有唯一名称，包内规划资料与源文件字节一致。网页端由 X4 留下读取、生成提示词、按权限写回或给出内容的三项原始对话证据，交 X1 判断。 |

## 3. 阻塞问题

**阻塞问题共 0 项。** 根据蓝图内的具体合同，未发现必须由设计方再选择产品行为、科研或验收语义、接口、权限或资源边界才能实现的事项。

以下事项已有处理规则，可按既定合同推进。

- **冻结与实际执行授权尚待取得。** `freeze.terminal.mechanism` 第 6.4–6.5 节和 `contract-authorization` 已给出冻结顺序、批准对象、交接及授权要求。当前处于设计检查阶段，后续按这些进入条件推进。
- **上游检查器是否可运行。** `q-checker`、`gates` 和 `fail-checker` 已指定固定提交、调用归属及无法完成时的接收方。实施者取得该依赖并记录实际结果，失败时按规定交 D1 处理。
- **网页端既有打包方法的具体位置。** `web-later.terminal.mechanism` 已将来源查找和复现交给 X2，并规定找不到或无法复现时申报偏离交 X1。方法选择已固定为复用既有方法，当前没有留给实施者的替代方案裁决。
- **恢复冲突如何取舍。** `state`、`writer` 的第 1.3a 节及 `fail-recovery` 已规定普通冲突的唯一保守处置、原始记录保留、重派写入披露、用户决定边界和暂停范围。
- **宿主、档次、线程或写权限不足。** `dispatch` 第 2.1–2.1a 节、`prompts`、`fail-role` 和 `web-later` 已给出等待、补材料、人工转交及网页端无写权限时交出内容的路径。
- **依赖大小及后续费用。** `freeze` 第 6.4a 节与 `contract-authorization` 已规定大小未记录时如实披露，首次下载或安装前记录实际大小，单项超过 100 MB 先取得用户授权。付费调用的预算、数据和恢复范围在实际任务首次调用前授权。

这些路径中的实际输入与观察仍须在后续执行时取得。

## 4. 实现自由度

- **内部代码组织。** 可自行安排函数拆分、变量命名、模块组织、错误收集与报告排版，保持 `record-check` 的命令参数、只读范围、输出字段和三态含义。
- **结构定义与模板的具体写法。** 可把已列明的字段、类型、枚举、空值、路径及引用规则落实为 Draft 2020-12 结构和模板，补齐字段描述与错误提示。具体依据在 `state`、`record-check`、`prompts` 及各记录节点。
- **哈希库的具体版本。** `state`、`gates`、`freeze` 已明确 Python 使用 `rfc8785`、JavaScript 使用 `canonicalize`，具体版本可在实施时固定，并按合同提供跨端逐字节对照例。记录检查依赖采用已指定的 `jsonschema[format-nongpl]==4.26.0`。
- **验收实现的代码与样例组织。** `acceptance`、`calibration`、`capability-check` 允许作者编写运行器接线、选择器、解析器及报告生成，按实际能力覆盖组织正例、危险坏例和缺证例。预期结果依据冻结语义及独立参考，资产变更按既定级别交 X1 审查。
- **生成配置的落地细节。** 可在既有生成机制中安排配置顺序、复制接线及相称回归，落实 `source-layout`、`execution-package`、`q-capacity` 已规定的目录关系、唯一技能名称、字节一致性和容量预算。
- **角色工作的文件划分。** X2 可在明确派发范围内拆分普通实现与专业子任务的文件和接缝，提交候选提案及验收资产提案；X1 按 `role-X2`、`candidate`、`acceptance` 的职责采纳。
- **普通展示与措辞。** 在固定字段、必要信息和冻结说明骨架下，可自行选择自然中文表述、表格布局及附录组织。D8 合批顺序的随机化实现可自行安排，并保留实际顺序、文字身份与轮次记录。

## 5. 结论

蓝图已给出可执行的职责、输入输出、判断规则和异常处理路径。完成既定冻结、交接及实际授权后，执行者可以按既定语义开工。

**阻塞问题数量为 0。** 当前 `versions` 为空，插件实施的进入条件仍须按 `gates`、`freeze` 和 `writer` 完成。本报告给出 D7 的设计冷读判断，其他关卡、宿主运行和产品验收的实际结果由各自后续记录承载。
