# D7 冷读

本报告仅依据当前 `blueprint.json`。蓝图仍是待审候选，插件实施以完成冻结和取得实际执行授权为前提。以下列出按蓝图准备实施时仍需设计方决定的事项。

## 1. 拟开工顺序

1. **先由 D1 关闭本报告中的阻塞问题，再固定受审快照。** 依据 `clarify`、`role-D1`、`contract`、`gates`。涉及协议含义的补定进入 Blueprint，随后按修订规则确定关卡有效范围。
2. **完成关卡、批准和冻结，再交接写权。** 依据 `freeze`、`gates`、`q-checker`、`writer`。首次冻结依次完成同一 `snapshot_sha256` 上的 D5 草稿档及 D6–D8、用户批准、追加首版、D5 冻结档复核、写入含三个摘要的 `freeze.json`。检查器接入固定提交 `c05edcf51bc93f8be82180fd4ad28a250937f195`。X1 在独立线程实际接收后，D1 最后一次状态提交切换 `phase` 和 `state_writer`，X1 回读后接手。
3. **实施共享文件协议、模板和记录检查。** 依据 `minimum`、`state`、`writer`、`record-check`、`dispatch`、`prompts`、`metrics`。先形成状态与结果记录、写入基线检查、幂等采纳、事件追加和完整派发，再接后续流程。涉及状态越权和安全边界的验收按 `capability-check` 启用 X3。
4. **实施设计端。** 依据 `design-roles`、`clarify`、`contract`、`gates`、`freeze`、`revision`、`q-inheritance`。把角色读写限制、澄清、四关卡、批准绑定及修订继承接入共同协议。
5. **实施交付端。** 依据 `delivery-roles`、`acceptance`、`calibration`、`candidate`、`evidence`、`deviation`、`sign`。串起候选提案、验收资产审定、三类校准、当前对象取证、返修和签发，并落实下文要求补定的交付状态转换。
6. **生成两个包，再从实际宿主验完整任务链。** 依据 `source-layout`、`planning-entry`、`execution-package`、`q-capacity`、`capability-check`。沿用生成器，把预算调为 12 个插件、32 个技能，保留既有能力。两个规划宿主和安装后的执行入口分别使用同一最终规则版本，完成正常链、坏例、缺证例及相关回归，再由 X1 按十三项清单判断交付。

## 2. 已经明确的接缝

| 接缝及节点 | 输入 | 输出与接收方 |
|---|---|---|
| 任务定位进入共同协议，`state` | 用户给出的任务、仓库、分支、任务标识和绑定目录，以及已有状态 | 同一任务唯一的 `STATE.json`，默认位于 `docs/assurance/<task_id>/`，两个插件共享 |
| 状态与结果采纳，`state` → `writer` | 状态修订号、文件身份、分支头，以及带派发和设计身份的角色返回 | 有基线校验且回读确认的状态更新，冲突、过期与待写记录保留 |
| 下一步进入提示词，`dispatch` → `prompts` | 当前有效状态、固定优先级、角色及档次、线程模式、材料和读写范围 | 一条下一动作或明确可并行的一批动作，每个角色各有完整提示词和独立写回位置 |
| 角色返回进入负责人，`role-D2` 至 `role-D8`、`role-X2` 至 `role-X5` → `writer` | 各角色在允许范围内取得的产物和观察 | `RESULT.json`、自然中文说明和原始产物定位，负责人核对身份后采纳 |
| 设计进入交付，`freeze` → `role-X1`、`writer` | 不可变 Blueprint、九项定位、四关卡、用户批准、执行授权和三个摘要 | X1 实际接收记录，以及 D1 确认接收后的一次写权切换 |
| 验收实现进入正式使用，`role-X2`／`role-X3` → `calibration` → `acceptance` | 验收资产版本、独立预期、正例、危险坏例和缺证例 | 同一实现的实际校准记录及 X1 审定，审定后才能成为正式验收引用 |
| 最终对象进入证据，`candidate` → `evidence` | X1 选定的候选、来源集合、构建或安装身份、数据参数及运行器 | 对应当前对象的原始证据，结论为 `passed/failed/unknown`，并注明支持范围和有效性 |
| 偏离进入返修或设计，`deviation` → `revision` | 实际差异、原始证据、影响范围和已尝试的处理 | 普通缺陷留在交付端，命中五类条件时交原 D1，暂停受影响范围及依赖 |
| 源规则进入安装包，`source-layout` → `planning-entry` → `execution-package` | 四个源入口、一份共用资源和复制映射 | 两个自包含插件，各暴露一个唯一命名的执行技能，包内另带同源规划资料 |

三个摘要各有明确用途。`snapshot_sha256` 绑定用户批准和冻结前关卡，`bundle_sha256` 绑定冻结后的完整文件，`semantic_hash` 用于语义版本、小修判断及交付派发核验。下文第一个问题涉及最后一项的覆盖完整性。

## 3. 阻塞问题

### B1. 九项合同引用的详细义务怎样进入语义身份

**涉及节点和字段**

`freeze.terminal.mechanism` 第 6.4–6.5 节，`revision.terminal.mechanism`，`q-inheritance.terminal.mechanism`，九个 `contract-*` 节点的定义字段及验收器定义字段，以及 `dispatch.terminal.mechanism`、`sign.terminal.mechanism` 等详细规则。

**需要设计方决定的问题**

第 6.5 节要求所有完成义务写入或明确引用到九个合同节点，同时把哈希输入限定为这些节点的指定字段和所引用需求全文。对于引用到其他节点的详细条款，是否还需要固定其目标内容，怎样固定？

当前九项合同已有概括性承诺，其验收器定义也重复了这些承诺。不过，详细的角色档次、线程规则和十三项签发条件分别写在 `dispatch`、`sign` 等节点中。所列哈希算法没有说明展开这些目标节点的内容，也没有要求把目标内容摘要放入九项合同的被哈希字段。例如，仅改变 `dispatch` 中 D6 的具体档次，按所列取值范围，九项投影可以保持相同。

**为什么阻塞**

`revision` 已把角色责任、接口等实际语义变化判为大改，这一人工判断规则明确。仍需补定的是它与“用 `semantic_hash` 机械判断语义版本、核验派发”的关系。执行者需要知道哪些详细条款必须影响该身份，才能实现合同完整性检查和派发核验。自行扩展哈希范围，或自行认定概括性引用已经覆盖全部条款，都会决定冻结身份与验收规则。

**可能的选项**

- 保持已列哈希范围，将完整义务或其固定内容身份纳入九项节点的被哈希字段，并明确定位规则。
- 规定引用解析与传递覆盖规则，让指定目标条款参加投影计算。
- 明确 `semantic_hash` 只标识有限投影，另行定义详细条款变化时的语义版本及派发核验规则，并调整当前完整性要求。

### B2. 独立单元签发后，整个任务处于什么状态

**涉及节点和字段**

`sign.terminal.mechanism` 的独立单元签发规则与签发后状态转换，`sign.outputs`，`state.terminal.mechanism` 中的 `phase`、`delivery.candidate_id`、`delivery.release_ref`，以及 `dispatch.terminal.mechanism` 的下一步选择。

**需要设计方决定的问题**

合同预先划分独立交付单元时，签发其中一个单元后，如何表示已交付部分与剩余义务，什么时候才将整个任务的 `phase` 设为 `delivered`？

`sign` 明确允许签发合同预先划定的完整合格单元。状态表把 `phase` 的变化写为“X1 签发后”，签发节点又要求回读后进入 `delivered`。现有 `delivery` 形状给出单个当前候选和单个签发引用，尚未说明多单元完成情况如何进入当前权威状态。

**为什么阻塞**

假设合同有两个独立单元，第一单元已满足全部条件，第二单元仍在返修。执行者必须决定此时能否结束任务、下一步还应派谁，以及如何防止第一份签发被理解成整个冻结范围完成。这会改变完成语义和调度行为。

**可能的选项**

- 0.1 只支持整个冻结范围一次签发，并相应收窄独立单元条款。
- 同一任务保留各单元的候选、证据和签发状态，全部必要单元完成后才进入任务级 `delivered`。
- 将各独立单元绑定到明确的独立任务状态，并定义共同冻结合同与各任务完成的关系。

### B3. 签发被后续事实推翻时，当前有效交付结论怎样撤回

**涉及节点和字段**

`sign.terminal.mechanism` 最后一段及签发记录形状，`state.terminal.mechanism` 中的 `phase`、`step`、`delivery.release_ref`，`evidence.terminal.mechanism` 的 `validity/invalidated_by`，以及 `record-check.terminal.mechanism` 的记录种类与引用检查。

**需要设计方决定的问题**

已进入 `delivered` 的任务出现真实失败时，撤回由谁决定、作用于哪份签发和哪些范围、保存什么记录，当前状态怎样重新进入返修，以及重新签发前旧交付声明的有效性怎样表达？

蓝图已要求保留原签发历史、另加撤回或返修记录，并要求 X1 按冻结标准处理用户指出的真实失败。证据层也已有失效字段。签发记录及当前状态尚未给出与之对应的撤回关系和恢复规则，记录检查入口也没有明确撤回记录由哪种结构承载。

**为什么阻塞**

只追加一条返修说明后，当前状态仍可能指向原签发并保持 `delivered`。直接把它改回 `delivery`，又需要确定哪些原签发范围仍有效、哪些证据必须重验，以及旧声明的撤回何时生效。执行者自行选择会改变对用户的交付承诺和后续派发。

**可能的选项**

- 由 X1 作出显式撤回决定，记录被撤回签发、影响范围和原因，同时更新当前状态并重开返修。
- 保留原签发为历史事实，通过新的有效性记录标识当前失效范围，并规定调度和重新签发如何读取该记录。
- 由 X1 先登记待复核事实、暂停相关交付声明，再依冻结标准作出维持或撤回决定，并明确各阶段的状态转换。

## 4. 实现自由度

- 函数拆分、模块组织、变量名、内部辅助类型，以及不改变入口和职责的代码复用。
- 将已明确的字段、枚举、空值规则和身份约束落实为 JSON Schema，选择可读的报错布局。
- 在既定写权、基线校验、回读和重试上限内，安排文件写入与提交步骤，保证部分失败可恢复、重复采纳幂等。
- 按既定覆盖义务选择具体正例、危险坏例、缺证例及回归样本，保留独立预期和真实样本身份。
- 在允许范围内安排内部工作包的具体编码次序、测试夹具和便宜检查的运行顺序。
- 选择提示词的自然中文措辞和版式，同时保留角色、档次、线程规则、读写边界、运输信息和完成标准。
- 在建议源目录布局内组织支持资料并接入既有生成器，保持约定技能名、包结构、资源可读性和副本字节一致。
- 依已规定条件由负责人决定 D3、D4、X3、X4、X5 的实际派发，记录依据；具体任务的仓库、授权和资源参数在该任务初始化时绑定。

## 5. 结论

**目前不能按完整既定语义开工，阻塞问题共 3 个。** 需要设计方补定语义身份的详细条款绑定、独立单元交付的任务状态，以及签发撤回后的当前有效结论与恢复规则。

共享协议、角色分工、首次冻结顺序和打包路线已有明确依据。上述三处补定后，才能据此实现一致的合同核验、任务调度和交付状态。
