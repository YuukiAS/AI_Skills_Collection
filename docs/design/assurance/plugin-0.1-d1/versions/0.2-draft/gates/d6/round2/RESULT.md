## 本轮新增 blocking

### B1 — freeze-review 的角色摘要把批准权写给了 D1

fr-roles 的角色分工摘要写成“D1 负责澄清、汇总、四关卡和批准冻结”。这与 role-D1 正文的“不代用户批准”“取得用户批准并冻结”，以及 fr-decisions / c-gates-to-freeze 中“用户批准 snapshot_sha256”直接矛盾。

**影响：** freeze-review 是用户直接阅读并批准的载体，这处转述会让批准决定权不唯一，属于冻结边界问题。

**关闭条件：** D1 机械改写 fr-roles，使其明确保持“D1 负责取得用户批准并执行冻结；批准者仍是用户”的原设计语义，不改变既有决定权。

### B2 — 新增整体完成条件把 D7 同时写成冷读关卡和回归执行者

gates 关卡表、role-D7.description 和 wr-gates.action 都把 D7 定义为“新执行者只读 Blueprint，列出开工前阻塞并判断能否直接开始已定工作”。但新增的 gates“本轮整体完成条件”、wr-gates.expectedResult 和 wr-gates.technical.expectedResult 又要求“D7 全部 9 个回归用例通过”。提示词同时明确说明实际回归仍未运行。

**影响：** 当前无法唯一解释 D7 的完成证据：它既被要求产出冷读开工结论，又被要求承担其角色定义中不存在的产品回归结果。这样会导致冻结条件误判或无法满足。

**关闭条件：** D1 将 D7 的整体完成条件改回与其角色一致的冷读通过语义；9 个回归用例的真实执行与通过应继续由 Blueprint 中实际负责该回归的机制承载，D6 不替 D1 猜测或重分配负责人。
