## 你的唯一任务

分别用自己的话复述每个单位的五件事：

1. 在做什么；
2. 拿到什么；
3. 交出什么；
4. 为什么这样；
5. 出错怎样。

然后判断是否存在真正会导致实际行为理解不同的歧义。

### confusion 只允许在以下情况出现

只有满足至少一项才记 `confusion`：

- 两种合理理解会导致不同执行角色；
- 会导致不同决定权归属；
- 会导致不同输入或输出；
- 会导致不同推进/暂停条件；
- 会导致不同通过条件；
- 会导致不同失败去向；
- 会导致不同用户动作；
- 不猜测就无法完成上面五点中的至少一点。

以下**不算 confusion**：

- 没写 JSON 字段名；
- 没写内部状态枚举；
- 没写日志结构；
- 没写具体文件格式；
- 没写保存路径；
- 没写任务书 schema；
- 没写时间戳、哈希字段或内部 ID；
- 没写具体实现代码怎样组织；
- 只是“还想知道更多细节”；
- 普通中文词还能进一步下定义，但上下文已经足够确定实际行为。

D8 不是设计审查。不要因为某个实现细节没展开就报疑惑。只要能正确理解“谁在什么条件下做什么、产生什么、失败怎么办”，就应当令 `confusions=[]`。

不要评价设计好不好，不提出修改建议，不搜索外部资料，不打开 GitHub 读取设计正文。

## 单位 1：`wr-gates`

round: 2

textHash: `500174474fd726b34ba5ba2fadcdcbe675c367764e2c688adceadaaec088b00b`

```text
这一步：完成四道冻结关卡

四道关卡分别是：
1. 结构检查；
2. 用户代理追问：站在用户角度逐个组件检查设计有没有把必要问题回答清楚；
3. 冷读：让一个没有参与设计的新执行者只看设计，判断是否已经能直接开工；
4. 读者复述：让新读者用自己的话复述每个必要步骤，检查文字有没有把已经确定的设计意思传错。

在做什么：
负责人在冻结前，让四道关卡都针对同一份当前设计完成检查。“冻结审阅”七部分也属于设计本身，因此同样接受用户代理追问。

拿到什么：
拿到当前设计，以及结构检查、用户代理追问、冷读和本轮读者复述各自的真实结果。验收器数量、回归数量和分类等机械统计直接从设计生成；角色档次直接引用正式角色表，不另外人工改写一份。

交出什么：
交出同一份设计上四道关卡各自的有效结果。只有结构检查、用户代理追问、冷读都已通过，并且设计负责人逐项确认本轮所有读者复述都正确，四道关卡才算整体完成，设计才能进入后续冻结步骤。

为什么这样做：
四道关卡分别检查结构、用户缺口、能否直接开工和文字能否被正确理解，不能用其中一道替代另一道。

出错怎样：
任一道关卡没有通过，四道关卡就没有整体完成。某段复述错误时，改写相关文字，并在下一轮全新读者对话里重新读改动单位以及与它属于同一步骤或同一失败路径的必要单位；旧文字的复述通过记录不能继续沿用。真正设计缺口没有关闭时也不能进入冻结。
```

## 单位 2：`supp-clarify-0.2`

round: 2

textHash: `a9cf3cc8cbbcf580e3ab6e32b7f0755c18f2728a2e5821e19505a70dff043cab`

```text
这一步：把需求问清楚

在做什么：
设计负责人先把尚未确定的事情分成三类。

第一类是只有用户能决定的偏好、范围、风险或授权，这类问题才问用户。

第二类是能够从仓库、资料或工具里查到的事实，这类问题由负责人自己查，必要时派执行角色去查，不让用户代查。

第三类是设计者本来就应该负责的普通技术选择，这类问题由负责人自己决定并写明理由，也不让用户替设计者做决定。

真正需要用户回答的问题会按依赖关系组织起来。某一轮只提出那些前提已经确定、现在已经可以回答的问题；这些问题彼此不依赖时，就在同一轮一次问完。依赖这一轮其他答案的问题等到下一轮再问。

每一道用户问题都单独编号，并附上负责人推荐的答案和一句理由；每一道题都单独接受回答，“是”表示接受该题的推荐，不用用户重新复述推荐内容。

拿到什么：
拿到用户原始需求、此前仍然有效的用户决定、可以自行查证的事实来源，以及目前还需要决定的问题。

已经回答过而且前提没有变化的问题不会重复询问。如果后来出现新事实，使旧回答赖以成立的前提失效，负责人会保留旧回答用于追溯，说明为什么这个问题需要重新打开、会影响什么，然后再次请用户决定。

交出什么：
澄清结束后，后续设计者拿到一份明确的设计输入：包括用户真正作出的决定、已经核实的事实，以及设计负责人自行作出的技术选择和理由。每个用户决定都和产生它的实际问题及回答记录关联，后续可以追溯来源。

只有所有会影响当前设计的用户决定都已经完成，设计负责人没有未经说明替用户作出的选择，并且用户确认当前需求和取舍已被正确理解，才进入正式设计。尚未查清的事实可以按既有规则作为明确的开放事项继续存在，但如果这个事实还是某个会影响当前设计的用户决定的前提，就必须先查清事实、再取得该用户决定，不能因为当前暂时没有可问的问题就提前结束澄清。

为什么这样做：
这样既不会把能自己查的事情和设计者应该负责的技术选择甩给用户，也能把同一轮已经可以决定的问题一起问掉，减少“问一个、答一个、再想到下一个”的反复往返。

出错怎样：
如果某个问题还依赖一个尚未查清的事实，只暂停这个问题；其他已经具备前提的问题仍然继续询问。如果这个被暂停的问题最终会影响当前设计，就不能在它仍未解决时结束澄清。仍有需要用户决定的问题没有处理，或者负责人偷偷替用户做了尚未授权的选择，都不能进入正式设计。新事实推翻旧决定的前提时，要说明原因和影响后重新询问，而不是继续默认旧决定有效。
```
