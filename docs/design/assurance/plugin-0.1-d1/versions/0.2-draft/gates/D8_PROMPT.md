### confusion 只允许在以下情况出现

只有满足至少一项才记 `confusion`：

- 两种合理理解会导致不同执行角色；
- 会导致不同决定权归属；
- 会导致不同输入或输出；
- 会导致不同推进/暂停条件；
- 会导致不同通过条件；
- 会导致不同失败去向；
- 会导致不同用户动作；
- 不猜测就无法完成上面五点中的至少一点。

以下**不算 confusion**：

- 没写 JSON 字段名；
- 没写内部状态枚举；
- 没写日志结构；
- 没写具体文件格式；
- 没写保存路径；
- 没写任务书 schema；
- 没写时间戳、哈希字段或内部 ID；
- 没写具体实现代码怎样组织；
- 只是“还想知道更多细节”；
- 普通中文词还能进一步下定义，但上下文已经足够确定实际行为。

D8 不是设计审查。不要因为某个实现细节没展开就报疑惑。只要能正确理解“谁在什么条件下做什么、产生什么、失败怎么办”，就应当令 `confusions=[]`。

不要评价设计好不好，不提出修改建议，不搜索外部资料，不打开 GitHub 读取设计正文。

## 单位 2：`supp-clarify-0.2`

round: 2

textHash: `07655582b8a0c486605d9a999f96ecf24a925a1c400d70710011e86b64f7bde1`

```text
这一步：把需求问清楚

在做什么：
设计负责人先把尚未确定的事情分成三类。

第一类是只有用户能决定的偏好、范围、风险或授权，这类问题才问用户。

第二类是能够从仓库、资料或工具里查到的事实，这类问题由负责人自己查，必要时派执行角色去查，不让用户代查。

第三类是设计者本来就应该负责的普通技术选择，这类问题由负责人自己决定并写明理由，也不让用户替设计者做决定。

真正需要用户回答的问题会按依赖关系组织起来。某一轮只提出那些前提已经确定、现在已经可以回答的问题；这些问题彼此不依赖时，就在同一轮一次问完。依赖这一轮其他答案的问题等到下一轮再问。

每一道用户问题都单独编号，并附上负责人推荐的答案和一句理由；每一道题都单独接受回答，“是”表示接受该题的推荐，不用用户重新复述推荐内容。

拿到什么：
拿到用户原始需求、此前仍然有效的用户决定、可以自行查证的事实来源，以及目前还需要决定的问题。

已经回答过而且前提没有变化的问题不会重复询问。如果后来出现新事实，使旧回答赖以成立的前提失效，负责人会保留旧回答用于追溯，说明为什么这个问题需要重新打开、会影响什么，然后再次请用户决定。

交出什么：
澄清结束后，后续设计者拿到一份明确的设计输入：包括用户真正作出的决定、已经核实的事实，以及设计负责人自行作出的技术选择和理由。每个用户决定都和产生它的实际问题及回答记录关联，后续可以追溯来源。

只有所有会影响当前设计的用户决定都已关闭、没有未经说明替用户作出的选择，并且用户确认当前需求和取舍已被正确理解，才进入正式设计。依赖未核实事实、但会影响当前设计的用户决定，进入设计前必须关闭；若用户明确接受以假设推进，则记入假设清单，逐项记录假设内容、用户接受依据、核实负责人和核实时点，并在冻结审阅时逐条复查，不能因为当前暂时没有可问的问题就提前结束澄清。

为什么这样做：
这样既不会把能自己查的事情和设计者应该负责的技术选择甩给用户，也能把同一轮已经可以决定的问题一起问掉，减少“问一个、答一个、再想到下一个”的反复往返。

出错怎样：
如果某个问题还依赖一个尚未查清的事实，只暂停这个问题；其他已经具备前提的问题仍然继续询问。被暂停的用户决定若会影响当前设计，进入设计前必须关闭；用户明确接受以假设推进时，必须按上述要求记录并在冻结审阅时逐条复查，不能由负责人默许跳过。仍有未关闭的用户决定，或负责人偷偷替用户作出未授权选择时，都不能进入正式设计；新事实推翻旧决定的前提时，要说明原因和影响后重新询问。
```
