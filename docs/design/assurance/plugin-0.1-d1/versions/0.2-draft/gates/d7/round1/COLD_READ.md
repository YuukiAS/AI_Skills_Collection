## 1. 拟开工顺序

以下是设计允许的实施顺序，不表示当前已获准实施。设计仍要求先完成对应关卡、取得批准并冻结，X1 实际接收后才开始插件实现；冻结前仅允许规定的现实核查和材料整理。

1. 明确任务定位与单写者协议：`state`、`writer`。把初始化、状态修订、事件追加、交接、写入不明与恢复规则做成共享资源和模板。
2. 建立只读结构及引用检查：`record-check`，同时实现 JCS 对照例、各记录结构及三态输出；不让检查入口执行记录里的命令或产生状态写入。
3. 建立角色资源与派发：`dispatch`、`prompts`、`role-D1` 至 `role-D8`、`role-X1` 至 `role-X5`。固定档次、会话、读写边界、阶段负责人及返回位置。
4. 实现设计端入口：`clarify`、`contract` 及九个 `contract-*` 子节点、`gates`、`q-checker`、`freeze`、`q-inheritance`。先澄清并生成任务书，再独立设计、汇总、关卡、批准、追加冻结历史、冻结档复查及交接。
5. 把冻结审阅七部分接入设计输出：`freeze-review`、`fr-decisions`、`fr-asks`、`fr-costs`、`fr-roles`、`fr-validation`、`fr-downloads`、`fr-nongoals`。应用中的审阅视图按蓝图交给单独实现任务；本插件不能把视图尚未实现说成已可用。
6. 实现交付端：`acceptance`、`calibration`、`candidate`、`evidence`、`deviation`、`sign`，并接通 `revision`、`metrics`。先审定验收资产并校准，再固定最终对象、取得当前证据、组织返修或退回，最后由 X1 亲读并签发。
7. 同源打包：`source-layout`、`planning-entry`、`execution-package`、`q-capacity`、`web-later`。保留旧能力，按 12 插件、32 技能预算生成；网页端复用已测通方法，找不到或不能复现时按既定偏离路线处理。
8. 最终验收：`minimum`、`capability-check`、`sign`。依完整用例集和所需专业角色观察同一最终候选；最终完整运行之后再改代码，须再次完整运行。这里必须先关闭 D7-B1。

## 2. 输入输出接缝

| 接缝 | 输入 | 输出与接收约束 |
|---|---|---|
| `state` → `writer` → `dispatch` | 任务、确切分支、状态修订号、文件身份及当前写者 | 单写者接受并回读的新状态，随后才选择下一动作；事件不能覆盖状态 |

| `role-D2` / `role-D3` / `role-D4` → `role-D1` | 各自完整原稿或有直接证据的事实 | D1 汇总的同一 Blueprint，保留原稿和取舍；不向独立设计者泄露对方方案 |
| `contract` / `gates` → `freeze` | 九项定位、对应受审快照的有效关卡、已关闭阻塞、真实批准及授权 | `freeze.json` 与不可变 Blueprint；批准只绑定 `snapshot_sha256`，另外保留 `semantic_hash` 和完整文件的 `bundle_sha256` |
| `freeze` → `role-X1` / `writer` | 冻结对象、批准、授权、三种身份及适用的小修继承链 | X1 实际读取并写接收记录；D1 最后一次状态提交切换阶段与写权，X1 回读后才写状态 |
| `freeze-review` → 独立审阅视图 | 七个节点的正文和来源、原角色表、当前快照、有效关卡及验收与回归定义 | 用户可读审阅及派生信息；不另造说明文件批准对象，不把未知下载大小当零 |
| `role-X2` / `role-X3` → `calibration` → `acceptance` | 验收资产提案、差异、独立预期、正坏缺证三类实际输出 | X1 审定的正式资产版本；改变语义交回 D1，作者不能自行准入 |

## 3. 阻塞问题

### D7-B1：回归全部通过数同时要求为 9 和 8

**节点：** `capability-check`；影响 `contract-regression`、`fr-validation`、`sign`。

**字段与冲突：**

- `capability-check.terminal.mechanism` 第 10.2a 节列出 R1–R8、S1，明确“共 9 个用例……全部通过才算本版本做完”；该节点的输入、输出与 `v-regression-set.oracle.description` 也要求 9 个用例、20 条检查。
- 同一必需验收器 `capability-check.validators[id=v-regression-set].criteria[0]` 的指标为“第 10.2a 节 R1–R8、S1 全部条目通过的用例数”，但 `operator=eq`、`value=8`。
- 同一验收器的 `method.command` 仍写“新能力 12”，而当前正文及其 `oracle.description` 列出包含 R8 两条检查的新能力 14 条。`walk-built.steps[id=wb-capability].action` 也仍称“8 个回归用例”，同一步的期望结果却要求 9 个。

**为什么不能自行开工：** 9 个用例全部通过时，通过数为 9，机器判据 `eq 8` 反而不通过；只通过 8 个又违反全量通过及零失败、零未知、零未执行的要求。这是直接影响签发的验收条件，不是代码组织或模板措辞。`contract-regression` 明确要求用例语义、期望和尺子由 D1 写定，实施者不能自行改尺子；`fr-validation` 又要求界面派生数量与设计一致。因此不能由实施者默选一处正文覆盖另一处必需判据。

**需要 D1 决定并统一的选项：**

1. 保留 R1–R8、S1 的完整范围，以 9 个用例全部通过为唯一条件；统一机器判据、执行说明、分组统计和走查中的残留数量。
2. 如果本版本确实只验 8 个，D1 明确决定哪个用例或哪些检查不属于本版本，并同步修改能力承诺、用例范围、分组、判据及签发条件，依修订规则处理；不能由实施者漏跑一个凑数。

关闭条件：受审 Blueprint 中，用例枚举、通过数指标、检查条分组、执行说明和最终签发前提只表达一套一致条件。此处计为一个共同原因的阻塞，未把每处残留分别重复计数。
