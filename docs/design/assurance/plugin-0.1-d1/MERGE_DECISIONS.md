# D1 合并记录：两份独立设计怎样收敛

日期：2026-11-11。合并对象是同目录上级的 [plugin-0.1-pro-a](../plugin-0.1-pro-a/)（设计 A）和 [plugin-0.1-pro-b](../plugin-0.1-pro-b/)（设计 B）。合并结果是 [SPEC.md](SPEC.md)。本稿尚未过 D5–D8，也没有冻结。

## 1. 底稿选择与取舍

**以 A 为底稿。** 两份的大方向一致：两个插件共用一份规则源，不加第三个总控插件，不建中央服务，状态以仓库文件为准，13 张角色卡、九项冻结合同、验收器分级、三类校准都忠实沿用流程 0.1。选 A 的原因：

- A 实际跑过结构诊断，并从远端回读核对过；B 当时没有终端，只做了文件内的自查。
- A 的单写者交接、冲突处理、候选与证据绑定、验收资产变更记录写得更细，可以直接开工。

**从 B 吸收四项：**

| 吸收内容 | 位置 | 理由 |
|---|---|---|
| 调度的固定优先级（冲突 → 用户决定 → 进行中角色 → 返修 → 必跑角色 → 条件角色 → 冻结/签发） | SPEC 第 2.2 节 | A 只给了条件表，没规定多个条件同时成立时先做哪个。固定顺序让同一状态只得到一个下一步，可以直接测试。 |
| 追加式事件日志 `history/events.jsonl` | SPEC 第 1.1 节 | 给审计、恢复和三项衡量提供原始事件；仍不能覆盖 `STATE.json`。 |
| 冻结合同的 `semantic_hash` | SPEC 第 6.4 节 | 给“语义版本是否改变”一个机械判据，是小修批准继承的前提。 |
| 十三项签发清单 | SPEC 第 7.5 节 | 与 A 的八项合并：B 拆得更细，单独列出“最后一次证据后候选未变”“权限边界未越界”等，便于逐项写 yes/no/unknown。 |

**分歧处取 A：**

| 分歧 | A | B | 取舍 |
|---|---|---|---|
| 设计退回后谁接 | 回原 D1 | 重新指定 D1 线程 | 取 A；流程原文规定回原 D1。 |
| 任务目录 | `docs/assurance/<task_id>/`，可直接看到 | 隐藏的 `.assurance/tasks/` | 取 A；用户习惯在仓库里直接看文档。 |
| 阶段划分 | `phase` 三值加 `step` 代号 | 十余个阶段加四个阻塞状态 | 取 A；`step` 已能表达位置，阻塞原因写进待决定事项和暂停范围，不另造状态。 |
| 交付后 D1 的写权 | 仍写设计版本、关卡派发和冻结记录，状态由 X1 登记 | 冻结后 D1 身份结束 | 取 A；保留 D1 对设计语义的权威，同时只有一个状态写者。 |
| 记录检查 | 一个只读入口，用现成 `jsonschema` | 多个脚本（state、dispatch、evidence 等） | 取 A 的只读检查入口作为 0.1 起点；写状态的辅助脚本由实现阶段按需要补，不预先铺开。 |

## 2. 三项已裁决问题

### 2.1 市场容量（用户裁决）

用户原话：“直接做新插件”。实施时把预算调整为 12 个插件、32 个技能，两个新插件正式进入市场；不删除、不合并旧插件，也不先走“只做直接安装包”的过渡路线。被拒方案：B 的“先直接安装、暂不上架”，以及合并成单一插件。

### 2.2 冻结后小修的批准继承（用户确认）

用户确认采用：**B 的窄范围加 A 的版本区分。**

- 小修最多改两个既有节点；不改接口、正常入口、失败路径，也不改任何读者已经复述过的文字；`semantic_hash` 不变。
- 满足时文档版本加一、语义版本不变，原用户批准和原关卡记录继续有效，D1 追加继承说明，只重跑 D5。
- 任一条无法证明就按大改：重跑 D5–D8，重新请用户批准。

被拒方案：A 原稿的“同一组件最多 3 个叶节点”，它允许改读者看过的文字而不重做复述。另一个被拒的是“每次小改都重走全部关卡”，那样会让流程里“小修只重跑结构检查”的规定失去作用。

### 2.3 Blueprint 检查器接入（D1 决定，用户同意）

两份设计都独立发现了同一处矛盾：起稿指南要求首版写 `versions: []`，而完整结构定义要求至少一条冻结历史，新设计因此在冻结前永远过不了检查。

决定：修在 Blueprint 的维护源，提供两档入口。

- **草稿检查**：沿用全部结构规则，只是不要求已有冻结历史，冻结前用。
- **冻结检查**：保留全部要求，冻结时和冻结后用。

被拒方案：B 推荐的“把检查器选择性移植进本仓库”。它会产生两份规则，以后容易不一致。上游修好之前，D5 一律记为无法判断。

## 3. 其他处理

- **GPT Work：** 0.1 只承诺按精确路径读取 `SKILL.md`，不承诺自动发现。两份结论一致。
- **入口：** 两个规划入口加两个执行入口，共用 `shared/assurance/` 一份规则源（A 的方案，也是 B 推荐的退路）。
- **私有信息：** A 原稿第 10.2 节写了私有试跑的仓库分支名，合并稿已改为不在公开仓库记录私有定位；原稿目录中的同一句也一并去掉了项目信息。

## 5. D7 冷读第 1 轮后的补定（D1）

D7 第 1 轮（Codex 冷读，只读 Blueprint）报告了 3 项阻塞问题。D1 的决定已写入 SPEC 第 6.2 节和第 6.5 节：

1. **语义哈希覆盖哪些内容。** 覆盖九个 `contract-*` 节点的定义字段、这些节点的验收器定义字段，以及这些节点引用的需求全文；排除进度和运行记录。影响完成语义的义务必须写进这九个节点，写在别处算设计缺口。代价是九个节点内的错字修复也算大改。被拒方案是从自然语言里人工抽取“语义片段”：那样判定不机械，而且容易漏掉义务。
2. **上游检查器改造归谁。** 作为本任务之外的独立前置工作，已交付在 Asteria-Blueprint `c05edcf`。实施只按固定提交调用。同时删去“冻结前可以继续实现其他部分”的说法：冻结前不开始任何实现。
3. **首次冻结绑定哪个对象。** 用户批准内容快照的 `snapshot_sha256`（不含历史）；冻结命令追加历史后，冻结档复验快照不变，再写 `freeze.json`。三个身份（`snapshot_sha256`、`semantic_hash`、`bundle_sha256`）分别承担批准、语义判定和文件存档。

原始冷读报告：`gates/assurance-0.1-d1` 分支的 `gates/d7/round1/COLD_READ.md`。

## 6. D7 冷读第 2 轮后的补定（D1）

第 2 轮用一个新的 Codex 线程冷读第 1 轮补定后的 Blueprint（SHA-256 `0111f023…`），报告了 3 项阻塞问题。D1 的决定如下，已写入 SPEC 第 6.5 节和第 7.5 节：

1. **语义哈希只覆盖九个合同节点，会漏掉写在别处的义务**（例如 `dispatch` 里的角色档次）。改为覆盖整份设计的定义内容，只排除进度、运行和出处记录。为了不让错字修复也必须重新批准，派发核验接受两种情况：当前值等于获批值，或者能沿一串完整的继承记录（小修记录）逐条到达获批值。这条修订取代第 5 节第 1 项“九个节点内的错字也算大改”的代价。
2. **分单元签发后任务处于什么状态。** 0.1 只支持整个冻结范围一次签发，删去分单元签发的条款。确实需要分批交付的，在设计阶段拆成多个任务。
3. **签发后被推翻怎么撤回。** 由 X1 先暂停交付声明，再作出“维持”或“撤回”的决定，写不可变的撤回记录；撤回后清空当前签发引用，相关证据标为失效，进入返修；原签发永远保留为历史。

原始冷读报告存放在 `gates/assurance-0.1-d1` 分支的 `gates/d7/round2/COLD_READ.md`。

## 7. D7 冷读第 3 轮后的补定（D1）

第 3 轮（新 Codex 线程，Blueprint SHA-256 `1b2ff929…`）报告了 2 项阻塞问题，比前两轮少，范围也更窄。

1. **哈希字段清单漏了节点 `terminal` 和 `failureQuestions`。** 改为排除法：从内容快照出发，只删去明确列出的进度、运行和出处字段，其余全部覆盖；新字段默认覆盖。这样以后不会因为漏列字段而再次出现缺口。
2. **批准链核验到底拦哪些派发。** 按阶段绑定不同对象：
   - 设计阶段的角色绑定受审快照，不查批准链，所以首次冻结前、小修后的 D5、大改后的关卡都能正常派发；
   - 依据冻结合同的交付工作才查批准链；
   - 交付期间的修订草稿不影响未暂停部分的交付派发。

原始冷读报告：`gates/assurance-0.1-d1` 分支的 `gates/d7/round3/COLD_READ.md`。

## 8. D7 冷读第 4 轮后的补定（D1）

第 4 轮（新 Codex 线程，Blueprint SHA-256 `2a098853…`）只剩 1 项阻塞问题：新任务还没有 Blueprint 时，第一次派 D2、D3、D4 应绑定什么对象。

决定：把派发角色分成两类，各自绑定不同的对象。
- **生成设计或核查事实的角色（D2、D3、D4）：** 绑定 D1 在澄清结束时写出的不可变“设计任务书”，内容只有需求、决定和事实，不含设计倾向。
- **检查已有设计的角色（D5–D8）：** 继续绑定受审快照。

被拒方案：
- 由 D1 先起草一份起始 Blueprint 交给设计者——这会给两位独立设计者一个共同的设计基线，削弱独立性；
- 只接受已经带有 Blueprint 的任务——这会砍掉从需求起步的正常入口。

原始冷读报告：`gates/assurance-0.1-d1` 分支的 `gates/d7/round4/COLD_READ.md`。

## 9. D7 冷读第 5 轮后的补定（D1）

第 5 轮（Blueprint SHA-256 `58b999ea…`）只报告了 1 项问题：`brief_sha256` 的计算方式没有定义。决定：对整个任务书 JSON 对象按规范化 JSON（键排序、UTF-8、无多余空白）计算 SHA-256，所有字段都参与，和其他身份使用同一套规则。只改格式不改变身份。

改动只有一句话，由 D1 直接写入 SPEC 和 Blueprint 中同一句出现的 21 处位置；草稿检查离线 0 个缺口。
