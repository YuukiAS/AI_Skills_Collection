# Design Assurance 与 Delivery Assurance 0.1：D1 合并规格

本稿由 D1 以独立设计 A（[plugin-0.1-pro-a](../plugin-0.1-pro-a/SPEC.md)）为底稿，吸收独立设计 B（[plugin-0.1-pro-b](../plugin-0.1-pro-b/SPEC.md)）的四项内容，并写入三项已由用户或 D1 裁决的问题。取舍理由、被拒方案和裁决原文见 [MERGE_DECISIONS.md](MERGE_DECISIONS.md)。两份原稿保留不改。

两个插件各提供一个规划入口和一个执行入口，共用状态格式、派发规则、13 张角色卡、提示词模板、修订告知和衡量记录。Design Assurance 把需求收敛成可冻结的 Blueprint；Delivery Assurance 在冻结范围内安排实现、校准验收器、核对当前成品与原始证据，并由 X1 签发。0.1 必须让一次任务从需求进入、经过规定关卡、交接、返修到交付都能找到明确接收者与可复制提示词；采用仓库文件和现有工具完成，不建设中央服务或常驻运行器。

最大风险是冻结合同遗漏了用户实际要的能力，后续检查因此认真验证了错误目标。D6 逐组件追问、D7 冷读和 D8 逐步复述分别检查缺口、可开工性和可理解性；交付端还必须从正常入口看最终对象，不能用文件齐全或校准样例通过代替正常任务成功。原先三项实现前裁决（Blueprint 检查器接入、冻结后小修的批准继承、市场容量）均已收敛，见 [MERGE_DECISIONS.md](MERGE_DECISIONS.md) 第 2 节。

这是 D1 汇总后的待审规格，尚未过 D5–D8，也不是冻结合同，不声称插件已实现。流程语义只来自[已认可的流程 0.1](../ASSURANCE_PROCESS_V0_1_20261110.md)。文中新增字段、数值和目录均是 A 为可实现性提出的具体设计；角色、档次、必跑条件、验收器分级和退回条件保持原流程。来源与实际检查边界见 [NOTES.md](NOTES.md)。

## 1. 状态文件与写入责任

### 1.1 一项任务，一份当前状态

被管理项目默认使用 `docs/assurance/<task_id>/STATE.json`。`task_id` 是初始化时固定的仓库内唯一标识，限小写字母、数字和连字符；已有任务标识可直接复用并记录，不按线程标题或插件版本重新生成。D1 首次进入时先查该任务是否已存在；同一任务的两个插件打开同一路径。用户已有明确目录时，初始化一次绑定实际目录，以后只读该绑定，不建立第二份状态。

当前状态由 `STATE.json` 唯一决定；Blueprint 决定设计内容，冻结快照决定完成语义，原始证据决定实际观察。聊天、派发提示词和报告中的状态仅是某次读取的投影，不能覆盖文件。状态不能凭自报“通过”推导能力完成，也不保存密钥、私有全文或大二进制。

建议的任务文件布局如下。路径是格式设计，尚未在任何被管理项目初始化：

| 相对任务目录的路径 | 内容与写入者 |
|---|---|
| `STATE.json` | 当前权威状态；设计阶段 D1、交付阶段 X1 单独写入 |
| `design/blueprint.json` | D1 汇总的当前设计；历史版本不原地覆盖 |
| `design/versions/<version>/blueprint.json` | 不可变设计版本；D1 负责内容，实际文件操作可委派 |
| `design/versions/<version>/freeze.json` | 九项定位、四关卡记录、批准和身份绑定；只引用 Blueprint 中的语义 |
| `dispatches/<dispatch_id>/PROMPT.md` | 负责人生成的完整派发提示词 |
| `dispatches/<dispatch_id>/RESULT.json`、`RESULT.md` | 被派出角色的结果和自然中文说明；各自只写自己的目录 |
| `dispatches/<dispatch_id>/artifacts/` | 角色交回的候选设计、检查记录、复述等 |
| `revisions/<revision_id>.json`、`returns/<return_id>.json` | 修订与退回的不可变原始记录 |
| `history/events.jsonl` | 追加式事件日志（采自设计 B）：每次状态写入、派发、采纳、冲突、告知各追加一行 `event_id,at,actor,kind,state_revision,refs`；只用于审计和恢复线索，不能覆盖 `STATE.json`，衡量记录从这里重建 |
| `delivery/candidates/<candidate_id>.json` | X1 维护候选身份与当前用途；实现者只提交候选提案 |
| `delivery/evidence/<evidence_id>.json` | 各证据作者保存原始记录；X1登记采用范围 |
| `delivery/acceptance-assets/<asset_id>/<version>.json` | 验收资产版本、校准与 X1 审定记录 |
| `delivery/releases/<release_id>.json` | X1 的签发记录，指向最终对象与原始证据 |

敏感证据留在用户已授权的持久位置，只在任务目录保存受众可读的定位。`private/` 这个目录名不形成访问控制；公开仓库不得因文件名含该词而提交私有内容。找不到合法且评审者实际可读的证据位置时，记录无法判断并补证。

### 1.2 当前状态的字段

JSON 使用 UTF-8、两个空格缩进、换行结束；未知值用 `null`，已知为空用 `[]`，不得用空字符串混淆。未知枚举或比当前支持版本更新的结构只读报告，不自动重写。时间使用带时区的 ISO 8601；用户说明按当前用户时区显示。

| 字段 | 类型与必需内容 | 何时变化 |
|---|---|---|
| `schema_version`、`process_version` | 固定为 `assurance-state/0.1`、`0.1` | 不做隐式迁移 |
| `task` | `id,title,repository,branch,root`，全部非空字符串 | D1 初始化；迁移须有明确定位与授权依据 |
| `revision` | 从 1 递增的整数 | 每次被接受的状态写入加 1 |
| `phase` | `design`、`delivery`、`delivered` | 初始设计、冻结交接完成、X1 签发后 |
| `step` | 当前动作的稳定代号；候选值见第 2 节 | 负责人采纳结果后 |
| `state_writer` | `D1` 或 `X1` | D1 与 X1 完成交接时切换一次 |
| `owners` | D1、X1 各自的 `host,thread_ref,assigned_by`；尚未绑定 X1 为 `null` | 首次绑定；不能悄悄把同一线程写成两个负责人 |
| `process_ref`、`plugin_refs` | 流程和实际加载技能的仓库/路径/版本及已知内容摘要 | 初始化与显式升级；不能仅凭市场名称推断加载版本 |
| `blueprint` | `draft_ref,draft_revision,frozen_ref,semantic_version,approval_ref`；未冻结项为 `null` | D1 发布设计或新冻结版本，X1只引用采纳 |
| `pending_decisions` | `id,question_ref,owner,affected_nodes,status,answer_ref` | 记录问题、回答与重新开放；不重复询问已有有效决定 |
| `dispatches` | 派发记录数组，完整形状见第 2 节 | 准备、发出、返回、采纳、作废 |
| `gate_results` | D5–D8 的 `gate,subject_ref,result_ref,status,coverage,validity` | 只采纳实际结果；状态为 `pending/passed/failed/unknown/stale` |
| `revisions`、`design_returns` | 不可变修订/退回记录的引用数组 | 有新记录才追加，不删掉失败历史 |
| `paused_scopes` | `node_ids,reason,return_id,resume_condition` | 只暂停受影响节点及其依赖闭包 |
| `delivery` | `candidate_id,acceptance_plan_ref,evidence_ids,required_roles,release_ref` | X1 组织交付；初始全部为空或 `null` |
| `measurements` | 原始衡量事件的引用与去重键 | 发生用户追问、退回或告知时追加；统计值临时计算 |
| `updated_at`、`last_change` | 实际写入时间；`actor,expected_revision,reason,source_ref` | 每次状态写入 |

`step` 是当前人工工作位置，不是后台状态机或自动执行许可。负责人读取后才能决定下一动作。`gate_results` 的通过只表示该关卡对指定设计版本的结论；`delivery` 中的运行结果只有第 7 节规定的三种语义。

### 1.3 单写者、交接与冲突

派出角色均不能修改 `STATE.json`。结果必须带 `dispatch_id`、读取的状态修订号、Blueprint 内容身份、受测候选身份（如适用）、实际读写清单与结果文件定位。负责人核对这些值后才采纳；重复提交同一派发同一结果幂等，不重复计数或再派工作。同一派发返回不同内容时保留两个版本并标注冲突，由负责人查清来源，不采用最后写入者获胜。

写状态前重新读取远端目标分支和当前状态，比较预期 `revision` 与基准文件身份。分支没有新增冲突时，用普通提交更新；使用 GitHub 文件接口时必须带当前文件 SHA，使用引用接口时必须带预期分支头且禁止强推。写入后回读同一分支、文件和新修订号。若写入结果不明，先回读查是否已成功，再决定重试，不能重复冻结、派发或签发。机械网络失败最多自动重新读写一次；仍失败保留待写记录，告知负责人恢复，不循环调用用户或改变权限。

并发仅允许角色结果目录独立写入。远端发生其他人的更新时重新读取，合并仍有效的结果引用；已经改变基线的结果标为 `stale`，记录还能支持的范围和必须重做的范围。不能只因分支上有无关文档提交便废弃所有证据，也不能把候选内容已经变化解释成无关提交。

冻结后 D1 发出绑定具体冻结版本的交接记录；X1 在另一个线程实际读到并写回接收记录。D1 核对接收后，用自己最后一次带预期修订号的状态提交同时将 `phase` 改为 `delivery`、`state_writer` 改为 `X1`；X1 回读确认后开始写状态。交接前 D1 仍是唯一写者；没有 X1 接收证据不称已接手。进入交付以后，设计退回由 X1 登记并暂停影响范围；D1 仍可写自己的设计修订、Blueprint、重开的关卡派发及批准冻结记录，不能直接改当前状态。X1 只能按原样登记这些设计决定、派发和新版本，不能改写其内容。这样保持一个状态写者，又保留 D1 对设计语义的权威。未受影响且已经获准的交付工作继续，签发等待所有相关退回关闭。

负责人线程暂不可用时保留原绑定并等待恢复；恢复后先读当前状态再读自身职责所需材料。不能仅改 `thread_ref` 伪造“沿用”。原线程确实无法恢复时，由用户明确指定接替线程，留下替换原因和授权引用；D1 与 X1 仍必须分开。这是已有线程规则的异常恢复，不是自动增加第三负责人。

### 1.3a 当前状态丢失或损坏时的恢复（D6 第 1 轮后补定）

**触发条件：** `STATE.json` 不存在、无法解析、未通过 `state` 记录检查，或者修订号与远端分支上的最新提交对不上。

**恢复步骤：**
1. 发现问题的任何角色立即停止，不再派发，也不写入任何记录，只把现象报告给当前阶段的负责人。不知道当前阶段时，报告给 D1。
2. 负责人从 git 历史里找出最后一个通过记录检查的 `STATE.json` 提交，作为恢复基线。
3. 在 `history/events.jsonl` 中找出基线修订号之后的事件，逐条核对对应的不可变记录（派发、结果、修订、冻结、候选、证据、签发、撤回），只补登有原始记录支撑的状态变化。
4. 事件与记录对不上，或者无法判断某个变化是否已经发生时，列为恢复冲突。负责人不能在两种说法之间挑一个当真，按以下规则处理（D7 第 17 轮后补定）：
   - **涉及冻结、批准、签发、撤回的冲突：** 交用户决定。
   - **其余冲突（普通冲突）：** 负责人只能采用一种固定的保守处置，即把这次变化当作**没有发生**。相关派发记为 `stale`，其结果不被采用；全部原始记录和事件原样保留，不删除、不改写。仍需要这项工作时，用新的派发编号重新派发。新派发的提示词必须列出原派发在仓库里已经留下的写入（提交和文件），接收者从当前仓库状态出发，不得假设原派发没有执行过，以免重复写入。
   - **保守处置做不了时也交用户决定：** 例如原派发留下的写入与重新派发的工作互相冲突，或者重新派发会产生无法撤回的外部后果（付费调用、对外发布、向他人发消息）。
   - **隔离：** 等待用户决定的冲突，把它涉及的节点以及依赖这些节点的工作写进 `paused_scopes`，暂停派发；其余范围在恢复记录通过检查并回读后照常恢复。
5. 恢复结果写成新的 `STATE.json`：修订号接着基线递增；`last_change.reason` 写 `recovery`；同时写不可变的 `recovery/<recovery_id>.json`，内容包括基线提交、补登的事件、冲突和处理结果。通过记录检查并从远端回读以后，才重新开始派发。
6. git 历史里一个有效的 `STATE.json` 都找不到时，不自动重建。负责人列出所有现存的不可变记录，交用户确认后再初始化。

### 1.4 记录的只读检查

为避免每张角色卡各自实现一套JSON判断，共用资源提供一个只读入口 `shared/assurance/scripts/check_records.py`，使用成熟依赖 `jsonschema[format-nongpl]==4.26.0`；运行环境为Python 3.10或更新的受支持版本。各记录结构使用JSON Schema Draft 2020-12，先用 `Draft202012Validator.check_schema` 检查结构定义，再用 `iter_errors` 收集记录错误，显式启用 `FormatChecker` 并核对对应格式依赖。引用只从同包预注册的本地结构读取，不在验收时联网取未知结构。版本与API依据为[jsonschema官方文档](https://python-jsonschema.readthedocs.io/en/stable/validate/)、[引用机制文档](https://python-jsonschema.readthedocs.io/en/stable/referencing/)和[4.26.0发行记录](https://pypi.org/project/jsonschema/4.26.0/)。这是拟采用依赖，本轮没有安装或运行该入口。

计划命令为 `python shared/assurance/scripts/check_records.py --task-root <目录> --schema <记录种类> --record <文件> --format json`；允许的记录种类为 `state/brief/dispatch/result/revision/freeze/candidate/evidence/calibration/return/release/revocation/recovery/measurement`（`brief` 见第 6.5 节，`recovery` 见第 1.3a 节）。入口只读指定任务目录与包内结构，检查必填字段、枚举、时间、相对路径越界、编号唯一性和记录间已声明的身份引用。涉及版本、角色或候选不一致时报告具体引用，不替负责人判断语义等价。退出值0只表示记录结构及可检查引用符合规则，1表示存在确定错误，2表示依赖、输入或引用证据不足而无法完成检查；输出包含 `assessment,errors,unresolved,checked_files`，绝不把2记作产品失败。

该入口不写状态、不提交、不派发、不签发、不安装依赖、不执行记录中引用的命令，也不替代Blueprint检查器、领域验收或负责人阅读。任务目录之外的合法证据只核对已登记定位与身份，不能越过授权自动读取。检查器自己的三类校准与版本也按第7节由X1审查。

## 2. 调度与下一步提示词

### 2.1 按条件选择，不替用户改变档次

调度每次先检查当前状态和来源身份，再确定待完成条件，最后输出“发给谁、哪个档次、新开还是沿用、做完交回谁”以及完整提示词。角色档次固定如下；技能不会把用户界面里的“极高”猜成某个 API 参数，也不声称已经自动选好模型。[流程 0.1 第 2–3 节](../ASSURANCE_PROCESS_V0_1_20261110.md)

| 角色 | 档次 | 会话规则 |
|---|---|---|
| D1、X1 | 规划端·专业：Claude 或 GPT Pro | 各自一个长期线程，彼此不同 |
| D2、D3 | 规划端·专业：Claude 或 GPT Pro | 每次独立设计新开；互不读取本轮对方产物 |
| D4、D5 | 执行端·普通：Codex 高 | 同一任务的盘点或机械检查可以沿用 |
| D6 | 规划端·普通：GPT 极高 | 每轮新开，不继承负责人上下文 |
| D7 | 执行端·普通：Codex 高 | 每轮新开，只给 Blueprint 和无设计暗示的运输说明 |
| D8 | 规划端·普通：GPT 极高 | 每一轮换一个新对话，合批处理本轮全部单位；用户每轮转交一次（第 2.1a 节） |
| X2 | 执行端·普通：Codex 高；数学符号、精细推导等改用执行端·专业：GPT Work 极高 | 当前实现任务持续沿用；专业子任务明确划定文件与接缝 |
| X3 | 执行端·专业：GPT Work 极高 | 首次独立新开；同一验收实现的返修沿用，不继承 X2 的解题过程 |
| X4 | 执行端·专业或现有专门插件 | 同一检查器按既定准则复验可沿用 |
| X5 | 规划端·专业：Claude 或 GPT Pro | 每次独立裁判新开，不看实现过程 |

没有满足档次、独立性或工具能力的入口时，生成给该入口的提示词并等待，不自动降档或让负责人自己冒充。此处“新开”表示实际新上下文；与文件读取隔离分别记录。宿主有经验证的独立子代理能力时可用，必须确认未继承被禁止的上下文；没有该能力时手动新开线程即可。

### 2.1a 规划端角色一律在 GPT 上跑，每轮每个角色转交一次（用户要求，2026-11-11）

用户的原话：“每个角色一轮就发一次”；“我说的是规划端角色，执行端 codex 倒无所谓”；“规划端就都在 gpt 跑吧，不然容易乱”。据此：

- **需要用户手动转交的规划端角色**（D2、D3、D6、D8、X5）一律在 GPT 网页端运行，不用执行端代替；每个角色每一轮，由用户转交的提示词最多一条。
- **负责人 D1、X1 不在此列**（D6 第 2 轮后更正）。它们按已认可流程，由 Claude 或 GPT Pro 担任，各自在一个长期线程里工作；规划 `SKILL.md` 由 Claude Code 和 GPT Work 直接读取。本插件自身：D1 由 Claude 担任；X1 由 GPT Work 极高担任（用户决定，2026/11/12），Claude 只负责机械地启动 X1 写在仓库里的 Codex 派发。负责人怎样派执行端，见下一条。用户这句话的本意是“需要我转交的那些角色在 GPT 上跑”，不是要取消 Claude 担任负责人。
- **执行端角色在哪里运行，以第 2.1 节表中的档次为准**（D6 第 8 轮后补定）：
  - 档次为 Codex 的（D4、D5、D7，以及 X2 的普通实现）：Claude 担任负责人时直接派发；GPT 担任负责人时生成完整提示词，由用户转交给 Codex。
  - 档次为 GPT Work 极高的（X2 的专业子任务、X3）：无论负责人是谁，都生成完整提示词，由用户在 GPT Work 里按该角色的会话规则新开或沿用对话转交；不得改用 Codex 代替，也不得降档。
  - X4：派发记录写明用“执行端·专业（GPT Work 极高）”还是哪一个现有专门插件。前者同 X3；后者在该插件实际所在的宿主运行，宿主需要用户转交时同样由用户转交。
  - 凡需要用户手动转交的执行端角色，与规划端角色一样，每个角色每轮最多一条。
- **执行端角色由当前阶段的负责人派发**（D6 第 1 轮后更正）：设计阶段由 D1 派发 D4、D5、D7；交付阶段由 X1 派发 X2、X3、X4。不需要用户转交的派发次数不限，不占用户的转交次数。规划端角色同样按阶段分：设计阶段由 D1 准备 D2、D3、D6、D8 的提示词，交付阶段由 X1 准备 X5 的提示词。
- **需要多位读者的规划端角色（D8）：** 每轮合成一条提示词，交给一个新的 GPT 对话。
  - 对话逐个处理本轮全部单位，顺序随机打乱；
  - 每个单位只依据它自己的文字作答，不得借用其他单位补全信息；
  - 结果记录 `reader_isolation: "single-thread-batch"`。

  D1 逐单位比对复述和原意：
  - 全部正确，这轮合批结果就是 D8 的有效通过；
  - 有单位读错，D1 改写这些单位的文字，下一轮在一个新对话里重读。重读时只放改过的单位和受影响的相邻单位，仍然只转交一条。
- **原先的“每一步每一轮换新读者”改为“每一轮换新对话”。** 独立性比逐步换人低，这是用户为了可操作性接受的取舍。冻结说明里要写明 D8 用的是合批方式。
- 本节取代 D7 第 8 轮后的补定（MERGE_DECISIONS 第 12 节）：不再要求关键单位另由执行端独立复述。

### 2.2 确定的优先级（采自设计 B）

调度读完当前状态后，按以下顺序找第一个成立的条件，只给出一个下一动作。允许并行的角色（如 D5–D8、D2 与 D3）作为一个“派发批次”一次给出，但批次内每个角色仍有独立的提示词、依据身份和写回位置，调度明确写出“本批次可并行”，不让角色自己推断依赖。

1. 状态冲突、身份或哈希不一致、负责人不合法；
2. 阻塞流程的用户专属决定；
3. 已派发且仍在进行的阻塞角色；
4. 失败关卡或失效证据对应的返修；
5. 当前阶段尚未完成的必跑角色；
6. 已满足触发条件的 D3、D4、X3、X4、X5；
7. 用户冻结、X1 签发或任务结束。

同一状态修订号必须得到同一结果，这是第 10.2 节“从当前状态给正确下一步”的直接验收对象。

### 2.3 设计与交付的条件表

| `step` | 进入条件 | 负责人给出的动作与完成后接收者 |
|---|---|---|
| `D1-clarify` | 新任务或出现必须决定的问题 | 分类查询、设计选择、用户问题；回答进入带出处需求 |
| `D2-D3-design` | 设计任务与读取边界已明确 | D2 必跑；D3 由 D1 按复杂/高风险决定并记录，本轮已强制启用；产物回 D1 |
| `D4-reality` | 已有代码/数据且盘点或小探针会改变设计判断 | D1 决定是否调用 D4；事实回 D1，同样可给两位设计者使用 |
| `D1-synthesize` | D2 及已启用角色返回，或关卡发现缺口 | D1 保留两份原稿、取舍理由与被拒方案，形成同一 Blueprint |
| `D5-D8-gates` | D1 已明确受审版本和九项合同内容 | D5–D8 全部必跑，可对同一稳定版本并行；结果回 D1 |
| `D1-approval` | 四关卡有效、关键开放问题已关闭 | D1 给用户可读冻结说明和精确对象，取得批准后生成冻结记录 |
| `X1-intake` | 冻结快照、批准和四关卡记录可读 | 新 X1 线程接收，确定候选与必需角色，派 X2 |
| `X2-implement` | 当前范围及授权可执行 | X2 实现、补验收、三类校准、申报偏离，交 X1 |
| `X3-acceptance` | 科研数值/统计、安全相关，或某验收器太弱需换人重写 | X3 独立完成相应验收实现；不把所有普通验收一律转 X3 |
| `X4-X5-check` | 当前候选已固定且所需原始证据可读 | 有既定准则和现成能力的维度启用 X4；无法靠准则和机械检查给出专业判断时必须启用 X5；两者可同时需要 |
| `X1-repair` | 实现、检查程序、环境或普通缺证问题，合同不变 | 回原 X2 或原验收作者；X1重审验收资产变化，重验受影响项及必要回归 |
| `X1-design-return` | 命中流程规定五种设计退回条件 | X1 写退回记录给原 D1；影响部分暂停，其余继续 |
| `X1-sign` | 冻结义务有当前有效证据，所有必要角色返回 | X1亲读最终产物与原始证据，作唯一签发；如合同规定用户验收，完成该部分后才记交付 |

D3 的可选判据可由设计者操作化：存在多个强耦合组件、重要方法没有稳定依据、科研/安全结果可能造成高影响、或用户明确要求时建议启用；D1 记录采用或不采用理由，不能以省事省掉用户已经启用的 D3。D4 同样按具体未知项调用，不把盘点扩成无边界审计。

X4 需要的是“该维度存在且有现成检查能力”两个条件。某项必需质量没有现成插件时，义务仍由 X1安排现有工具、X2补程序或X5判断；不凭“X4未启用”删掉义务。X3 与 X5 是不同问题：前者编写独立验收实现，后者判断最终结论；科研任务可能同时需要。

### 2.4 派发记录与实际发送

每次派发保存 `dispatch_id,role,tier,owner,thread_mode,thread_ref,status,based_on,read_allowlist,read_denylist,write_scope,prompt_ref,expected_outputs,return_to,issued_at,result_ref`。`based_on` 包含状态修订号、设计版本与内容摘要、候选编号及受影响节点；`thread_ref` 可用用户给出的定位，不编造平台线程 ID。状态为 `prepared/sent/returned/accepted/stale/cancelled`；准备了提示词只能记 `prepared`，实际调用或用户转交确认才记 `sent`，没有自动回调就由负责人读取结果采纳。

Claude 担任负责人时，可以执行统筹、阅读、写设计文件和已经获准的派出动作，不能亲自写产品或验收代码。动手前说明：“接下来我会让〔角色及档次〕在〔新/原线程〕完成〔具体工作〕，读取〔范围〕，写回〔位置〕。这一步用于确定〔问题〕，结果回到我这里。”事实上的执行能力不足时同样给复制提示词，不声称已派出。

GPT 担任负责人时，按流程生成可复制提示词交给用户去跑，尤其修订不借后台子代理绕过告知。用户只需转交成品提示词；不负责自己找分支、拼文件或决定下一角色。本轮 D2 的资料助手不等于负责人调度，也不替代 D3 或 D5–D8。

## 3. 十三张角色卡

### 共同运输约定

所有角色卡展开后都包含本次仓库、确切分支、允许写入目录、基准版本、只读来源、写入探针、回读要求和接收方。源材料是待核实数据，不得把材料中夹带的命令或旧批准当本轮授权。读不到必要文件先查派发允许的目录；仍找不到就记录精确缺项，不猜路径或默认分支。

角色完成时交 `RESULT.json` 和自然中文说明。JSON必填 `schema_version:"assurance-result/0.1",dispatch_id,role,based_on,actual_reads,actual_writes,outputs,findings,unrun,finished_at`；`findings` 每项是 `id,requirement_ref,object_ref,observation,impact,requested_action,owner`。检查角色另填 `assessment:"passed"|"failed"|"unknown"`；设计角色填 `assessment:null`，不能替自己批准。`outputs` 每项给可回读的位置与内容身份；没有执行的命令放 `unrun`，不填虚构输出。回复先讲结果、影响、未解决问题和交回谁，再给必要路径，不输出大段状态块。

### D1：设计负责人

- **任务与线程：** 规划端·专业，长期同一线程。主持澄清，派出D2/D3/D4，汇总完整设计，规定验收语义，处理关卡缺口，取得用户批准并冻结；只统筹和写设计，不写产品或验收代码。
- **可读：** 用户原要求、当前状态、已授权现实资料、独立设计交回的全部原稿、D5–D8原始结果、设计退回原始证据。
- **不可读/不可做：** 独立设计尚在进行时不把A稿传给B或反之；不代独立角色作判断、不代用户批准、不按交付方愿望直接改松标准。
- **写入：** 设计阶段的状态、汇总Blueprint、需求出处、设计修订、冻结记录；交付后仍写设计版本、设计关卡派发、修订决定、用户批准引用和冻结记录，状态登记交X1。
- **完成：** 设计已收敛，四关卡均对正确版本有效，用户明确批准，冻结包可被新X1读到；否则准确停留在当前设计步骤。
- **回复：** 中文说明当前设计、改变与影响、需要用户决定的具体问题；若可继续，附下一角色的完整提示词。

### D2：独立设计者 A

- **任务与线程：** 规划端·专业，每次独立新开，交完整Blueprint而非局部提纲。自行查事实、作设计范围内的技术选择，把真正需负责人或用户决定的事项集中成问题。
- **可读：** 共同任务、用户需求与来源、规定流程、格式、现实核查事实、允许的已有实现。可读既定输入，不能凭“独立”忽略真实需求。
- **不可读/不可做：** 本轮D3的分支、产物、提交或摘要；D1未公开给双方的倾向性比较；不冻结、不实现插件、不把未跑验收写成通过。
- **写入：** 派发指定的A目录/分支，包含完整Blueprint、规格、问题与来源记录。
- **完成：** 每条设计分支落到真实实现、具体设计或有负责人和影响的开放问题，材料在远端可读，剩余决定已集中。
- **回复：** 说明推荐组成、最小范围、风险、重要问题及文件位置，交回D1。

### D3：独立设计者 B

- **任务与线程：** 规划端·专业，按条件启用、每次新开；一旦启用，任务完整度与D2相同，不是审查A稿。本轮用户已启用。
- **可读：** 与D2同一共同任务、格式、需求和事实基线；某一方发现新的客观事实，由D1同步事实本体给双方，不传另一方设计。
- **不可读/不可做：** 本轮D2的分支、产物、提交或摘要，以及负责人比较结论；不签发、不冻结、不实现。
- **写入：** 指定B目录/分支，禁止覆盖A结果。
- **完成：** 交完整Blueprint及必要问题和来源，远端可读；未启用时D1记录理由，不伪造B通过。
- **回复：** 按自身结论说明组成、范围、风险、问题和定位，交D1，不评价未读过的A。

### D4：现实核查

- **任务与线程：** 执行端·普通，可沿用同一盘点任务。检查已有代码、数据、入口和环境；只运行对具体未知项有决定价值且已获准的小探针。
- **可读：** D1列出的实现/数据/规则与待核实事实；记录实际环境和输入。
- **不可读/不可做：** 不为了比方案读取本轮独立设计原稿；不扩大数据、费用、设备或外部副作用；不把烟雾探针当完整能力验收。
- **写入：** 自己的盘点结果、原始探针输出、环境与未运行项；不改产品代码或权威状态。
- **完成：** 每个指定事实分别有直接证据、反证或明确无法判断及最小取得方法。发现前提不成立直接报告D1。
- **回复：** 先说现实支持什么、推翻什么、哪些未验证，再给证据位置；返回D1。

### D5：结构检查

- **任务与线程：** 执行端·普通，同任务机械复验可沿用。对派发的准确Blueprint调用已确认的检查入口，报告结构、引用、端口、历史和来源问题。
- **可读：** 本次Blueprint、声明的来源与版本、检查器源码/版本/说明、必要的D8记录及疑问文件（由所选入口决定）。
- **不可读/不可做：** 不以设计者摘要替代JSON；不删规则、不造冻结版本、不把离线或局部检查写成完整通过；不亲自补设计缺项。
- **写入：** 原命令、环境、退出结果、完整原始报告、所查范围与未查范围。
- **完成：** 见第6节D5标准。检查器不适配或外部来源不可读时给 `unknown` 并指明原因，不能借文件级自检冒充D5。
- **回复：** 哪类结构成立、哪些缺口影响后续、是否完整检查，交D1。

### D6：用户代理追问

- **任务与线程：** 规划端·普通，每轮新开；以用户视角沿所有有效组件追问正常使用、失败、边界和旧能力。
- **可读：** 用户需求原文和来源、受审Blueprint、共同角色卡；答案必须在Blueprint中找到明确位置。
- **不可读/不可做：** 负责人聊天、设计过程和为其辩解的摘要；不能以自己的常识补出答案后判通过。
- **写入：** 每个组件的疑问、Blueprint答案位置、仍缺什么、对用户结果的影响及应由谁补。
- **完成：** 全部有效组件有检查记录；所有影响任务结果、开工或验收的问题都能由Blueprint回答。非阻塞建议单列，不随意增新需求。
- **回复：** 用户会在哪一步卡住或误解、缺口的位置与关闭条件；回D1。

### D7：冷读

- **任务与线程：** 执行端·普通，每轮独立新开；只看Blueprint，列出实质开工前仍须询问的决定，不实施。
- **可读：** 受审Blueprint全文；派发封套只含仓库、分支、文件身份、写入范围和角色规则，不含设计答案。可以读Blueprint中作为内容组成部分的内嵌合同，不另开SPEC找答案。
- **不可读/不可做：** SPEC、历史聊天、D1汇总解释、D2/D3设计过程、旧D7回答、实现过程；不调用探针替设计补缺口。
- **写入：** 拟开工顺序、明确接缝、所有还需问的问题、被影响节点与开工影响。
- **完成：** 不能留下必须由设计方决定的阻塞问题。合同已经允许的普通代码细节可由执行者自行定，不能为“零问题”压下真实歧义。
- **回复：** 能否按既定语义开工、具体还缺什么、哪些只是实现自由度；回D1。

### D8：读者复述

- **任务与线程：** 规划端·普通，每一步每一轮新读者。0.1按Blueprint正常走查与系统失败路径里的每个有稳定编号步骤，以及格式要求的每条失败路径整体说明，分别作为派发单位；工具调用和机械状态写入不另算读者步骤。
- **可读：** 一句项目简介、当前一步的短标题和“做什么、拿到什么、交出什么、为什么、出错怎样”正文；不提供预期复述答案。
- **不可读/不可做：** 负责人上下文、其他读者复述、评分意见、整套设计的补充解释；不通过猜前后文替当前文字补信息。
- **写入：** 原样复述、确实看过的文字和身份、疑惑、实际读者与轮次。由D1比较原意后记录判断；读者不能自己声明作者意图已被保真理解。
- **完成：** 每个必要步骤及失败路径整体说明有当前文字对应的真实复述，最后一轮理解正确；含义不对先重写，再换新读者。小修时按第5.1节“批准继承”保留旧复述与文字哈希并追加继承说明，不伪造新复述。
- **回复：** 用自己的话说此步发生什么及条件，列明不理解处；回D1，不交泛泛“可读”评分。

### X1：交付负责人

- **任务与线程：** 规划端·专业，与D1分开的长期线程。接收冻结合同、安排实现/校准/专项/独立判断、审查全部验收资产变化、维护候选证据、组织返修和唯一签发；不写产品或验收代码。
- **可读：** 冻结Blueprint、批准、当前状态、所有候选与原始证据、偏离记录、专业结论；签发前本人必须读最终产物和对应原始观察。
- **不可读/不可做：** 不把实现者摘要当亲读，不改变完成标准，不用自己判断替代必需X3/X5，不把用户验收缺失写成自动通过。
- **写入：** 交付状态、派发、候选与证据索引、验收变化审定、设计退回和签发记录。
- **完成：** 同一最终候选满足全部冻结义务，所需用户部分已完成，实际交付对象可取；否则留在返修、补证或设计退回。
- **回复：** 当前成品达到了什么、还缺什么、谁接下一步；签发时给有边界的交付声明及最终对象。

### X2：实现者

- **任务与线程：** 一般实现使用执行端·普通，数学符号或精细推导用执行端·专业；同一任务沿用。按冻结合同实现，默认编写验收实现并三类校准，主动申报全部偏离。
- **可读：** 完整冻结语义、公开核心用例、正常调试证据、项目现有运行器、获准代码/数据/环境。保护用例只有确有访问授权才能读。
- **不可读/不可做：** 不修改冻结语义、用户批准、X1签发、别人的原始证据；不以已有测试清单替代完整要求，不自行批准验收资产变化，不把独立会话叫隐藏测试。
- **写入：** 指定实现范围、提交的验收实现/资产提案、运行原始证据、候选提案和偏离记录；不能写当前权威候选或状态。
- **完成：** 实现与检查接入正常路径，关键正例/坏例/缺证例实际运行，最终对象和旧能力证据可读，全部未运行/替代/偏离明确报告。完成自己职责不等于总体交付。
- **回复：** 实现结果、正常入口观察、未运行与偏离、候选与证据定位，回X1。

### X3：独立验收器实现者

- **任务与线程：** 执行端·专业，首次独立新开；科研数值或统计、安全相关验收，或弱验收器需换人重写时必须启用。对触发的验收资产负责，不接管全部实现。
- **可读：** 冻结语义、外部/解析独立参考、输入输出合同、必要最小调用接缝；弱验收修复可读失败用例和旧检查实现，但不能采用被测输出作黄金答案。
- **不可读/不可做：** X2的解题过程、为候选辩护的总结、未授权保护用例；不从待测实现倒推真值，不擅改阈值或支持范围。
- **写入：** 独立验收代码、参考来源、正坏缺证校准和与X2的共同依赖说明。
- **完成：** 验收可从正常运行器调用，三类校准结果正确，独立性限制已说明，经X1审定后才能用于正式签发；不是自己准入自己的完成标准。
- **回复：** 能检出哪类错误、哪些共同盲点仍在、校准与运行位置，回X1。

### X4：专项检查

- **任务与线程：** 执行端·专业或现成专门插件，对冻结准则下的版式、文案规范、视觉回归、领域规则等逐项检查。
- **可读：** 当前最终产物、固定准则、必要原材料、原始渲染或运行结果；需要保真比较时必须同时读源材料。
- **不可读/不可做：** 不临场改评分标准、不自动接受新视觉基线、不把截图当交互完成、不宣布总体交付。
- **写入：** 观察对象与身份、准则、实际结果、原始证据和适用范围；不能改当前候选或权威状态。
- **完成：** 被派维度全部有当前证据，无法访问的明确为无法判断；复验绑定修复后的最终对象。
- **回复：** 专项结论及其边界、具体不合格处与证据，回X1。

### X5：独立裁判

- **任务与线程：** 规划端·专业，每轮新开。机械准则无法解决的专业判断必须启用，例如科学结论是否成立、推导是否正确、图表是否误导。
- **可读：** 冻结验收语义、当前最终产物、必要原始数据/来源/推导与运行观察、允许声明范围。对象若是代码可读最终代码；不能读开发经过来被说服。
- **不可读/不可做：** 实现过程、X2/X1的辩护摘要、其他裁判结论和旧评分；不自改语义、不只读摘要、不替X1签发。
- **写入：** 针对具体主张的独立结论、证据、反例、限制和无法判断项。
- **完成：** 所有派发主张有可复核专业判断，证据不足诚实保留；意见冲突由X1按冻结标准核对，涉及标准变化才回D1，不能反复换裁判挑赢家。
- **回复：** 哪些结论成立、条件是什么、哪里不成立或无法判断，直接指向最终对象与原始依据；回X1。

## 4. 提示词规则与模板

提示词开头用一小段中文说明当前任务、这轮边界、最终交付。生成时将角色卡正文与本次材料清单合成一份完整消息，不要求接收者记住上个聊天。相同流程文件只引用定位，避免把历史研究整篇塞入；会改变权限、独立性或验收的要求必须展开。角色读限高于方便性：D7不附SPEC，D8不附答案，X5不附实现者摘要。

所有输入定位包含仓库、确切分支以及已冻结时的固定版本或内容身份；所有输出定位包含明确分支与目录。不允许默认回退 `main`，不让用户补已知仓库、提交或路径。任何必需值仍未确定，调度应指出缺哪项并由负责人查明，不能输出带空占位符的“可直接执行提示词”。下面花括号是模板变量，正式生成时全部替换。

### 4.1 通用派发模板

```text
当前任务是{任务概述}。你担任{角色名称}，使用{档次}，{新开或沿用线程的具体说明}。这轮只完成{范围}，交回{实际产物}，由{负责人}接收。

仓库：{repository}
唯一写入分支：{branch}
唯一写入目录：{write_scope}
本次派发：{dispatch_id}；依据：{受审设计/候选的固定身份}

先在上述目录的 WRITE_PROBE.md 写入本次派发编号并提交、从同一分支回读。成功后开始实质工作；已存在同一派发探针时核对内容，不覆盖别人的探针。结束删除并回读；删不掉则保留并说明。不得因无写权换仓库、换分支或扩大权限。

按顺序读取：
{逐项实际材料定位及读取用途；独立角色只含允许材料}
不得读取：{本次明确的禁读范围}

{完整角色卡中的任务、读写边界、判断标准、完成要求}

把结果写到{RESULT及实际产物路径}，记录实际读写、未运行项和原始证据。先提交并回读，再回复。不得把历史日志、预期结果或自己摘要写成实际运行结果。

最终用自然中文说明完成了什么、哪些尚不能确定、结果写在哪里，以及需要{接收方}处理的事项。你的结果不代表整个任务冻结或交付。
```

写入测试只证明该指定目录与分支可写，不证明产品环境、安装权限或数据授权。重复恢复同一派发时沿用已经核实的探针记录并重新核对远端，不制造无限探针提交。对于D7/D8，调度器提前完成运输身份核对；其提示词只包含必要定位，不要求它们读取会泄露其他设计内容的状态或全仓材料。

### 4.2 负责人继续工作的模板

```text
继续{任务名称}，沿用当前{D1或X1}线程。先从{仓库和分支}回读{STATE路径}，再读{本次新结果定位}。这是{派发编号}的返回，依据{设计或候选身份}。
核对返回结果是否仍对应当前对象；只采纳仍有效的范围。推进{明确下一动作}，更新你有权修改的记录，并告诉我下一步交给谁。你若是GPT负责人，遇到应转交的修订或外派工作只生成并保存完整中文提示词，准备不记成已执行；你若是Claude负责人，先告知我，再做当前宿主确实支持且已经获准的动作。自己读取、整理和登记结果仍按原职责完成。
```

调度不自动跨宿主发送消息，不假称控制了模型选择、开启了网页线程或收到结果。0.1 的正常入口是负责人读取状态后给出并保存下一条提示词；宿主已有且本任务获准的派出能力只是执行这种决定的方式，不另造自动调度服务。

## 5. 修订分类、事前告知与事后说明

### 5.1 先判语义，再看节点数量

出现以下任一变化即大改：改变需求或允许声明；改变正常入口、最终消费对象、成功/失败/无法判断含义；改变阈值、总体、证据真实度、不可替换方法、允许替代或旧功能承诺；改变权限、数据、费用、账号、设备边界；改变跨组件输入输出的字段含义、调用顺序、失败接收者、角色责任或写入权；或需要用户作新决定。改一个字也可能属于大改。

在上述变化全部不存在后，小修还须同时满足以下全部条件（范围采自设计 B，比 A 原稿的“同一组件最多 3 个叶节点”更窄）：

1. 只影响至多两个既有节点，不新增、删除、替换或重排节点；
2. 不改需求原文或来源；
3. 不改连接、跨组件接口、权威、正常入口、失败路径，也不改任何 D8 读者已经复述过的走查文字；
4. 九项冻结合同的语义哈希（第 6.4 节）不变；
5. 不引入只有用户能决定的新问题；
6. 改动只限错字、同一固定对象的链接或定位修复、文件哈希与提交号、非语义技术说明、实现状态，且字段级差异能证明以上各条。

无法证明任一条时按大改处理；不能靠把多个节点并成一个、或把一次大改拆成几次小修绕过。

**批准继承（已裁决）。** 文档版本与语义版本分开记。满足上述小修条件时，文档版本加一、语义版本不变：原用户批准和原 D6、D7、D8 记录按原范围继续有效，旧 D8 复述及其文字哈希原样保留，D1 追加一份继承说明（逐项写明九项合同为何不变、实际差异、前后告知定位、新的 D5 结果），不伪造新的复述或新的批准。语义版本一旦变化，全部关卡重跑并重新取得用户批准。

| 情况 | 分类与负责方 | 必要处理 |
|---|---|---|
| 同一含义的错字、同一固定对象的链接修复、非语义技术说明 | D1小修 | 事前告知、版本差异、仅重跑D5；按上文“批准继承”沿用原批准与读者记录 |
| 更换接口字段含义、换正常入口、降低或提高合同阈值、删除旧能力 | D1大改 | 回D1汇总，重过D5–D8及用户批准 |
| 日志、选择器、解析器、运行器的等价维修 | X1交付内修改 | 按第7节分类、审查、校准与重验，不自动改Blueprint |
| 宣称只是“更严格”，实际排除原合同允许的实现或增加义务 | D1语义修订 | 不能由X1自行批准 |

小修完成前暂停受影响节点及依赖消费者；其余工作继续。大改也按实际影响控制停工，不为未受影响的已有结果制造重做；重新冻结前不得用旧批准支撑已改变语义的部分。多次小修累计越过同一组件或接口边界时，应按累计差异重判，不能把一次大改拆成许多小修。

### 5.2 修订记录

`revisions/<revision_id>.json` 必填 `id,author_role,from_blueprint,to_blueprint,affected_nodes,dependency_closure,classification,classification_reasons,semantic_comparison,trigger,foreseeability,before_notice,after_notice,diff_ref,gate_effects,approval_effect`。`classification` 为 `minor/major`；`trigger` 为 `user-question/executor-stop/runtime-failure/review/proactive-update`；`foreseeability` 为 `foreseeable/runtime-only/undetermined`，最后一种必须说明缺何证据、谁负责裁定，不能统计成零缺口。

`semantic_comparison` 对照九项合同逐项说明保持或改变的事实，不能只有一个“等价=true”。`before_notice`、`after_notice` 保存确实已给用户看的消息定位和时间；仅写好模板不算已告知。`diff_ref` 指向实际新旧版本差异；没有可定位差异不能复用旧批准。

### 5.3 告知模板

动手前：“我准备修改〔具体内容〕，因为〔事实或问题〕。按流程属于〔小修/大改〕，影响〔节点及用户结果〕；〔暂停范围〕先停，其他部分继续。接下来由〔角色、档次、新/原线程〕完成〔动作〕。”GPT负责人随后给完整提示词；Claude负责人在实际操作前先发这段说明。

完成后：“已把〔旧版本〕改为〔新版本〕，差异是〔会改变理解或行为的内容〕，原因是〔依据〕。这次问题属于〔本可想到/跑了才知道〕，依据为〔简短解释〕。〔关卡和批准的有效范围〕，接下来〔实际接收方和动作〕。”尚不能归因时明确暂未判定及缺少的证据，不用“跑了才知道”掩盖本可查明的设计遗漏。

X1对交付内验收资产变更按第7节留记录，并在交付汇报时一并告诉用户；流程并未要求每个日志或选择器维修都另请用户批准。若动作改变现有数据、费用或权限边界，仍按真实授权范围处理，不能以“小修”免除必要授权。

## 6. 澄清、冻结关卡与合同格式

### 6.1 澄清怎样结束

D1先把每个问题归为三类：只有用户有权决定的偏好、范围、风险、授权与互斥取舍；可从当前源码、文档或实际观察查出的事实；设计者应作出的技术选择。只把第一类交用户，先完成其余两类能够完成的工作。一个问题同时包含事实与偏好时先查事实，再提出剩余的最小选择。

问题记录为 `id,text,category,why_needed,options,recommendation,consequences,source_refs,affected_requirements,status,answer,answer_source,supersedes`。`category` 为 `user/fact/design`；同一选择已存在有效回答时直接引用，不重复提问。新事实推翻回答适用前提时保留旧答、写明重开原因和影响，不能悄悄改写用户原意。每批只问影响当前设计的互斥决定；后续一般实现细节不凑进问题表。

澄清结束需要：会改变设计的用户问题已得到回答，事实问题已查清或以有影响、有负责人、有停止路线的开放节点表达，设计者选择已有理由。开放节点可以存在于D2候选；进入冻结时，影响能力、开工、验收或授权的开放问题必须关闭。不是把未知全部藏进“以后再定”，也不是要求用户保证永不发现新事实。

### 6.2 四个冻结关卡

| 关卡 | 直接检查对象 | 通过标准 | 未通过交回哪里 |
|---|---|---|---|
| D5 | 准确版本的JSON、端口/连接、需求路线、证据来源、历史与所需相邻文件 | 原检查器适用范围真实运行完成；没有结构和跨引用错误；所有叶子是三种合法终点；四环境走查与四问失败路径有真实内容；来源可核对。机器检查不能代替专业与可读性结论 | 设计缺项回D1；检查器/环境问题也回D1说明具体取得办法，结果记无法判断 |
| D6 | 原需求与Blueprint里的所有有效组件 | 逐组件问题都有Blueprint内答案定位；没有漏掉用户正常入口、关键失败、旧能力或必须决定的事项 | D1汇总补缺，按修订范围重判 |
| D7 | Blueprint全文及最小运输封套 | 新执行者无需设计者再决定产品、科研、接口、验收或权限就能开始已定工作；开工阻塞问题为零，允许合同内普通实现自由度 | D1补全设计，不能让冷读者临场设计答案 |
| D8 | 正常与失败走查中每一步、每条失败路径整体说明的当前文字 | 每轮一个新的 GPT 对话合批复述本轮全部待读单位（顺序随机，每个单位只依据自身文字），D1 逐单位对照原意判断；每个单位在最近一次被读时复述正确，文本身份一致，原样复述保留，并记录 `reader_isolation: single-thread-batch`（见第 2.1a 节） | D1 改写读错的单位，下一轮在新的 GPT 对话里重读改动单位及同一步骤或同一失败路径的单位 |

D5–D8可以并行读取同一稳定受审版本。D1收集到修改意见后生成新版本，按实际影响标明哪些旧结果已失效，不能把不同版本各过一项拼成冻结。对首次冻结或大改，四关卡必须共同覆盖待批准的设计；小修按流程仅重跑D5，批准及读者记录按第5.1节“批准继承”沿用。

**检查器接入（已裁决）。** 现有 Blueprint 检查器有一处自相矛盾：起稿指南要求首版保留 `versions: []`，完整结构定义却要求至少一条冻结历史，新设计因此在冻结前永远过不了检查。修法放在 Blueprint 的维护源，不在本仓库复制一份检查器：Blueprint 提供两档入口——**草稿检查**沿用全部结构、端口、引用和来源规则，只是不要求已有冻结历史，冻结前的 D5 用它；**冻结检查**保留全部要求，冻结时及冻结后的 D5 用它。两档都要能区分“结构不成立”“外部证据不可访问”“完整检查完成”三种结果，第三态留在 Assurance 的证据记录里，暂不改变 Blueprint 的进度显示。上游修好之前，D5 结果只能记为无法判断；当前候选保留 `versions: []`，绝不虚构冻结快照绕过检查。

**上游改造的归属（D7 第 1 轮后补定）。** 检查器两档入口是本任务之外的独立前置工作，已由 D1 派出并交付：`YuukiAS/Asteria-Blueprint` 分支 `fix/draft-check-tier-20261111`，提交 `c05edcf`（两档检查、三态退出码、任意 GitHub 来源定位）。Assurance 实施不修改 Blueprint 仓库，只按固定提交调用；该分支并入 Blueprint 主线后，改为固定主线提交，并由 D1 作为小修更新这里的定位。

### 6.3 冻结合同九项

冻结合同本体仍是Blueprint的固定版本。九项通过其需求、节点、接口、验收器、证据及权威关系表达，下面给出每项必须包含的具体形状。`freeze.json`只保存这些内容的节点/字段定位、内容身份和批准记录，不复写第二份可独立修改的标准。

| 项 | Blueprint必须明确的内容 | 推荐定位字段形状 |

| 1. 能力与声明范围 | 每项实际用户能力、支持环境、允许对外声称什么；明确未包含的内容 | `capability_id,requirement_ids,node_ids,observable_result,allowed_claim,scope` |

| 3. 成功、失败、缺证据 | 可观察的三态，哪些观测能支持结论；产品失败与无法观察分开 | `criterion_id,success,failure,unknown,claim_effect` |
| 4. 必需证据与不可替换方法 | 要看何种原始证据、真实到哪层、谁能读；决定语义的方法列为不可替换 | `criterion_id,evidence_types,fidelity,non_substitutable_methods,reader_access` |
| 5. 禁止替代 | 对具体承诺禁止哪些mock、代理、缩范围、低配实现及其可识别表现 | `capability_id,forbidden_substitution,why_invalid,detectable_counterexample` |

| 7. 三类控制例 | 正例应通过、危险坏例应失败、缺证例应无法判断；独立参考及期望结果来源 | `case_id,criterion_id,kind,input_ref,expected_result,oracle_ref` |

在这两个插件自身的候选Blueprint中，九项已有具体设计节点：能力是完整派发/冻结/交付职责；正常入口是规划SKILL与两个Codex执行入口；禁止以文件齐全、旧候选、同线程自审或“缺证默认通过”替代；旧保护包含现有两个维护插件与其他已安装插件；真实验收见第10节。上游检查器两档入口完成并实际通过前，不写成已过D5。

### 6.3a 回归用例集：怎样算这个版本做完（用户决定，2026/11/13）

单个组件的验收器全过，不等于整个东西做完。每次首次冻结或大改，合同都要带一份**回归用例集**；最终候选从正常入口把这份用例集全部跑过，才算这个版本做完。

**每个用例写清五件事：**
1. **来源：** 真实发生过的案例（优先，例如用户实际用过、出过问题的一个 prompt），或者为某项新能力专门写的案例。
2. **输入：** 一次就能给出的完整输入。插件类任务是一条 prompt；软件和网站见下文“不是一条 prompt 的产品”。
3. **看什么：** 最终产出里要检查的具体现象，例如“讲清楚某件事，并且没有未加解释的英文术语”。
4. **谁判、按什么尺子判：** 脚本（能机械判定时）、X5（需要专业判断时）或用户本人。尺子在跑之前写好，判定时看真实产出的全文或实际页面，不看摘要。
5. **期望：** 新版本上应该得到什么；如果来自已经出过的问题，还要写旧版本上的表现。

**数量怎么定：** 不定固定数字，由覆盖规则决定，既不能少到漏掉新东西，也不追求大而全：
- **每一项新能力至少一个用例**（新能力取自冻结合同第 1 项的能力清单）。
- **每一个要修的真实问题一个用例。** 这类用例必须**先在旧版本上复现出问题**，再在新版本上通过；旧版本上复现不出来的，不能证明修好了什么，不计入。新能力在旧版本上本来就没有的，记“旧版本不具备”即可。
- **旧能力不全部重复回归**，只选两类：本次改动实际碰到的代码、共享规则或生成路径所影响的旧能力，每项一个用例；加上一个固定的冒烟集，覆盖最常用的几种旧用法，最多 5 个，跨版本沿用。
- **难度要合适：** 每个用例应能从一次输入、一次输出直接判断；需要多轮来回才能判断的，拆成几个单次用例或改写输入。
- **能合并就合并（用户要求，2026/11/13）：** 一次输入能自然地同时检验几项能力或几个问题时，合成一个用例，不必每项单独一个。合并后的用例逐条写出各自要看的现象和尺子，判定时逐条记录；任何一条不过，整个用例不过，但能看出是哪一条。覆盖规则按“条”计：每项新能力、每个要修的问题至少有一条检查。版本可以分批做，本版本没覆盖的能力留给下一版本的用例集。

**谁负责（不新增角色）：**
- **写用例集：** D1，在设计阶段写进合同；D6 在冻结前核对冻结说明里的用例数量和分组与设计一致。
- **复现旧问题：** X2 在动手修之前，先在旧版本上跑“要修的真实问题”类用例，留下原始输出。
- **跑用例：** 脚本判的由 X2 跑；要在真实宿主上操作的由 X4 跑；要专业判断的交 X5 按尺子判；写明由用户判的交用户。
- **组织和判定：** X1 负责安排上面这些派发，亲自读每个用例的原始输出并逐条记录通过与否；最终候选上整份用例集全部通过，是 X1 签发的前提。

**冻结和判定：**
- 用例集随合同冻结。之后发现新的真实问题可以**追加**用例，但不能删除、替换或改写已有用例和尺子。
- 有用例不过，就是这个版本没做完：回到实现修复，不能换题、不能改尺子、不能用“其余都过了”代替。
- **修复后重跑哪些（用户要求，2026/11/13）：** 开发过程中，修完只重跑没过的用例，以及本次修改实际碰到的部分所对应的用例；不必每修一次就全部重跑。**最终候选确定后，在同一个最终版本上把整份用例集完整跑一遍**，全部通过才算做完；这一遍之后再改代码，就要再跑一遍完整用例集。
- 用例本身被证明写错了（例如期望与已批准的合同矛盾），按修订流程交回 D1，不由实现者自行改。

**不是一条 prompt 的产品（软件、网站、数据分析等）：** 同样的原则，把“一条 prompt”换成“一个写好的场景”：
- **软件或命令行工具：** 一个场景是给定的起始状态加一串固定命令，检查退出状态、输出文件或输出内容，能写成自动测试的就写成自动测试。
- **网站或界面：** 一个场景是固定的操作步骤加固定的屏幕尺寸，用浏览器自动化执行；能机械判断的（元素存在、不重叠、不越界）用断言，观感类的用固定尺寸截图交人或 X5 按尺子判。
- **数据分析或科研计算：** 一个场景是固定输入数据加固定参数，检查输出数值是否落在事先写好的容差内，或与参考结果一致。
- 每个场景仍然要能一次跑完、直接判断；不允许依赖人在中途临场操作。

### 6.4 冻结记录和接收

`freeze.json`必填 `schema_version:"assurance-freeze/0.1",task_id,blueprint_ref,snapshot_sha256,explanation_sha256,bundle_sha256,document_version,semantic_version,semantic_hash,nine_item_refs,gate_refs,open_questions,user_approval,authorization_refs,created_by,created_at`。`nine_item_refs`恰好九项，每项引用现有节点/字段；`snapshot_sha256`、`semantic_hash`、`bundle_sha256` 的定义与用途见第 6.5 节，`freeze.json` 同时记录这三项；`gate_refs`恰好D5–D8并说明覆盖与有效性；冻结时阻塞型 `open_questions`必须为空；`user_approval`含用户实际回答、来源、时间和批准对象身份。未批准时不得生成带批准值的冻结记录。

D1给用户的冻结说明按第 6.4a 节的格式写。用户批准内容版本后，才生成不可变快照和记录。工具成功创建快照不是用户批准；所有必要授权也不能从“同意设计”自动推导。

X1接收记录为 `handoff_id,from_thread,to_thread,freeze_ref,read_artifacts,accepted_at,unresolved`。没有实际读取或仍有影响开工的矛盾时不接手实质实现，写出具体问题给D1；仅缺某项执行环境可在原合同允许的准备范围内处理，不重新制造整轮设计。

### 6.4a 冻结说明的格式（用户决定，2026/11/13）

冻结说明是用户批准前唯一要读的东西。它写漏了什么，用户就等于在没看到的情况下批准了什么。所以每次首次冻结或大改，D1 都按同一个骨架写；骨架固定，内容随任务不同。

**写法要求：**
- 写给用户本人看，用日常语言。正文不出现文件名、路径、字段名、哈希和节点编号；这些只放在附录。
- 正文控制在一页左右；验收器清单可以放在正文之后单独一节，不受一页限制。
- 说明里的每一条都必须能在 Blueprint 里找到出处，Blueprint 里没有的承诺不能写进说明。反过来，Blueprint 里任何会影响用户决定的内容，说明里都不能漏。

**固定骨架（按顺序）：**

1. **一句话结论：** 批准以后会得到什么。
2. **你这次在做的决定：** 批准就等于同意的取舍，尤其是用户没有明说、由设计者定下的默认做法，以及被放弃的方案和放弃的理由。
3. **做完时你会看到什么，你自己怎么验：** 用户能亲眼看到或亲手试的结果，按任务类型写：
   - 网站或界面：有哪些页面，在哪些屏幕尺寸上，大致长什么样；
   - 软件或命令：从哪里开始用，正常情况和出错情况分别得到什么；
   - 插件：装到哪里，怎么调用，在哪些宿主上能用；
   - 研究或分析：结论以什么形式给出，什么结果算失败。
4. **验收器：** 一共多少个，分几类，每类多少个。每类用一两句话说清它测的是什么功能、怎么判通过；需要真实宿主、真实设备或专业判断的验收器单独点名。用户关心的是“测了什么功能”，不是检查项的原文。
   **回归用例集**（第 6.3a 节）：一共几个，按“新能力 / 要修的真实问题 / 受影响的旧能力 / 冒烟集”分别多少个；每个用例一句话说清输入是什么、看什么、谁判；整体规则是全部通过才算这个版本做完。
5. **需要下载或安装的大件：** 单项超过 100 MB 的软件、编译器、模型、数据集、容器镜像等，逐项写出名称、大约多大、为什么需要、装在哪台机器上。没有就写“没有”。
6. **不能降级的：** 实现者不能拿什么来代替。
7. **实现者可以自己定的。**
8. **权限、费用、时间：** 会动哪些仓库和账号，有没有付费调用，大约要多久。
9. **这次不做的。**
10. **和上次批准相比改了什么：** 只在大改后重新批准时写。

**附录：** 要批准的 `snapshot_sha256`、文件 SHA-256 和提交号；D5–D8 各关卡的结果；正文每一节对应的 Blueprint 节点。

**检查：** 冻结前，说明与 Blueprint 一起交给 D6。D6 在原有的逐组件追问之外，再对照 Blueprint 查说明有没有漏写影响用户决定的内容、有没有写 Blueprint 里没有的承诺、验收器数量和分类是否与 Blueprint 一致、大件下载有没有漏。发现问题按 D6 的缺口处理，交回 D1。

**说明的身份（D6 第 7 轮后补定）：** 冻结说明是一个独立文件，它的身份 `explanation_sha256` 是该文件原始字节的 SHA-256（与 `bundle_sha256` 一样不做规范化）。D6 的结果写明它检查的 `explanation_sha256`；D1 交给用户批准时写明说明的 `explanation_sha256`；用户批准和 `freeze.json` 同时记录 `snapshot_sha256` 和 `explanation_sha256`。三处必须是同一个值。D6 检查之后说明只要有改动，原来对说明的检查就失效：由 D6 对新说明重做上面四项检查（Blueprint 没变时，不必重做逐组件追问）。

**大件下载的依据（D6 第 7 轮后补定）：** 第 5 节只能写 Blueprint 里有依据的内容。Blueprint 没有记录某项依赖的大小时，说明必须写“大小未记录”，不能凭常识写“很小”。实施时，执行者第一次下载或安装任何依赖前，先记录它的实际大小；单项超过 100 MB 的，先经用户授权再下载。

### 6.5 冻结对象与语义哈希的精确定义（D7 第 1 轮后由 D1 补定）

**规范化规则（D7 第 6 轮后补定）。** 本规格所有“内容哈希”（`snapshot_sha256`、`semantic_hash`、`brief_sha256`）的输入，都是按 [RFC 8785 JSON Canonicalization Scheme（JCS）](https://www.rfc-editor.org/rfc/rfc8785) 规范化后的 UTF-8 字节，不加结尾换行。JCS 统一规定了键排序（按 UTF-16 码元）、字符串转义（非 ASCII 字符原样输出，不写成 `\u` 转义）和数字格式（ECMAScript 规则），所以同一个 JSON 值在任何一端都只得到同一串字节。实现使用现成库：Python 用 `rfc8785`，JavaScript 用 `canonicalize`，具体版本在实施时固定。共享资源中附一组对照例，包含输入、规范化字节的十六进制和 SHA-256，至少覆盖中文字符串、嵌套对象的键排序和整数，各端必须逐字节通过。`bundle_sha256` 例外：它是冻结输出文件原始字节的 SHA-256，不做规范化。

**三个身份，各管一件事。**

| 身份 | 怎样计算 | 用途 |
|---|---|---|
| `snapshot_sha256` | Blueprint 检查器 `snapshotOf` 取出的内容快照（`title,summary,sources,requirements,nodes,connections,evidence,walkthroughs,failurePaths,failureQuestions,complexityNote`，不含 `id`、`schemaVersion`、`versions`），按RFC 8785（JCS）规范化 JSON 的 UTF-8 字节（不加结尾换行）计算 SHA-256 | 用户批准的对象；D5 草稿档、D6、D7、D8 的结果都绑定它 |
| `semantic_hash` | 见下文 | 判断语义版本是否改变；小修判定与交付派发核验 |
| `bundle_sha256` | 冻结命令输出的、带 `versions` 历史的完整 Blueprint 文件本身的 SHA-256 | 冻结后文件的存档身份；X1 接收时核对 |

**首次冻结的顺序。**
1. D5（草稿档）、D6、D7、D8 对同一 `snapshot_sha256` 全部通过。
2. 用户批准这个 `snapshot_sha256`。
3. 用 Blueprint 冻结命令追加首个版本。新版本的 `snapshot` 必须与获批快照逐字节一致，即重算得到同一个 `snapshot_sha256`。
4. 对冻结命令的输出文件运行 D5 冻结档。冻结档本来就会检查“最新版本快照等于当前内容”，这里再核对它等于获批的 `snapshot_sha256`。
5. 写 `freeze.json`，同时记录 `snapshot_sha256`、`bundle_sha256`、`semantic_hash`。

因为内容快照没有变化，第 1 步的关卡结果和第 2 步的批准继续有效，不需要重新批准；第 4 步只是机械确认，不通过就不写 `freeze.json`，回到 D1 查明原因。`freeze.json` 的必填字段 `blueprint_sha256` 以 `snapshot_sha256` 和 `bundle_sha256` 两项代替。

**`semantic_hash` 覆盖的范围（D7 第 2 轮后修订）。**
- **按排除法计算（D7 第 3 轮后改定）：** 从 `snapshot_sha256` 用的同一份内容快照（`snapshotOf`）出发，**只删去**以下进度、运行和出处字段，其余全部保留：
  - 每个节点（含子节点）的 `designStatus,implementationStatus,evidenceIds,ringLabel`；
  - 每个验收器的 `status,notRunReason,runs`；
  - 顶层 `sources,evidence,title,summary,complexityNote`。

  节点的 `terminal`（包括 `mechanism`、`acceptance`、`retry`、`packages` 等）、顶层 `failureQuestions` 以及以后新增的任何字段，默认都在覆盖范围内。要排除新字段，只能由 D1 修改这份排除清单。
- **计算：** 删去后的对象按RFC 8785（JCS）规范化 JSON 的 UTF-8 字节（不加结尾换行）计算 SHA-256。任何定义内容的变化都会改变它，不需要判断哪段文字是语义。
- **与小修的关系：** `semantic_hash` 改变只说明“定义内容变了”，不自动等于大改。第 5.1 节的小修（错字、非语义说明）也会改变它；这时 D1 写一条修订记录，字段包括 `from_semantic_hash`、`to_semantic_hash`、字段级差异、逐条等价理由和新的 D5 结果，作为一条“继承记录”。
- **派发核验，按阶段绑定不同对象（D7 第 3 轮后补定）：** 每次派发都在派发记录的 `based_on` 里写明绑定对象，再按角色检查：
  - **生成设计或核查事实的角色（D2、D3、D4）：** 绑定“设计任务书”的身份 `brief_sha256`（D7 第 4 轮后补定）。设计任务书是 D1 在 `D1-clarify` 结束时写出的不可变文件 `design/briefs/<brief_version>.json`，字段为 `schema_version:"assurance-brief/0.1",task_id,brief_version,requirements,user_decisions,facts,open_questions,read_allowlist,read_denylist,created_at`：
    - `requirements`：每条需求带原话出处；
    - `user_decisions`：已有的用户决定；
    - `facts`：已查清的事实及其来源；
    - `open_questions`：允许设计者自行处理的开放事项；
    - 读写范围：允许设计者读取的材料范围。

    它只包含需求、决定和事实，不含任何设计倾向，D2 和 D3 读到的是同一份。重新设计或大改时，若需求有变，D1 写新版本的任务书。`brief_sha256` 是对整个任务书 JSON 对象按RFC 8785（JCS）规范化 JSON 的 UTF-8 字节（不加结尾换行）计算的 SHA-256，所有字段都参与，与本节其他身份用同一套规范化规则；派发方、接收方和只读记录检查都按这一定义计算（D7 第 5 轮后补定）。派发记录的 `based_on` 写 `brief_sha256`；之后任务书再出新版本，绑定旧版的结果标为 `stale`，由 D1 判断还能支持哪些部分。D4 若在任务书之前就需要做现实核查，D1 先写一份只含待核实问题的任务书版本。
  - **检查已有设计的角色（D5–D8，包括小修后重跑的 D5、大改后的整轮关卡）：** 绑定本次受审的 `snapshot_sha256`，只检查受审文件确实是这个快照，不检查批准链。首次冻结前没有获批值，也照常派发。
  - **依据冻结合同的工作（X1 接收，X2–X5 的实施、验收、专项和裁判）：** 绑定一个“有效冻结对象”，即获批的 `semantic_hash`，或者从它出发沿完整继承链到达的值。链条断开、有记录不满足第 5.1 节，或者遇到大改记录，就拒绝这次派发并退回 D1。
  - **交付期间出现修订：** 正在编辑的草稿不影响交付派发。未受影响的工作继续绑定原有效冻结对象；只有暂停范围（`paused_scopes`）内的节点暂停派发。小修的继承记录写完后，新值才成为有效冻结对象；大改须重新批准后才替换。
- **为什么这样定：** 覆盖整份定义内容，判定完全机械，不会漏掉写在别处的义务（例如 `dispatch` 里的角色档次）；而错字修复仍可以走小修，不必每次重新批准。D1 的人工判断只出现在继承记录里，并且必须留下字段级差异供事后核对。

## 7. 验收器、候选、证据与签发

### 7.1 验收实现可以修，完成定义由D1决定

验收语义说明要证明什么；验收方法说明观察对象和证据怎样取得；验收实现是脚本、选择器、参考计算、运行器接线及报告生成。D1冻结语义和不可替换方法，X2默认写实现，X3按已定条件独立写相关实现，X1审查所有验收资产变化并决定能否用于当前交付。

| 变更级别 | X1可批准的充分条件 | 校准与证据处理 |
|---|---|---|
| `diagnostic` 增加诊断 | 只增加观察，不代替必需验收、不改变判定 | 诊断本身记录运行；若接线影响正式检查则按机械修复处理 |
| `mechanical` 机械修复 | 观察对象、语义、阈值、覆盖和真实度均未变；例如修路径/选择器/解析/抖动 | 对新验收版本重新跑正、坏、缺证例，并重验受影响的当前候选 |
| `equivalent-method` 等价方法替换 | 对观察对象、阈值、覆盖、证据真实度四项分别有等价依据；不可替换方法不在可替换范围内 | 保留新旧对照、差异解释与三类校准；不能只凭输出差不多判等价 |
| `supplemental` 更严的补充检查 | 新反例或回归已被原冻结义务蕴含，没有排除合法实现或新增产品义务 | 新检查三类校准，保留旧正例仍可通过的证据，验证当前候选 |
| `semantic` 完成定义改变 | X1无批准权 | 给D1提案，未形成新冻结版本前不得替换当前标准 |

每个变化保存在验收资产记录中：`asset_id,old_version,new_version,author,changed_paths,diff_ref,classification,criterion_refs,semantic_invariants,equivalence_evidence,calibration_refs,x1_decision,notice_ref`。`x1_decision`含实际审阅人、时间、接受/拒绝/需设计决定、理由和依据。执行者可以先在自己的候选目录修改检查实现；X1审定前不能替换当前正式验收引用。没有真实权限隔离时，这是可核对的职责规则，不宣称文件在技术上已被锁住。

删用例、换黄金结果、提高容差、改变样本总体、自动接受视觉新基线、取消旧功能保护，都先检查是否改变语义；不能用“测试维修”统称。更加严格的阈值也改变完成定义，不能因为更严便越过D1。

### 7.2 每个关键验收器的三类校准

关键验收器是用于支持冻结能力、禁止替代、旧功能承诺或重要安全边界的正式检查；纯诊断日志不因此成为关键验收器。每个关键验收至少一个正例、一个危险坏例和一个缺证据例，并实际调用同一个验收实现。正确结果应为 `passed`、`failed`、`unknown`；把缺日志报成产品失败或默认通过，均是校准失败。

校准记录必填 `calibration_id,asset_ref,criterion_refs,author_role,reference_basis,cases,environment,runner_ref,executed_at,raw_evidence,assessment`。`cases`每项为 `case_id,kind,input_ref,expected,observed,raw_ref`，`kind`只能是 `positive/negative/missing-evidence`。`expected`由冻结语义和独立参考确定，不从当前候选输出生成；`observed`是实际运行结果。`assessment`是校准是否符合预期，不与候选自己的三态混淆。

坏例必须表达真实的降级或领域错误，例如用源码冒充已安装对象、旧截图冒充当前运行、删除受保护行为、错误公式或误导图；只把指标数值改一位，通常仅能测试阈值运算。缺证例要真正移除或使必要观察不可用，不用错误成品冒充缺证。控制例依据与实际样本身份保留，若被修复使用则进入已知回归，不再叫未见样本。

校准发现验收器太弱需换人重写时，X1必须启用X3；X2不能通过反复改自己的断言取得独立资格。科研数值/统计或安全相关验收，即使X2已经写了检查也须启用X3。新线程减少上下文影响，不保证真值独立；X3应说明解析参考、独立实现或外部标准的来源及共同依赖。

已通过三类校准只证明该验收器能区分这些已知情形。正式交付还需从正常入口跑当前最终成品、保护旧能力，并取得所需X4/X5专业证据。0.1不默认建设隐藏样本服务；只有真实访问权限能限制实现者读取的样本才能称隐藏，否则写可见、未见或后加入样本。

### 7.3 候选与证据的精确绑定

候选提案可以由X2提交，只有X1能在状态中选为当前候选。`candidate_id`在同一任务内唯一；内容改变产生新候选，旧记录不改写。签发对象不仅是代码提交，也包括用户最终拿到的构建、安装实例、部署版本或文档。

| 候选字段 | 必填语义 |
|---|---|
| `schema_version,task_id,candidate_id,freeze_ref` | `assurance-candidate/0.1`、任务、候选和对应冻结合同 |
| `source_set` | 每项 `repository,revision,paths,content_hashes`；无法用单提交描述时完整列出来源集合，不省略未提交内容 |
| `final_objects` | 每项 `object_id,type,locator,sha256_or_observed_identity,identity_method,source_binding`；动态服务另记版本与观察窗口 |
| `build_install_deploy` | 适用的构建/安装/部署记录、来源映射、命令与原始输出；不适用给原因 |
| `runner_set`、`environment` | 检查器版本、实际入口、运行器/插件身份、系统与设备/账号类别、影响判断的配置；不含秘密 |
| `data_and_parameters` | 数据身份、总体/划分与参数/随机种子；若不涉及数据给明确原因 |
| `scope`、`created_at`、`supersedes` | 所验冻结能力、实际创建时间、被替代候选；不靠新编号丢掉旧失败 |

`assurance-evidence/0.1`的单条证据记录包含 `evidence_id,task_id,candidate_id,freeze_ref,criterion_refs,asset_refs,producer,observed_objects,normal_entry,environment,observed_at,raw_refs,assessment,observations,supports,does_not_support,limitations,validity,invalidated_by`。

- `producer`：角色、宿主/工具及实际执行者；不把转述者冒充观察者。
- `observed_objects`：与候选对象逐项匹配的身份和测量层级，清楚区分源码、构建、安装、真实运行。
- `raw_refs`：原始完整输出、全文、渲染、交互记录或数据；含持久定位、内容摘要、可访问受众与敏感级别。路径存在不证明证据质量。
- `assessment`：`passed/failed/unknown`。未运行另以 `execution_status:not-run`记录且 `assessment:unknown`，不能伪造一次运行。
- `observations`：实际事实和数值；`supports`是能支持的能力/主张，`does_not_support`是不可外推范围；不填“所有能力”。
- `validity`：`current/stale/rejected`及原因。旧证据保留，不能删除后当没有失败。

同一关键签发结论必须由最终候选从正常入口直接通过。开发期证据可以帮助返修，不能把多个不同候选各通过的部分拼成交付。纯记录文件更新可以产生新的仓库提交，但若被测源文件集合、构建/安装对象和验收实现均未变，应记录逐文件等价依据，不能改写旧运行的真实提交；凡候选、产物、判据、验收程序、数据或关键环境变化，则将实际受影响证据标为失效，并安排重验。

源码变但构建未更新、构建一致但安装实例不明、URL相同但部署已切换、截图无时间或不能对应当前对象，均不能支持当前真实运行声明。动态服务的证据仅覆盖实际观察窗口，不能自动宣称永久在线。X1须核对身份链，也须亲读内容；哈希相同只解决对象一致性。

### 7.4 偏离与设计退回

X2对每次交回提交偏离表，包括明确“未发现偏离”的声明与核对范围，不能省略。每项为 `deviation_id,candidate_id,requirement_ref,expected,actual,reason,kind,impact,raw_refs,proposed_action,owner,status`；`kind`为 `deviation/substitution/not-run/evidence-gap`。主动申报不等于获得许可，X1应逐项判断能否在冻结范围内返修。

偏离申报模板：“冻结要求是〔原能力或方法〕，当前实际完成的是〔事实〕。差异来自〔原因〕，影响〔范围和声明〕，依据在〔原始记录〕。建议〔同任务返修或交D1〕。没有运行/没有取得的部分是〔明确内容〕。”禁止把一串绿色检查当作“无偏离”的替代。

X1只用以下五种 `return_reason`退回设计，并附原始证据：`contract-conflict-or-missing-decision`、`new-fact-invalidates-design`、`required-method-impossible-without-equivalent`、`completion-standard-change`、`user-only-decision`。记录 `return_id,reason,freeze_ref,affected_nodes,dependency_closure,evidence_refs,attempted_in_scope_repairs,decision_needed,proposed_options,paused_scope,continuing_scope`。技术失误、暂时环境故障、一般缺证与明确范围内的程序修复留在X1同一任务。

退回模板：“当前卡在〔具体事实〕，它命中〔五类中的一类〕，涉及〔冻结条款及节点〕。已尝试的合同内处理是〔实际做过的动作〕，仍不能解决的原因是〔证据〕。请原D1决定〔最小设计问题〕；〔受影响部分〕暂停，〔不受影响部分〕继续。”没有真的尝试过就写未尝试及原因，不为填表制造高成本试验。

### 7.5 X1签发清单与签发记录

X1本人依次核对下列条件，任何必需项仍为失败、无法判断或过期，都不签发整个冻结范围。0.1 只支持对整个冻结范围一次签发：不做分单元签发，也不能通过临时缩小声明把缺项变成交付。确实需要分批交付的，在设计阶段拆成多个任务，各自冻结、各自签发（D7 第 2 轮后收窄）。

清单逐项记 `yes/no/unknown`，任何 `no` 或 `unknown` 都不能写成无条件交付（条目合并了设计 A 的八项与设计 B 的十三项）：

1. 当前冻结版本、Blueprint 哈希、`semantic_hash`、用户批准、实际执行授权与任务/分支一致，设计退回已经关闭。
2. 当前 `candidate_id` 就是用户将收到的最终对象：最终源码集合、构建/安装/部署或最终文档身份与受验对象一致。
3. 每项冻结能力、不可替换方法、禁止替代与旧功能都有对应直接证据或冻结合同明确规定的人类判断。
4. 关键验收资产已由 X1 审定，并完成正例、坏例、缺证例三类校准。
5. 正式验收、回归和专项检查都作用于同一最终候选；最后一次证据之后候选未再改变。
6. 正常入口的完整成功链真实发生，关键坏例不会产生被禁止的成功产物，缺证例没有被默认通过；不能只验保守拒绝。
7. 旧能力和代表性回归未退化。
8. X3/X4/X5 已按条件启用，结果覆盖正确对象；未启用者有未触发条件的具体依据。
9. 所有偏离、替代、未运行项和证据缺口都有处置，不能因无人提出便视为不存在。
10. 权限、数据、费用、账号和设备边界没有越界。
11. X1 亲自读取最终产物与承载关键结论的原始证据，记录具体观察、矛盾处理和结论；实现者摘要仅作索引。
12. 合同要求的用户验收已有实际结果；修订已按规定前后告知。
13. 对外声明没有超出冻结范围和实际证据，交付文件或安装对象可被用户取得。

签发记录为 `schema_version:"assurance-release/0.1",release_id,task_id,issuer_thread,freeze_ref,candidate_id,delivered_objects,criterion_evidence_map,acceptance_asset_decisions,role_evidence,personal_reading,disposition_of_deviations,user_acceptance,claim,issued_at`。`personal_reading`每项包含 `object_or_evidence_ref,read_at,observation,conclusion`；一个“已读=true”不够。`criterion_evidence_map`逐项指向当前原始证据，不仅指向汇总报告。签发后回读记录与最终对象，状态才进入 `delivered`。

若用户明确否定真实产物，X1回读产物并按冻结标准处理；内部通过不能推翻真实失败。

**签发后的撤回（D7 第 2 轮后补定）。** 撤回只由 X1 决定，而且只针对整份签发（0.1 没有分单元签发）。
1. 签发后出现可能推翻结论的新事实时，X1 先登记这个事实，暂停对外的交付声明。状态写入：`phase` 从 `delivered` 回到 `delivery`，`step` 为 `X1-review-release`，`delivery.release_ref` 保留原签发。
2. X1 按冻结标准核对后，作出“维持”或“撤回”的决定，写不可变记录 `delivery/revocations/<revocation_id>.json`，字段为 `schema_version:"assurance-revocation/0.1",revocation_id,task_id,release_ref,decision,trigger_ref,evidence_refs,invalidated_evidence,reason,decided_by,decided_at`，`decision` 取 `upheld` 或 `revoked`。
   - **维持：** 状态回到 `delivered`，原签发继续有效。
   - **撤回：** `delivery.release_ref` 置为 `null`，原签发记录原样保留为历史；`invalidated_evidence` 中列出的证据标为 `stale`；`step` 进入 `X1-repair`，若命中五类设计退回条件则进入 `X1-design-return`。之后按正常返修流程重新取得证据，签发一份新的记录，新记录的 `supersedes` 指向被撤回的签发。
3. 只读记录检查入口增加记录种类 `revocation`，并核对 `release_ref` 指向的签发确实存在。

原签发记录永远不改写，也不删除。

## 8. 衡量记录

衡量只服务流程改进，不额外给用户增加填表工作。负责人从已存在的疑问、退回和修订记录生成三项汇总，并保留原始事件定位。每个事件有 `event_id,task_id,freeze_ref,occurred_at,source_ref,related_ids`，同一问题的连续追问共享问题编号，重复转交不重复计数；用户发现了不同缺口则分别记。

第一项是冻结后用户仍问的“本可想到”问题数。每个用户问题保存原话、涉及节点、发现时的冻结版本、归因及理由；设计者当时已有材料足以推出的遗漏算本可想到，只有新运行事实才能暴露的算跑了才知道。未能判断的另报数量，不能按零处理。归因可修订，但必须保留原结论与新证据。

第二项是设计退回次数及五类原因。X1每次实际退回算一次事件；重复发送同一请求不增计数，实质不同的新退回保留新编号。交付内返修另列作诊断，不混成设计退回，也不能为降低统计把真正的语义变化留在交付端。

第三项是修订事前和事后是否都告知。每条修订对照实际通知时间、动手时间、完成时间与消息定位，分别记录已告知、未告知或无证据；事后补录不能伪装事前已告知。汇总显示应告知条数、实际完成条数和未完成事件，不靠生成了模板就计成功。

0.1不设“必须零追问、零退回”的发布阈值，因为现实新事实可能合理出现；发布首先要求记录可信、缺口能回到正确负责人、用户不用自行编排下一步。任务结束由D1/X1依据原始记录说明哪些缺口应进入插件回归，单个项目的专业细节仍留在该项目，不上传中央公开仓库。

### 9.2 Claude Code 与GPT Work怎样读同一规划规则

派发或入口参数必须给出“源仓库及固定提交”，或“宿主确认实际可读的完整插件根目录”，不能只给一个技能名称。0.1规划端正式路径是从前一种定位读取规划 `SKILL.md`，再从同一提交的 `shared/assurance/`读取支持文件；只有宿主确实开放完整包时，才从确认过的包根目录读取相同资源。正文引用这份已确认资源根，不用固定的多层 `../` 链假装同时适配两种布局。包内 `planning/`是随包资料，不承诺宿主会把它自动发现为技能或允许技能资源工具访问任意包根目录。不得以当前工作目录猜来源，也不得在包资源缺失时偷偷读取别的版本。缺资源就报告实际缺项，不能把只读了入口标题称为已加载完整规则。

Anthropic官方说明Claude Code支持 `SKILL.md`、YAML元信息和支持文件；OpenAI官方说明相同技能结构用于ChatGPT与Codex。[官方技能资料](https://code.claude.com/docs/en/skills)与[OpenAI技能资料](https://developers.openai.com/plugins/build/skills)支持同源内容复用。任意仓库路径自动发现、自动安装、自动新建GPT Pro网页线程和自动选择“极高”并不能由文件格式推出，本设计不作这种承诺。Claude专有 `context: fork`只能在实际支持的宿主使用，并检查上下文传递；它不是隐藏用例权限。

0.1的跨宿主最低验收是：两个规划宿主实际读取同一候选正文、至少一张角色卡和一份模板或结构定义，证明资源来自同一固定来源，分别从已有任务状态生成正确下一步；GPT Work能在执行端·专业任务里消费同一角色合同；Codex从安装后的正式执行入口收到派发、完成角色工作并回读结果。源码可读不等于安装成功，某一个宿主成功也不替代另一个宿主的观察。

### 10.2a 本插件 0.1 的回归用例集（按第 6.3a 节，D1 补定，2026/11/13）

### 10.3 留到0.2或以后

可延后的是跨宿主自动新建/恢复线程、自动发消息、后台调度、任务看板界面、中央数据库或服务、隐藏用例基础设施、通用验收器平台、所有项目预设适配器和历史任务自动迁移。ChatGPT 网页端打包已按用户决定纳入 0.1（第 9.4 节）。它们不是0.1正确性的前提；有真实任务证明文件与现有入口不足时，再提出明确增量。

0.1也不承诺所有复杂任务都不再发现设计缺口、独立模型不会误判或纯文件权限能阻止有写权的人篡改。能够承诺的是：缺口与偏离会按规定留下证据和接收方，无法判断不会被写成通过，最终签发明确绑定当前成品，用户能直接拿到下一条完整提示词。
