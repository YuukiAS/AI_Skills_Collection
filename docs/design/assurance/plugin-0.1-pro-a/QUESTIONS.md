# 需要设计负责人收敛的三个问题

流程0.1已经明确角色、档次、验收器归属、修改权限和退回条件，本候选直接落实这些决定。下面只保留会改变实现范围或批准含义、不能由D2自行宣布成立的三项。建议D1先裁决技术接入与仓库实施范围；只有第二项涉及已认可流程的批准解释时，需要用户明确确认。它们不影响本轮独立候选交回，但必须在对应能力冻结前解决。

## Q1：Blueprint检查与冻结怎样成为新插件可调用的通用入口？

**为什么需要决定。** 指定的起稿指南要求首次保留 `versions: []`，完整结构定义却要求至少一个冻结版本。现有完整检查还把结构检查、读者记录和特定项目的疑问位置绑定在一起，不能直接用于一个新插件任务。验收运行结果也没有“无法判断”。若直接说现有命令开箱即用，会让D5与首次冻结互相等待，或诱使实现者造历史、换项目名、压掉缺证结果。

**需要谁决定。** D1决定采用哪条适配路线、哪个仓库承担通用接口及本次实施边界；若要在本轮指定写入范围之外实际修改上游，应由后续明确授权的任务处理。本设计没有修改外部仓库。

**选项。**

1. 在Blueprint维护源提供明确的草稿检查、正式冻结检查和通用项目参数，再由Assurance调用。草稿检查复用原结构、端口、引用和来源规则但不要求已有冻结历史；冻结保留四关卡与用户批准；第三态留在Assurance证据记录，暂不改变Blueprint进度算法。
2. 在AI_Skills_Collection写一个薄适配层调用Blueprint已有校验模块，显式传入草稿阶段与本任务疑问/读者记录；上游未来再一般化。必须证明没有复制或省略原规则，也不能用自己的弱检查冒充官方完整检查。

**推荐。** 选项1。把检查器的通用问题留在其维护源，Assurance只保留调用合同和失败处理。0.1无需顺带重做Blueprint界面，也无需为第三态立即扩大它的显示结构；候选与证据记录独立保存三态即可。建议接口必须能区分结构不成立、外部证据不可访问和完整检查完成，避免全部塞进一个失败码。

**未决定时怎么走。** 本候选保持未冻结，能完成其他设计与普通格式诊断；不能给D5通过或承诺完整冻结能力已经可用。状态与角色卡等不依赖此选择的部分可以继续准备。

**依据。** `YuukiAS/Asteria-Blueprint`，分支 `draft/blueprint-round7-20261107`，`docs/planner-guide.md`、`docs/content-model.md`、`content/blueprint.schema.json`、`content/check.mjs`、`content/freeze.mjs`、`content/round7.ts`、`content/validation.ts`。

## Q2：冻结后的小修怎样继承原批准和读者记录？

**为什么需要决定。** 流程一方面要求D5–D8全部通过且用户批准才冻结，另一方面明确小修只重跑D5。指定Blueprint实现对正文任一句变化都会使读者记录失效。若每次错字修正都重新跑全部关卡并请用户批准，小修规则无法生效；若任何新版都自动继承，又会给改变完成标准留下通道。

**需要谁决定。** D1先给出对流程的解释并让用户确认批准继承的含义。X1和执行者没有权临场解释“用户到底批准了什么”。

**选项。**

1. 区分文档版本和冻结语义版本。满足本候选的小修判据时，文档版本增加，语义版本不变；D1记录九项语义逐项等价、实际差异、前后告知和新的D5结果。原用户批准及未变关卡按明确范围继承，原D8复述和旧文字哈希保留原样，新增继承说明而非伪造新复述。语义变化仍全套重过关卡并重新批准。
2. 只允许完全不触及已复述正文、接口或九项合同内容的改动走小修；触及这些内容一律按大改。规则机械清楚，但会把无语义变化的文字修订也升级，增加等待。

**推荐。** 选项1，前提是D1必须逐项证明等价，不能仅填一个布尔值；无法证明时按大改。继承是已有批准适用范围的记录，不是新用户批准，也不是D8重新通过。Q1的检查器接入须能识别这种明确的继承关系，不能让工具偷偷绕过当前记录要求。

**未决定时怎么走。** 保留原冻结版本；提出小修差异但不激活新版本。受影响部分等待D1决定，其余依原合同可继续。首次冻结和已经确定的大改不受此问题影响，仍须四关卡和用户批准。

**依据。** 本仓库 `docs/design/assurance/ASSURANCE_PROCESS_V0_1_20261110.md` 第3、7节；`YuukiAS/Asteria-Blueprint`，分支 `draft/blueprint-round7-20261107`，`docs/planner-guide.md`、`content/readability.ts`、`content/check.mjs`。

## Q3：新增两个执行插件时，市场容量调整是否纳入同一实施合同？

**为什么需要决定。** 当前市场已经有10个插件和30个可调用技能，配置及生成器分别把上限设为10和30。本候选采用两个独立插件、各一个执行技能，不把13张角色卡暴露成技能；仍需要12个插件和32个技能。仅写新目录而不处理约束，生成与普通安装入口就不能成立。

**需要谁决定。** D1在汇总实施范围时确认即可；无需重新问用户是否还想要已经明确要求的两个插件，也不需要重新设计原有插件组合。

**选项。**

1. 同一实施合同中把预算调整为12个插件、32个技能，同步相关断言、说明和回归；保留原有全部能力。
2. 0.1先从独立本地包安装两插件，中央市场接入后移。必须据此收窄分发声明并取得相应范围决定，不能声称中央市场入口已完成。

**推荐。** 选项1。它与用户要求直接可用的两个插件最一致，也避免引入另一套长期分发路径。两份规划正文作为包内资料直接读取，不作为额外市场技能；后续网页端另打包仍按流程安排。

**未决定时怎么走。** 可以完成源技能和包结构设计；不能声称中央生成、安装与0.1完整分发已经通过。不能偷偷删旧技能腾位置，也不能不说明就抬高上限。

**依据。** 本仓库本分支 `scripts/codex_marketplace_config.json`、`scripts/build_codex_marketplace.py`、`docs/workflows/PLUGIN_VERSIONING_AND_CHANGELOGS.md`。

## 已由设计A直接细化、不再要求用户重答的事项

默认任务目录、单状态写者、结果去重、基线冲突处理、角色输出格式、三态记录、提示词变量、无服务的打包结构均已有具体方案。D8的步骤单位按指定Blueprint指南取正常走查每一步、失败路径每一步及整体收场说明；不把每条工具调用变成新的审查。小修“最多同一组件3个叶节点”是本候选的可判定细则，D1可以在两份方案收敛时比较，不必单独向用户发起技术选择题。

不重新开放这些已有决定：D2必跑、D3按条件且本轮已启用；D1/X1不同线程；X2默认编写验收实现；指定高风险与弱验收必须X3；开放专业判断必须X5；签发归X1；新会话不等于隐藏用例；旧报告通过不等于新插件完成。
