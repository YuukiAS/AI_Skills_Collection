# 产品开发交付纪律：修订完整版 v2

日期：2026-09-14  
性质：附件《Lite Handoff Completion Discipline》的完整修订提案。本文及关联 TODO 的提交仅是设计与维护记录，不代表插件、Bridge Kit 或各项目的本地安装已升级。不是本轮产品开发执行授权，也不自动覆盖已冻结任务、权限或合法状态机。

## 一、问题判断与证据边界

需要解决的不是“让用户把要求再说清楚”，而是代理反复把产品经理、设计师、测试员和调试员的工作交还用户：需要人工操作时不明确询问，能够自行检查的明显问题却反复要求人工验收；增加代码和测试数量，却未证明原始使用路径真正可用。

本提案结合用户本次反馈、所附 22 条初稿、可检索的历史对话片段，以及当前远端仓库文件。历史检索不是完整聊天导出；没有取得全部 thread 标题与上下文。本轮也没有运行任何用户机器上的应用。因此下列案例是事故记录及规则分析，不是“当前版本仍然有缺陷”的现场判定。

| 案例 | 已有依据 | 能说明的问题与边界 |
|---|---|---|
| Bobbio 反复视觉返修 | 9 月 14 日可检索片段要求回到 Figma；中央 Frontend Design TODO 记录无语义的大圆形、相邻控件样式不一致、重复入口和未设计状态 | 设计源没有真正约束实现；不能用局部 CSS 修补替代整屏设计。未重新检查当前原生应用。 |
| Lucerna 关闭/隐藏与刷新 | 用户本次明确反馈关闭叉号越修越差；当前 AGENTS 已要求真实 Windows 点击、隐藏而非退出、刷新反馈、真值和同批回归测试 | “已有规则”不等于执行入口真正遵守；缺的是针对性测试和原生交互闭环。没有可靠恢复那次聊天的完整标题与日期，不杜撰。 |
| Mica 反复真人验收 | 9 月 14 日检索片段要求先止损，Copy 与 connector residual 要有真实失败证据、旧实现失败和新实现通过后再真人确认；仓库已有限制重跑和真实浏览器安全边界 | 不能以不忠实的模拟场景与测试通过替代真实故障，也不能用用户重试充当开发循环。对话片段的要求不是本轮操作浏览器的授权。 |
| SeminarArc 验收责任 | 9 月 13 日检索片段要求独立产品/设计验收，而非 Codex 自称完成；当前用户报告未完善 Figma 就乱设计 | 支持把实现声明与产品验收分开。未取得对应按钮/箭头事故的完整历史原话，具体视觉表现只按本次用户报告记录。 |

这些案例不能证明每次任务都真正加载过同一个插件。因此先区分：规则缺失、已有规则未执行、插件未触发、项目代码缺陷、工具/宿主能力缺失；不能直接把所有失败都断言为某插件的实现 bug。

## 二、职责放置

| 层 | 应承担什么 | 不应承担什么 |
|---|---|---|
| Lite / 项目 AGENTS 的短底线 | 原目标不可偷换；需要用户时显式询问；不重复索取同范围授权；变更与测试配对；遵守既有设计；保留未完成项；引用正确插件/项目规则 | 不复制整套详细设计/测试手册；不另造状态机；不靠插件是否加载决定基本诚实性 |
| Verified Workflow（workflow-core） | 识别任务边界、选择证据、安排人工介入、制止无信息重跑、核对交付与恢复路径、调用专业能力 | 不判断图标该用哪套、按钮该多宽；不复制 Bridge Kit 的运行时与审批实现 |
| Frontend Design（web-development）及平台专业能力 | 设计完整性、Figma 往返、交互状态、整屏质量、原生/网页/模拟器的适配验证 | 不决定用户授权；不新增通用审批或运行状态 |
| Bridge Kit | Lite 模板分发、宿主交互/恢复/交接能力与合法状态映射；在证据证明底层有缺陷时修复它 | 不承担产品视觉设计；不因行为规则不足就新建 runner、ledger、watcher 或无限重试框架 |
| 项目仓库 | 项目特有产品不变量、真实 bug、具体测试、设计位置、已接受行为、待解决产品工作 | 不保存第二份中央插件 TODO；不让普通 Executor 自行扩张全局政策 |
| AI Skills Maintainer（ai-skills-core） | 去重、确定 owner、检查实际调用与安装版本、推动可验证的规则落地 | 不把“TODO 已记录”写成“生产已修复”；不把单次产品偏好升级为通用禁令 |

推荐是“短底线常驻，详细流程按需加载，专业标准由专业插件负责”，不是两边各复制一份全文。旧插件缺席或触发失败时，短底线仍然有效；详细条款只读取本次任务适用部分。

## 三、供 Lite / AGENTS 使用的完整短底线

以下是未来经授权更新模板时可采用的完整短块；本轮未安装到任何项目。

1. 开始前确定本次原始目标、当前对象/版本、适用设计源、关键验收和已接受的不变量。小修用短说明即可，不为每次修改制造长计划。
2. 只有用户能够完成的动作或决定一旦成为前置条件，立即通过可用的用户交互通道明确询问；没有专用工具就发清楚的可见消息并保存恢复点。不得静默等候、用轮询代替询问，或标为完成。已明确批准的同一范围不得再问；新范围必须重新授权。
3. 每个新增功能、行为变化和 bug 修复都要在同一批变更中包含匹配的测试；测试已有覆盖时指出对应断言。无法自动化的目标边界必须说明缺口，并提供可重复的最小检查，不用截图代替可写的逻辑测试。
4. 先复现并解释故障，再做最小修复；代码、构建、模拟场景或自审通过，不等于真实用户路径通过。证据必须绑定本次对象、环境和构建，不得拿旧产物或另一测试界面冒充。
5. 有明确 Figma/设计源时必须遵守。设计本身需要改变或缺状态，先补设计；实现偏离设计则修实现。禁止顺手增加未设计的按钮、箭头、装饰和交互。
6. 交付前自行走通受影响的主要使用路径，检查整屏质量及关联既有行为。明显问题不得交给用户或外部审阅者当第一轮质量检查。
7. 相同故障再次出现或重跑没有新增证据时，先核查诊断、测试忠实性和候选版本；不得无变化地继续跑或继续叫用户试。只暂停受影响路径，其他已授权且独立的工作可以继续。
8. 用自然中文区分做完、未做、失败、待用户动作及恢复方式；遵守现有合法状态，不发明状态字段。产物放入项目规定目录；AI_Skills_Collection 的不可公开交付物放在 repo 内 `private/exports/`，不把 repo 外临时目录作为交付位置。只在发现实际新问题时去重记录，项目问题留项目、插件问题进入中央 owner TODO。

## 四、完整执行规则（替换附件初稿，不是补丁）

### 1. 可恢复的用户动作必须显式请求

先判断缺的是能自行查到的事实、已获授权的普通操作、仅用户能做的操作，还是新的产品/风险决定。前两类自行处理；后两类及时询问，不要等本轮耗尽或写最终报告才说。

询问须说明：为什么需要用户、准确窗口或页面、一个最小动作、预期看到什么、用户只需回复什么，以及确有风险时哪些操作不要做。能由代理安全收集的路径、日志和文件不交给用户找。可预见的账户、设备或权限依赖在任务开始时集中辨认；后续仅问新增缺口。

优先使用宿主实际提供的用户输入工具；没有该工具就使用可见消息并暂停依赖步骤。只写文件、只写日志或反复检查用户是否回应，都不算询问。不得声称桌面通知已发送，除非真实工具结果证明。用户答复后从保存的同一步恢复，不重新做整轮验收。

“等待用户”“等待外部”和“不可恢复失败”在语义上必须区分，但映射到各系统现有合法状态；不能把某系统允许的 `blocked` 一概宣布非法，也不能把一次请求后的等待伪装成终态成功。

### 2. 不得提前宣布完成

完成标准来自原始请求的正向结果。提交代码、测试通过、出图、建立任务、完成某阶段或写自审，都不能替代用户要求的真实结果。

但只要求设计、计划或只读诊断的任务，完成相应产物即可；不得擅自追加实现、上线、真人验收等门槛。发现提前完成，应纠正声明，在权限和现有协议允许时恢复当前任务，并明确剩余条件；不改写已接受的历史证据。

### 3. 当前证据的相关性优先

证据要匹配目标的版本、环境、页面/窗口、数据类别和时间。现场故障应优先核实当前可观察状态，但截图不是对原因的最终证明，仍需与日志、测试和实现交叉核对。

现场暂不可读时，暂停依赖现场假设的破坏性或高风险动作；允许继续已授权的静态分析、隔离复现和有明确依据的可逆修复。旧证据可帮助诊断，不能冒充当前现场通过。除用户明确要求更严格前置条件外，不因缺一个现场步骤就冻结整个项目。

### 4. 修复前定义准确故障

写清实际表现、发生位置、预期行为、复现条件、证据以及本次假设。一个窄问题不需要全仓审计。

确定性 bug 原则上用同一相关测试证明旧实现失败、新实现通过；先检查旧环境与依赖，避免把环境差异当修复效果。不能为了制造旧失败，危险地回退真实数据或线上系统。间歇故障、性能问题及无法保留旧二进制的情况，使用可追溯现场记录、受控重复测量或替代证据，并明确证明强度，不伪造旧失败。

### 5. 新功能与修复都必须有针对性测试

不只 bug 修复：新增功能和行为变化同样需要匹配测试，覆盖成功路径及本次风险相关的失败/恢复路径。修复优先增加会抓住旧故障的回归；已有测试足够时指出具体断言，不能为了数量重复增加。

逻辑可自动测试就写自动测试；截图、人工检查和静态字符串扫描不能替代逻辑断言。原生交互、视觉或真实服务可补专门证据，但要说明自动化与人工分别覆盖什么。闭环记录用中文说明“旧问题—修改—新结果—防复发检查—真实入口”；现有协议需要机器字段时继续用其已有字段，不创建新 schema。

### 6. 验证真实交互结果

对本次新增、修改和受影响的按钮、菜单、开关、刷新、复制、恢复及生命周期步骤，验证可见、可达、可激活、目标状态改变、反馈可理解和忙碌状态能结束。检查重复点击、取消、失败、恢复、异步完成等与本次风险相关的情形。

控件渲染出来、命令存在或类型检查通过，都不能证明交互有效。并非每个小改动都重测整个产品所有控件；范围由依赖和风险决定。

### 7. 按缺陷所属层修复

逻辑、状态、缓存或生命周期错误必须修对应行为，不用文案、动画和 CSS 掩盖。视觉错误同样是产品缺陷，不因“功能能用”而延期；布局、命中区域、原生窗口区域也可能影响点击。

先判断是设计缺口、实现偏离还是行为错误。逻辑修复与设计工作可以并行；不得把“逻辑优先”理解为允许先随意设计、以后再补 Figma。

### 8. 保护已经接受的工作

修改共享组件、状态或运行逻辑前，识别受影响的既有行为；修改后做针对性回归，不为形式重跑所有旧里程碑。

例如 Lucerna 的关闭隐藏到托盘、托盘恢复、不擅自加拖动、刷新非阻塞，属于项目具体契约，应留在该项目并落实到测试，不写成所有产品的通用交互。

### 9. 真实值、缓存值和未知值必须诚实

真实数据、最后一次成功数据、过期数据、模拟数据、未配置、无权限、不可用和加载中必须可区分。缓存允许显示，但需要合适的时间/新鲜度说明。

确实未知时可以显示未知；禁止为了界面好看编造数字，也禁止在产品要求保留上次成功值且该值仍可用时无理由清空为未知。不能把缓存说成刚刷新成功。不要把某产品应显示的额度或状态泛化为所有产品必须取得的服务数据。

### 10. 目标界面必须有对应证据

网页模拟不能替代要求的原生桌面、真实浏览器、移动端、真实服务或真实用户数据边界。测试证明其覆盖的那一层，声明不得超出证据。

原生应用检查必须识别确切构建和启动入口，不能测试了新源码却让用户打开旧应用。Android 模拟器可覆盖其适用边界；只有任务需要的硬件行为才要求真机。原生证据优先只捕获目标窗口；任务需要托盘或系统布局时才纳入周边，避免扩大隐私暴露。

### 11. 视觉质量与整体一致性

可见变更应与同尺度、相应状态的基线/设计比较。除溢出、对齐和可点击性，还检查整体层级、主要任务、控件家族、图标来源、密度、空状态和交互状态。

无语义装饰、重复入口、过度强调维修/诊断操作、无规则的箭头按钮，以及看起来像调试面板的界面，都应在交付前自行发现。判断依据是当前产品设计与平台约束，不统一强迫所有产品使用某种审美、图标库或尺寸。

### 12. 测试报告解释保护了什么

不要只报告命令全绿或测试数量。简短说明每组测试防止哪个用户可见失败、覆盖哪一层，以及哪些目标仍未验证。

开发循环优先最小相关测试；候选稳定后才跑所需完整测试。未影响相关行为的纯文档变化不要求全套产品测试。禁止为提高成功率修改验收含义、削弱断言或把故障路径移出测试。

### 13. 人工验收不是开发调试器

调用用户前，代理须完成自己能够安全执行的检查、准备准确候选与稳定启动入口、消除已知明显缺陷，并只把确实剩下的人类动作交给用户。

诊断采样与最终验收分开：缺少真实场景证据时，可以明确请求一次最小诊断，不假称“已经修好请验收”；用户明确要求先止损或停止人工测试时，必须遵守。不能用“人工预算”作为拒绝必要询问的借口。

上轮人工失败后，再次请求前须说明新增了什么证据、修了什么原因、哪个测试能抓住旧失败。没有变化不重复请用户试。不要让用户重新提供已经获得的回答或同范围授权。

### 14. 提示词必须完整且可执行

用户要求生成或修订提示词时，提供完整新版，不只给补丁。包含本次目标、当前事实、允许和禁止范围、所需证据、关联检查、人工依赖和结束条件。

已有权威文档可引用精确位置，不把全部历史规则复制进每个小任务。按项目规定落盘，注明应在哪个现有任务继续；需要新任务时说明具体原因，不要求用户猜工作流。

### 15. 工具不适用时停止冒充

原生控制、浏览器工具或截图工具不能可靠完成目标动作时，说明具体失败并暂停依赖路径；不能拿假点击、未经授权的注入、旧截图或另一个界面冒充成功。

本地隔离测试可以合法使用测试框架、程序化事件和模拟接口；它们不是现场黑盒证据。允许符合既有授权、隐私及任务限制的等价诊断工具，但不可绕过被明确拒绝的权限、数据或操作边界。优先修复已有 helper，不无限发明新工具链。

### 16. 真实数据、账户和生产安全

遵守当前任务确切的设备、数据、服务、用途、凭据和费用边界。同范围已明确授权的动作不用重复审批；扩大边界必须询问。repo 里的计划不自动等于当前操作授权。

隔离 profile 不等于隔离数据目录，fixture 不等于可任意上传。不得未经授权改真实库、会话、更新器、系统服务、网络配置或基础设施。敏感证据留在项目允许的私有目录，不提交密钥、原始私密内容或未经批准的截图。

### 17. 尊重里程碑范围

本轮只做本轮承诺的产品增量。不要因测试顺利就自行进入下一阶段，也不要让已接受里程碑每次重新接受完整验收。

复用历史证据时保留其历史身份；本次影响到的行为须补新证据。目标拆分不能成为提前宣布整体完成的借口。

### 18. 自审不等于独立复核

生产者必须先检查自己能发现的明显问题，独立审阅者再确认盲区及规定的产品质量。审阅者应直接查看相应证据，不照抄生产者的成功字段。

独立复核、外部模型和真人验收仅在任务、风险或既有规则要求时引入，不自动给每次小修增加付费审阅或多角色流程。不得让同一执行者换个角色标签自称独立确认。

### 19. 复用权威辅助工具

截图、原生启动、探针、构建、打包和证据收集优先复用仓库已验证的工具。工具失效时先确认输入、版本、平台和权限，再做有限恢复。

普通修复不顺手重写共享工具或全仓政策。必要扩展在权限内增加针对性测试；超范围则留下准确建议。收集的证据和用户要下载的产物按项目规则落盘，不用临时控制台输出代替。

### 20. 基础设施替换先建后拆

仅在基础设施任务适用：验证新路径就绪、关键服务可用和回退方式后，才退役旧路径。用户只授权备路时不碰主路，只授权诊断时不实施修复。

这不是所有产品小修都需要的额外阶段，也不允许以“保可用”为名无限保留竞争性恢复进程。

### 21. 最终报告必须反映真实状态

先用自然中文说明用户现在能做什么，再说明完成了什么、未完成什么、证据边界及需要用户的唯一下一步。内部状态继续遵守已有协议，不强迫用户阅读一屏机器字段。

分清做完、部分完成、验证失败、等待用户、等待外部、未知和未测试；不得把未验证藏在成功摘要里。写回文档、推送仓库、升级本地安装、运行新构建和实际验收是不同事实，逐一按真实结果说明。

### 22. 一句话完成定义

在本次请求的范围内，所要求的正向结果已由对应证据确认，新增/修改行为有匹配检查，受影响的已接受行为未退化，数据与声明真实，所要求的设计质量没有降级；必需的人类或独立验收完成后，才可称整体完成。

仅要求计划、诊断或设计产物时，按那个产物的完成标准结束，不擅自扩为产品实现。

### 23. 设计变化先回到设计源

存在权威 Figma 或明确设计参考时，将其视为实现约束，而不是灵感图。开始当前界面增量前检查将发布的主要状态、控件家族、必要尺寸变化和交互意图是否有依据；可以用已有组件变体和清晰状态说明，不要求每个微小改动画全套页面。

发现设计问题或缺状态：先更新原有权威设计，再实现；发现实现偏离：保留设计并修实现。不得把已乱改的成品反向导入后宣称“设计已同步”。设计访问不可用时显式报告，仅暂停依赖设计决策的变更，继续独立且安全的工作。

完整界面任务走“设计补齐与自审 → 实现 → 实际目标界面的整屏对照 → 行为和质量自审 → 必要的外部/人工确认”。单独设计任务不强制追加实现。新增按钮、箭头、卡片、诊断入口须能解释服务哪个用户动作，不能仅为凑功能或填空白而加入。

### 24. 重复失败必须改变方法

同一故障再次出现、同一检查在没有新信息时重复失败，或人工指出上一轮相同问题时，触发一次小型原因复盘。核查实际运行版本、复现忠实性、数据/环境差异、故障假设、规则是否加载、修复是否只碰表象以及是否引入回归。

为当前任务设有限、可观察的尝试预算；若仓库已有预算就复用。预算耗尽不是宣布成功的理由，也不是必须把整个项目写成不可恢复失败。先暂停失败路线，选择新的有证据假设、改进诊断、在权限内回退危险改动，或向负责规划的人请求真实决策。

每次有意义的重试应新增信息或检验不同假设。进度更新解释实际结论和待解决点，不报空泛“仍在处理”，不承诺不存在的后台执行。不要再开无限 fixture、全套测试和人工确认循环。

### 25. 每轮按需沉淀，但不自动膨胀规则

只在出现新故障、用户纠正、反复失败、规则冲突或遗漏不变量时做小型复盘；正常任务没有新教训可以不新增文档。

项目代码 bug、具体交互语义和产品待办留项目；跨项目的流程/插件问题进入中央 owner TODO 并去重。项目记录可引用中央条目，不复制第二套插件清单。已有规则却仍失败时，记录实际调用、版本/安装和执行路径，优先查为何未生效，而不是再写同义规则。

记录事实不等于批准改中央插件。普通 Executor 可以在已授权文档范围内记录建议和补项目回归；不能自行修改全局授权、任务状态、强制验收、默认成本、版本或设计方向。项目 AGENTS 的小型防复发修改也需在本轮或既有授权范围内；否则交 Planner 判断。

维护者负责抽象与推广：先看已有规则和跨项目证据，再明确适用边界、反例、原失败回放和不相关场景回归。没有中央访问时明确说未记录，不另建影子插件 TODO。

## 五、实施与验收建议

本轮只提交本文和中央维护待办。未来实施应分清“行为规则”和“工具真的支持该行为”：先确认原入口及故障，再对 Lite 模板、Verified Workflow 或宿主交互做最小必要修改。保持一个权威所有者，短底线是分发后的必要约束，不是第二套详细流程。

建议优先实施显式用户请求、原目标完成和变更配测试，再实施设计闭环与失败止损。不得等全部插件完成才提供基本约束；也不得在未授权项目里直接改 AGENTS。

回放至少覆盖：缺一次用户动作时会明确请求；相同授权不会再问；只有模拟测试通过不能宣称原生可用；旧版关闭无效会被针对性测试抓住；缺 Figma 状态先补设计；连续无信息重跑会停止失败路线；纯文档任务不会被强制要求真机、Figma或付费审阅。

不能只用“规则文字存在”的静态测试证明生效。需从实际安装/加载入口执行行为回放，记录候选版本和证据，并检查 Lite、不同宿主状态语义、纯文档任务等相邻场景。现场复核仍须单独授权，不利用本提案触碰用户账户或设备。
