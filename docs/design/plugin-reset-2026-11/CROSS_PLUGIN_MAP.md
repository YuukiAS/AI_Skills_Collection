这些记录反复指向同一种用户体验：后台事实和检查很多，读者却仍不知道眼前的东西是什么、为什么有用、下一步怎么办；一旦要求删减，又可能丢掉必要解释或已确认内容。下表只把已有反馈放在一起，不决定由谁实现，也不裁定四个能力应合并或拆分。

计数基线为 `d4875a72`。一个带 `status` 或 `feedback_status` 的源条目算 1 条，混合正反例也计在内；详细候选文件整体算 1 条。每行允许同一源条目涉及多个根因，所以**横竖都不能相加当成独立事故总数**。共享案例在不同待办出现也分别计记录，不宣称发生了多次独立事故。`presentations` 仅补充交叉证据，不为其整理完整问题包。

“该出现什么内容”与“怎么表达”，待办证据支持以下区分：

1. “该出现什么内容”：读者是谁、要核对什么、哪些背景和限制必要，哪些整块说明应删除或移走；读者意识状态行 15、39、66、371 与科研创作状态行 300、445、514、548 有直接记录。
2. “怎么表达”：普通英文、缩写未解释、否定式包装、机械句式和重复断行；清楚表达状态行 126、453、470、622、654、853 有直接记录。
3. 两者都涉及：概念和公式在稿里但没有解释对象、为什么需要它、怎样进入下一步；清楚表达状态行 10、526 与科研创作状态行 100、138、154 有记录。
4. 两者都涉及：内部维护说明既可能整块不该出现，也可能确有操作价值但没翻译成读者动作；读者意识第 252–361 行明确反对把所有工作流信息一律删掉。
5. 两者都涉及：图注应解释科学对象而非讲自己怎样做幻灯片；幻灯片状态行 340、349 同时记录多余图注和缺失必要解释。
