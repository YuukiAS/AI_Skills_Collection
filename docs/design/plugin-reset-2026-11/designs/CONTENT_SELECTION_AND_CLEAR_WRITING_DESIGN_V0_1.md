# content-selection 与 Clear Writing 联合设计书 v0.1

## 1. 一页结论

**建议做成两个平级的独立插件，各提供一个公开技能。内容选择负责让作品值得读，Clear Writing 负责让选定的内容读得懂。** 用户可以直接选择其中一个；制作报告、幻灯片或界面的插件，则根据任务顺序调用它们。用户无需在六个写作技能之间选择，也无需在每轮返修时重新提醒“说人话”。

内容选择在两个时点介入。制作前，它根据读者要理解、判断或完成的事情，决定内容的删留、顺序和可见层级；成品出来后，它查看完整的实际作品，检查组合后的焦点、重复、留白和阅读负担。删掉一组文字以后，页面需要怎样重新安排，由原制作方负责落实；内容选择继续检查修改后的作品。

Clear Writing 收拢为一个入口，内部按**解释与答复、连续成稿、界面文字**三种场景处理。中文、英文、简体中文和香港繁体中文是表达参数；长稿重组是成稿场景中的处理方式。事实、公式、引用、状态、最新修正和已确认内容的保护，成为所有场景共同遵守的必经要求。

v0.1 应交付以下可用能力：

- 普通回答能够一次答全明确问题，把对象、原因、关系和行动讲清楚；收到“没听懂”以后，能够换一条具体的解释路径。
- 文档、幻灯片文案和界面文字在冻结前完成必要的内容取舍与表达处理；整块无价值内容可以被删除，必要清单、限制和操作信息得到保留。
- 长稿可以重新组织，同时保住命题、证据、限定和引用之间的关系；局部修改能够保住已经接受的其他内容。
- 完整成品经过实际阅读或查看，返修结果与最终交付对象一致。
- GPT 与 Codex 都能承担内容判断和写作；具有相应工具的一端负责机械核验、渲染检查和写后回读。

科学结论、产品功能、图形语义、排版制作和发布继续由现有负责人承担。本轮为 `presentations` 定义可接入的内容与验收接口；其他产物插件的全面接入、宿主级全局发送拦截，以及大规模效果研究，安排在后续版本。

## 2. 架构

### 2.1 两个插件、两个公开技能

| 插件 | 公开技能 | 负责什么 | 何时使用 |
|---|---|---|---|
| 内容选择，标识为 `content-selection` | `content-selection` | 制作前的内容准入、顺序和可见层级；成品后的整件作品复审 | 用户直接要求审查作品内容，或产物负责人在制作前、成品完成后调用 |
| Clear Writing；建议保留现有安装标识 `writing-style` | `clear-writing` | 在确定的内容与修改范围内完成清楚表达，并保护原意和已确认内容 | 用户直接要求解释、改写或润色；已接入的产物入口在正文冻结前调用 |

这里的“产物负责人”就是当前负责报告、幻灯片、界面或其他作品的 GPT、Codex 或领域插件。它负责取得材料、调用能力、处理返修和交付，无须增加一个协调插件。

两个插件通过同一份内容计划协作。产物负责人先取得内容选择结果，再交给 Clear Writing 完成文字，随后制作并查看成品。发现问题时，由负责人把问题送回对应环节，避免两个插件互相调用、反复推翻彼此的决定。

用户单独选择 Clear Writing 时，当前宿主承担上述协调责任。普通答复、既定结构内的润色和局部改词，可以直接完成；涉及整件作品的实质删留或结构重组时，宿主先调用内容选择，再继续写作。用户直接选择内容选择审查已有作品时，则先取得内容处置结果；只有任务同时要求返修文字，才继续调用 Clear Writing。

### 2.2 内容选择：制作前完成取舍

制作前的判断围绕三个问题展开：读者来这里要解决什么问题，哪些信息足以支持这个任务，以及这些信息应怎样出现。

**先确定阅读任务。** 从用户要求、目标读者和已有材料中提取明确的问题。理解一种方法、比较两条路线、核对一次发布、继续下一步操作，都可以成为有效的阅读任务。已知信息直接使用；只有读者或用途的歧义会实质改变删留结果时，才需要补充确认。

**再按含义处理内容。** 同一个意思可能出现在标题、正文、图注和侧栏，内容选择应识别它们的关系，而非逐个文本框孤立判断。对每个需要处理的内容单元，选择适当结果：

| 处理结果 | 适用情形 |
|---|---|
| 直接保留 | 读者当前需要据此理解、判断或行动 |
| 压缩表达 | 信息必要，但可以减少重复或展开程度 |
| 改用图表 | 关系、比较或结构用图表更容易理解；具体制作交给媒介负责人 |
| 移到次级位置 | 信息需要保留，但适合附录、展开区或可回查链接 |
| 删除 | 对当前阅读任务没有必要贡献，或其含义已由其他位置充分承担 |

这些结果共同表达“留下多少、放在哪里、怎样呈现”，无需再建立一套平行的处置分类。必要限制应留在它所限定的结论附近；不能仅凭附录中仍有同一句话，就认定主文保留了完整含义。

**最后安排阅读顺序和可见层级。** 优先让读者看到当前问题的答案，再提供理解该答案需要的对象、关系、证据和条件。界面先让人知道状态、后果与动作；工作台保留当前有效入口、接手者及必要条件；次级页面应当是值得独立回访的对象。信息已经充分时，允许结束说明和保留空白。

领域负责人已经冻结的科学主线、章节或页序构成输入边界。内容选择在允许范围内安排信息；涉及改变科学论证、产品功能或冻结骨架的建议，交回原负责人决定。

### 2.3 内容选择：成品后检查组合效果

成品复审必须取得读者实际消费的对象：完整文档、全部目标幻灯片、实际图形，或界面在相关视口和状态下的呈现。纯文本能够支持文字判断；涉及空间、换行、图文关系和交互状态时，还需要相应的真实呈现。

复审检查的是整件作品形成的阅读效果：

- **焦点是否清楚。** 主结论是否被次要提示、维护说明或装饰性内容抢走。
- **组合后是否重复。** 单独看来有用的标题、正文、图注和侧栏，放在一起是否反复解释同一件事。
- **删改后是否协调。** 删除内容后，布局、图文比例、阅读顺序和留白是否需要重新安排。
- **是否泄漏内部过程。** 编辑讨论、执行记录和验收说明是否进入了面向读者的正文。
- **是否讲得过多或过少。** 保留的内容能否支持读者完成任务，新增解释是否仍提供实际价值。

每个需要返修的问题只需说清：**发生在哪里、怎样妨碍读者、应调整什么、必须保留什么、由谁处理。** 内容删留问题回到内容计划，措辞问题交给 Clear Writing，科学或产品含义问题交给领域负责人，布局和交互问题交给制作方。

查看范围与修改范围分别控制。复审可以查看整件作品；局部返修只修改本轮允许的区域，以及确实受到该修改影响的相邻部分。其他区域即使存在可改善之处，也先记录给负责人，避免借一次小修重做已经接受的作品。

首次复审应覆盖完整目标对象。返修过程中可以按问题定位检查；最终交付前，再确认整件作品的关系仍然成立。

### 2.4 Clear Writing：按读者场景组织内部能力

Clear Writing 的公开入口先识别实际交付对象，再按需读取对应的场景参考。三个场景具有不同的阅读任务，因此保留不同处理方法。

| 内部场景 | 读者需要什么 | 处理方法 |
|---|---|---|
| 解释与答复 | 得到当前问题的答案，理解对象、原因、关系或下一动作 | 先给判断；补上对象如何变化、为什么产生结果的连接；综合不同来源；同轮答全明确问题；后续回答聚焦新增信息 |
| 连续成稿 | 脱离聊天背景后，仍能顺着全文理解内容 | 在确定的主线内安排段落、定义、例子、公式和证据；维持全文术语与语气；检查标题、正文、图注和表格之间的配合 |
| 界面文字 | 立即理解当前状态、操作后果和可执行动作 | 根据控件角色、真实状态、相邻文案、地区和必要披露写作；检查整页重复与语气；保留可访问名称和必要条件 |

语言与地区不再构成独立入口。中文正文使用自然中文表达普通概念，精确名称和机器字符串按需要保留；英文科研表达继续保护证据强度与限定关系。简体中文和香港繁体中文根据同一产品含义分别写作，保留各自自然的用语。

长稿重组属于连续成稿的深入处理方式。它复用现有实现中有价值的语义提取、关系记录、分块写作和组装能力，并明确分工：

1. 产物负责人从权威来源中整理命题、证据、条件和精确内容；专业歧义由领域负责人解决。
2. 内容选择据此确定读者问题、内容去向和阅读顺序，形成唯一的内容计划。
3. Clear Writing 按该计划完成文字、衔接和必要的解释，再对照来源检查保真。

原有长稿路线中的 `Reader Plan` 因而成为内容选择的输出，Clear Writing 消费它，不再维护第二份独立的内容排序方案。

普通聊天中的句子排序、重复压缩和例子选择属于表达组织。整件作品的专业信息删留、章节主次和跨页面安排，则由内容选择处理。这个边界使短答保持轻量，也让正式作品有明确的内容负责人。

### 2.5 保真：所有删改共同遵守的边界

保真要求由 Clear Writing 维护，作为所有表达场景的公共规则；产物负责人在内容选择前就提供同一份保护要求。用户无需再选择一个“保真技能”。

需要保护的内容随任务而变：

| 本轮任务 | 可以改变什么 | 必须保住什么 |
|---|---|---|
| 润色或局部修改 | 指定范围内的用词、句式、段落衔接 | 原有实质内容、已确认结构及范围外内容 |
| 保真重组 | 获准调整的标题、顺序、段落组合和呈现形式 | 全部实质命题、证据、限定、比较关系和引用归属 |
| 摘要或内容删减 | 按读者任务减少内容、合并重复、调整可见层级 | 结论成立所需的条件、重要负结果、必要操作信息和明确要求保留的内容 |
| 纯排版或渲染 | 字体、尺寸、位置及其他获准的呈现属性 | 已冻结正文、公式含义、状态和内容关系 |

共同保护的对象包括事实、数字、单位、公式、引用、比较对象、归因、不确定性、完成状态，以及确需逐字匹配的代码、命令和标识。科学定义缺失时，先从已有权威材料中补齐；仍无法确定的部分交回领域负责人。

保护还包含两项经常被遗漏的要求：

- **已经拒绝的内容保持退出。** 被要求删除的整节说明，不能换标题、改措辞或移到另一处重新出现。
- **最新事实与认可文风分别取用。** 旧稿可以作为可读性的参照，当前事实和状态继续服从最新权威材料。

必要条件应与其结论保持对应，数字应属于正确的对象，引用应支持正确的主张。机械检查可以发现字符串缺失；这些关系仍需对照来源判断。

### 分界

以下五类边界来自本轮覆盖材料。它们决定两个插件分别做什么，以及交接时必须带上什么。

| 实际问题 | 内容选择负责 | Clear Writing 负责 | 交接内容 |
|---|---|---|---|
| 发布说明删掉了具体核对清单，却留下维护元信息 | 保留用户要核对的对象与配置范围；删除无用整节 | 把保留事项写成可逐项对照的说明 | 核对任务、必留清单、已拒绝内容、本轮修改范围 |
| 专家科研图反复解释标题和坐标已经说明的边界 | 判断哪些限制会改变专业推断，哪些说明可以删 | 写清必要来源、比较条件、视觉编码和限制 | 实际图、读者水平、科学条件、获准注释 |
| 界面文字像内部政策 | 决定说明是否出现、放在哪一层；识别缺乏产品依据的内容 | 按真实状态、用户后果和地区写出自然文案 | 控件角色、状态、邻文、必要披露、可访问名称 |
| 长报告有公式，读者仍需自行拼接逻辑 | 安排主线、对象与公式的出现次序，确定辅助材料位置 | 补上已知对象、计算作用和推理连接，完成保真重组 | 命题与关系、公式定义、阅读目的、允许重排范围 |
| 工作台把历史指令和当前动作混在一起 | 保留当前有效动作；安排历史和次级信息 | 写清接手者、入口、前置条件和停止条件 | 当前权威状态、有效动作、链接用途、必须保留的条件 |

发现科学或产品事实缺失时，两个插件共同返回原负责人补充；发现选定内容在当前页面或篇幅内无法讲清时，返回内容选择调整层级。已有授权范围内的普通删冗余、改词和返修直接完成。

## 3. GPT 端与 Codex 端分工

### 3.1 两端均承担判断与写作

| 技能 | GPT 端 | Codex 端 |
|---|---|---|
| `content-selection` | 从用户直接请求或产物插件进入；读取材料，形成内容计划；取得成品后进行整件复审 | 从用户直接任务或制作入口进入；同样完成内容判断；结合源码、文件、渲染和真实状态检查处置是否落实 |
| `clear-writing` | 完成解释、成稿、界面文字和保真重组；检查本轮所有实际交付的文字对象 | 同样完成写作与语义核对；将修订落实到目标文件，并结合差异、渲染或回读确认结果 |

两端的语义规则和交接格式共用一个来源，宿主配置只负责入口与工具适配。GPT 取得完整成品和所需工具时，可以完成成品复审；Codex 直接接到任务时，也应自行完成内容计划，不能默认等待另一端替它做判断。

机械核验按实际环境安排。Codex 通常可执行本地文件、哈希、差异和精确项检查；GPT 端具有相应执行工具时可以执行同样检查。纯技能封装本身提供的脚本执行和全局发送拦截能力为“无”，不得仅凭插件已安装推断这些能力存在。

可观察证据包括内容计划怎样改变了作品、完整文字是否回答读者问题、受保护内容是否保持，以及实际成品中问题是否消失。技能读取或调用记录用于确认入口，不能独立证明效果。

### 3.2 两端共用一份轻量交接

交接使用现有任务材料中的一个小节即可。短答可以直接在当前上下文中传递；长稿、跨端任务或需要写入文件的任务，再保存明确的对象与版本定位。

必要信息包括：

- **读者与任务：** 谁来读，要理解、判断或完成什么，目标语言与地区是什么。
- **权威材料：** 当前来源、最新接受稿和用户修正；旧稿作事实来源还是文风参考，应当分清。
- **编辑范围：** 本轮允许修改什么，哪些内容必须保留，哪些内容已经被拒绝。
- **内容计划：** 保留、压缩、转图、移层或删除的内容，以及必要的相邻关系。
- **交付对象：** 本轮实际交付哪些正文、文件、页面或界面状态，各自使用哪个候选版本。
- **复审结果：** 看过哪些实际对象，剩余问题在哪里，下一步由哪位现有负责人处理。

一轮同时交付聊天说明、Markdown 和 PDF 时，要分别确认这些对象经过了适用检查。聊天里写得清楚，不能代替文件正文经过处理；Markdown 正确，也不能代替 PDF 的实际呈现正确。

正文处理完成后才进入文字冻结。随后发生的纯排版保持文字不变；若渲染暴露出必须改词或调整内容的问题，负责人回到对应步骤修复，再检查新的成品。

### 3.3 为 presentations 保留的接口

本轮只确定它需要怎样消费两个插件，不改变其故事规划、模板、渲染或通用验收器架构。

**GPT 端的内容交接以页面为单位，同时保留整套叙事关系。** `presentations` 提供每页的读者问题、专业结论、证据、必须可见的定义与限定，以及已冻结的页序。内容选择返回每页保留什么、移走什么、如何确定主次，以及与前后页怎样连接。Clear Writing 再处理整套可见文字，包括标题、图注、标签和必要说明。

**Codex 端接收同一份页面计划与文字候选。** 制作后，通用验收器应能核对目标页是否齐全、文字和渲染来自哪个版本、精确内容是否保持，以及已经提出的问题是否落实修复。内容选择查看完整成品；Clear Writing 检查实际显示中暴露的表达、上下文和换行问题。

通用验收接口将机械结果与阅读判断分开返回。来源一致、文件存在、页数齐全等检查可以由程序完成；焦点是否清楚、限制是否贴近结论、全套文字是否容易理解，由实际看过来源和成品的审阅者判断。具体字段见附录 C。

### 3.4 正常入口与未完成情况

v0.1 对“自动使用”的承诺限定为：**已经接入的入口会在正确阶段调用，同一任务无需用户重复点名。** 独立安装、普通请求和新会话都要经过真实入口验收；全面跨插件接入按照第 7 节逐步完成。

调用方缺少某项能力时，应先使用既有安装和任务恢复方式补齐。尚未取得成品时，可以继续完成内容计划、文字稿和来源核对，但整件成品复审保持待完成。后续收到成品后，从这一环节继续。

审查发现普通缺陷，留在同一任务内修复。发现输入事实矛盾或需要改变已冻结范围，交回原负责人处理。材料外传、付费审查和外部写入继续遵守当前任务已有授权；两个插件不产生新的执行授权。

## 5. 必要验收检查

v0.1 保留以下六项插件验收检查。它们用于证明六类实际能力；日常任务只执行与当前对象有关的检查，不要求每次短答都走完整套流程。

| 检查 | 检查什么，以及怎样算失败 | 判定方式 | 覆盖范围 | 运行端 |
|---|---|---|---|---|
| **1. 内容取舍后仍能完成阅读任务** | 读者需要的解释、核对项、限制和操作条件仍在；无用整块实际消失。缩短后漏答、换标题保留拒绝内容，都算失败 | 模型或人判断；必留对象与出现位置可机械辅助 | 内容准入、删减、防御重复、操作信息、必要解释 | 两端均需有正常入口证据 |
| **2. 完整表达与解释修复** | 完整首答或成稿能讲清对象和关系；收到未理解反馈后改变解释路径。只换词、同义复述、停在检讨，算失败 | 阅读完整回答或全文；不能按字数、禁词或固定段数评分 | 解释连接、全文语气、段落、术语、多轮回答 | GPT 与 Codex |
| **3. 保真与局部返修** | 对照来源及最新接受稿，检查命题、证据、限定、公式、引用和状态；检查修改范围及旧拒绝内容。语义漂移或擅改已确认内容，算失败 | 精确项和差异机械检查，加来源—成品语义比较 | 长稿重组、最新事实、局部修改、专业边界 | 两端；有执行环境的一端运行辅助脚本 |
| **4. 界面状态与整页文案** | 在真实界面上下文中检查状态、后果、动作、地区表达和必要信息；检查可见标签及可访问名称。把未知写成暂无、删掉必要条件，算失败 | 状态覆盖可机械辅助；自然度与理解需看实际界面 | 界面减负、四类状态、地区表达、必要披露 | GPT 可检查实际截图和上下文；Codex 可检查页面与相关操作状态 |
| **5. 整件成品复审** | 看完整消费对象的焦点、层级、重复、留白和图文关系；确认删改后布局协调。仅检查源文件或修改句，不能通过 | 实际阅读或查看完整成品，机械结果辅助定位 | 文档、幻灯片、图形、界面与 Blueprint 的整体质量 | 能取得完整成品的一端；正式验收由能看见成品的既有独立审查承担 |
| **6. 正常入口交付同一份已审作品** | 验证普通请求、已接入上游、GPT→Codex 和 Codex 直接发起；确认冻结、制作、回读使用对应版本。审旧稿交新稿、只审聊天说明、需反复提醒，算失败 | 入口、版本、差异和回读可机械核对；同时检查实际输出 | 安装与调用、冻结前处理、跨端交接、实际交付一致性 | 两端及实际写入端 |

六项检查共同采用以下证据安排：

- **先保住已有能力。** 开发回归包含已知问题、已接受正例，以及纯机器内容、纯排版、必要长解释等应保持不变的情况。
- **直接比较完整结果。** 对有代表性的任务，在相同宿主设置和来源下比较旧入口与新候选。新候选应改善读者完成任务的能力，同时保住原本正确的内容；不能以“调用次数更多”表示增益。
- **最终候选统一。** 正常安装、入口、保真与成品检查绑定同一最终候选。跨端和跨插件的成功链要实际走通。
- **未见材料预先冻结。** 开发完成后再冻结新的任务、来源、评审标准和运行次数。根据结果修过的样本转为开发回归；失败记录保留。
- **区分证据性质。** 本轮汇总中的私有案例转述可以指导设计，脱敏重建可以用于开发；它们不能冒充已取得原件的真实失败回放。已有人工正例也不能自动写成插件运行成绩。

受控交付入口还应直接验证一次：候选在审查后发生内容或呈现变化，旧审查结果不再足以支持交付。检查器应指出需要重新检查的对象，而非沿用旧结果。

## 6. 现有实现怎么处理

### 6.1 六个旧技能的去向

| 现有技能 | 处理 | 理由 |
|---|---|---|
| `response-clarity` | 并入“解释与答复”场景 | 保留具体解释、完整回答和多轮修复能力，统一进入新入口 |
| `chinese-prose`，生成目录为 `zh` | 改写并入“连续成稿”及共同中文表达要求 | 中文成为表达参数；减少与普通答复、界面和长稿路线之间的重复转交 |
| `scientific-prose`，生成目录为 `sci` | 并入科研表达参考 | 保留英文科研表达、证据强度和图注能力，专业结论继续由领域负责人决定 |
| `scientific-rewrite` | 拆分职责后并入长稿处理 | 语义提取与保真继续复用；内容排序归内容选择；文字实现与组装归 Clear Writing |
| `writing-fidelity`，生成目录为 `fidelity` | 保留并改写为所有场景的公共保护要求 | 保真成为必经步骤，用户无需单独选择；移出布局执行等制作职责 |
| `product-ui-copy` | 改写并入“界面文字”场景 | 保留产品状态、地区与邻文处理；更新内容选择、写作和前端制作之间的交接 |

新发行包只暴露统一技能。旧调用点及安装组合在切换前逐一迁移，旧源文件在必要的兼容期内承担转接作用；兼容性通过真实调用验证后，再移出活动技能集。历史内容保留在版本记录中。

### 6.2 脚本与参考材料

现有 `rewrite_support.py` 选择性保留：继续提供来源定位、哈希、精确项、关系覆盖和长稿材料检查。它的关键词分流、格式检查及模型自行填写的审校结果，均不能作为自然度或语义正确的独立证明。具体函数的去向列在附录 D。

参考材料保留有用的解释正例、失败回归、来源和许可信息；重复规则并入对应场景。固定组会模板从活动依赖中移除：该模板仍推荐未被请求的时间脚本和固定章节，与现行主规则存在直接冲突。仅调整入口名称会保留这一冲突，因此迁移必须检查实际会被读取的参考文件。

触发用例重新组织为统一入口的正常请求与反例。原有共享脚本和测试继续承担自己的机械职责，不因两个插件重建而删除；新增或修改的断言应对应实际入口、保护要求和生成关系。

### 6.3 安装、生成与版本

原始技能与生成包继续保持明确关系：修改源码和生成配置，再用现有生成器产生插件包。新 GPT 封装与 Codex 包消费同一份规则，分别验证自己的实际加载入口。

安装组合需要一并处理。当前 `global-baseline` 直接安装保真、中文和英文科研技能，没有包含 `response-clarity`；`codex-writing-style` 才列出全部六个。新入口应替换这些分散引用，使常用组合确实取得它所声明的能力。

建议保留 Clear Writing 的现有安装标识 `writing-style`，公开技能改为 `clear-writing`，新增 `content-selection` 插件。设计书的 v0.1 表示本次重设计的首版；正式发布版本在实施与验收收口时按仓库规范确定，当前设计不重置既有版本记录。

## 7. v0.1 与之后版本

**v0.1 完成两个插件本身的可用闭环。** 内容选择具备制作前判断和成品后复审；Clear Writing 具备三种场景、公共保真及长稿重组。两端各有直接入口，普通请求能够进入适当处理方式。首批正常消费验证覆盖独立调用、长稿组合调用和既有 README 终审入口；实际成品检查覆盖所声明的代表性载体。`presentations` 在本轮取得明确接口，其生产接入留给相应实施任务。

**0.2 优先完成高频产物入口的实际接入。** 按各插件自己的批准方案，将 Research Authoring 与 `presentations` 的正文冻结、语言处理、真实成品复审和返修连接起来。新增价值是用户从原产物入口开始，就能得到经过完整处理的作品。该阶段也验证真实外部写入后的回读，以及多轮返修中已确认内容的保持。

**0.3 根据真实使用扩展界面、图形和工作台。** 重点是更多状态、视口、信息层级和持续更新场景，验证当前动作替换历史指令、跨页面重复控制，以及小修后的整体协调。新失败优先进入已有检查与回归集合；只有出现不同能力或责任边界，才增加新的机制。

外部减负提示、`academic-humanizer` 等候选资源，以及大规模跨载体可靠性研究，后续按具体缺口选择。资源只有实际进入正常路径、改变输出并取得增量证据后，才算采用。检测器规避不进入产品范围。

## 附录 C：交接与通用验收接口

以下为接口语义。可写入已有任务文件，也可由调用方映射为 JSON；短任务无需生成一组阶段文件。

### C.1 输入与内容计划

| 字段 | 含义 |
|---|---|
| `target_id`、`target_kind` | 本次实际交付对象及类型；同轮多个对象分别识别 |
| `reader`、`reader_task`、`locale` | 读者、阅读任务及语言地区 |
| `source_refs` | 当前权威来源与版本 |
| `accepted_base` | 最新接受稿；仅作风格参考的材料另行说明用途 |
| `edit_scope` | 本轮编辑类型、可修改范围及冻结结构 |
| `required_meanings` | 必留命题、条件、状态和关系 |
| `exact_items` | 确需逐字匹配的内容及其必要出现位置 |
| `rejected_content` | 用户已拒绝的含义或整块内容 |
| `content_units` | 内容单元、来源、读者用途、处置结果和目标位置 |
| `required_relations` | 必须共同出现或保持对应的结论—条件、数字—对象、主张—引用关系 |

已有长稿语义材料继续复用其标识与来源锚点。内容选择输出的计划成为后续写作、保真核对和成品复审共同使用的版本。

### C.2 成品复审输入与结果

| 字段 | 含义 |
|---|---|
| `candidate_identity` | 当前文字、源文件及呈现版本的对应身份 |
| `visible_text` | 本次全部目标可见文字，包含标题、图注、标签等 |
| `rendered_views` | 实际页面、幻灯片、图形或界面状态；注明范围与视口 |
| `observed_surfaces` | 实际查看过的对象及范围 |
| `unobserved_surfaces` | 尚未取得或未能查看的必要对象 |
| `findings` | 位置、读者影响、所需修改、保护要求及负责方 |
| `mechanical_results` | 已实际执行的文件、版本、精确项或范围核验 |
| `reader_review` | 对照来源和成品形成的内容、表达及整体判断 |

同一内容产生 Markdown、PDF 或其他形式时，各自文件可以不同，但必须能够追溯到同一内容候选。仅文字哈希相同，不能证明布局版本相同；呈现变化后要检查新的呈现。

通用验收器应分别检查对象完整性、版本对应、机械约束和未解决问题。审阅者还须确认自己获得了所需的来源与完整成品。机器记录缺失、来源有歧义、成品未观察和质量不合格应分别说明，便于原负责人继续处理。
