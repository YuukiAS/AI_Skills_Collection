# Research Authoring 重设计 v0.1

## 1. 一页结论

**Research Authoring 按“给谁读”组织能力：本人研究笔记、导师与合作者的研究故事、学生材料，以及预留的论文读者入口。首版实现前三类，让研究文档讲清问题、方法怎样计算、证据支持什么，以及读者需要理解或完成什么。** 同一类读者需要的 Markdown、PDF 和双语版本，都在同一个技能内处理。

GPT 负责读者判断、科研论证和写作，依次调用 `content-selection` 形成内容计划、调用 `clear-writing` 完成表达。Codex 接收确定的正文和制作约束，负责渲染、机械检查、发布与回读；需要增删内容、改变研究结论或调整阅读结构的问题，回到当前 GPT 处理。成品返回后，GPT 在这次创作中查看完整作品，并调用内容选择检查组合效果。

v0.1 的交付范围是 **GitHub Markdown、正式 PDF，以及按需打包这些已有成品的 ZIP**。本人笔记保留学懂所需的定义、推导和例子；研究故事把方法、数据、比较与实验转向串起来；学生材料完整交代题目、任务与必要规则。文献检索、引用核对和论文写作沿用现有 `paper`、`litcite`，本轮保持原样；Notion 原生页面、复杂 Office 制作、可填写表单和题库另行处理。

**每次实际调用，随成品交付一份执行证据文件。** 文件逐条列出规则编号、成品原句或位置；发生改写时列出改前与改后。GPT 端附文件，Codex 端推送文件；未调用本插件的聊天保持原有输出。研究正文与执行证据分开，读者先看到所需内容。

首版只安排四个真实回归：本人笔记、导师报告、学生简报、已接受学生材料的小修与打包。现有报告规则和 PDF 工具已有可复用部分，新增工作集中在读者入口、两端交接、轻量机械验收和实际文件对应关系。设计依据、112 行覆盖明细、规则编号及迁移清单均在附录，现有能力的事实依据见[附录 E](#附录-e来源与采用边界)。

## 2. 架构

### 2.1 一个插件，按四类读者拆技能

用户入口继续叫 Research Authoring。建议保留现有安装标识 `research-writing`，用下表的三个新技能承接本轮创作；论文读者保留现有入口。格式、语言和长短作为技能内部参数，不再拆出“PDF 报告”“Markdown 报告”或“英文报告”技能。

| 读者与技能 | 负责什么 | 何时使用 | v0.1 状态 |
| --- | --- | --- | --- |
| 本人研究笔记：`research-notes` | 帮用户学懂、复习和判断已有研究；安排定义、计算过程、必要推导、邻近比较及项目用途 | 用户点名，或已进入 Research Authoring 的任务明确要求学习笔记、方法说明、个人研究分析 | 实现 |
| 完整研究故事：`research-story` | 给导师、组会听众、合作者和跨领域读者解释问题、价值、方法、证据与研究转向；也处理已有研究材料的书面提案、研究纪要和进展报告 | 用户点名，或产物调用方明确要求这一类读者的研究文档 | 实现；四种听众属于同一个技能，按其知识背景调整解释深度 |
| 学生材料：`student-materials` | 根据课程权威材料写作业说明、项目简报、讲义及普通文字检查表，落实累计批注 | 用户点名，或教学材料制作任务调用；题目、评分政策和方法要求由课程来源提供 | 实现 |
| 论文读者：现有 `paper` | 保留将来接入同一读者架构的位置 | 正式论文、返修和补充材料仍使用旧入口 | 原样保留，本轮不改造 |

`litcite` 继续保留为现有文献配套能力，位于这次读者分类之外。它与 `paper` 的旧入口、内部源技能和现有职责均不因本次设计被修改，也不自动成为前三类新技能的调用步骤。

自动选择只发生在**已经进入本插件的文档任务**内：根据明确读者选择技能，随后连续完成所需工作。普通科研问答不因出现公式或论文名就自动调用本插件。其他插件可以交入明确的读者任务、来源和产物范围；已有上游结论及冻结结构作为输入。读者确有歧义并会改变内容时，再问一个具体问题；已知信息直接沿用。

### 2.2 三个新技能各自增加什么

**本人笔记让用户能在当前文档中重建推理。** GPT 先确定用户卡在什么关系上，再组织对象、假设、输入、计算、中间结果和解释。一个方法出现时，就近说明它为何适用于当前问题、与邻近方法有什么差异，以及必要的适用条件。公式中的符号在首次使用处获得解释，关键推导写够；外链承担来源与深入阅读用途。笔记篇幅取决于理解任务，摘要不能自动替代所需推导。

**研究故事让第一次接触项目的读者理解为什么值得研究、实际做了什么，以及结果改变了什么判断。** GPT 先稳定方法身份、数据与子集定义、计算过程和比较条件，再组织证据。多轮实验只保留影响科学判断的因果顺序：哪个现象暴露了什么问题，下一实验区分什么解释，新证据怎样改变选择。诊断结果、数值恢复、测量稳定、训练改进和最终效果分别按实际证据说明。已有结果、历史决定、当前解释和未完成计划保持各自身份；是否需要主图、表格或导师决定，由本次阅读任务决定。

**学生材料让学生清楚完成什么任务，并保住课程已经决定的要求。** 作业以题目和必要背景为主，项目简报交代任务、数据、产出和公开规则，讲义按学习目标组织解释与例子。GPT 从课程材料取得事实，保留已批准的公开分值和限制；评分设计、答案生成、题库筛选和替学生决定方法仍交原领域负责人。批注中的删除、保留和局部修正跨轮继承，已接受版式作为当前任务的依据。

三类技能共享来源、修订和交付约束；它们的区别落在研究或教学任务上。通用内容取舍与语言表达继续调用任务 2 的两个插件。

### 2.3 调用关系与正常使用

一次正常任务按以下关系完成，当前 GPT 始终负责成稿的研究或教学含义：

1. **读者技能准备专业输入。** 从来源恢复问题、方法、证据、已接受稿、累计修正和允许改动范围；区分事实、解释、假设与计划。
2. **GPT 调用 `content-selection`。** 传入读者任务、专业必留内容及保护边界，由它确定内容去向、顺序和层级。输出是本次唯一内容计划。
3. **GPT 调用 `clear-writing`。** 按内容计划完成全文、图表文字和必要解释，随后确认科研含义及条件关系保持。仅交内容稿时，GPT 以完整 Markdown 文件执行下一步的整件查看后交付；需要制作或发布时，交给 Codex。
4. **GPT 查看完整成品。** 直接交付的 Markdown 由 GPT 取得完整文件；需要制作的对象由 Codex 返回完整文件、可见文字、全部目标页面和机械结果。GPT 调用内容选择检查整件作品，必要文字返修再调用 Clear Writing。当前任务中的修改沿原范围继续，最终按已授权目标交付并回读。

这次成品查看属于当前作者完成作品的过程，不另设独立审查人、逐轮聊天检查器或后台运行器。用户已有明确的读者、正文批准、制作要求和发布授权时，直接沿用。依赖暂时不可用时，保留已完成稿件和准确剩余环节，恢复后接着做；调用记录必须反映实际调用。

共享接口沿用任务 2 的内容计划和成品回传字段，技术对应见附录 C。本流程中的内容选择、写作与成品阅读判断全部在 GPT 端完成；Codex 消费已经确定的内容，执行制作与机械检查。验收规模按本任务最新裁决限定为四个真实案例，共享插件在其他任务中的使用服从其当前正式入口。

## 3. GPT 端与 Codex 端分工

### 3.1 每个技能怎样交接

| 技能 | GPT 交出的内容 | Codex 完成的工作 | 遇到内容问题时 |
| --- | --- | --- | --- |
| `research-notes` | 完整笔记、来源、公式及解释关系、必须相邻的段落、允许修改范围 | 生成目标 Markdown 或 PDF，核对文本与公式表示、标题和链接，返回实际页面 | 将缺项、差异及对应页面交回 GPT；由 GPT 补推导或改解释 |
| `research-story` | 完整研究故事、方法和比较条件、表图角色、结论边界、待补结果位置 | 依指定形式制作，核对图表及引用定位、内容版本和输出文件 | 由 GPT 判断结果是否改变解释、故事或所需决定 |
| `student-materials` | 学生正文、课程事实来源、累计批注、接受母版、语义分组与文档家族约束 | 依既定模板制作，核对公开要求、允许差异、页面与发布文件集 | 涉及新增任务、评分、内容删留或阅读分组时回 GPT；课程政策仍服从课程负责人 |
| 论文读者位置 | 本轮沿用旧 `paper`、`litcite` | 旧能力保持原样，未接入本次制作流程 | 论文功能另有明确任务时再设计 |

Codex 单独收到前三类任务时，可以处理已有完整正文的制作与发布。缺少内容稿时，它给出当前缺少的材料及回到 GPT 的明确入口；已有足够输入时继续执行。跨端交接优先使用当前任务已有文件和传递渠道；v0.1 不新增自动跨会话调度，也不假定两个环境天然共享文件。

### 3.2 正文确定、用户批准与局部修订

GPT 完成内容判断后，交给 Codex 的是**本次确定的正文及允许改动范围**。这个交接可以来自用户已经接受的稿件，也可以来自用户已授权创作的候选稿。前者保留接受依据，后者如实作为候选；技术检查和 GPT 完成写作均不能代签用户认可。

普通新稿默认先完成可读候选；用户已授权直接制作或发布时，按该范围继续。课程或项目已有“先审正文再发布”的要求，就沿用这一次有效批准。新增课程要求、实质改变已接受科学结论、扩大修改范围时，由 GPT 先处理专业问题，只有当前授权确实不能决定的选择才交用户。这样保留批准边界，也避免把详细候选中的“所有正文都另走一次人工批准”推广为首版默认。

局部修改开始时恢复已接受母版、仍有效批注和被拒内容，不用最新文件名猜母版。GPT 提供可改内容与必须保留的关系；Codex 按确定补丁或制作约束执行。改文件名、补链接和打包只改变对应对象。范围外文本与资源可以精确比对，语义变化和版式是否仍适合阅读由 GPT 结合真实成品判断。确需更换模板或整体重排时，先说明受影响范围，再按已有授权处理。

未完成实验采用明确的待补位置，结果到来后更新对应事实和解释；会改变原研究判断的结果由 GPT 正面修订判断。双语材料按实际读者请求形成可独立阅读的两版，并核对科学含义、数字和公式。两类任务都沿用上述修订边界。

### 3.3 首版支持哪些产出

| 覆盖材料中的产出形式 | v0.1 决定 | 交付边界 |
| --- | --- | --- |
| 正式 PDF | 纳入前三类读者技能 | Codex 复用 `render-chinese-math-pdf`；返回完整 PDF 与全部页面供 GPT 阅读。沿既有文档家族制作，源文件按用户需要交付 |
| GitHub Markdown 及普通 Markdown 文件 | 纳入 | GPT 写稿；需要 GitHub 发布时由 Codex 写入指定位置、回读并取得目标页面。文件交付不自动扩成 PDF，也不自动取得远端写入授权 |
| Notion 学习页 | 原生发布与客户端验收放到 0.2 | 本轮吸收自足解释、标题层级和公式归组；不据此宣称 Notion 块写入、多端显示或旧块清理已经支持 |
| 可编辑 Office／DOCX／LaTeX 交付物 | Office 与独立 LaTeX 创作后移；现有 TeX 制作中间文件继续使用 | 正式 PDF 的既有 LaTeX 路线保留；用户要求源文件时交实际生成源，不新增复杂 Word 比较稿或论文排版能力 |
| ZIP 与发布文件集 | 纳入机械包装已有成品 | 按显式清单打包当前正确版本，未改组件保持原内容；执行证据另交用户，不混入学生发布包 |
| 表单、口试简报、题库等家族 | 普通文字检查表可随学生稿；可填写表单、口试专门材料与题库后移或不做 | 学生作业和讲义消费已确定的课程内容；题库筛选、考官答案与评分系统不进入 v0.1 |
| 论文、返修、补充与审稿材料 | 本轮不做 | 现有 `paper`、`litcite` 原样保留 |

纸张、字体、字号、行段距和标题层级优先继承当前文档家族与接受稿。GPT 标记需要连在一起的题目、公式解释、引文归属和元数据，Codex 将这些约束落实到制作。页数偏好与硬性页数分别记录；内容放不下时先在允许范围内处理排版，仍有冲突则把具体页面返回 GPT。历史正例只适用于相应家族，不变成所有文档统一的字号或页数。

### 3.4 通用验收器保持机械职责

v0.1 增加一个轻量机械检查入口，复用现有 PDF 工具和文件比对，检查本次文件是否齐全、是否对应交接正文、精确内容和允许改动是否满足、指定格式是否完整、发布后是否仍是同一份文件。页面测量只检查已有的明确约束；缺少测量能力的项目标出缺口。

**检查器分别返回实际检查结果、待 GPT 判断的问题和未观察范围。** 确定的文字丢失、错用文件、超出允许范围的改动或明确版式约束失败，会阻止相应文件作为完成品发布。密度、留白和语义分组等阅读问题由 GPT 看完整页面处理；无依据的通用阈值不升级成硬标准。处理方式和规则定位写入同一份执行证据。

现有 PDF 脚本能提供字体、文本、部分表格与公式线索，其默认预览及启发检查不足以代表全文质量。因此本次制作入口要收齐实际页面，检查器也只声明自己测到的性质。GitHub 源码回读与页面显示分别记录；页面尚未观察时，如实说明这一项未完成。接口与复用限制见附录 C、D。

### 3.5 每次调用的执行证据

每次本插件实际进入任务，就维护一份与本次成品对应的执行证据文件。GPT 端在回复中附上文件；Codex 端随任务推送文件并回读。跨端、多个格式以及两个共享插件的调用结果合并在这一份文件里，不为每个内部步骤另写一份报告。

文件逐条覆盖适用规则，列出**规则编号 → 成品原句或精确位置 → 改前与改后（如有）**。新稿标为新增；删除记录原位置与删除后的相应范围；纯机械规则引用实际文件、页面、差异或回读位置。未适用规则写具体原因，尚未完成的检查写缺口。正文中没有对应内容时，不用“已检查”填充成品引用。

本插件规则采用附录 A 的稳定编号。共享规则通过任务 2 的小节定位引用；其覆盖行编号不冒充规则编号。证据文件在本次写作和制作过程中积累，服务于用户核对实际成品，不设置新的独立检查器。未调用插件时不输出该文件；仅调用旧 `paper`、`litcite` 的任务继续服从原协议。

## 5. 必要验收检查

**v0.1 采用四个真实回归案例。** 一次完整任务同时观察读者理解、内容保护与制作交付，不把覆盖索引的 30 个候选检查拆成 30 道门。下表描述实施时应取得的证据，本设计阶段未运行插件回归。

| 真实回归 | 检查什么，怎样判断失败 | 机械可判还是需模型／人判 | 覆盖内容与运行端 |
| --- | --- | --- | --- |
| 1. 本人技术笔记：公式齐全仍读不懂 | 用已有失败笔记及批注，完成一份可独立复习的 Markdown；读者能顺着对象、定义和中间计算理解结果。隐藏外链后仍缺必要推导、首次符号无法定位含义，算失败 | GPT 阅读来源与全文，判断解释链；Codex 检查保存、公式表示、标题及目标页面；用户原批注作为判断依据 | 本人笔记、科学计算和符号顺序、来源保留；GPT 写作，Codex 发布与回读 |
| 2. 导师研究报告：从实验年表恢复研究故事 | 使用已记录的导师报告，讲清问题、使用价值、方法、数据、比较与实验转向，保留结果边界。内部过程主导正文，或把计划写成已有结果，算失败 | GPT 判断科学故事、比较资格和证据含义；Codex 制作正式 PDF、查精确内容和格式，返回全部页面 | 导师／合作者故事、两共享插件调用、PDF 正常路径；GPT 定稿并阅读成品，Codex 制作 |
| 3. 学生项目简报：累计批注与接受正例 | 使用有真实删除、保留意见和接受版式的学生简报，完整保留任务、公开规则及必要说明。删除内容换词复活、擅加要求、损坏已接受阅读节奏，算失败 | GPT 判断课程要求与信息必要性；Codex 比对精确内容、批注落实位置、字体和页面 | 学生技能、来源权威、家族身份、语义分组；两端各按职责运行 |
| 4. 已接受学生材料的小修与打包 | 按真实小修请求只改指定内容，保持其余接受材料；生成正确文件集，交可打开文件及一份执行证据，远端回读一致。选错母版、无关组件变化、未获准的构图退化或交错文件，算失败 | Codex 核对母版、差异、文件清单、机械结果与回读；GPT 判断语义和版式变化是否合理 | 有界修订、完整页面、制作权限、ZIP 和发布身份；也观察超范围变化时返回 GPT 的行为 |

四例都从准备发布的真实技能入口开始，取得完整产物及本次执行证据。回归采用已有真实材料，失败后在同一任务中修复受影响问题并重新检查；不靠改写例题或丢掉失败结果制造成绩。材料尚未取回时先记录缺口，不能用待办转述替代原稿；具体来源和素材条件列在附录 B.4。

原 `paper`、`litcite` 的源内容与入口保持不变，用静态差异核对保护这一范围，不另跑论文回归。版式、双语和不同格式只检验四例中实际使用的部分。更多文档家族、完整双语专项、复杂比较稿、Notion 多端显示和长期跨项目可靠性放到后续版本；首版不引入未见样本冻结、新旧入口全量对比或统一认证流程。

## 6. 现有实现怎么处理

现有 `report` 已包含问题、证据、导师报告和 PDF 委派要求；本次重设计重点是让这些要求进入读者入口及实际交接。`paper`、`litcite` 保留现状。五份学生共享合同保留历史文件，其中有效的学生任务、累计认可、局部修订和语义分页要求，分别并入本次共用约束；新入口不再默认逐份加载整套旧流程。[实现来源与逐项清单见附录 D](#附录-d现有实现逐项去向)。

| 现有部分 | 处理 | 原因 |
| --- | --- | --- |
| `report`／源 `research-reporting` | 改写，职责并入三个新读者技能；旧名保留轻量兼容转接 | 单一报告入口难以直接表达三类不同阅读任务 |
| 导师／组会参考 | 并入研究故事的专业参考，保留真实正反例 | 继续使用科学问题、比较和转向逻辑，通用表达交任务 2 |
| `paper`、`litcite` 及 12 个内部源技能 | 原样保留 | 论文与文献功能不在本轮修改范围 |
| 五份学生共享合同 | 有效要求分别并入本次约束，历史文件保留 | 保住已接受内容与分页经验，取消对旧重型流程的默认整套加载 |
| 独立 PDF 技能及其五个脚本 | 复用正式路线和可测检查 | 已有制作能力可用；本插件补交接和结果消费，不重造 PDF 引擎 |
| 现有生成器、配置与安装组合 | 复用生成器，实施时更新源映射与依赖 | 生成目录不能直接作为编辑源；新会话必须取得正确入口 |
| 新的机械验收入口、调用证据与 GitHub 回读连接 | v0.1 新增轻量适配 | 当前生成包内尚无这些完整实现，不能把文档要求当成已具备能力 |

GPT 封装与 Codex 包共用规则来源，但加载不同职责的入口：GPT 加载专业写作与两共享插件，Codex 加载制作与机械检查。现有仓库已明确 Codex 生成路径，本轮未发现 Research Authoring 新版 GPT 专属构建入口；实施时用现有个人技能插件封装机制补上 GPT 分发，不新增服务或运行平台。

本文件的 v0.1 是本次重设计的第一版。现有正式包为 `research-writing@0.2`；本次仅提交设计书，不变更其版本、安装、README 或发布状态。真正发布时依仓库版本规则处理连续版本，并同步入口说明及安装组合。

## 7. v0.1 与之后版本

**v0.1 交付可以使用的三类读者入口与两端制作链。** 范围包括研究和教学内容组织、任务 2 的实际调用、接受稿保护、PDF／Markdown 制作、必要机械检查、发布回读及每次调用的一份执行证据。四个真实案例用于发现这条链上的实际缺口；已有正确内容与已有论文、文献能力一起保留。

**0.2 优先补 Notion 原生页面与更多真实文档。** 新增价值是长期学习页可以正确更新目录、块结构与公式，并把远端回读和实际客户端显示分别验证。DOCX 按真实需求选择一个文档家族接入，避免同时宣称全面 Office 支持。继续补独立报告家族、完整双语版本和日常小修的回归。

**0.3 依据使用反馈完善长稿和持续更新。** 重点是多来源长稿、跨轮结果更新、文档家族一致性与复杂语义块的制作可靠性；可填写学生表单仅在出现具体需求后适配。论文、检索和引用核对若要重设计，另开明确范围；教师、考官、审批者、实施者与发布者专属创作不随版本自然扩入。

后续新增检查优先进入已有能力的回归案例，不因一次失败新增读者技能或整套审查流程。代码、文件和来源对应关系继续可查，质量判断保持针对真实成品。

## 8. 需要用户裁决的问题

**本轮没有需要用户补答才能完成设计的新增问题。** 四类读者、两个共享插件的职责、GPT／Codex 分工、逐次调用证据和轻量回归已经由正式提示词确定。

其余选择在本文给出明确推荐：首版支持 Markdown、PDF 和成品打包，Notion 与复杂 Office 后移；保留现有安装标识与论文、文献入口；普通候选按现有授权完成，涉及已有明确批准条件时沿用该条件。这些都是当前范围内的设计决定，后续若要扩大格式或改批准方式，再就具体变化提出选项。

短任务直接使用当前上下文。跨端任务优先在已有任务文件中承载下表字段；没有合适文件时新增一份 `<文档名>.handoff.json`。它是本次任务的静态交接，不另建服务、注册表或状态数据库。成稿及执行证据各有自己的文件，避免把交接字段写进科学正文。

| --- | --- |

| `reader`、`reader_task`、`locale` | 从四类读者中选择，具体背景和语言作为参数；不能自动增加教师、发布者等读者 |

| `accepted_base` | 真正已接受的稿件及其依据；没有接受稿时为空，候选与风格参照另外标清 |
| `edit_scope` | 本次可改内容、冻结结构及纯制作允许调整；局部修订使用已确定范围 |
| `required_meanings`、`required_relations` | 科学命题、条件、数字对应对象、证据关系、公式解释及教学任务关系，由 GPT 给定 |
| `exact_items` | 需要逐字保持的数字、文案、标签、文件名等及出现位置；公式体与允许的目标平台表示分开记录 |

| `findings`、`mechanical_results`、`reader_review` | Codex 写可测结果与定位；GPT 写专业阅读判断及必要返修；完成文件由当前实际结果决定 |

只补充以下研究文档需要的输入，继续放在同一份交接中：

| 增补字段 | 最少需要表达的内容 |
| --- | --- |
| `document_family` | 所属家族、既有模板／接受稿位置、纸张字体层级的已知约束 |
| `semantic_blocks` | 需要相邻的题目、公式解释、引文归属、元数据；可续块、短块和连续区域；已许可或明确禁止的硬分页 |

### C.2 Codex 通用机械验收器

建议在现有研究共享源码中新增 `scripts/check_research_artifact.py`，生成后随 Codex 制作入口分发；此路径为拟新增实现。它消费上述交接、实际源文件和制作结果，按本次目标运行必要的确定性检查。项目已有明确机械检查可被调用并原样记录结果，其规则由原项目维护。

| 检查对象 | 机械检查可以确认什么 | 仍由 GPT 判断什么 |
| --- | --- | --- |
| 交接与文件 | 输入和目标文件可读、实际正文版本对应、清单完整、精确定位存在 | 来源是否足以支持科学判断、候选是否真的被用户接受 |
| 内容及差异 | 精确项与指定位置、受保护范围差异、链接和标题结构、许可转换后的对应关系 | 语义等价、必要推导、删减是否合适、被拒内容是否换词复活 |
| Markdown | 编码与结构、数学节点及分隔符、表格与资源链接、代码区是否被误改 | 公式含义、符号解释、真实页面上的阅读顺序和可读性 |
| PDF | 可打开性、页数、文本抽取、明确的字体纸张约束、预览页覆盖；复用现有工具的可测结果 | 研究故事、图文关系、真实尺度下的密度、留白与阅读分组 |
| ZIP／发布集 | 实际组件列表、正确文件版本、无关组件内容不变、证据文件与学生包分离、远端回读 | 所选组件是否有相应接受依据；该依据由 GPT 交接，不由脚本推测 |
| 执行证据 | 适用规则的记录存在，引用位置能定位，改前改后确实取自对应文件 | 该原句是否充分体现规则；自填记录不能自动证明判断质量 |

机械结果包含逐项结果、已观察对象、明确失败、需 GPT 处理的问题与未完成范围。确定性错误或应做而未完成的机械项目返回非零结果；机械项目通过时也只报告这些项目。`reader_review` 保持独立，由 GPT 实际阅读填写，检查器不生成“科学正确”“用户已接受”或总体质量认证。

PDF 制作调用既有 `render_scientific_pdf.py`，为完整成品取证明确指定 `--preview-pages all`，并核对实际生成页数。现有脚本默认只预览首页；表格检查只抽取前 12 行，公式检查主要检查词元存活，字体嵌入检查也有启发性质。这些限制随结果传递，不能写成全部内容已被严格验证。需要读细节时提供清楚的局部页面，不用一张整篇缩略图代替阅读。源码依据见[附录 D.3](#d3-现有脚本与检查逐项处理)。

GitHub 页面沿官方支持语法制作：聊天／作者稿使用的行内与独立公式，在发布副本中按 GitHub 支持的数学表示转换。转换仅作用于解析出的数学节点，保留公式体以及原定行内／独立层级，跳过代码、普通货币和受保护原文。GitHub 官方文档列出美元分隔与 `math` 围栏等支持方式，因此源码正确与页面实际呈现要分别确认；这一适配依据列在附录 E 的外部资料中。

制作错误在同一 Codex 任务内修复，原稿和输入保持可恢复。超出给定范围的内容或语义布局变更回 GPT；GPT 处理后只替换相应输入继续。渲染依赖缺失时保留已完成正文并说明缺哪个依赖，不换未经同意的正式 PDF 路线。目标页面无法取得时记录未观察范围，不把源码回读升级为页面显示已验证。

### C.3 一份执行证据的最小结构

建议名称为 `<文档名>.execution-evidence.md`。同一次任务中的嵌套插件调用和制作返修接续该文件；后续新的独立调用更新相应任务文件并保留版本记录，避免长期全局审计。多份成品可共用一份证据，但每条引用必须注明目标文件与版本。

| 栏位 | 记录要求 |
| --- | --- |
| 规则编号及来源 | RA-01～RA-15；调用共享插件时引用其来源小节或已有正式编号 |
| 本次适用情况 | 适用；或写出本次不适用的具体原因；未执行、缺输入与未通过分别说明 |
| 成品原句／位置 | 从实际文件提取原句并写章节／段落／页码；机械项定位文件、页面、差异或回读记录 |
| 改前→改后 | 使用接受稿或本次实际输入与最终候选的准确文字；新增、删除、纯格式变化各按实际记录 |
| 实际结果与待处理项 | 简述是否体现规则、剩余具体问题及谁处理；不能用一句“规则已遵守”替代原句或位置 |

RA-15 的证据位置是本文件的交付入口及其目标清单，不再生成“证据文件的证据文件”。纯删减可引用原段落与成稿对应边界、文件差异；机器行为规则可引用准确检查或远端结果；无需为这些情况在科学正文添加句子。

GPT 在回复中附上可下载的该文件；Codex 在本次授权的任务仓库和分支推送并回读。已有授权直接使用；用户明确只读时保持只读并说明证据未推送，不能自行另建远端位置。发送给学生等最终读者的包只含其目标成品，执行证据作为给用户的独立附件或仓库文件。

内容选择和 Clear Writing 的贡献在本文件中体现为实际内容去向、成稿原句及改写差异，调用记录仅作定位。依赖没有实际运行时写清缺口，不能把读过技能说明写成已执行。
