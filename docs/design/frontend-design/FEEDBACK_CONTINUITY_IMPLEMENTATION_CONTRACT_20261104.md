# Frontend Design：设计连续性与反馈返修 v1（实现合同）
日期：2026-11-04
状态：BOUND DESIGN PROPOSAL — 尚未修改正式插件，也不构成发布
目标仓库：`YuukiAS/AI_Skills_Collection`
目标现有插件：`web-development` / Frontend Design v0.4；核心 source 为 `skills/tools/frontend/frontend-visual-systems/SKILL.md`
唯一试点：真实 Asteria Blueprint / Atlas 历史归档，用于检验通用反馈行为；不得把项目专用节点、数据、布局硬编码到插件。

## 一、为什么现有流程仍然不够

现有 Frontend Design 已经有 P0–P4、F-A–F-D、S1/S2/S3、coordinator-first、真实宿主与制作方自检。现有 `workflow-core` 也要求保护已接受行为、拒绝虚假 PASS 与重复失败重跑。这些已发布能力应**复用而不是重建**。

未闭合的问题是：用户对具体画面提出一个反馈后，系统**没有强制将“反馈原意—当前准确版本—此前接受范围—允许改变的局部—旧功能回归”绑定成同一个可执行修改任务**。模型会把局部反馈解释成全新产品需求、修改整个布局甚至换图形隐喻。验证随后保护模型自己误解的目标，而不是用户原意。

修复对象应是正常 Frontend Design 入口在“已有版本上的反馈”分支的**决策和返修行为**，不是另造一种设计师或一个永驻 Planner–Critic 流程。

## 二、结果契约：从「每反馈一轮重设计」变为「每反馈一个已证实差异」

所有模型/会话复用一个产品仓库里的设计事实源。**产品连续性是 repo+固定候选+明确的用户接受范围，不是“某个模型永远在线”。** 一个长期对话不能拥有唯一设计真相；Claude、GPT Astra、GPT 高/极高可在相同基线下接替设计判断，Codex 执行明确的机械修改，GPT Pro 仅在复杂科学/架构判断触发，Work 只在风险匹配的独立验收触发。

一个新反馈的默认单位为当前产品的一个修复事务：找到 **actual candidate/ref、用户具体反馈、正确/错误处、影响范围、保留项、目标状态和最小回归证据**，判断是否需要设计决策后再执行。未经证据证明，`S3` 不得从一条局部否定中自动推导。

### 反馈分类（复用现有 S1/S2/S3，而不是增加一套状态机）

**S1 局部修复**：布局溢出、字号、文案、连线穿字、交互 bug、已批准设计与实现不一致等。在现有设计基线内修复；不要求新 Figma、完整 P0–P4、Pro/Work 或重新提问。Codex 可直接落实无歧义的实现问题；设计相关的有限差异由现有 Frontend coordinator 说明后交 Codex。

**S2 有限设计调整**：当前任务链中的一个或几个相邻界面需要改变信息主次、节点/边可见性、密度、机制表现、详情行为。只修改受影响状态；保护全部无关的已接受内容。模型必须提出具体结构改动、影响面和最小视觉对照。改变用户尚未确定的产品关键取舍时，只问真正需要的那个问题，等待用户回答。

**S3 整体方向重设计**：用户明确要求整体重做，或在同一个真实任务链上有证据证明当前结构无法通过 S1/S2 达成目标。必须指出被破坏的产品假设、哪些旧能力仍应保留、隔离实验分支、最小可证伪候选与回滚路径。未经用户批准不得全量重做。

**禁止**把“减少过载”译为“删除关系/证据”或把“不要无意义连线”译为“所有图不要边”。范围不确定时，从当前真实状态做最小可逆探针，而不是猜出一套新全局设计。

## 三、跨会话维护的最小事实源（不新增数据库或大型流水线）

**如果项目已有 canonical Figma、design spec、原型及用户确认记录，直接引用；不强行新建格式。** 如果没有长期可读的设计事实源，才在项目仓库建立一份短文档（建议 `docs/design/CURRENT_DESIGN_BASELINE.md`）。它只记录：

- 当前候选：repo / branch / fixed commit / 正确真实宿主或预览入口；
- 用户**明确接受**的范围及原话/版本证据；明确区别「局部值得保留」「历史指定母版」「整产品接受」；
- 冻结的关键用户任务及必要的 2–5 个视觉/交互锚点，引用原图和具体可操作状态；
- 未确认的产品选择和当前没有能力验证的部分；
- 当前应该保留的有效机制/数据/关系与禁止回退行为；
- 最近的修订、基线变化和回滚 commit。

用户没有接受某个候选时，必须标为 `CANDIDATE`，不能自动升为 `ACCEPTED`。规范只冻结已经决定的内容，不强迫模型填满所有栏目，更不把审查报告当用户接受凭证。

**跨工具入口**：Codex 通过项目 `AGENTS.md`，Claude Code 通过项目 `CLAUDE.md`（若存在）读取/引用**同一份**项目设计基准；GPT Pro/Work 使用同一固定 GitHub 路径和提交。入口文件只是短指针，不得复制一整套独立设计事实，避免工具更换后出现两份互相冲突的视觉规范。没有项目级 `CLAUDE.md` 时，在当前任务交接中显式给路径即可，不为每个项目强制新增它。

每条反馈不必另建文件。小修改直接在 PR/任务正文中保存一个紧凑的变更说明；复杂 S2 或 S3 可以在当前 canonical design 下新增少量决定记录。不要制造第二份项目 TODO 或新增持久状态机。

### 单次反馈的最小修改合同

```text
CURRENT_CANDIDATE = <repo/ref/commit + user-visible view/state>
USER_FEEDBACK = <用户原话或原图中的精确位置>
CLASS = S1 | S2 | S3
WHY_THIS_CLASS = <为何不必/必须改变已冻结产品语义>
KEEP = <具体需要保留的已接受状态/画面/交互，注明证据；没有就写 NONE_CONFIRMED>
REPAIR = <本轮明确允许修改的部分及可观察预期>
OPEN_DECISION = <真正会改变产品方向、必须问用户的事项；没有则 NONE>
UNTOUCHED = <不得修改的邻近功能/视觉>
VERIFY = <实际宿主下的改后目标任务 + 原来已通过的相关任务>
ROLLBACK = <固定 commit 或可恢复快照>
```

这是一份**修改工作说明**，不是用户需要填写的表。协调模型或 Codex 自己从源文件、截图和用户反馈中补齐，只在真的缺关键决定时才问用户。

## 四、执行与验收的真实闭环

1. **先观察再改**：锁定当前候选和界面状态，重放用户实际遇到的问题；失败复现或证据不够时明确所缺的一件事，不读取全仓全部历史。
2. **确认最小差异**：模型输出 S1/S2/S3、`KEEP`、`REPAIR`、`UNTOUCHED` 和预期用户可见变化。S3 必须有单独用户批准；S1/S2 按原有授权和既定规范推进。
3. **Codex 实施**：从同一基线独立 worktree/branch 出发，只改授权范围；代码缺陷直接修，发现真正的产品/科学歧义退回对应设计/领域负责人，不自行补出新产品隐喻。
4. **真实界面验收**：重放本次失败路径 + 一个足以检查 `KEEP` 未坏的相邻任务；固定相同视口/宿主/对象数据/缩放及截图。浏览器只证实浏览器，Obsidian/桌面必须有对应真实宿主证据。
5. **返修闭合**：用实际截图/操作后状态解释“改了什么、原来正确的部分是否仍然正常”；只在 exact candidate 上判断。没有修好必须如实标明，不能依据 build/test/静态图自动声明视觉完成。

**停止规则**：两轮仍重复同类用户否决；`KEEP` 被破坏；测试通过但真实宿主失败；实际反馈与实现目标不一致；新候选没有任务/信息结构差异；本轮没有可验证差异。此时停止自动返修，只输出被推翻的假设、仍有效部分和唯一最小下一动作；不能默认加一次 Pro/Work/完整重设计。

## 五、模型/费用路线：能力按需调用，而不是固定角色排班

低成本默认：Codex 先做本地查错、截图、检出和可确定的 S1 修复；普通 S1/S2 解释由当前可用的较低成本、足够可靠的 GPT 高/极高完成。只有真正涉及主空间组织、视觉方向、严重信息密度或连续产品行为的决定，才由 GPT Astra 或 Claude 提出、比较最小候选。若存在科研数学/机制充分性争议，按需 GPT Pro；接近阶段验收且存在制作方盲点，按需 Work。

**不硬编码某个模型永远正确或某个模型不可替代。** 模型的能力与价格依用户现有环境/中转的实际用量验证；在一个设计问题上可用 Claude 与 Astra 做独立候选，但不要每个反馈都并行两份。Asteria 的高价值设计评判要用真实任务及已接受画面验证，而不是“哪个模型写出来更像设计师”。

上下文规则：反馈只加载当前基线、相关原图、当前任务链及本轮差异；历史 PDF/深度研究只在出现具体新疑点时按页/按段读取。换模型或新对话时仍只需上述权威文件，不重新跑整个 Deep Research。

## 六、归属与现有插件的最小改动

- **Frontend Design 的 coordinator** `skills/tools/frontend/frontend-visual-systems/SKILL.md`：增加“已有产品反馈入口”、最小 S1/S2/S3 分类、保留/修复/回滚、实际界面回归要求。不要重复现有 P0–P4 和 F-A–F-D。
- `skills/tools/frontend/product-ux-planning/SKILL.md`：只补“用户反馈可能是局部症状，不自动升为整体产品选择”的判断，以及仅对未决实质取舍提问。
- `skills/tools/frontend/visual-direction/SKILL.md`：只补“已认可设计不是灵感，而是不可静默破坏的局部设计权威”；新视觉方向不能自动覆盖 `KEEP`。
- **workflow-core**：沿用已有保护已接受行为、准确证据等级、真实用户入口和重复失败止损，不再新建同义工作流。
- **ai-skills-core**：按现有维护合同做 source/generated parity、真实案例回放、版本/发布等；不要强行升级其他插件或重建 generator。
- `plugins/codex/plugins/**` 是生成层；不能手工修改。正式代码任务按仓库 `AGENTS.md` 使用 `workflow-core + ai-skills-core + web-development` 进入既有 Reviewed Handoff。此文档本身不代表发布。

不用新增顶级 Frontend Skill、Designer Agent、MCP、数据库、Planner–Critic、视觉审查产品或跨项目共享的产品状态服务。

## 七、必须通过的真实回归（通过=改变实际生产行为，不能只在说明中写出术语）

| 场景 | 输入 | 正确选择与结果 | 必须排除 |
|---|---|---|---|
| Atlas V06→V07 | 用户要求去掉匿名桥梁和无意义边，保留论文层科研关系 | S2，仅处理相关图层与关系；保留可核实论文邻域；补真实 Obsidian 渲染/任务链 | 直接删除所有边变七块分类入口，并用单元测试保护 |
| Blueprint Workbench | 用户认为整屏过载，但实现台的多绑定/切换/行号方向正确 | S2，降低默认密度，保护实现台已认可部分，展示同内容前后证据 | 模板 IDE 全替换、删掉实现台 |
| Atlas Visual v1 | 静态画面有潜力，真实 Obsidian 极小字体、截断与边穿字 | S1 或局部 S2；在真实 Obsidian 上解决；用户没有整版接受就仍是候选 | 静态 PASS 替代原生验收 |
| 精确 CSS 修复 | 用户只要求一个按钮间距和文字截断 | S1，Codex直接改、浏览器定向验收 | 拉 Figma/Pro/Work 或整个 P0–P4 |

| 旧证据冒充新候选 | 新 commit 没截图，旧 commit 测试/截图很多 | 缺真实候选证据，不得 user-ready | 一个 PASS 汇总不同版本的证据 |
| 模型切换 | Claude 判断后 Codex/GPT Astra 接手同一修复 | 从 repo/commit/设计基线恢复；不重问已答需求、不重新选整屏视觉 | 对话换人导致产品重建 |
| 无认可基线 | 历史存在若干已被否决的视觉候选 | 保留工程事实与仅被部分肯定的能力，标 `CANDIDATE`，允许小范围探针 | 将某版本自动标 `ACCEPTED` |

需要至少一轮“真实产品正常反馈→更新既有候选→两条任务链与画面对照”的端到端验证，不能只靠关键词检测或生成器测试宣布修复有效。与现有 S1–S3、F-A–F-D、review admission、跨插件未触发任务做兼容回归。

## 八、可执行的实施边界与完成条件

本轮是 v1 设计合同。实施应按现有插件维护工作流进行一次**有边界的源文件变更和回归**，不得为这项改进另造三套基础设施。

完成条件：

1. 普通既有产品反馈实际进入 Frontend Design 的修复分流，而非默认新设计；
2. S1 小修不多出强制审批或大规模复查；S2 只改受影响任务链；S3 必须有用户明确确认；
3. `KEEP` 有可检查的真实表现，未因视觉改版被静默破坏；
4. 测试与真实用户任务一致，旧错误的可执行保护被修改或删除；
5. 生成的正式插件入口和 canonical source 一致，回归没有破坏其他 Frontend/非 Frontend 使用；
6. 候选本身实际渲染后由制作方先验收，用户不再承担第一次发现基本错误的工作；
7. 被用户确认的新设计决定能跨会话/跨模型继续，离线取消另一个模型也不会丢失；
8. 只有通过真实回放、生产级插件消费及维护验证后，才能声明新版本正式可用。

验证没通过就只报告具体未闭合项，不发布、不改 `release` 或 `main`。


## 九、已建立的可运行机械原型与正式插件接入差距（2026-11-04）

本分支新增实物：`experiments/frontend-feedback-continuity/design_guard.py`、`test_design_guard.py` 和 `README.md`。它已在临时 Git 仓库执行 10 项本地单元测试，证明：拒绝越界文件、旧 commit 证据、遗漏 KEEP、虚构宿主、脏工作区、缺失/篡改证据哈希、未经授权 S3，以及不能未经用户认可更新基线。

**这十项只能证明机械保护原型，不证明视觉质量或正式插件已生效。** 正式实现应复用/吸收该原型而非重写第二套工具，并完成以下真正可见闭环：

- **新产品方向先看成品片段**：Frontend Design 使用真实数据与用户任务，优先生成 1–2 个能实际操作的狭窄方向样本，包含正常视口截图与一个关键交互；用户选择的样本才升级为当前设计基线。这里补的是“第一次设计可能选错隐喻”的上游问题，不只是反馈返修。
- **有版本的产品基准**：跨模型统一读取 repo 的一个 canonical design reference，明确用户接受范围；版本与截图/交互证据绑定同一 commit。不需要强制建立一套新目录结构，如果项目已经有合格设计 authority，引用即可。
- **反馈变更守卫**：普通反馈自动生成可见差异和保护项，工程实现必须通过 `design_guard check` 的范围/身份/证据检查。只有用户明确认可且必要的真实任务检查完成后才通过 `promote` 产生新的基准候选。
- **真实观察接口**：生产工具需从已有 Playwright/Obsidian CLI/MCP 得到同一任务的旧版与新版画面/录制，附宿主、视口、对象、commit 和验证结果。旧坏新好至少覆盖 Blueprint 的实现台保留与 Atlas 的有意义论文关系保留；没有实际截图或真实任务链就不得标为“用户可用”。
- **模型替换验收**：先由一个模型锁定正确局部及其证据，再让另一个模型在新会话只读取 canonical reference 完成定向返修，验证不重复解释需求、不丢原来正确的交互。Claude、GPT Astra、GPT 高/极高只是可替换的设计判断方，不能依赖某个模型的私有聊天记忆。

**完成标准不是“新增了一个 guard 脚本”，而是用户在下一次真实反馈后看到：AI 找到当前准确画面 → 仅修改应改的部分 → 自动复测需要保护的内容 → 前后截图与操作结果可查 → 明确认可后才更新下一版。**
