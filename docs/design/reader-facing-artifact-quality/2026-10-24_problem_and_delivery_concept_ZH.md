# 面向读者的成品质量：实际问题与单入口交付构想

**日期：**2026-10-24  
**性质：**用户反馈与设计方向记录；未冻结架构、未授权实现或发布。  
**起点：**`main@69ae0ab4d09435357a18f7e0aee21b02e16c0a96`。  
**范围：**跨 ChatGPT 网页版／客户端与 Codex 的作品生成、编辑和交付；不修改任何已有插件的正式行为。

## 1. 要解决的真实问题

用户反复收到技术内容大体正确、但最终呈现含有大量不必要解释、修辞和功能的作品。失败横跨 Notion 页面、GitHub 正式文档、科研学习网站、软件界面、架构图、图片、幻灯片和普通聊天回复。核心成本是用户必须一遍遍指出哪些段落、按钮、交互或视觉对象本来就不该存在，成为成品的第一轮编辑和验收者。

用户可以接受在任务开始时**明确选择一个可靠入口**，但不希望每轮分别选择多个插件，也不希望重复提醒「调用 Clear Writing」「不要出现 AI 味」。设计由 GPT 先做再交给 Codex，或者直接交 Codex，都应符合相同的最终质量标准。

质量标准是**面向当前读者的内容必要性与自然表达**。它不等于统一缩短文字：数学推导、机制解释、必要操作说明、真实产品状态、重要的限制或权限信息都应完整保留。GitHub 的内部日志、机器协议、开发提示词和无需给普通读者看的执行证据，可以采用较低的成品文风要求；用户明确要求写入 GitHub 的正式文档和报告仍按正式作品验收。

## 2. 已观察到的失败模式

以下根据用户在 2026-10-23 至 2026-10-24 的会话中展示的画面与反馈归纳。原始截图与私人研究内容未复制进公开仓库；这些是**已知问题样本**，不能日后冒充全新泛化测试。

| 载体 | 实际出现的问题 | 不能采取的表面修复 |
| --- | --- | --- |
| 数值方法学习网站 | 正常数学实验旁加入无必要的「完成这一章」、自我确认与产品说明 | 一味删除数学解释，或仅让提示语更流畅 |
| 软件 UI（Lucerna） | 装饰性的蘑菇被额外设计成「点击蘑菇柔光扩散」的操作和引导；演示／内部状态解释挤入常规界面 | 只润色引导文字，保留无依据的交互 |
| 架构／流程图 | 「谁实现、谁审查」、内部限制、验收状态等说明占据视觉空间；部分职责关系本身确有价值 | 机械删掉所有职责关系，损害架构语义 |
| Notion 研究任务页面 | 阅读清单表格额外附一整列重复解释；规则之后继续写假想反例、辩护和训诫；聊天中解释本次修改的文字被带入页面内容 | 把整列逐句换词、或者删掉真正影响研究独立性的读取要求 |
| ChatGPT 对外说明及正式文档 | 「不是 X，而是 Y」式无端纠正、单句成段、非必要英文、过量章节、反复向用户交代内部过程 | 靠禁词、限制段落数或简单字数阈值判定质量 |

跨载体的共同失效机制：**生成者把内部思考、实现说明、审查证据或显示自身考虑周全的文字提升为面向读者的内容**。有时还把没有必要的视觉创意提升为真实产品功能。此前已经出现「相关语言技能实际加载但完整回答仍失控」的记录，说明技能存在、局部文案自然与整件作品合格是三个不同事实。具体责任仍需按生成路径核实，不能把上述所有案例未经验证就归咎于某个正式插件版本。

## 3. Clear Writing 与成品级能力的责任边界

**Clear Writing（现有 `writing-style`）**继续作为唯一通用文字质量来源：自然中文、减少非必要英文和机械断行、纠正模板化套话、全文连贯、正确解释数学与技术内容、保留证据和事实含义。普通聊天解释、正式文档正文、表格说明、界面短文案分别走已建立的适当专业路线。需要完整写入外部文档时，应审查**该文档本身**，不得用漂亮的聊天汇报替代。

**各领域技能**决定内容、结构和视觉／产品语义：Frontend Design 负责页面上哪些文字与功能应当存在；Scientific Visualization 负责图示关系与视觉编码；Presentations 负责页面与整套演示稿；Research Authoring 负责研究文档结构、证据和正文／附录的分配。删除一个无依据的按钮、交互或整列说明，往往必须由这一层决定。Clear Writing 不得凭措辞好坏擅自改模型结论、产品权限或设计范围。

**拟议成品交付入口**负责跨技能路由和实际交付：识别成品与内部信息、确认领域处理和 Clear Writing 已真实完成、组织候选作品的最终审查，并保证交付对象与接受审查的对象一致。它不维护第二套写作风格规则，也不直接接管上述领域的专业判断。

新建一个用户可见的「成品交付」插件是**候选包装方案**，不是本记录已批准的实现决定。应先比较现有插件／协调技能的扩展是否已足够；只有正常入口、跨插件调用或受控发布确实需要时，再评估新的插件或 MCP 服务。禁止为了形式上的「一键」重新实现现有技能、审查器或状态机。

## 4. 候选日常使用路径

**ChatGPT 先设计，再交 Codex：**用户选择一次成品入口并说明目标；GPT 用对应领域技能形成明确的用户可见内容范围和必要事实；内部设计理由、执行说明留在协作材料；Codex 按获准范围完成候选；对最终用户可见自然语言执行 Clear Writing；检查完整渲染、内容与功能；合格后才进行正式交付。设计简报不应逐字变成网页文案。

**用户直接交 Codex：**省略跨模型设计交接，仍使用同一套内容准入、文字处理、真实渲染与成品审查标准。不能因为直接开发就放弃作品级判断。

**Notion／GitHub 正式文档：**先形成供全文审查的候选正文，再通过受控工具写入目标；写入后回读实际内容并核实版本及排版。编辑器的操作解释和完成汇报只留在聊天或内部记录，不自动追加到页面。

**图片／图示／PPT／软件 UI：**先生成候选，再以实际图片、页面、幻灯片、原生界面和必要交互为依据进行检查。必要时返回制作端删除无关元素，而非只给文案换词。

**普通 ChatGPT 文本回复：**仍优先依靠 Clear Writing，研究如何提高长对话正常入口的实际消费率与完整答复审查，不能声称已有每轮插件强制调用机制。

## 5. 交付阻断与平台边界

理想方案要把「检查」与「正式发布／写入」相连：仅当审查结果绑定当前候选文件、页面、提交或渲染版本，且必需问题得到修复，才允许由受控发布工具执行正式交付。执行者口头声称「已审查」「全部通过」不能替代证据。

但必须区分**技能要求**和**真正的发布权限**。单独安装 Skill／插件不保证能拦截所有工具调用。ChatGPT 普通对话中立即显示的回复、原生直接生成的图片、绕过该入口的 Notion 写入或仓库部署，都可能在正式审查之前已被用户看到。严格的「先审后看」只能对确实经由候选区和受控发布工具的任务主张有效，其他路径需明确标识为未受控；不能承诺任何情况下永久零漏判。

隐私、未发表科研材料、模型调用费用和既有授权边界继续按仓库与目标系统规则处理；不得以独立审查为由擅自外传私有内容或启用付费调用。

## 6. 怎样验证有用，而不是只证明写了新规则

将上面的五类案例作为**已知回归**。从真实 ChatGPT／Codex 正常入口提出新网站、文档、Notion 编辑、图示和软件界面请求，**不在提示词中额外提醒避免 AI 味**，检查实际加载／消费的技能、候选内容、最终渲染与交付动作。

验证时必须同时证明：
1. 内容边界正确：无依据的文案、整块重复说明、凭空新增的功能被实际移除，而非只是改写得更自然。
2. 保真正确：数学推导、科学解释、真实角色／因果关系、必要安全与权限信息没有被误删。
3. 入口真实：显式选择一次目标入口后，领域路线及必要 Clear Writing 路线确实发生；ChatGPT 与 Codex 两种发起方式分别测试，不能用一个环境替代另一环境。
4. 成品真实：审查者看到完整实际作品；检查与交付绑定同一版本；未审查或审查失败的候选不能通过受控发布入口。
5. 泛化正确：开发中已反复看过的案例只算回归；在冻结候选与标准后，用未见过的其他作品检验，并保留适当的合法反例。

禁止以源文件存在、单元测试、关键词扫描、漂亮的候选示意图或执行者自述冒充端到端效果。至少先做可复现的小范围正常入口样机，再确定新插件／MCP 方案与正式发布范围。
