# Planner / Critic 合同完善方案 v0.1

日期：2026-10-17  
状态：待独立 Critic 审查  
目标：只完善 ChatGPT Web 长期 Planner / Critic 协作合同，不修改 `workflow-core`、具体 Plugin/Skill 或 Bridge Kit 运行实现。

## 1. 背景与目标

本方案直接处理：

- `docs/workflows/CHATGPT_WEB_COLLABORATION_REGRESSIONS_2026-10-17.md` 记录的九类真实问题；
- 当前 AI Research Stack Project setting 备份：
  `docs/project-settings/AI_RESEARCH_STACK_PROJECT_INSTRUCTIONS_SNAPSHOT_2026-10-17.md`；
- 当前 `PLANNER_ROLE_CONTRACT.md` 与 `CRITIC_ROLE_CONTRACT.md`。

目标不是增加新的工作流、角色、状态机、插件或自动化，而是让已有 Planner / Critic 在 ChatGPT Web 中真正承担四件事：

1. 审查必须经得起普通用户沿正常路径追问；
2. 用户只需面对稳定、少量的人工接收方；
3. 非终态必须自动给出唯一下一入口；
4. PASS 必须让用户理解自己到底批准了什么。

## 2. 当前规则为什么仍不足

现有合同已经有多项正确原则，例如：

- PASS 绑定对象、版本和阶段；
- Critic 检查过重、过简与实际入口；
- REVISE 后应自动给 Planner prompt；
- execution-ready PASS 必须审 Proposal / Goal / Kickoff；
- 曾经 REVISE 后的最终 PASS 应给用户可读闭环说明。

但九类真实失败说明仍有四个结构性缺口。

第一，现有 Critic 规则偏重“审查材料是否充分”，没有把“普通用户会怎样连续使用和追问”变成 PASS 前必须实际回答的反证面。因此一个文档很完整的方案仍可能在启动、配置、进度可见、权限拦截、恢复或接手路径上留下大洞。

第二，现有“下一角色 prompt”只覆盖部分 Critic / Planner 路径。仓库内部的 Reviewer / Verifier / Terra 等身份仍会泄漏到 ChatGPT Web，导致某些结果绕过 Planner/Critic 的用户交接合同。Clear Writing 第二轮自动 Reviewer 耗尽后只报 REVISE、不告诉用户下一步给谁，就是这一缺口。

第三，当前 execution-ready 主要检查执行包完整与授权边界，但没有一句足够硬的判据：“第一个尚未完成的必需动作必须已经属于 Codex”。因此名为 Codex handoff 的材料仍可能隐藏 Planner / Critic / Reviewer 前置依赖。

第四，用户可读 PASS 说明当前只在“同一对象曾经 REVISE”时强制要求较完整闭环。首次就 PASS 的复杂设计反而可能只得到 PASS + 路径 + Kickoff，使用户不知道通知接口、逐任务配置、危险动作拦截层、失败恢复等关键机制到底怎样设计。

## 3. 设计原则

### 3.1 不新建角色和工作流

人工 ChatGPT Web 交接收敛为三个接收方：

- Planner：方案、范围、恢复路线或职责需要重新判断；
- Critic：独立审查和批准；
- Codex：已经 execution-ready 的实现或已冻结范围内执行。

现有仓库协议中的 Reviewer、Verifier、Terra 等精确身份不删除、不重命名；它们可以继续作为自动任务、机器状态、证据生产者或仓库内部角色。**但它们默认不再成为要求用户手工选择的新 ChatGPT Web 接收方。**

如果某个现有自动 Reviewer / Verifier / Terra 真实存在，就让自动流程自己消费；如果自动入口不存在或已耗尽，而下一步需要重新做方案判断，则回 Planner；如果需要新的独立方案审查，则交 Critic；如果冻结方案允许直接做局部执行修复，则交 Codex。不得只说“再找 Reviewer”。

### 3.2 不新建 PASS 状态枚举

不增加 `DESIGN_PASS`、`PRODUCT_PASS` 等新状态机字段。继续使用现有 review stage / 对象定位，但用户正文必须明确：

- 本次批准了什么；
- 只证明到哪一层；
- 还没有证明什么。

### 3.3 正常使用路径优先于文档完整

Critic 不因为 Proposal / Goal / Kickoff / Gate Matrix 齐全就默认可执行。对会改变用户实际工作方式的设计，必须能回答当前范围内真正重要的正常使用问题。

### 3.4 解释关键机制，而不是重讲整份 Plan

PASS 的用户说明不是第二份 Proposal。只解释会改变用户体验、权限、安全、自动化、费用、通知、恢复或后续操作的关键决定。内部结构、哈希、测试编号和不影响用户判断的细节留在仓库。

## 4. 对 Planner 合同的拟修改

### P1. 在 Active Design Context 增加人类版本与机器定位分离

保留现有 task key、路径和 commit 作为机器定位。

新增规则：

- 新的人类方案版本默认使用简单连续形式，如 `v0.1`、`v0.2`、`v1`、`v2`；
- 只有存在真实成熟度语义时才使用 alpha / beta / rc；
- 历史 `C11`、`R0`、批次号、Gate 编号等可继续作为精确 locator，但不得作为新的用户主版本体系；
- 不新造 `C'` 一类临时版本语法。

对应问题：8。

### P2. 在“五遍预检 / 提案内容”中加入正常使用六问

对于工作流、架构、长期任务、权限/恢复或自动化设计，Planner 在送 Critic 前按适用范围回答：

1. 用户怎样开始；
2. 正常运行时实际发生什么、用户能看到什么；
3. 哪些重要行为有默认值，哪些能逐任务配置；
4. 高影响或危险动作由哪一个真实层负责拦截或审批；
5. 失败、断线、等待或自动轮次耗尽后怎样恢复；
6. 当前阶段结束时谁负责下一步。

不是每个小任务都机械写六个标题；但任何与核心能力直接相关的问题若仍只能回答“以后再设计”“理论上可以”，不得提交 execution-ready package。

对应问题：1、5、9，并强化 2。

### P3. 强化 owner-first 和反过度设计

跨组件设计必须先回答：

- 当前职责的 canonical owner 是谁；
- 已有 owner 为什么不能直接承担或轻量适配；
- 若要新增层，它具体阻止哪个真实失败；
- 为什么这个收益值得新增维护面和故障面。

发现相邻 Plugin/Skill 或平台问题时，默认记录证据并交给 owner；当前任务只有在职责调整本身已经进入审查范围时才能修改别的 owner。

已有调度器、平台原生机制、服务管理器、领域能力或 Bridge 正常入口能承担职责时，优先复用或适配，不因“统一”而复制第二套路由器、watcher、状态机或长期服务。

对应问题：7。

### P4. 把“非终态续航责任”从 Critic 特例提升为 Planner 通用职责

Planner 处理任何外部审查结果、自动 Reviewer 结果、执行中断或恢复结果时，只要当前任务不是终态，就必须确定一个唯一的下一用户可见接收方。

规则：

- 需要改变设计/范围/恢复语义 → Planner；
- 需要独立审当前方案 → Critic；
- 设计与审查均完成且第一个未完成动作可由执行者完成 → Codex；
- 真正只有用户才能做的产品选择、私有上传或授权 → 先提出最小用户动作，完成后仍自动生成下一角色 prompt。

若内部自动角色真实存在且可用，可说明自动继续；否则不得假设它存在。

对应问题：3、4。

### P5. Codex handoff 增加“首个未完成动作”硬门

任何准备称为 Codex handoff / Kickoff / execution-ready 的包，在送 Critic 前必须确认：

> 第一个尚未完成的必需动作属于 Codex，并且在它之前不存在未完成的 Planner / Critic / 人工 Reviewer / 产品决策 / 未确认自动任务。

允许用户“发送 approved kickoff 本身”形成已经写清的 bounded authorization；但不能把尚未作出的产品选择或尚未完成的独立审查藏进 kickoff。

若该条件不成立，就不能生成面向用户的 Codex handoff。

对应问题：5，并减少 3、4。

### P6. 真实失败触发有限同簇检查

当一个真实失败证明某个机制本身有洞，而不是单个数据/环境偶发问题时，Planner 在提出修复前检查同一机制的一跳相邻路径，例如：

- 正常成功 / 失败 / 恢复；
- 首轮 / 轮次耗尽；
- 自动接手存在 / 不存在；
- 权限允许 / 拒绝；
- 同一 owner 的主要入口 / 邻近入口。

只检查与已证实失败共享同一因果机制的邻域，不升级成全仓或全系统审计。

对应问题：6。

### P7. Planner 给 Critic 的包加入“用户关键决定摘要”

复杂设计送 Critic 时，附一个短摘要，最多聚焦真正会影响用户理解的关键决定，例如：

- 机制到底怎么工作；
- 默认开启什么；
- 哪些可以逐任务配置；
- 危险动作在哪里拦；
- 通知/费用/外部副作用怎样触发；
- 失败后如何恢复。

这不是最终 PASS 说明，而是让 Critic 能检查“用户是否会真正知道自己批准了什么”。

对应问题：9。

## 5. 对 Critic 合同的拟修改

### C1. 明确 Critic 是 ChatGPT Web 的统一人工独立审查入口

在不改变仓库内部机器角色身份的前提下，增加：

- 用户手工切换独立审查线程时，默认接收方统一为 Critic；
- Reviewer / Verifier / Terra 等若是自动或仓库内部角色，可继续运行并产出证据；
- 不得因为自动 Reviewer 不存在、已耗尽或不能继续，就要求用户自己新开一个“Reviewer”线程；
- Critic 读取这些内部审查结果作为证据，但不把内部角色名称重新变成用户路由责任。

对应问题：3、4。

### C2. 将“六个核心判断”完善为包含正常使用反证的七个判断

新增一项“正常用户路径能否问穿方案”。

Critic 在当前审查阶段按适用项独立回答：

1. 怎么开始；
2. 正常运行中真实发生什么；
3. 用户看到什么、可配置什么；
4. 关键权限/危险操作在哪里由真实机制阻断；
5. 失败、断线、等待、轮次耗尽后怎么恢复；
6. 下一角色是谁，能否真实接手。

若其中任何一个属于核心承诺，却没有明确 owner、机制或阶段边界，则 REVISE。不能用“实现时再补”掩盖会改变架构、权限或用户体验的核心未知。

对应问题：1、9。

### C3. 强化 PASS 范围陈述，防止语义膨胀

每次实质 PASS 的自然中文结论必须显式包含：

- “本次批准的是……”；
- “这不代表……”或等价边界说明。

不得让设计 PASS 自然演变成实现 PASS、产品可用或正式发布结论。后续引用旧 PASS 时必须保留原阶段和边界。

不新增新的 PASS 枚举。

对应问题：2。

### C4. Execution-ready PASS 增加首个未完成动作检查

现有 Proposal / Goal / Kickoff 三件套检查继续保留，新增：

- Critic 必须列出当前“第一个尚未完成的必需动作”；
- 只有该动作可由 Codex 在 approved scope 内执行，才可 `READY_FOR_CODEX=YES`；
- 如果仍需 Planner 设计、Critic 审查、人工 Reviewer、用户产品选择，或依赖一个未验证存在的自动任务，则必须 REVISE 或转到正确接收方；
- “之后可能需要自动 Reviewer”只有在该自动入口已验证存在、绑定当前任务且合同允许时，才可视为执行链的一部分。

对应问题：5，并强化 4。

### C5. 所有实质 PASS 都要给用户关键机制说明，不再只限“曾经 REVISE”

把当前 §6.3 从“曾经 REVISE 后的最终 PASS”扩展为所有实质设计 / execution-ready PASS 的比例化用户说明。

至少按当前对象真正相关的部分说明：

- 这次批准了什么；
- 最重要的机制怎样工作；
- 用户正常使用时会看到什么；
- 默认行为与逐任务可配置项；
- 权限、安全或危险动作由哪一真实层执行；
- 通知、费用、外部副作用何时发生；
- 失败、断线或自动轮次耗尽后如何恢复；
- 哪些能力仍未实现、未验证或不在本次 PASS 内；
- 下一步唯一接收方。

复杂方案可以有 5–10 个关键决定；简单方案保持简短。禁止复制整份 Plan、堆路径/字段/测试名或用术语替代解释。

对应问题：9，也增强 1、2、4。

### C6. REVISE / 非终态必须保证下一跳，不只生成状态

保留当前 §6.2 的自动 prompt，但强化为：

- 所有正式非终态，只要下一步需要另一个人工 ChatGPT Web 线程，就必须给唯一接收方和完整可复制 prompt；
- 用户可见接收方默认只使用 Planner / Critic / Codex；
- 如果内部自动角色将真实接手，说明已验证的入口，不再要求用户手工转发；
- 如果无法确定谁能接手，这本身是工作流缺口，不能把状态写成“已交接”。

对应问题：3、4。

### C7. Critic 关闭真实机制 blocker 前做有限同簇反证

对于已经暴露“机制级”而非单例级失败的 blocker，Critic 在关闭前检查 Planner 是否覆盖共享同一因果机制的一跳邻域。

Critic 不得借此无限增加新 blocker；只有同一机制直接可推导的相邻失败才能要求补齐。

对应问题：6。

### C8. 过重设计和跨 owner 修改必须有正面证明

在现有“是否过重或过简”中增加：

- 新增路由器、watcher、状态机、长期服务、控制层前，必须明确已有 owner 为什么不能满足；
- 跨 owner 修改必须证明职责调整本身已被批准；
- “为了统一”“更保险”“以后可能有用”不是充分理由；
- 若成熟平台/现有 owner 能解决，Critic 应要求删除多余层，而不是仅记为非阻塞优化建议。

对应问题：7。

### C9. 人类版本命名也进入 Critic 检查

若新提案使用临时、不可预测的人类版本体系，Critic 要求改为简单连续版本；历史机器 locator 不需重命名。

对应问题：8。

## 6. 九类问题覆盖映射

| 问题 | 主要关闭机制 |
|---|---|
| 1. 一问就露洞仍能 PASS | P2 + C2：正常使用六问 / 用户路径反证 |
| 2. PASS 范围膨胀 | C3 + C5：明确批准层级与未证明边界 |
| 3. Reviewer / Critic 等角色混乱 | P4 + C1 + C6：用户人工接收方收敛为 Planner / Critic / Codex |
| 4. REVISE/BLOCKED 后不知道给谁 | P4 + C6：所有非终态唯一下一跳 + 完整 prompt |
| 5. Codex handoff 进去后还找 Planner/Critic | P5 + C4：首个未完成动作必须属于 Codex |
| 6. 修一个又冒一个 | P6 + C7：同因果机制的一跳邻域检查 |
| 7. 越界改 owner / 过重路由 | P3 + C8：owner-first + 新控制层正面举证 |
| 8. `C'` / `C11` / `R0` 等命名 | P1 + C9：简单人类版本 + 机器 locator 分离 |
| 9. PASS 后仍不知道具体设计 | P7 + C5：用户关键决定摘要 + 所有实质 PASS 的机制说明 |

## 7. 不修改什么

本轮不修改：

- `workflow-core`；
- 任何领域 Plugin / Skill；
- Bridge Kit runtime、Host Policy、Reviewed Handoff 状态机或 Persistent Run；
- GitHub Project schema；
- 自动 Reviewer / Verifier / Terra 的机器协议；
- 当前 AI Research Stack Project setting 本体。

Project setting 会在角色合同方案稳定后单独做一次有边界的同步修订，避免合同与设置同时变化导致难以判断哪一层负责。

## 8. 外部核查

本轮只做了与权限边界和审查透明度直接相关的最小外部核查。

OpenAI 当前公开说明强调两点：

1. Codex 的 sandbox 与 approval policy 是实际技术边界；低风险动作应在边界内顺畅执行，高风险或越界动作才需要明确审查。
2. Auto-review 可以减少不必要的人类审批，但不会取消 workspace 限制，也不能替代所有批准。

这支持本方案的两个方向：PASS 说明应告诉用户危险动作究竟由哪一真实层拦截，而不是只说“有安全机制”；同时，只有真实存在且可用的自动审查入口才能被算作执行链的一部分，不能把“理论上有 Reviewer”当成已经接手。

本方案不把 OpenAI 的具体产品结构复制进内部 Planner/Critic 架构。

## 9. 验收标准

独立 Critic 应至少用以下真实场景反证本方案：

1. 一个类似 Persistent Run / ETA 的设计首次就 PASS：用户是否能在不重读 Plan 的情况下知道通知入口、默认值、逐任务配置、失败恢复和未实现边界；
2. 一个类似 Slurm 安全设计：用户是否能知道 `scancel` 到底由哪一实际层拦截，而不是只看到“安全”；
3. 自动 Reviewer 第二轮 REVISE 且自动修复耗尽：回复是否自动决定下一接收方并给完整 prompt；
4. 一个 Codex kickoff 仍藏着未完成 Critic / Planner 决策：是否会被 execution-ready gate 拒绝；
5. 一个 Clear Writing 发现 Research Authoring 问题：是否会先路由 owner 而不是顺手改另一个插件；
6. 一个已有成熟 scheduler / service 可以承担任务：是否会拒绝无充分收益的新路由器 / watcher；
7. 一个机制级失败：是否检查一跳相邻路径但不会膨胀成全系统审计；
8. 一个历史文件仍叫 `C11`，但新方案使用 `v0.2`：是否保留历史 locator 而不继续发明临时版本体系。

## 10. 实施边界

本 v0.1 只有在独立 Critic PASS 后才能修改正式合同。

若 PASS，实施仅应修改：

- `docs/workflows/PLANNER_ROLE_CONTRACT.md`
- `docs/workflows/CRITIC_ROLE_CONTRACT.md`

合同版本建议从 1.4 升到 1.5，表示同一角色体系内的兼容行为完善，不改变 Planner / Critic 的基本职责分工。

不需要 Codex 工作流插件改版，不需要 Bridge 发布，不需要新增自动化。
