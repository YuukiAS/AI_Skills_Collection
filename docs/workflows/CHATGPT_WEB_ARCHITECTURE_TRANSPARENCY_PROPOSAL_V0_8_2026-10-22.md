# Planner–Critic 1.8 修订提案 v0.8：让用户在实现前看清架构

日期：2026-10-22。任务：`chatgpt-web--pass-integrity`。设计分支保持 `design/chatgpt-web--pass-integrity-v0-4`。
正式依据：`main@f1de8e85957d32a50f4458349f450ec65add13bb` 的 Planner/Critic 1.7 与能力验收政策 1.2。
本版替代 `0bd4dbf09be68811cafac53afdaad0f671206023` 中 v0.7 的待审设计；旧文件保留为历史，不再作为当前执行依据。
阶段：设计修订，待独立 Critic；本轮只允许 PROCEED / REVISE，不实施、不授权 Codex。

## 1. 给用户的方案说明

这轮选择的办法，是在现有 Proposal 中先写清“给用户看的机制说明”，让它和技术方案一起接受独立 Critic 审查。不给它另建一套发布系统，也不等到 PASS 时才临场总结。你从第一次提案就能知道真正用了什么技术，并在投入实现之前反对不合适的选择。

Planner 写方案时，先从你的目标挑出会影响决定的技术选择，再解释它怎样处理一次具体任务。假如取消作业依赖 Wrapper，就必须说明它包住了哪个命令、哪些调用能经过它、哪些可能绕过；如果选择 `PreToolUse`，就必须说明它在哪个动作之前触发、用什么查询真实作业信息、谁把确认问题送到你正在看的聊天、没确认为什么不能继续。只有“有安全检查”这样一句话，不能代替这些解释。文件哈希、测试流水和部署路径继续保存在技术证据里。

Critic 要从用户要求和实际源码独立检查，再把技术方案与这份说明逐项对照。方案明明使用 Wrapper，说明却只写“安全拦截”；方案只覆盖普通 Codex 调用，说明却写“所有取消都无法绕过”——这两种情况都必须退回。同样，文字很顺但实际执行入口不存在，也不能通过。技术正确和说明忠实可懂必须同时成立。

通过后，给你展示的是 Critic 已核对过的完整机制说明，另加它自己的批准理由、真实变化和剩余边界，最后才是可复制交接。不会把一份受审说明换成临场生成的审计摘要；Critic 也不能照抄 Planner 就自称完成独立审查。若它发现真实矛盾，应明确指出矛盾在哪里并退回，而不是替 Planner 偷换方案。

任务中断时仍按同一个原则处理：先解释实际影响，再由当前责任方确定谁修、先修什么。普通实现错误留在原 Codex 任务；需要改架构或权限的回 Planner；当前 Planner 能继续做的就继续做。只有确实需要你切换线程或操作界面时，才交给你已经准备好的完整提示词或最小动作。

这套办法的作用，是把关键技术选择提前公开，并让独立审查真正检查你将阅读的内容。它仍依赖模型遵守合同，不能冒充浏览器发送前的程序拦截。本轮就先按这个办法工作：当前这一节是实际待审说明，下一位 Critic 必须审它是否忠实于后面的机制，并在回复中让你看懂判断；不能只同意“以后应该这样做”。

## 2. 用户要求与本轮更正

完整记录见 `CHATGPT_WEB_USER_NEEDS_AND_PLANNER_LESSONS_2026-10-22.md`。稳定目标是让用户能够理解、比较并否决重要架构选择，而不是只优化措辞。

关键名称并非噪声。若更换某项技术会改变安全边界、正常入口、数据用途、费用、维护复杂度或用户是否接受方案，就要在正文保留足够精确的身份与解释。Slurm 的 Wrapper、`PreToolUse` 与 MCP 是这种信息；归档媒体类型通常不是。没有固定英文比例、标题数或字数限制。

用户不是执行审计员。完整证据、命令、路径、提交、协议字段放在仓库和机器交接中；正文必须自行建立机制、例子、取舍、证据与限制的理解链。普通问答不机械升级为方案审查。

## 3. 原架构的归因与保留范围

1.7 已经规定正常使用六问、关键执行链、非终态唯一下一入口、比例化用户说明和失败分流。不能再说中央合同完全没有这些要求。观察到的失效包括：调用方未遵循既有规则、任务提示词缩小最终审查、说明只在审查结束后临场生成，以及把完整说明质量误当作字段存在性。

v0.7 的接口真实性核对、条件性验证、非终态交接、同一候选验证、正式集成和回读方向保留。其“当前 1.8 已经解决”措辞改为“拟议机制准备解决”，因为设计尚未正式实施。

本版实质改变审查对象和生成顺序：机制说明成为 Proposal/Plan 内一个有准确位置的受审部分，而非批准后临场附属摘要。它不取代技术审查，不形成第二份架构事实来源。

前文提出的强制发布网关、独立常驻语言审查器、自动改造 Codex 接收口均不进入本轮。当前没有证明这些能力已存在，也没有理由先把本问题扩大成平台工程。

## 4. 正式设计机制

### 4.1 在原方案内准备机制说明

Planner 在首次实质提案及重要修订时，用现有 Proposal 的前部章节写机制说明；普通任务可只用几段，不新增固定报告册。进入完整执行包后，Plan 引用同一段说明，Goal 与 Kickoff 引用同一批准包，避免各处各写一套不同架构。

说明至少覆盖本任务真正重要的决定：选择哪项具体机制及入口、为何不用最有竞争力的替代、真实请求经过哪些判断和执行步骤、关键安全或失败边界、用户使用改变、证据强度和未完成部分。不是固定六标题；一个连贯例子可以同时解释多项。

机制名称与适用边界必须真实。不能把未知实现概括成“安全层”；也不能因为举例便利捏造 API、Hook、自动角色或已有能力。解释不出来时先补证据或设计，不把技术空白交给写作技能补齐。

### 4.2 重要选择披露：用替换反证检查抽象空话

Critic 检查：如果把真实方案的 Wrapper 换成 Hook、把机器共享配置换成每仓配置、把原生工具换成外部付费服务，用户正文是否几乎不用改？若会，而这些替换实质改变任务，则说明隐藏了关键决定，需要返修。

这不是要求每项接口都出现于正文。判断依据是当前用户是否需要该信息来理解或反对方案。科学模型、统计假设和模板/渲染方式也适用同样判据；不能硬套 Slurm 名词。

### 4.3 证据对照，由原独立 Critic 完成

仍只有 Planner 与 Critic 两种人工角色。Critic 先读稳定用户要求和直接来源，再审 Planner 的取舍与说明。它沿一个代表性正常请求和最关键失败路径核对：正文承诺能否由方案和现实能力支持，具体机制是否真的位于所宣称的位置，有无覆盖范围夸大。

对应关系留在现有 review 文件，可用简短文字或小表，不新建需求数据库。缺依据不能用“文字通顺”放行；只会列证据也不能代替用户解释。

出现过 REVISE 的任务，要解释关键问题的实际关闭：旧方案为何失效、改变了哪个机制、用户少承担什么工作，以及哪些层没有变。保留 1.7 §6.3 的语义，但不将所有 finding 编号倾倒到用户正文。

### 4.4 同一受审说明进入实际交付

审查记录绑定执行包的准确提交与机制说明所在章节。通过时，Critic 在正文展示已经核对的说明核心全文，并给自己的结论；不得只贴链接让用户打开仓库，更不得重新用内部审计摘要替代。当前轮次已充分展示且用户仅问局部问题时，可只解释该局部，不机械重贴全文。

若核心机制、保证或许可需要改变，先退回修订；不在 PASS 回复内偷偷改设计。纯措辞调整不自动使技术批准失效；但调整后仍必须保留机制身份、关键因果关系、条件和独立判断。缺少用户交付时属于交付未完成，不能用零散补句追认原不完整 PASS，也不凭此声称技术方案一定错误。

没有额外的“说明通过”顶层 PASS。正式结论类型继续由中央合同控制；最终执行就绪审查仍只有一次 PASS，并一次给齐完整说明、批准定位和短 Codex 入口。机器内容不交给 Clear Writing 改写。

### 4.5 非终态同样先完成责任判断

受阻时从证据判断实施缺陷、设计矛盾或界面限制，不能笼统归为“缺一个环境”。当前 Planner 的调查/修订工作不能回扔用户；存在多个责任方时由 Planner 决定先后。需要转交时直接附准确材料与下一条提示词。

用户普通追问默认是解释请求。只有新证据暴露原承诺无法成立，或用户明确增加范围，才回到设计。保留普通 bug 默认同任务 Codex 修复的既有语义。

### 4.6 写作辅助与正常触发

项目设置已经把设计/审查路由到角色合同；正式实施后在 Planner 合同 §6/§11 和 Critic 合同 §6.1/§6.3 直接嵌入上述具体职责，不要求用户每次 @Clear Writing 或重贴审查清单。任务专用 prompt 只提供对象与定位，不再另定义输出合同。

Clear Writing 在事实和方案已确定后处理表达，不能选择技术、制造证据、删除关键技术名称或代替独立审查。本轮已读取已安装的 `response-clarity` 与 `chinese-prose` 并用于分别整理聊天说明和设计文档；这只是写作应用，不冒充独立质量验收或平台自动拦截。

## 5. 三种备选与选择理由

继续在末尾加“说人话、少英文”的规则，成本最低，但真实失败已经证明它不能防止正文选择错误或隐藏机制，故不作为主修复。

新增外部质量服务和强制发布网关可以在一个真正受控的运行入口约束流程，但当前 Web、工具、费用、传输和接收端尚未闭合；为了修说明先建设这些系统会扩大故障面。本轮不采用，不声称以后永不需要。

推荐复用原双线程和版本文件：Planner 提前形成说明，Critic 独立对照来源审它，批准绑定这份说明及同版技术合同，交付不再临场换稿。它改变真实输入、审查对象与交付来源，日常不增加角色或额外批准轮次。是否足够仍要看本轮和后续正常任务结果。

## 6. 本方案自身怎样工作

假设 Planner 为新插件选了一个额外后台服务，却在正文只写“自动处理”。按 §4.1，服务的存在、启动方式、必要性和失效后果应已进入说明；按 §4.2，若把服务替换为按需工具仍不影响正文，Critic 应识别说明过空；按 §4.3，Critic 要对照方案确认谁真正启动它。缺失就 REVISE，不允许把“之后部署再看”留给 Codex。

对本治理提案同样适用：真正运行入口是现有 Web Planner/Critic 对话、GitHub 文档与既有授权后的 Codex 执行；没有隐藏网关、自动第三模型或浏览器拦截。§1 就是待审交付文本，§4 是它所解释的机制。下一位 Critic 必须亲自比较两者，并在回复中解释为何认可或否定，不得预设本提案正确。

## 8. 验证设计：先看真实工作，不先增加关卡

当前 Planner 回复与下一条 Critic 回复就是第一次实际应用；保存完整文本和准确审查对象，不用“读过规则”代替结果。用户反馈未认可时，不把本轮标成好示例或总体完成。

沿用 v0.7 的已知案例 A/B/C 作为开发材料，不冒充未见样本，也不预设 C 必须 PASS。A 检查错误执行就绪与关键接口；B 检查停止后的实际交接；C 检查复杂方案批准时的机制说明和完整交付。保持原来源，发现真实缺陷就如实记录，不临场换成容易通过的案例。

增加的检查对象是同一案例中的说明与技术来源是否一致，包括隐藏 Wrapper、错说 Hook 类型、只报测试名、删除必要深度这类对照；不机械增加顶层 Gate 或固定样本数。运行输入与评分依据分开：运行线程只收到角色、实际任务和必要来源，不喂正确 finding、应出现哪些技术名或参考答案。若运行线程访问了评分材料，记录污染，不称独立发现。

历史案例只能证明已知问题的处理。正式“默认生效”主张还需在集成到 main 后的下一次真实设计/审查中观察：用户只提出普通任务，不再次提醒读规则或解释哪些点，线程自行读取角色合同、展示机制并给正确交接。当前按用户要求进行的演示不能替代这项观察。此项验证绑定一个提前冻结的真实任务；无任务时诚实保持待验证，不伪造成功、不自动新建产品任务。

## 9. 权限、候选与完成边界

本轮仅写原设计分支中的本版文件和用户需求记录。下一步是设计审查 PROCEED / REVISE；不能发 Codex 执行入口。

后续执行方案保留先冻结角色候选提交、确定性检查、实现后 Critic 安全检查、真实 Web 验证、集成 main 和远端回读的顺序。冻结提交在提交完成后由后继证据记录引用，不能要求文件包含它自己所在提交的哈希。版本文件只能证明身份，不证明可读性。

本版撤销旧草案中新建正式工作树固定落在 `/tmp` 的安排。最终执行定位按届时目标仓库和 Bridge 现行规则核实，保持同任务，不预设新增后台运行机制。

仅有好看的本轮回复不证明长期可靠。没有程序拦截的 Web 合同不能保证每次遵循；本方案可以被反证，发现正常入口仍隐藏关键选择或反复不遵守时，应停止成熟度声明并定位调用路径，不用无限加规则或挑选好样本掩盖。

## 10. 外部经验与采用边界

AWS Prescriptive Guidance 的架构决策记录指引强调记录背景、决策、替代与后果，并由团队审查、保留历史。其公开指引也明确：记录决定并不会自动解决不遵循决定的代码。本版只借鉴“决定与后果可见、审查同一对象、保留历史”，不引入 ADR 工具或新登记系统。
