## 1. 用户决策说明

**这版批准前希望解决的问题，不是模型不知道“要说人话”，而是连续审查中缺乏责任人检查真正交到你手里的解释。** 现有 Planner/Critic 1.7 已要求自然中文、具体机制、独立审查、唯一下一入口。过去仍发生过技术选择被抽象掩盖、实际安全接口未验就宣称准备就绪，以及 Critic 连续把审计流水当成 PASS 说明。只继续增加同义写作要求，不能阻止同一失败复发。

**真正改变的是两个人工角色之间接收审查的动作，而非新系统。** Planner 在同一 Proposal 中维护你当前应该了解的完整技术决策说明，讲清选用了什么具体方法、为什么不选关键替代、正常请求如何经过它、安全或失败在哪一步处理、哪些判断已验证、还有哪些未定事项。重要机制返修时同步更新当前说明，不再让你自行从过去五轮回复拼出现在采用了什么。

Critic 独立读取真实技术证据，不仅审技术是否成立，还要实际看这段准备交给你阅读的说明是否隐藏决定性选择、夸大能力或遗漏关键因果过程。它必须分别说明三种结论：`REVISE` 意味着什么真实缺陷会导致用户目标失败及最小修补，`PROCEED` 意味着方向可以继续但还不能实施，唯一执行就绪 `PASS` 则意味着完整实施范围、关键执行接口、安全和恢复已具备本阶段证据——**并不意味着产品已经上线**。

接下来的关键不同在于：**接收 Critic 的 Planner 必须核对这份真实审查交付，而不是只读取一个 PASS 状态。** 中间审查本来就回 Planner，不增加新转发。如果技术论证充分但用户回复仍像日志，Planner 可从同版已审方案和 Critic 的原始事实忠实组织你应得到的解释，不再请同一 Critic 第四次重复宣布 PASS；但如果独立技术理由缺失、所审版本不一致、风险仍未知或超出授权，就不能借“修改文案”放行，必须退回真正补审。

唯一最终技术 `PASS` 仍只能由独立 Critic 产生，但**它不再直接提供 Codex 执行消息**，而是额外回原 Planner 一次做读者交付接收。Planner 核对获准的精确方案、原始 Critic 技术结论及你将看到的架构说明，忠实展示其机制、已解决问题与未验证边界，然后才生成可机械复制的短 Codex 提示词。Planner 无权代 Critic 批准技术、修改范围或暗中授予费用/数据权限。代价只是在最终批准后增加**一次已有线程之间的机械转发**；平常 `REVISE/PROCEED` 不增加转发。

例如一个复杂系统原方案采用只能包住特定命令的 Wrapper，却在给你的说明里声称“所有危险操作都会被拦截”，独立审查必须从真实调用路径发现可以绕过的情况，并给出 `REVISE`。后来改用平台原生执行前 Hook，Planner 必须同时更新说明，明确 Hook 的精确名称、触发条件、执行前检查和确认如何发生。若 Hook 处理器实际启动失败时的危险后果尚未验证，最多说明设计方向可以继续，不能把“已有 Hook”说成安全验证通过。经过多轮修复后，最终批准要解释真正采用的当前机制与历史问题如何解决，而不是列出“以前的问题都关闭了”。这个例子只说明审查方法，不规定所有插件采用 Hook，也不是任何实际产品的完整历史复述。

这套方案**不依赖 Mica、外部审核模型、第三个人工角色或新的服务/状态机**。当前项目设置原本就要求线程读取 `main` 的角色合同；1.8 正式合入后，接收职责才会成为新线程默认的合同要求。ChatGPT Web 本身没有可由本项目使用的不可绕过发送前拦截，因此这是一项经过独立相互核对的治理改进，不是绝对不会写坏答案的程序保证。是否真正长期有效，必须在没有再次提醒“讲清机制”的真实多轮任务中观察。

本轮正式批准若成立，**只批准修改治理角色合同及既有回归证据，并开始对应验收；不批准插件发布、修改其它产品、付费调用或新建 Mica/Bridge 组件。** 完整产品或治理正常入口是否可靠，要由实施后独立检查、真实网页回放、正式源合入后的新任务来证明。

## 2. 已冻结的用户目标与边界

保留 v0.10 中稳定的全部用户要求，包括每轮理解进度与三种结论的技术理由、明确关键技术/替代、一个成功链和关键失败链、证据强度、自然中文、可机械复制交接、失败责任、权限边界、多轮不丢架构、不反复提醒及独立审查。用户无需成为角色路由器、仓库管理员或报告文字修订者。

原两角色和当前项目设置不变；现有 `PLUGIN_CAPABILITY_GATE_POLICY.md`、Clear Writing 产品、Slurm、Bridge Kit、Mica、Plugin Creator、其他中央插件不改。不建全局审查网关、软件状态机、数据库、额外脚本服务或人工 Reviewer。

## 3. 同版说明的唯一身份：Critic 已提出并接受的技术收口 A

只在**同一个原 Proposal** 的前部使用稳定的章节标题 `## 1. 用户决策说明`；用户说明仍是原技术 Proposal 的组成部分，不新建第二个长期真相，也不要求其它任务固定字数或六段模板。

在每个已提交候选中，说明身份由以下三个既有事实共同确定：
`proposal path + proposal version + exact package commit`。
审查时 Critic 记录实际读到的版本与章节，Plan/Goal/Kickoff 只用同一个 package commit 引用原说明，不复写另一份描述。

当具体机制、使用方式、安全保证、职责或权限发生实质变化，Planner 在**同一个新版本** 的 Proposal 中修改技术正文和用户说明，再交 Critic 审查。旧审查仅证明旧版本；无关文字修饰不重新打开已批准技术。机器路径/提交在审查来源保留，读者正文不以这些替代解释。

## 4. Critic 技术权威与 Planner 交付边界：收口 B

唯一技术 `PASS` 必须满足：确切任务、同版完整 Proposal/Plan/Goal/Kickoff、原用户承诺、实际接口/安全/恢复证据均由独立 Critic 审查。它在面向用户的正文说明为什么可批准；机器交接只提供 `NEXT_HANDOFF=PLANNER` 与准备给原 Planner 接收的完整 `COPY TO PLANNER`，不直接提供 `COPY TO CODEX`。

原始独立审查必须保存：原 verdict、审查阶段、准确包身份、支持 verdict 的具体技术理由及实质 findings（包括未验证、权限限制与恢复边界）。有 repo 写入权限时保存原审查全文；无写入权限时 `COPY TO PLANNER` 自包含审查技术依据和必要原文，由原 Planner 按收到的原文忠实归档。不得凭空声称 Critic 创建了 GitHub review commit。

接收 Planner 的判定是既有任务上的一次有边界检查：
- 独立技术审查充分、版本一致、用户解释合格：忠实展示原说明和独立判断，然后给短 `COPY TO CODEX`；
- 技术判断充分、只是 Critic 自己的中文整理不佳：只以**已审原 Proposal 和 Critic 原 findings** 恢复易读解释；不新增机制、事实、技术保证或授权；不要求 Critic 重复技术 PASS；
- 技术依据不足、身份错位、关键风险未审、技术事实与批准矛盾：不能归因成写作缺陷；不给 Codex 入口，返回真正的独立审查或由原 Planner 修方案。

**Planner 交付检查不是第二个技术 PASS。** Planner 既不能覆盖原 verdict，也不能制造新的“READY”技术批准或变更冻结范围。发现实质新证据需要改变技术语义时，旧批准对新语义失效并返回正规 Planner–Critic 轮次。最终短 Codex prompt 继续引用同版原批准与用户当次授权，自己不新开范围。

## 5. 原 1.8 其它重要机制保持不变

沿用旧 v0.7 已经正确的行为：任务专用提示词不得覆盖中央最终审查；关键跨工具接口需实际证据或在副作用之前冻结合法条件性验证；任务中断须明确唯一责任方与可复制的下一入口；解释、矛盾证据和新要求区分；候选版本和证据同一身份；实现后安全审查与正式主分支集成必须有真实对应回读。具体可执行版本、阶段和失败边界全部由同版 Execution Plan 冻结。

## 6. 真实验证与声明上限：收口 C

原有真实负例与必要正控保留为已见开发回归。新增的**真正可观察行为**来自：一次 `REVISE` 后技术机制变化时，Planner 是否自发刷新当前说明、Critic 是否独立抓住过期内容；收到无用 Critic PASS 时，Planner 是否识别并忠实补读者层或拒绝缺技术依据的审查；仅 `PROCEED` 时能否讲清为什么仍不能执行；最终技术 PASS 后是否先回 Planner 且绝不自行扩权；正式源合入后，在用户没有再次提醒的真实新任务里能否持续做到。

这些都必须看**完整原始回复与真实来源**，不得只看 `PASS` 字段、字数、测试数、哈希或 Clear Writing 是否被调用。单次实际演示、历史案例和模拟通过均不能被称为未经见过的新任务或者所有未来轮次可靠。

## 7. 目前可以做什么、不能做什么

本版 v0.11 是**供最终执行前独立 Critic 审查的完整包**。当前只已获得 v0.10 **设计阶段 PROCEED**，尚无本版实施批准；只有 Critic 对同版 Proposal/Execution Plan/Goal/Kickoff 作出唯一 `PASS + READY_FOR_CODEX=YES`，且用户实际发送获准的实施消息，Codex 才能修改正式角色合同。

启动位置、合法 Git 操作、具体验收场景、独立审查责任、无付费/生产副作用和失败后谁接手均在同版 Plan/Kickoff 中冻结，不留给 Codex 猜产品语义。
