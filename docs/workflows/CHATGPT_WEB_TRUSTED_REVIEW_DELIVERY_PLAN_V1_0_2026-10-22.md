# Planner–Critic 1.8 实施准备计划 v1.0：正式批准交付的真实边界

日期：2026-10-22
任务：`chatgpt-web--pass-integrity`
提案：`docs/workflows/CHATGPT_WEB_TRUSTED_REVIEW_DELIVERY_PROPOSAL_V1_0_2026-10-22.md`
设计分支：`design/chatgpt-web--pass-integrity-v0-4`
当前仅供设计 Critic `PROCEED/REVISE`，不是 Codex Goal/Kickoff 实施授权。

## 1. 为什么推翻 v0.9 的充足性判断

v0.9 新增同版读者说明，但没有让其消费、版本校验和最终用户呈现脱离自由文本生成。它无法阻止另一次“模型读过合同但仍输出审计报告、自己 PASS”。本 Plan 不再将 Project setting + Role Contract + Handoff 三层称作新执行保证；这些本来就在 1.7 里。

v1.0 要求三个彼此不同的可观察对象：
- **语义正确**：Critic 实际阅读用户说明全文并对照原始技术依据作独立判断；
- **版本正确**：非模型的确定性核对拒绝技术包、已审文本、审查记录不一致；
- **用户确实看见**：正式显示表面从受审文本源直接呈现同一全文；若只有自由文本回复，必须降级为未验证的演示，不可自称受控正式交付。

这三项不能由一次“已调用 Clear Writing/已读合同”代替。

## 2. 在正常设计里生成什么

每个真正需要 Planner–Critic 的设计，在原 Proposal 前部维持一段“给用户看的架构说明”，而非通用模板：

- 真实选择了哪些关键机制及必要准确名称；
- 若采用不同技术会实质影响用户决定，为什么没有采用；
- 一个真实请求从进入、判断、执行到用户结果的因果过程；
- 关键成功/失败、授权、恢复边界与证据强度；
- 多轮修改时旧机制改为何种新机制、用户体验如何变；
- 哪些内部路径/哈希/日志不能直接当成读者解释。

读者说明与专业技术方案属于同一 Proposal/commit。Critic 独立读真实来源后审它，不能只是证明“有一段标题叫架构”。如果具体技术选择对用户决策不可见，判不合格。

## 3. 核对工具的准确职责及正常入口

计划优先复用 AI Skills 当前 Python 测试/验证基础（`scripts/skills.py` + `tests/`），由 Codex 在独立最终执行就绪批准后选择最小实现；**正式签发前必须先冻结具体命令与在真实执行链中的调用点**，不得由 Codex 自己决定替换架构。

确定性核对预期输入：
- 当前任务身份及准确 package commit；
- Proposal/Plan/Goal/Kickoff identities；
- Proposal 内读者说明的原始内容/可校验身份；
- 当前独立 Critic 的实际 verdict、准确来源和所审文本身份；
- 下一条发给 Codex 的 bounded execution identity。

预期拒绝：
- 审旧包、新版 Plan 已改；
- 读者说明改了，但旧 Critic PASS 被继续使用；
- 只有 PASS token、没有独立审查原文或读者说明定位；
- 用户可见说明声称与技术包不是同一版本；
- task/key/执行入口串到另一个仓库；
- 执行提示词语义超出批准权限。

证明途径：
- 正向：完全同版的已审资料通过版本核对；
- 负向：人为替换一个必要内容/版本，正常校验入口真实拒绝，并且下游 Codex 启动/正式交付入口不继续；
- 测试不需要任何真实产品 mutation、付费模型或帐户变更。

**重要资格门槛**：如果核对仅是 GitHub CI/可选脚本，而普通用户直接粘给 Codex 的入口没有实际消费它，就只能称“机器一致性检查”，不能称“Codex 无法绕过的授权屏障”。若正式用户正常入口没有可绑定的受控启动动作，Critic 必须要求重新设计或收窄产品承诺，不得 PASS 这项强保证。旧有 Bridge Reviewed Handoff 可作为成熟入口比较，但当前任务不自动强制所有普通设计任务采用 Reviewed Handoff/Control，也不擅自改 Bridge 的执行协议。

## 4. 独立专业审查如何避免变成填字段

Critic 源于独立 ChatGPT Web 线程，先读当前用户目标/源码/技术方案，再读读者说明；必须核对一个真实用户成功链与最重要失败链，并对会影响技术判断的架构选择做“技术替换反证”。

审查结果应明确能否根据给定正文作出技术同意或反对决定。Slurm 用具体 `PreToolUse`、`PermissionRequest`、`mcp_tool`、`scontrol` 和 Wrapper 的真实差别判断，不能机械把这些名词推广到科研/幻灯片任务。

技术包发生重要变更而读者说明仍是旧机制，Critic 不能拿旧 PASS 批准新版本；若出现真实阻塞只能 REVISE。若 Critic 回复自己把受审说明替换成计划摘要，不能因为内含正确字段就称完整交付成功。

这里的语义真实性仍需要独立人类式专业判断。多次已见错误能作为开发回归，不能宣称自动判定永远正确。

## 5. 受控呈现的最小可行性核查：不把 Mica 现状当能力

候选扩展：`YuukiAS/Mica-for-ChatGPT` 当前 main 的 `extension/src/content.ts` 已有针对 ChatGPT turn 的 DOM 选择器与观察器，可作为发现，但当前 manifest 仅允许 ChatGPT Web 站点，主要功能是长会话可靠性；它不是正式审批渲染器。

仅在经过额外设计与权限批准后，允许作最小隔离验证：

1. 由确定性代码从一个公开安全版本读取实际已审用户说明，不把模型生成文本当身份；
2. 在隔离浏览器模拟 ChatGPT 消息页，把该文字原样显示在可区分的“正式受审说明”区域；
3. 人为调换用户说明版本、删掉独立审查证据或错配任务时，不出现“已批准”外观/执行复制按钮；
4. 原生聊天正文可以照常显示，但未核验的自由回复不得获得正式审批标记；
5. 证实没有接触 ChatGPT 授权对话或用户真实 Edge 账户；没有读取私有 GitHub 数据或存储密钥；
6. Mica 自身尚未满足其 P0 前提时不得借本任务强行扩项。

如果隔离环境成功，才由下一独立设计轮审：正式部署是否应新增权限、如何支持私有仓库、真实 Web 渲染是否稳定、何处提示该设备不支持、是否超出用户当前愿意采用的浏览器客户端范围。此处明确不将“Chromium extension 通常能读 DOM”误认为已验证 Mica 正式能力。若不能达到用户直接看见审定文本的要求，不能把无控制的 Web 消息称为强保证。

## 6. 跨轮如何让新机制持续运行

正式项目设置仍仅负责选择 Planner/Critic 并要求读最新 main 合同。单靠它不防遗漏。

新要求落实到已有角色合同：
- Planner §6/§7/§10/§11：负责用户说明的形成/每次重大返修更新/来源身份；下一角色 prompt 传当前准确 package；
- Critic §4/§6.1/§6.3：独立审读者说明与专业技术；明确自己批准的是哪版全文；不给“有摘要”就 PASS；
- 如果正式用户呈现/执行流程已经具备受控核对入口，则**实际正常路径消费**机器核对结果，而不是只在提示词声称执行；
- 用户每轮只发原任务/转发自动生成的 locator，不再重复写作者规范。

若后续角色自动忽略合同，没有受审文本，则受控显示/启动入口应检测缺失并停止声称批准，而不是继续显示一个官方 PASS。若目前不存在这样的正式入口，必须如实标注仅达到候选合同遵循层，不能自夸已经堵住所有失败。

## 7. 验证按失败机制分层，不能样本喂答案

- **技术选择被隐藏**：真实 Slurm、Bridge 通知/配置、科研方法/演示文稿技术方案；先让生成线程从普通任务与真实来源自行发现机制，独立评审再用审查标尺判，防止把要出现的答案提前贴在生成 prompt。
- **回复不合格**：三次 Critic 审查流水式 PASS、Phase C 非终态停止；检查完整自然中文解释、具体机制、风险、下一步，而非关键词/长度。
- **跨轮丢失**：至少一次真实 `REVISE → 方案技术变化 → 用户说明同步/未同步 → Critic 新版审查`；不给第二轮增加特殊语言提示。故意保留旧说明时，机械身份检查和 Critic 专业审查要准确拒绝。
- **假批准的机器版本**：旧 commit、缺审查原文、跨 task、随便修改说明后自报 PASS，正式版本核对必须拒绝。
- **真正受控呈现**：仅在 Mica 可行性已获额外授权后，隔离实际渲染原文，对更改版本造成的状态转变给真实截图/DOM 与文本字节证据，失败后不发布已批准标记。
- **正式默认入口**：正式 main 合入后、在提前选择的下一真实任务中不额外提醒，分别查看角色合同是否消费、受审说明是否持续更新、正式入口是否展示正确版本。无真实用户产物不能宣布整体完成。

## 8. 版本、授权、实质改动归属

当前仍为 v1.0 **设计阶段**；不实施角色合同或产品代码。原 v0.7/v0.8/v0.9 是历史候选、不是获得全量 PASS 的正式 1.8。

本轮允许改动的仅是当前设计分支的 Proposal、Plan、Goal、Kickoff、Critic prompt、设计 manifest 和稳定用户需求记录。**不修改**正式 main、Project setting、Capability Gate Policy、Clear Writing、Bridge、Slurm、Mica、Plugin Creator、生产运行时或分支保护规则。

若最终建议增加真正的“受控呈现”或“受控启动”，那属于产品/跨仓库职责扩展，需在最终执行就绪前分别独立核验成熟入口与权限，不能把是否新增服务/SDK/GitHub 权限留给 Codex。

不为了强制表现出质量而对所有普通问答、多数低风险单文件修改添加审核；仅针对正式高成本架构/插件/Bridge 批准出口。

用户不负责人工维护 GitHub Issue/Project；同 task key 保留，按最新 Maintenance Board 自行定位/延续记录。当前没有 verified Mica/Bridge 新能力，不得声称已部署。

## 9. 最重要的失效反证

若我们只把用户说明写在 Proposal，Critic 仍能在 ChatGPT Web 自由消息中输出无用审计文字，这**不是**该用户级目标已经解决。

若我们只写了核对脚本，而正式 ChatGPT/Codex 正常入口不消费，就也**不是**强制闭环。

若我们只在 Mica 合成页显示了原文，未证明真实安装/权限/当前线程可用，也**不是**正式 Web 已可靠交付。

如果上述反证还成立，宁可诚实给 `REVISE` 并明确尚需真实接口验证，也不能重新给一个“已经完全解决”的设计 PASS。
