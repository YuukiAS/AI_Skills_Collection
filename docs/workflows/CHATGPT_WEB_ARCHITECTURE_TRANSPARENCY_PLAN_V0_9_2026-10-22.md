v0.8 已设计“用户机制说明提前形成、Critic 独立核对、正式 PASS 使用同一受审说明”；这点保留。v0.9 必须闭合用户新指出的**持续运行条件**：

## 2. 角色合同的可实施精确改动

### 2.1 `PLANNER_ROLE_CONTRACT.md` §2/§6/§7/§10/§11

**§2：正常入口的持续消费**

首次进入、恢复工作、新的实质设计轮次实际读取最新正式角色合同；在同一任务继续下一审查/返修阶段时核对合同版本、当前任务包和上轮独立审查定位，未变的长源不机械重复全文读取。发现 main 合同已变，按最新正式规则工作，不从旧聊天沿用过期例外。若源不可达，不得冒充已加载。

**§6：形成用户可用于决定的机制说明**

在首次重要 Proposal 的前部直接写出决定相关的技术选择及准确名称、为何不用竞争替代、沿代表性任务的完整因果执行过程、在哪个真实层拦截或确认、失败/恢复/未验证边界、正常使用改变。说明与同一 Proposal 技术正文共享版本，不能靠另一个无归属的总结文件解决。

**§7：同时对照原始技术依据**

送 Critic 时把当前用户说明全文、真实来源和完整技术方案共同列为同版审查对象；不只给“方案附带了摘要”的字段。对缺证据的具体能力先补证据或标注 conditional，不能靠语言模式推断平台支持。

**§10/§10.1：每轮实质返修要更新说明并完成交接**

收到 `REVISE`、新的用户要求或执行事实后，明确哪些机制/职责/风险/正常入口发生实质改变；在当前完整新版 Proposal 中同步改用户说明，并解释旧决定退出原因及新决定带来的用户影响。若只是普通实现错且不改变受审机制，说明不应为形式主义重写，但须能指出无变化的理由。当前 Planner 能合法完成的修订继续做，不把归因工作交还用户；真正需要用户跨线程交接时给完整、已填身份的 `COPY TO CRITIC`。

**§11：单一来源与提示词范围**

Plan/Goal/Kickoff 指向同版 Proposal 的用户说明和准确提交，不能复制成互相漂移的两套架构。给 Critic/Codex 的短交接携带准确任务、阶段、来源、审查结果、执行边界，不要求用户额外粘贴长篇“说人话”说明。任务 prompt 若与正式角色合同冲突，不能默默采用任务 prompt。

### 2.2 `CRITIC_ROLE_CONTRACT.md` §2/§4/§6.1/§6.2/§6.3

**§2：每一新的正式 review 都绑定当前版本**

每轮从用户原要求和当前事实独立审，不照搬 Planner 说明。核对当前包相对上一 review 的技术改动与用户说明改动，尤其说明是否陈旧。老审查者已经看过旧版不能视为已审当前最新版。

**§4B/F/G：技术正确与可理解同时审**

要求具体选择能回指技术来源，至少沿一个代表性正常任务与关键失败任务检查因果关系。用“技术替换反证”：重要机制若换成另一种会改变用户决定的技术，而正文无需改变，说明隐藏关键选择，应提出独立 blocker。对照实际能力而非只看纸面组件：真实 actor、hook/matcher、MCP capability、权限、格式/物化、受控验证与恢复。避免把所有实现日志提升为用户正文。

**§6.1/§6.3：同版用户说明是最终执行就绪审查对象**

完整包审查除技术方案、Goal、Kickoff 外必须审用户说明**最终全文**及对应的真实机制。不能只检查有无摘要或关键词。最终 PASS 的用户正文应呈现已审说明的实质内容与 Critic 自己基于事实的独立判断，解释关键 `REVISE` 如何关闭，不得将其换成新的审计清单。若技术方案在审查时需要变更，回 Planner 形成完整新版本；纯语言润色必须保留重要技术选择、执行保证及限制。没有通过说明质量审查，就不形成有效完整的 execution-ready PASS。

**§6.2：继承合同而非每轮再教一遍**

`PROCEED/REVISE` 的下一用户入口必须由已有规则自动产生真实可复制的 `COPY TO PLANNER`；最终 PASS 是短 `COPY TO CODEX`。这些提示词只负责身份/事项，不复制长写作准则。不许以任务 prompt 对最终合同的缩窄作为豁免。若当前 Critic 不写文件，其完整回复就是审查交接原文，不伪造“review commit已保存”。

## 4. 当前审查和以后所有审查如何衔接

**本次 v0.9 设计审查**：当前 Planner 直接交付 Proposal §1 的完整机制说明，并指出 §3 与本 Plan §2 的实际职责来源。Critic 的一次阅读不等于生效；其回复须自己讲清默认来源链、跨轮更新和边界，而不是只复述本段。

**若此次 Critic REVISE**：Planner 按 finding 修改完整 Proposal、Plan、Goal、Kickoff 和必要用户说明，放同一个新的 exact package commit，交接只带新 locator；Critic 重新从当前版本独立审。用户无须再次提醒解释 Hook 等关键技术。

**若 PROCEED**：Planner 补齐 final execution-ready package；最终 Critic 重新审完整当前用户承诺、技术和说明以及真实执行接口。只有唯一 PASS 及用户授权才能实施。无证据不得把“可继续设计”当“可执行”。

**若实现中普通错误**：同一 Codex 修；若改变用户承诺/安全/权限/主要架构/恢复语义，原批准不覆盖，回 Planner 更新说明并复审。状态和下一入口必须直接向用户讲清。

**若新的插件任务**：经当前 Project setting 的正式角色入口自行读取最新 main 合同，开始自己的领域 Proposal；不携带 Slurm 的特例，必须披露该领域真正影响技术取舍的具体机制。

## 5. 验证：把“跨轮不用重复提醒”作为被测能力

既有 v0.7/v0.8 用例全部沿用其已知样本和冻结来源，不机械增加 Gate 或固定数量。调整现有真实验证合同：

### 5.1 候选阶段跨轮验证（完整对话，不是单次回答）

启动时为了试验尚未合入 main 的 1.8，**一次性**告知线程 exact 候选角色合同与真实任务；之后的 `REVISE` 往返只传任务版本、审查结论和普通请求，**不再附“必须说人话、必须说明机制名称”等评分答案**。

用同一真实复杂方案完整观察：
- 初轮 Planner 是否主动写机制说明（若设计含重大 Hook/Wrapper/MCP、科研算法或模板选择，应真实出现适用的精确技术）；
- Critic 是否核实机制、真实执行入口、替代方案和说明；
- 一轮真实 `REVISE` 后，Planner 是否同步修订技术和用户说明，并从事实解释改变；
- 下一轮 Critic 是否发现说明与更新技术不符并拒绝，或有直接证据地认可一致性；
- 若事实最终支持唯一 PASS，Critic 是否在用户正文里交付同版说明并给短 Codex 入口；若仍有 blocker，诚实保持 REVISE。

保存**每一轮完整普通输入、完整输出、真实读取轨迹、候选身份、版本与独立判断**。只看末轮或只检查字段不算连续性。不得让生成线程看到评分答案；若已看过标记为已知回归，不能声称盲审。没有得到合法正控不允许无限换样本或强迫 PASS。

### 5.2 正式 main 后自然任务验证

真实合入并 fresh readback main 的 1.8 后，才进行一个已预先冻结、真实存在的新插件/Bridge 设计或审查任务；普通用户请求不再告知角色规则或机制解释清单。验证新线程是否自行调用最新角色合同并持续提供有价值的机制说明和交接。若真实任务尚无，保留此项未验证；不能制造付费/生产副作用或拿候选试验替代。

注意此正常测试并非要求随机普通聊天调用 Planner/Critic；仅覆盖项目设置本来规定要进入正式设计/审查的任务。

### 5.3 用户读者质量验收

原始实际技术方案及全部用户可见文本都必须真实可读。独立 Critic 判断解释是否足以让用户**明确知道技术选择、能比较并有理由拒绝某方案**，而非只知道“模块负责什么”。对于失败案例，要判断是否有用确切技术身份、因果实例和失败边界，并主动丢弃无决策价值的审计流水。

机械检查只核身份、路径、文本是否同版以及机器字段；不靠关键词/字数保证用户质量。真实正反例（Slurm、Bridge、Clear Writing Phase C、复杂技术说明）用于不同风险的有界验证，不追加无限样本。只有目前评价范围内的结论，不宣称永不出错。

## 6. 治理候选及 main 集成

保留既有候选同一身份方案，但避免自引用哈希：完成角色合同/真实验证合同后提交 `GOVERNANCE_CANDIDATE_COMMIT`，后继 evidence 另行引用它及精确文件 blob；candidate-defining source若变化旧验证失效。

本地确定性验证 → 已有实现后 Critic（`PROCEED_TO_FINAL_EVALUATION / REVISE`）→ 冻结的 Web 实测 → 候选接受 → 现有仓库规则下的集成前检查/普通 non-force merge/push main → 远端回读两份正式 1.8 合同。

用户打开 fresh Web 对话/选择角色若仍需要手动操作，应由 Planner 预备准确 prompt 与回传位置；用户只操作必要 UI，不负责找文件和选择内部 reviewer。无验证的自动 UI 能力不能假称存在。正式启动实施须按当时实际仓库/Bridge 规则确认执行定位；不能沿用新正式工作树建在 `/tmp` 的过时草案。

main 合入不自动代表多轮默认能力已验证；最终说明严格区分源安装、当前候选实际演示和后续正常任务结果。
