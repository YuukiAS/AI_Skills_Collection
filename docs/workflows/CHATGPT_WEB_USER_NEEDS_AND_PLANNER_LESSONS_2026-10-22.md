# 用户真正需要什么，以及本轮 Planner 必须纠正什么

日期：2026-10-22。
任务：`chatgpt-web--pass-integrity`。
性质：用户要求与 Planner 复盘记录，供同一治理任务及未来插件、Bridge 方案审查引用；不是已经生效的 1.8 合同，不是新的全局用户设置。
来源：当前用户连续纠正与当前仓库事实。用户要求高于下文 Planner 对实现办法的建议；Critic 可以反对建议，不能把用户要求当作 Planner 自行添加的偏好。

## 1. 稳定的用户要求

用户要保留对架构的理解权和否决权。以后设计任何插件或 Bridge Kit，都应在投入实现以前看到：到底选择了什么机制、为什么选择它、一个真实任务怎样经过它、哪里实现关键保证、失败怎么办、还有哪些未验证前提。不能只给批准结论和一段执行提示词，让用户机械复制后才从事故中发现架构不合意。

“说人话”不是去技术化、少写几个英文或一律写短。Hook、MCP、Wrapper 以及 `PreToolUse` 这类名称，若会影响安全边界、使用方式、维护成本或方案选择，就必须准确披露，并解释它在这里做什么。不得把它们统称为“安全机制”后省略真正的实现选择。

用户不需要消化调查过程中产生的全部资料。归档媒体类型、临时路径、提交哈希、测试编号、状态矩阵等，除非直接改变当前判断或用户明确追问，否则留在仓库证据和可复制交接里。技术说明必须选择对判断有用的信息，而不是把审计报告缩短后当作解释。

机制要通过真实例子讲清楚。例子要揭示决策链和执行边界，不能只讲“模块甲负责安全、模块乙负责确认”。例如取消作业时：具体在哪个工具调用前拦截、从哪里查询真实分区、确认出现在哪个聊天、没确认为什么不能执行、检查故障时怎样阻断。Slurm 是证据与示例，不是所有未来任务的固定回答模板。

需要科研、数学或工程深度时，应保留充分的对象定义、因果关系、公式、实例与限制。不能为了减少阅读负担删掉理解方案所需的内容；也不能用“用户不关心细节”擅自隐藏可能导致用户否决方案的决定。

技术执行资料与用户正文分层。用户可以机械复制完整交接提示词，不需要先读懂其中的路径、提交、协议字段。正文则必须能独立帮助用户判断方案是否值得推进。

任务中断时要说清实际状态、问题归属、下一责任方和用户需要的最小动作。当前 Planner 仍能合法处理的工作应继续处理。不能以“需要某种执行环境”结束，也不能让用户自行找人、查仓库或拼接下一条提示词。

这不是要求用户每轮额外签署一张确认表。重要选择应在原有提案、独立审查和授权时机透明呈现；同范围已批准决定不得重复索权。

## 2. Planner 之前判断错在哪里

**错误一：把必要技术名称当作阅读噪声。** 此前“你不需要知道采用 Hook、MCP、Wrapper”的说法错误。用户需要知道这些选择，正是为了能在错误实现之前反对。应按决策价值筛选，而非按是否英文、是否专业来删除。

**错误二：没有读取和应用现行规则，就不断补写规则。** 正式 Planner 1.7 的正常使用六问、执行中断后唯一下一入口，以及 Critic 1.7 的第 6.3 节已经要求真实机制与用户说明。不能把每次违规都归因成中央规则缺失。

**错误三：把更严的验收口号当成改进生成方式。** v0.7 规定整篇回复验收，但没有把待展示的机制说明变成现有独立审查实际取得的对象。技术审查完才临场写摘要，依然可能漏掉关键选择。

**错误四：过早承诺新的强制发布系统。** 前文提出“受控交付入口”和“Codex 不接受未经审查的批准”，但没有证明当前普通 Web 与 Codex 入口已有这些技术阻断能力。应区分拟议合同检查与真实程序强制，不把拟建网关当成已经可用，也不因模型一次不遵循就自动扩大到 Bridge/Mica/API 工程。

**错误五：给审计线程喂归因答案，再把认同当作独立发现。** 用于判断默认行为的运行输入不能附上“请发现这三个问题”“请使用这几个文件里的具体结论”。必要任务定位和候选规则身份可以给，判分答案留给评审；访问过答案的结果不能称盲审。

**错误六：以修复可读性为由重新打开产品架构。** 用户问已批准机制如何工作，应先按原包解释；只有真实矛盾或用户新增范围才重新设计。改变 wording 不应变成新增 MCP、网关或操作系统隔离的借口。

## 4. 本轮成功标准

用户不读机器交接，也能指出本提案选择了什么机制、为什么、怎样生效和哪里仍受限制；还可以在实现前明确反对关键选择。下一位独立 Critic 必须直接审查本轮真实说明和它对应的方案，而不是等未来测试时才开始遵守。

本记录不宣称用户已经认可 v0.8，不宣称 Critic 已通过，不宣称模型遵循性得到技术保证。

## 4. 2026-10-22 跨轮连续性补充：不能要求用户每轮重申

用户明确指出：本轮交给 Critic 的额外详细提示词即使有效，也不能证明以后每次返修都能自行遵守。治理任务的真实目标是：一旦正式 1.8 合同生效，后续每次进入该项目的 Planner/Critic 设计、返修、审查、最终批准及停顿恢复时，仅凭普通用户任务和任务定位，自行读取最新正式合同、当前方案和受审用户说明；不要求用户重复说明“说人话、保留关键 Hook/Wrapper 名称、提供因果例子、不要倒审计流水、正确交接”。

该要求带来明确分层：
- ChatGPT Project setting 负责初始化与角色合同最新 main 路由。它已经具备此要求，不重写 Project setting。
- 正式 Planner/Critic Role Contract 1.8 才是所有后续轮次的长期通用规则，不能让任务专属提示词成为唯一规则来源。
- 原 Proposal 的前部机制说明是本任务当前版本的受审交付对象；实质设计返修时应更新这一部分，并与技术方案保持同版。不允许留着旧说明，另靠 Critic 在最终 PASS 时口头补充。
- 各角色的下一条交接提示词只传递真实任务/阶段/来源/版本，不手工重复一长串用户写作要求；接收线程应自行消费正式角色合同。
- 本治理候选正式合入 main 之前，普通项目仍加载 1.7；候选试用必须在首轮明确绑定准确候选 1.8 文本，不得假称 v0.9 草案已默认生效。
- 只检验一轮好回答不能证明连续性。至少要在同一真实复杂设计中经历返修→更新说明→独立复核→下一交接，并观察后续只提供普通任务定位的轮次是否自己仍然执行合同。再以一项提前冻结的正式 main 后正常任务核实跨新线程触发。
- 即使通过这些验证，原生 ChatGPT Web 输出仍非程序级不可绕过，不能声称所有未来消息都会自动经过强制质量拦截。不能拿此边界当借口不建设上述真实默认机制。

这一补充与此前所有稳定要求同等重要。Slurm 是验证架构透明度的证据，不得变成针对 Slurm 的专用模板。需要对所有插件、Skill、Bridge Kit 设计与审查采用同一责任分工。


## 5. 2026-10-22 进一步纠正：旧的入口链已存在，不能当作新修复

用户指出：“现在在用的架构不就是这样？我凭什么相信你就能解决多轮后开始不说人话不给我讲的问题？你新增了什么？”

事实：正式 1.7 已由当前 Project setting 要求读两份 Role Contracts，并要求解释具体机制、独立审查、完整交接。过去仍出现过 Critic 长篇内部状态、未说明技术取舍、后续修订只改交接长度却自报 PASS、Phase C 中断无人给实际下一入口。v0.9 只新增“说明前置、版本同步与多轮验证”，确实改善文档审查对象，但没有提供脱离模型自述的**正式交付身份核对**或**直接显示已受审全文的可控表面**。不能再次拿“合同生效了，就会自动执行”作为已证实保证。

因而真正需要回答三层不同的事实：
1. 技术解释是否由独立专业 Critic 对照真实方案和用户要求审过——模型专业判断，仍可能出错；
2. 读者说明、实际技术包、独立审查和执行交接是否由**正常路径上真正运行的机器核对**证明同版，错版不得作为正式批准继续；
3. 用户实际看到的是否是上述受审原文，而不是最后由模型重新生成的无用摘要；如果原生 ChatGPT Web 无法受控呈现，就不能谎称这层强制已经存在。

经实际读取：GitHub 可提供版本化源、AI Skills 有现成 Python 工具链，Mica 当前有 DOM 内容脚本但尚无正式受控批准展示能力，Bridge Reviewed Handoff 有运行协议但不是 ChatGPT Web 的消息渲染器。任何新增脚本如果不被正式用户入口消费，或 Mica 仅运行本地合成测试却没有真实显示核验，都不得称已解决。Mica 目前的 P0、认证与权限未核实可支持本任务修改；本轮只能提交跨仓库候选设计与受控可行性要求，不能偷偷实施。真正允许的实施范围须后续按独立审查和用户授权决定。

用户不需要另一份工程长日志，也不应被告知“做不到”。需要的是具有现实入口、能定位责任、能真实拒绝错误批准且不会在每次交接退化的方案；能力未验证时先做最小合法实验，再决定具体实现，而不是装作已经保证。


## 6. 最终纠偏：不使用 Mica，优先补原角色之间的交付接收

用户再次明确：不要任何 Mica 扩项，不要凭一次聊天问题升级大版本或另造平台；要把所有长期需求列明，让用户在**每轮**了解当前进度和 `PASS/REVISE/PROCEED` 的真实技术理由，多轮返修后不退化成垃圾报告。此前提出 v1.0 是错误范围扩大，不应当成为正式方案。

对 1.7 的直接核查表明：已有项目设置/两角色合同/交接 prompt、自然中文、真实技术与一屏 summary。用户正确指出过去几轮“新设计”不过换方式重复旧规定；**新增规定不足以当作新增效果**。

当前 v0.10 选择的有边界的新增实际动作：

- 将原 Proposal 前部的用户方案解释从“摘要”改为专业 Critic 真正会核对的同版本读者决策说明；
- 同一任务每次实质技术变动须同步更正该说明，下一 Critic 独立核对说明是否仍对应真实机制；
- 通过本来就存在的 `PROCEED/REVISE → Planner` 交接，明确由接收 Planner 核对 Critic 完整回复：技术依据明确但表述失焦的，Planner 忠实补正读者说明；独立技术依据不足的，退回补审，不把坏报告直接推进；
- 提议唯一最终 `PASS` 不再直通 Codex，而由独立 Critic 作唯一技术裁定之后多一次原 Planner 接收/用户交付，再给短 Codex 入口。这是实质改变旧合同，需要独立设计审查评估额外机械转发成本，不能自定为已批准；
- 保留现有关键接口证据、实际用户 Gate、真实身份/合入验证、最小用户动作，不新增第三审核者、Mica、付费模型或常驻系统。

这些也不是原生 ChatGPT 网页发送前 Hook 的百分百强制保证。是否真正减少用户追问和误批准，必须由没有反复提醒的新正常任务及真实连续返修验证；只凭文档增加或本轮角色口头表示学会了不能认定完成。
