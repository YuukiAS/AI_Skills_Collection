# 用户真正需要什么，以及本轮 Planner 必须纠正什么

日期：2026-10-22。
任务：`chatgpt-web--pass-integrity`。
性质：用户要求与 Planner 复盘记录，供同一治理任务及未来插件、Bridge 方案审查引用；不是已经生效的 1.8 合同，不是新的全局用户设置。
来源：当前用户连续纠正与当前仓库事实。用户要求高于下文 Planner 对实现办法的建议；Critic 可以反对建议，不能把用户要求当作 Planner 自行添加的偏好。

## 1. 稳定的用户要求

用户要保留对架构的理解权和否决权。以后设计任何插件或 Bridge Kit，都应在投入实现以前看到：到底选择了什么机制、为什么选择它、一个真实任务怎样经过它、哪里实现关键保证、失败怎么办、还有哪些未验证前提。不能只给批准结论和一段执行提示词，让用户机械复制后才从事故中发现架构不合意。

“说人话”不是去技术化、少写几个英文或一律写短。Hook、MCP、Wrapper 以及 `PreToolUse` 这类名称，若会影响安全边界、使用方式、维护成本或方案选择，就必须准确披露，并解释它在这里做什么。不得把它们统称为“安全机制”后省略真正的实现选择。

用户不需要消化调查过程中产生的全部资料。归档媒体类型、临时路径、提交哈希、测试编号、状态矩阵等，除非直接改变当前判断或用户明确追问，否则留在仓库证据和可复制交接里。技术说明必须选择对判断有用的信息，而不是把审计报告缩短后当作解释。

机制要通过真实例子讲清楚。例子要揭示决策链和执行边界，不能只讲“模块甲负责安全、模块乙负责确认”。例如取消作业时：具体在哪个工具调用前拦截、从哪里查询真实分区、确认出现在哪个聊天、没确认为什么不能执行、检查故障时怎样阻断。Slurm 是证据与示例，不是所有未来任务的固定回答模板。

需要科研、数学或工程深度时，应保留充分的对象定义、因果关系、公式、实例与限制。不能为了减少阅读负担删掉理解方案所需的内容；也不能用“用户不关心细节”擅自隐藏可能导致用户否决方案的决定。

技术执行资料与用户正文分层。用户可以机械复制完整交接提示词，不需要先读懂其中的路径、提交、协议字段。正文则必须能独立帮助用户判断方案是否值得推进。

任务中断时要说清实际状态、问题归属、下一责任方和用户需要的最小动作。当前 Planner 仍能合法处理的工作应继续处理。不能以“需要某种执行环境”结束，也不能让用户自行找人、查仓库或拼接下一条提示词。

这不是要求用户每轮额外签署一张确认表。重要选择应在原有提案、独立审查和授权时机透明呈现；同范围已批准决定不得重复索权。

## 2. Planner 之前判断错在哪里

**错误一：把必要技术名称当作阅读噪声。** 此前“你不需要知道采用 Hook、MCP、Wrapper”的说法错误。用户需要知道这些选择，正是为了能在错误实现之前反对。应按决策价值筛选，而非按是否英文、是否专业来删除。

**错误二：没有读取和应用现行规则，就不断补写规则。** 正式 Planner 1.7 的正常使用六问、执行中断后唯一下一入口，以及 Critic 1.7 的第 6.3 节已经要求真实机制与用户说明。不能把每次违规都归因成中央规则缺失。

**错误三：把更严的验收口号当成改进生成方式。** v0.7 规定整篇回复验收，但没有把待展示的机制说明变成现有独立审查实际取得的对象。技术审查完才临场写摘要，依然可能漏掉关键选择。

**错误四：过早承诺新的强制发布系统。** 前文提出“受控交付入口”和“Codex 不接受未经审查的批准”，但没有证明当前普通 Web 与 Codex 入口已有这些技术阻断能力。应区分拟议合同检查与真实程序强制，不把拟建网关当成已经可用，也不因模型一次不遵循就自动扩大到 Bridge/Mica/API 工程。

**错误五：给审计线程喂归因答案，再把认同当作独立发现。** 用于判断默认行为的运行输入不能附上“请发现这三个问题”“请使用这几个文件里的具体结论”。必要任务定位和候选规则身份可以给，判分答案留给评审；访问过答案的结果不能称盲审。

**错误六：以修复可读性为由重新打开产品架构。** 用户问已批准机制如何工作，应先按原包解释；只有真实矛盾或用户新增范围才重新设计。改变 wording 不应变成新增 MCP、网关或操作系统隔离的借口。
