## 1. 给用户看的完整机制说明（本轮实际交付对象）

**这一版不靠每次给 Critic 一条特别详细的“说人话”提示词。** 它规定一条长期默认工作链：项目设置在相关任务开始时指向最新正式角色合同；Planner/Critic 根据角色合同自行读取并开展工作；每轮实质设计与返修都更新同一个方案中的用户架构说明；Critic 独立核对说明与技术依据；最终批准直接交付已核对的说明和完整机器交接，而不是重新写一份审计摘要。

具体来说，你以后只提出“设计某插件的下一版”或“继续这个方案的返修”。项目设置中已有的角色入口要求读取仓库 `main` 的 `PLANNER_ROLE_CONTRACT.md` 和 `CRITIC_ROLE_CONTRACT.md`。当这次拟议的 1.8 **真正实施并合入正式 main 后**，这两个文件会成为默认执行规则：Planner 每次准备重要提案，先告诉你选择了什么真实技术、为什么选它、一个实际任务如何经过这些机制、关键危险动作在哪里被拦、失败怎样恢复；不能只列功能名称或测试编号。Critic 每次审查，要反查真实源码/方案与这段说明，确认技术选择没有被抽象词隐藏、保证没有被夸大、用户能据此接受或否定架构。

例如 Slurm 取消保护：若方案使用 `PreToolUse`，正文必须说清它是 Codex 对 `Bash` 工具执行前的拦截点，怎样使用 `scontrol show job -o` 查实际分区，怎样阻止原 `scancel`，为何由并列的 MCP 处理器在当前根聊天展示确认卡；必须说明 `PermissionRequest` 为何还要再挡一次、是否采用 `PostToolUse`、Hook 启动失败会怎样、正常入口覆盖到哪，为什么不采用可被直接命令绕开的 Wrapper。这些精确技术名称是决定信息，不能因英文或专业而省略。大量文件哈希、完整测试日志仍留仓库。如果是一项统计模型或演示文稿，透明的则是实际模型、方法假设、模板、渲染/编辑架构，而不是机械套用 Slurm 章节。

**返修也自动沿用这套要求。** 假设第一轮选择 Hook，Critic 因实际平台限制判 `REVISE`；Planner 将方案改成另一种确有根据的执行结构，那么必须同时把同一份用户架构说明改为新事实，并解释旧机制哪里不行、新机制怎样工作、你的使用和风险有什么变化。不能只修改内部 Plan，保留第一轮写得漂亮但已经过期的说明。下一条给 Critic 的提示词只须包含任务和新的确切版本；Critic 依正式角色合同自行核对新说明、技术变更和原阻塞关闭情况。再次 `REVISE` 仍按同样关系进行，无需你重新教它怎样回答。

批准以后，Critic 在用户正文里展示真正审查过的机制说明，并提供自己独立形成的判断、原关键问题如何关闭、剩余风险与用户下一步。最后另给准确批准定位和短 Codex 提示词，供你机械复制。**真正关键的是被批准的技术方案与提供给你阅读的说明同版、同审查对象，不能把审查结果临场换成内部日志。**

这不是一条可以在普通 ChatGPT Web 强制拦截任何消息的程序 Hook；它是通过已存在的项目入口、版本化角色合同、实际待审文稿和独立 Critic 构成的持续工作机制。规则是否真的生效，必须在真实多轮返修中验证，正式合入 main 后还要用一个没有再次提醒“讲清楚”的新任务验证。若模型仍不执行，就不能宣称 1.8 的正常使用能力可靠，更不能用单次好看的回答自证完成。

## 2. 问题归因：v0.8 漏掉的不是更多“写作禁令”

正式 1.7 已有机制解释、正常用户路径、唯一下一入口和自然中文要求。这些写在合同里仍发生了 Slurm 架构选择被抽象、Clear Writing Phase C 回复断在 blocker、Critic 三次复述审计计划的事故。真实缺口包括：

1. 重要技术选择通常只存在于庞大技术方案，读者说明在最终结论时临场生成；没有将其作为提前准备和审查的对象。
2. v0.8 修复了“审什么”，但没有写清每次 `REVISE` 后谁刷新说明、Critic 怎样对照已改变的技术方案、下一线程怎样在不被喂详细规则时继续工作。
3. 项目设置路由的是 `main` 的正式角色合同；候选分支有再好的要求，在合入前也不会自动成为新线程的正式合同。
4. 机械字段、角色自查或 Clear Writing 调用记录不能证明整个说明有实际决策价值。单独给某次 Critic 的定制提示词只证明该轮可能照做。

v0.9 不新增同义语言禁令，而是明确默认触发、同版说明更新、跨轮接续、独立验证与正式生效的身份。

## 3. 长期正常入口：各层到底干什么

### 3.1 项目设置 = 入口，不改现有项目设置

当前生效项目设置 §1–3 已要求识别设计任务、在第一次进入/恢复/新实质轮次读取 `AI_Skills_Collection` 最新 main 的两份合同，并让 Planner/Critic 依其职责工作。§0、§18 约束中文读者说明。**现有项目设置足以提供入口，不再加一层提醒。**

生效前：main 还是 1.7；候选试验必须显式绑定准确的候选 1.8 合同，不能冒称普通入口已启用。
生效后：新线程仅从用户任务与当前项目默认设置自行进入 main 的 1.8；用户不必附特殊提示词。老线程处理新的实质阶段时应重新核实 main 是否变化；同一未变合同不机械反复全文读取。

适用范围：AI Research Stack Project 中的 Planner/Critic 设计与审查、返修、相关执行中断与恢复；不是无条件控制 ChatGPT 全平台、别的 Project、Codex 所有随意回复。

### 3.2 正式角色合同 = 每轮要实际履行的工作

拟实施在 `PLANNER_ROLE_CONTRACT.md` 的 §6/§7/§10/§11：
- 形成同一提案的读者机制说明，明确选择、替代、一个真实请求、失败和证据边界；
- 每次实质返修改变机制/行为/保证/关键执行入口时，**同一版更新该说明**，说明原阻塞的解决和新增差异；若技术修订不改变用户说明，须有真实理由；
- 当前技术 Plan、Goal、Kickoff 都引用这一版 Proposal 的说明，不复制第二个可能漂移的说明；
- 送 Critic 的对象必须包含最终用户将看到的说明全文及直接技术证据；
- 当前 Planner 能继续的事继续完成；必须用户交接时准备完整提示词。

拟实施在 `CRITIC_ROLE_CONTRACT.md` 的 §4B/F/G、§6.1/§6.2/§6.3：
- 先从用户目标和事实独立审，再查机制说明；不能把 Planner 解释当作客观事实；
- 对重要技术进行“替换反证”：把实际 Wrapper 换成 Hook、共享配置换成每仓配置或付费外部服务，若正文仍成立而决定实质改变，说明隐藏了重要信息，应 `REVISE`；
- 每次返修核对 **技术方案改变 → 用户说明改变/不变理由 → 旧阻塞关闭证据**；缺项不得给最终 `PASS`；
- `PROCEED/REVISE/PASS` 的正文都要基于当前受审说明和自己查到的事实讲清用户当前要判断的事项；最终 PASS 必须交付受审说明，不靠链接或临场审计摘要；
- 机器交接与人话正文分离，短提示词不得重定义用户阅读规范。

### 3.3 GitHub 中的当前版本 = 跨线程连续性锚点

同一个 task key 与既有设计分支保留。每版 Proposal 开头（不新增独立 registry）存放**当前受审的用户架构说明**。该版 Plan/Goal/Kickoff 指向同一准确提交与相关章节；Critic 记录所读对象与自己核实的结论。下一轮接手者从最新任务版本与上一审查结果定位，不依赖长聊天记忆。

每轮实质返修产出完整新 Proposal，而不是旧文档末尾追加不相容的变更段落。候选身份必须绑定真正的文本；不能拿“旧说明已审过”支持新技术方案。

### 3.4 交接提示词 = 任务定位，不是规则来源

同一任务的 `COPY TO CRITIC / PLANNER / CODEX` 只须准确标识任务、阶段、分支、执行包与上轮审查位置、明确授权或停止事项；不用每轮手工贴“说人话、必须举例、必须叫出 Hook 名”等长清单。

接收方按项目默认设置与角色合同自行读取通用规则，再读当前任务资料。如果任务专用提示词企图覆盖、缩小或绕过中央合同，Critic 应当拒绝这种冲突。交接内容不能以路径取代你看得懂的正文。

## 4. 原有 1.8 已设计机制必须保留

- 任务专用提示词与中央合同兼容性；
- 唯一最终 execution-ready `PASS + READY_FOR_CODEX=YES`，同回复附批准定位与短 `COPY TO CODEX`；
- PASS 后解释、矛盾证据与新增需求的处理区别；
- 影响实施/安全恢复的关键接口真实证据、可验证与条件性假设的区别、风险匹配的受控小探针与失败停止；
- 非终态回复实际完成唯一下一责任方与可用 handoff，不能只说“找一个环境”；
- 同一正式候选、实现后 Critic 安全门、真实 Web 验证、合入 main 与远端回读；
- 正常使用中的实际用户质量高于 CI/字段回执，不新设顶层通用 Gate；
- 原有两个独立人工线程，不新增另一个人工审查者、数据库、后台服务、发布网关、模型 API 或控制状态机；
- Project setting、Capability Gate Policy、Clear Writing、Bridge Kit、Slurm、Mica、Plugin Creator 等产品均不在本轮修改范围。

## 5. 实质性的验证办法，而不是再给测试线程答案

保留 v0.8 里历史已知负例与复杂任务的证据，但修订测试时必须对**连续性**给出可观察结果：

**候选阶段：同一任务连续返修。** 在新线程第一次加载候选 1.8 的准确合同和真实任务定位，此后只按正常工作传递审查决定、文件位置与更新版本。至少观察一次 `Critic REVISE → Planner 修改技术方案并同步更新读者说明 → Critic 审更新版`，若进入最终 PASS，再检查交付准确受审说明与短执行入口。第二轮不再补发“要讲清架构”的特殊要求。每轮保存完整输入、完整用户可见输出、真实读取/工具证据和对应版本。若未修改说明却改了重要机制，或仅复述测试名，判候选失败。若任务事实并不允许 PASS，诚实保留 REVISE，不为验收强迫通过。

**正式 main 后：新任务默认入口。** 提前冻结一个真实、非人为给出解释答案的插件/Bridge 设计或审查任务。用户只发普通任务，不在该轮再次要求读规则、点名技术机制。新 Planner/Critic 应自己读取最新 main 的 1.8；形成说明、更新返修、独立核对与正确交接。无合适新真实任务则该项未验证，不能拿候选试验替代。

**独立定性判断。** 阅读真实整篇用户输出，判断关键技术选择是否有精确身份、因果实例、取舍、可信证据与必要限制；是否把普通内部流水倾倒给用户；是否能据此同意或反对方案。判定来自当前任务和原始事实，不是字符串计数。核对方必须能获得完整原文。生成线程不接收评分答案，不能把已知失败向它喂成“自发发现”。

候选通过只证明受测条件表现，不能宣称概率为零或原生网页存在发送前强制检查。

## 6. 候选和正式生效的界线

- 本 v0.9 只是设计包。当前 main 仍是 1.7，没有自动默认 1.8。
- 设计审查只能 `PROCEED / REVISE`；最终执行包另经 execution-ready Critic 审查、用户授权后才由 Codex 改正式合同。
- 1.8 源码候选冻结后，验证材料必须绑定该候选；实现后既有 Critic 做最终评估前安全审查；需要 fresh ChatGPT Web 时预先准备最小用户界面交接，不伪造可自动创建新对话。
- 验证与集成满足既有条件后才合入并从远端回读 main 的两份正式角色合同；从此才有理由期待新线程经项目设置自动使用 1.8。
- main 集成仍不等于“已经证明每轮都遵守”。还须靠第 5 节的连续返修与正式入口样本，才接受默认行为成熟度。
- 原生 ChatGPT Web 当前没有本项目受控的发送前语义拦截器；无法通过文档给出技术级永不违规的保证。若将来真实默认入口仍反复忽略，按原失败归因排查 Project→角色合同消费→交接→生成内容→评审，不继续堆同义规则。

## 7. 备选与为何选择这条路线

- **继续往每次交接提示词里塞很多“说人话”要求：**只能改善单轮，且用户必须重复提醒；拒绝。
- **继续只修改角色合同文字而不改变交付对象：**1.7 真实失败已反证；拒绝。
- **新增强制浏览器网关、第三模型或常驻审查器：**如果要求真正技术强制，未来可以另案研究，但当前不存在可信的正常 Web 入口与必要授权；在本轮为解决跨轮职责问题先造新系统，会增加成本和新的失败面；暂不采用。
- **当前推荐：项目设置已有入口 + 正式 1.8 Role Contract + 同版说明/仓库锚点 + 独立 Critic 审查 + 多轮真实验证。** 它复用成熟机制，不增加日常人工角色或用户重复要求；不夸大强制能力。

## 8. 本轮就如何自证

本文件 §1 就是 Planner 给用户看的当前方案说明，§3 是它具体将怎样实现，§5 是怎样证明跨轮有效；与执行计划 v0.9 同版。下一位 Critic 必须在不照抄我结论的情况下核对这三处是否一致，并在自己的用户回答中解释这条长期来源链、返修如何刷新内容、为什么当前尚未默认生效；若有真实缺口，直接 `REVISE`，不要仅表示同意“以后应该自动”。

只修改原设计分支，本轮不修改正式角色合同、main、项目设置、Bridge 或任何插件产品，不启动付费验证。用户需求已记录于 `CHATGPT_WEB_USER_NEEDS_AND_PLANNER_LESSONS_2026-10-22.md`。
