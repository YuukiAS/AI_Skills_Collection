## 一、稳定用户需求：本次全部明确覆盖

以下是当前用户在多轮消息中直接提出或反复纠正的需求，不应因某轮 Critic 只审局部问题而消失：

1. **不做机械传话者。** 用户在正常 Planner 与 Critic 回复中直接理解架构和进度，机械复制交接提示词即可，不自行查仓库、拼证据或决定内部角色。
2. **每一轮可定位进度。** 当前是设计、返修、最终执行前审查、实现、验收还是发布；哪些已确定、哪些还没确定、上一轮改变了什么、用户现在需不需要动作，都要直接说清。
3. **明确每种结论的含义和理由。** `PROCEED` 是哪部分设计足以继续、离执行仍差什么；`REVISE` 是哪个真实问题会让用户目标失败、保留什么、怎样最小修；`PASS` 是批准哪套具体机制、什么证据足够、历史阻塞如何关闭、为何现在允许交付执行，而不是三个英文状态标签。
4. **关键技术选择必须公开。** 例如使用 Wrapper、Hook、MCP、`PreToolUse` 或某个统计模型、渲染引擎、模板：具体名称和选择理由如果会改变用户判断，不能被“安全层”“自动化组件”掩盖。
5. **讲具体因果流程。** 用与当前任务相符的真实例子说明输入如何触发决策、调用哪个真正入口、执行/阻断在哪里发生、为什么这个机制能实现承诺；不能只描述模块职责。
6. **比较替代并敢于否决。** 用户应在实现前有足够信息反对过重 Wrapper、多余服务、错误模型或低配替代；不得把历史投入当保留理由。
7. **证据和结论真实。** 设计/实现/正常入口/发布分开；哪里亲自验证、哪里只是条件性前提、哪里仍然未知都清楚，不能用测试、配置、资料数量或 `PASS` 字段夸大能力。
8. **自然、连贯的专业中文。** 保留必要的技术名、公式和示例深度；删除无决策价值的路径、归档格式、哈希、状态流水和普通英文，不把“说人话”误解成删技术或一律缩短。
9. **机器和人类材料分层。** 完整 Proposal/Plan/Goal/Kickoff、审查清单和执行身份留仓库；用户阅读的是被消化过的机制、风险、进度和决定；精确机器交接单独直接可复制。
10. **多轮返修不退化。** 同一任务经历 `REVISE → Planner修订 → Critic复核` 多轮后，仍保留最初用户承诺和已经成立的决定，明确本轮增量及当前完整架构；不重新退化成只报告最新 finding。
11. **用户无需反复重申要求。** 正常 Project setting → 最新正式 Role Contracts → 准确任务方案/审查记录 → 下一接收角色；任务专属提示词只传身份和阶段，不充当唯一的“讲清楚”指令。
12. **Critic 真正独立。** 审查真实来源和正常路径，不照抄 Planner，不靠旧 PASS 或自己宣布“写得清楚”替代证据；对原版/新版做明确的独立判断。
13. **每轮结论必须能继续任务。** 若中断，用户知道为什么停、谁解决、哪个动作确实需要自己完成；非终态不以“找一个有工具的环境”结束；不反复让用户授权同一范围。
14. **失败能被下一责任方拒收。** 不能 Critic 交一篇垃圾报告却让下一环节只抓取 `PASS` 就启动 Codex；不合格的正式交接不能在下游冒充有效批准。
15. **最低必要复杂度。** 不新增 Mica 依赖、强制浏览器网关、新常驻服务、第三人工角色、付费模型、数据库、另一套长时状态机或固定十页报告；优先用已有 GitHub 版本与 Planner/Critic/既有 Codex 入口。
16. **真实证明而非新规则自夸。** 用已发生的 Slurm、Bridge、Clear Writing、坏 Critic PASS 与至少一次没有补发“说人话”提醒的连续多轮正常工作验证；已见样本不是未见证据，用户否定实际结果不能被内部 PASS 推翻。

## 二、为什么现有 1.7 失效：不是缺规则，而是三处职责没有闭环

### 失效 A：用户说明不是设计与审查的共同对象

Planner 1.7 §4/§6 已要求机制与关键决定，Critic 1.7 §4/§6.3 已要求说明。但技术决策散在 Proposal/Plan，用户说明常在最终回答时由 Critic临场概括。即使审查准确，仍可把 Wrapper、精确 Hook、授权边界等决定性内容省略，用户不能在实施前有效否决。Clear Writing 只能改善已经选择的内容，不能替代架构语义审查。

### 失效 B：单轮回复虽有规定，下一角色不负责“拒收不合格解释”

过去出现三次内容无实质改善仍自报 PASS 的回复。旧合同主要规定**发送者应当**怎样答，没把**接收者必须审查用户交付是否充分**作为继续任务的实际前置步骤。所以 `PASS` 和 locator 可能绕过错误用户说明被继续消费。仅加一条同义“whole-response quality”不会改变这种失败路径。

### 失效 C：多轮只围绕最新 blocker，缺少同一版当前决策的持续展示

某轮 `REVISE` 修了一个风险，但原用户承诺、先前选定技术、替代取舍和已关闭问题没有稳定的用户阅读源。下一轮可能只解释最后一个 finding。旧版有精确 Git identity，却缺少将**技术变化、用户理解和当前进度**一起更新的完整轮次交付。

另有实质执行问题：Clear Writing Phase C 批准包缺归档物化/恢复和 fresh Web 执行者的真实接口证据；安全停止后交接只描述环境能力需求。保留 v0.7 对接口真实性和下一责任方的正确改进。

### 对 v0.9 和错误 v1.0 的直接否定

v0.9 只重述 Project setting/Role Contract 的默认读取，未补接收方拒收；不够。v1.0 转而新增 Mica/外部渲染和另一套批准工具，把聊天治理问题错误扩大为新产品开发，缺少当前正式用户入口/权限/成本证据；本版彻底排除，不引入新的主方案。

## 三、选择的机制：在既有双线程内建立“同版读者说明 + 相互交接验收”

### 3.1 单一当前方案：在原 Proposal 开头维护用户决策说明

每个重要架构任务仍沿用原任务键、既有 Proposal/Plan/Goal/Kickoff，不新建中央进度数据库或额外状态。Proposal 前部包含当前版本完整而比例适当的用户架构说明：

- 当前目标与进度，哪些判断已稳定；
- **真实技术选择及重要替代**，必要时明确哪个 Hook/命令/算法/模板、为何不用另一种；
- 一条代表性正常请求及关键失败请求的因果运行过程、权限/恢复边界；
- 本轮相对上轮修了什么、旧阻塞怎样关闭、当前尚未决定或证明什么；
- 对用户实际使用和下一步的影响。

它是同一个 Proposal 的读者层，不是第二份技术来源。技术方案或安全保证发生变化，Planner **必须在提交同一完整新版时同步修订这段说明**；如果技术未改变，无需每轮机械重写全文，只要确认当前说明仍对得上事实。Plan/Goal/Kickoff 只引用本版文件，不复制出多个会漂移的“架构真相”。

### 3.2 Critic 不审“有没有摘要”，而是审真实说明与技术是否一致

Critic 首先独立读取用户最初承诺和当前真实技术来源，再读这一版 Proposal。把用户说明与 Plan 中的具体机制、真实入口和最重要失败边界逐一比对。例如技术方案采用 Wrapper，用户说明却只写“通过钩子拦截”，或只覆盖 Codex Bash 却写“任意 shell 无法绕过”，应因实质错误 `REVISE`。如果替换成另一个显著不同的技术方案，正文几乎无需修改，则说明隐藏了有决策价值的设计。

Critic 自己也必须在本轮 review 的用户前部说明 **为什么** `PROCEED/REVISE/PASS`，不靠“已核对全文、测试足够、C1/C2关闭”替代判断。机器 findings 放后面给 Planner/Codex。

### 3.3 核心新机制：下一接收方验收交付，不只读取状态

在目前两个人工线程的现有自然交接处增加**接收义务**，不增加第三角色或额外正常循环：

- Critic 收到 Planner 方案时，检查当前用户决策说明**实际存在、可读、与当轮技术一致**；不合格就 `REVISE`，即使机器执行包结构齐全。
- Planner 收到 Critic 的 `PROCEED/REVISE` 时，先核对 Critic 实际有没有解释结论的用户意义、证据、保留部分、未完成问题和唯一下一入口；若只给状态/流水账，不当作完成的正式交付去推进新方案。由当前 Planner直接生成针对缺失的最小“补足审查交付”提示词，返回原 Critic；不让用户重新教“说人话”。
- **最终 `PASS` 改为“独立技术批准 → 原 Planner 交付验收 → Codex”**。这是本版对 1.7 §6.1/§6.2 **明确提出修改**的地方：Critic 仍是唯一独立技术裁决者，只它可以给 `PASS`，但 PASS 当轮不给最终 `COPY TO CODEX`；改给可直接转发原 Planner 的短 `COPY TO PLANNER`。Planner 必须从同版已审 Proposal 的用户架构说明与 Critic 原 review 重新读取并核对，负责最后展示**已审的机制正文 + Critic 的独立批准理由/剩余限制**，并渲染短 Codex 入口。Planner 不允许推翻 Critic 技术决定、自授 PASS 或扩权；若发现实质技术矛盾，返回 Critic/必要时重开设计，不能发给 Codex。

**额外成本明确披露：只在最终 execution-ready PASS 增加一次原 Planner 接收/交付核对及一次用户机械转发**。中间 PROCEED/REVISE 原本就交 Planner，无额外人工审查环。选择这点成本，是为了避免用户像过往那样收到未解释的 PASS 后直接去 Codex、几天后才从错误 Wrapper 或失效 Hook 发现路线错了。若未来已验证可由现有正常工具自动完成等价交付校验，独立新设计才能替换，不自行假设已自动化。

### 3.4 进度不断裂：当前轮次的读者信息始终从同一任务版本取

各阶段的用户可见正文的重点因 verdict 不同而不同：

- **Planner 初始设计：** 当前问题、实际技术选择、为什么、代表性流程、证明/风险、未定事项、送 Critic 审什么。
- **Critic `REVISE`：** 哪项机制会怎样失败；为何必须改；哪些正确决定保留；最小修补与下次证据；不是否定全部设计。
- **Critic `PROCEED`：** 哪些决策已经足以继续；为什么目前不等于可以执行；哪些 Plan/Goal/权限/实测前提仍需冻结。
- **Critic `PASS`：** 批准什么确切技术机制，过去真实 blocker 如何关闭、关键依据、还有哪些不在执行前批准范围内；明确下一步先交原 Planner 作读者交付接受，不给未经接受的 Codex 入口。
- **Planner 接受最终 PASS：** 忠实展示该版已经受审的架构说明与独立评判（不得临场改变技术），并给用户无需另外整理的短 Codex 提示词。
- **实现中断/发布状态：** 真实完成/未完成、影响用户的部分、普通 bug 回 Codex 还是语义改变回 Planner、谁现在继续、用户是否需要最小动作。

不是强制每轮复制完整历史大报告。当前已稳定且本轮未变的技术只需必要地再说明其与当前决定的关系；影响用户反对权的重要变化必须明确展开。

### 3.5 版本和交接如何保持一致

既有 GitHub commit/branch/文件就是权威定位，不新增自定义签名或 state schema。每轮：
- Planner 形成完整新 Proposal 和当前用户说明，提交并读回；交 Critic 的提示词包含准确任务、review 阶段、相关路径和不可变版本；
- Critic 独立核对相同版本，回复有自己的结论、用户解释和稳定 findings。当前连接如只能只读，完整回复即原始审查记录，由接收 Planner 忠实归档；不假称自己写了 review commit；
- 下一 Planner 先核对收到的 Critic review 所审版本与当前方案一致、是否真正解释了结论，再决定修订或最后交 Codex；
- Codex 入口开始前按现有仓库/Bridge 的正常权限和证据规则检查当前批准对象和相应用户授权，不把用户短提示词、聊天里孤立的 PASS 或旧 Review 当实质权限。此步只声称可由实际普通入口验证的身份检查，不说有浏览器级不可绕过拦截。

任务专用交接 prompt 只负责**准确位置**，通用质量职责来自 main 的正式角色合同；不会每轮加一串新写作规则。项目设置目前已经能路由两份角色合同，无需修改。

## 四、为什么优于旧方案，以及哪里仍需诚实

**旧：** Planner 有“应该解释”条款，Critic 最后临场写摘要、自评可读性，然后直接把 `PASS` 发 Codex；中间返修只报告局部 finding。

**新：** Planner 在审查前写完整用户决策说明；Critic 的专业审查包括这份具体正文；收到 Critic 结果的原 Planner必须检查它是否真正解释结论；最终 Critic PASS 不能再不经另一线程接收就直接流向 Codex，用户最终收到的是已审版本的说明而非 Critic 临场重写的审计流水。

新增的是**审查对象前移、下一责任方拒收、最终 PASS 后的独立接收、跨轮当前说明维护**，而不只是更多“写作规则”。

真实限制也必须承认：ChatGPT Web 没有我们已经验证的程序级回复发送拦截。角色合同仍可能被模型忽略；额外接收层增加的是现实独立检查机会，而不是绝对保证。**完成声明须靠真实无提示多轮验证；任何一轮报告不合格，就不能宣布整套机制已经正常可靠。** 本版不引入 Mica、任何新服务或低配“机器文本评分器”。

## 五、要证明什么，如何验收

### 5.1 本任务自己先试

这份 Proposal §一–四就是 Planner 实际准备给用户的设计说明，独立 Critic 本轮应亲自核对需求列表、原合同、真实事故和方案，并且它自己必须在回答中讲清 `REVISE/PROCEED` 的机制理由，不能只是说“本版更清晰”。

### 5.2 真实多轮反例与正例

复用真实 Slurm、Bridge Notifier/持久任务、Clear Writing Phase C 和近期失败的三次 Critic PASS；新增场景集中在实际未覆盖的能力，不机械加同义 Gate：

- **中途真实 `REVISE`：** 从一个明确的技术架构切换到不同机制；下一 Planner 必须同步当前用户说明，Critic 实际核对。仅改 findings 而仍显示过期机制为失败。
- **坏 Critic 接收：** 给下游 Planner 一份从真实历史抽取的“结论看似通过但正文只倒日志”的独立审查，Planner 在不接收额外说人话指令时必须判断不能作为有效读者交付，不会直接生成 Codex 执行入口；它应给原 Critic 一次具体的交付补正要求，不无故重开技术审查。
- **真实 `PROCEED`：** 说清哪些已稳定、为什么仍不能 Codex，下一 Planner 做什么，不能写成 PASS。
- **真实最终 `PASS`：** Critic 独立技术审查后只交原 Planner；Planner核实技术版本/报告/用户说明后，忠实向用户交付机制解释和短 Codex prompt。审查者与接收者不得由同一线程假装独立。
- **不应改变：** 普通解释、局部可逆修复不被升级成复杂审查；必要科研长推导、专业英文标识、代码与公式不能被强制压短。
- **真正无提示连续性：** 候选规则首次合法绑定后，在后续轮次只给普通任务和定位，不再复制“说人话”的答案；正式 main 集成后，还须在新真实插件/Bridge 设计任务观察相同结果。

已见真实反例为开发回归；成功的历史 Critic 阅读材料不能冒充未见样本。分开记录是否读过源、是否用了实际用户说明、是否可交接、实际是否能启动。评价是专业完整阅读，不以字段/字数/英文比例代替。

### 5.3 真实发布界线

正式角色合同的源修改、同候选评估、独立实现后检查、用户必要授权、集成到 main/远端回读与真实普通入口验证均须成立才称相应阶段完成。本治理不改变 Capability Gate 1.2、Project setting、产品代码、Mica/Bridge 或 Slurm。若实施阶段出现需要新增平台/模型服务才能交付的意外，不准在现有 1.8 授权下偷做；回 Planner–Critic。
