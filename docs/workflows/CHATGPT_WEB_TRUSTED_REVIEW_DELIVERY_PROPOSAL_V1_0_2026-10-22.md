# Planner–Critic 1.8 重新设计提案 v1.0：把架构说明从“模型应当输出”变成“可验证的正式交付”

目标仓库：`YuukiAS/AI_Skills_Collection`
设计分支：`design/chatgpt-web--pass-integrity-v0-4`
参考候选：v0.9 @ `074327fb212dce018972421289b65601b6910799`
正式治理基线：`main@f1de8e85957d32a50f4458349f450ec65add13bb`，Planner/Critic 1.7。
阶段：Planner 新设计轮，仅设计审查 `PROCEED/REVISE`；不得实施、合并 main、修改 Mica/Bridge 或开启付费验证。

## 1. 首先回答用户：为什么 v0.9 不足以相信

用户问：旧机制本来就依赖 Project setting → Role Contract → Handoff，为什么 v0.9 用同一链就能保证多轮返修仍说人话？

正确结论：**不能。v0.9 没有提供足够的新技术约束。** 它新增“说明提前写、随方案改、独立 Critic 阅读”，有必要，但触发、执行、最终用户显示仍全靠模型。正式 1.7 §4/§6.3 已要求解释具体机制，§2 已要求读合同，§6.2 已要求生成交接；现实中还是出现过隐藏实际选择、临场汇报审计流水、三次无实质改进仍自报 PASS、Phase C STOP 未完成下一入口。v0.9 的“继续靠合同”不能独立于同一失败原因。

新设计必须改变**被批准的对象、机器可检查的身份与用户真正消费内容的呈现途径**。否则即使合同升到 1.8，也只能说增加了文字规范，不能说堵住了过去的故障。

## 2. 对照真实事故找责任位置

### Slurm：用户不知晓决定性架构选择

已出现多轮 Wrapper/直接命令/Hook/MCP/本地确认等实质性选择；用户在批准前可能看不到实际采用的技术，从而无法提前否决。修法不是统一禁止 Wrapper，而是使“实际选择了什么、为什么、真实请求如何经过它、边界在哪”成为独立可审正文。正常审查必须用源证据反查，例如明确 `PreToolUse`、`PermissionRequest`、并行的 `mcp_tool`、`scontrol show job -o` 的真实作用，而不是“安全机制”。

### Critic 三次不合格 PASS：规则已在，但生成和自评是同一过程

现有 1.7 §6.3 要求解释技术和多轮 REVISE 的实质变化；Critic 连续用工作计划概述代替架构机制说明，且被用户指出问题后只修改交接长度。仅检查“回复出现架构段落/五字段”无法处理。必须有**事先固定、完整、可直接展示的用户架构说明**，在独立审查后不允许临场换文；还必须有一个不依赖原 Critic 自报的方式确认显示版本与被审版本相同。

### Clear Writing Phase C：PASS 前没有现实接口证明，STOP 后没有下一入口

旧方案没有证明真实插件归档可供恢复程序消费，也没有证明 Planner 能新建 fresh Web conversation/选择插件。受阻后回复仅说需要某种执行面。原 v0.7 正确的关键接口现实核对、条件性验证、下一责任方与可复制 prompt 全部保留，不因本轮用户说明改造而丢失。

### 共通失败

源文档、模型说它读过合同、机器字段、用户实际看到的消息之间缺少可验证的连续性；产物存在与用户真正收到、可理解不能画等号。额外写规则不足以修补这个断点。

## 3. 三种现实路线的比较与选择

**A. 继续只修改 Project/Role/Prompt。** 当前事实直接反证，无法拦住模型漏读、临场改写或假 PASS；不再当充分方案。

**B. 提前准备审定版用户说明，交原 Critic 独立评价，版本绑定并真实持续验证。** 这是 v0.9 的主线，实施代价较低，但原生 ChatGPT Web 没有强制呈现绑定版本的执行层，无法独立证明用户看到的就是受审原文。作为必要基础保留，不声称独自解决用户全部要求。

**C. B + 机器核对批准身份 + 受控的正式用户呈现入口。** 推荐作为能最终满足“多轮后不能退回空谈”的目标架构。先复用当前 GitHub 版本文件和独立 Critic，在现有 AI Skills 工具链中增加最小的同版批准核验；用户可见内容由真正受控的渲染入口读取**审定全文**，不由最后一条自由生成的 Critic 消息重写。若要在 ChatGPT Web 内直接显示，已有 Mica 浏览器扩展是可研究的最小候选，但**目前没有这个能力**；Mica 的 P0 功能边界、权限、加载状态、私有仓库读取与页面变更兼容性都须先证明，不能直接批准实施。

C 不是另建通用大服务或第三人类角色；其中“机器校验”只能保证版本与必要文件一致，文本是否真的讲清楚仍归原独立 Critic 和真实用户验收。无法验证的正式显示/执行入口不得被称为已实现。

## 4. 真实工作机制：一个 Slurm 设计从第一轮到第五轮

**第一次 Planner 提案**

在原 Proposal 的一个固定前部区域写完整`用户架构说明`，并记录影响判断的确切机制选择。举例：方案使用哪个 `PreToolUse` matcher，在命令真正运行前如何查 `scontrol` 的 JobId/Partition，原 `scancel` 是否被拒绝，MCP 是否确实在当前可见根聊天显示确认，为什么不用 Wrapper，以及安全覆盖边界。具体源依据仍留在同版技术 Plan，不倾倒给用户。

**Critic 第一次 REVISE**

Critic 不能只是说“说明合格”。它应独立对照用户承诺、源码和实际入口审查文稿，拒绝遗漏 Wrapper 的实际采用、技术保证夸大或没有恢复措施的决定。审查结论和所读 Proposal 的 commit/用户说明内容身份保持对应。

**Planner 改方案**

若改用 MCP/Hook 等不同架构，同一新提交必须改写该用户说明，解释旧选择退出原因、新流程和风险。原 Critic 的审查只对旧提交有效；不能跨方案重用。若仅修改不改变语义的错字，机械检查无需无限重审全文专业判断。

**后续 Critic PROCEED/REVISE/PASS**

新线程凭正式项目设置读取 `main` 角色合同、任务当前文件与前轮审查；交接 prompt 仅传任务和准确提交，不再重复用户的通用要求。Critic 审查说明与方案同版，若真实执行接口未验证继续 REVISE。最终 PASS 除独立结论，还必须绑定此版已审**完整**用户说明，不能把它临场换成审计清单。

**正式用户交付与 Codex**

对每个实际准备给用户看的审定说明，保留精确来源版本和读者正文身份；正式展示入口应从该来源直接呈现准确文本。若当前显示入口没有这项可观察能力，就不能称“受审正文已确保交付”，哪怕 Critic 在聊天里自报 PASS。

同理，短 Codex 执行入口只有在批准记录与当前技术包、用户说明的版本一致时才可被正常批准入口提供。若使用普通 ChatGPT Web 自由文本作为唯一交付，以上性质仍只是遵循合同，不可冒充技术强制。

## 5. 最小机器核对：保证哪个事实，不保证哪个事实

建议在 `AI_Skills_Collection` 既有 `scripts/skills.py`/测试框架内选择性实现一个有限的治理包核对操作，具体接口由最终审查冻结，**不是新后台服务**。输入为当前 task key、Proposal/Plan/Goal/Kickoff 的准确版本、当前拟展示用户说明的原文和 Critic 实际审查证据。它可以确定性拒绝：

- 技术包提交与审查对应版本不一致；
- 缺少完整用户说明或没有被审查的全文定位；
- 技术方案已经实质修改而审查仍绑定旧提交；
- PASS 记录缺少可验证的独立 Critic 来源或批准范围；
- 短执行入口指向另一个任务/版本或审查记录。

**不可夸大的地方：**文件哈希、字段匹配、格式检查不能证明中文自然，也不能证明 Critic 真的懂安全架构；更不能保证自由聊天实际显示了文件。审查真实性只能由可访问源码和独立评审证据支撑，不能把同一 GitHub 用户提交的一个字段伪装成独立加密签名。普通正式入口是否消费该工具必须用真实正常调用证明；如果只是 CI 报告，不能声称 Codex 已无法绕过。

## 6. 用户实际显示：必须正视 ChatGPT Web 不受控

对于用户要求的“我直接在当前聊天里看懂，而不是去仓库找文档”，只靠 GitHub 文件和角色 Prompt 没有真正的显示保证。

已有 `YuukiAS/Mica-for-ChatGPT` 0.1.7 有 ChatGPT Web 内容脚本与 DOM 观察能力；但当前职责是长线程可靠性和页面诊断，尚没有可信的“取得同版审定说明 → 验证审批身份 → 在当前界面呈现准确全文 → 无有效审查时标记未批准”的正式能力。它的 manifest 当前 host_permissions 仅有 ChatGPT Web，GitHub 源取用/私有权限未经批准也不可假设。

拟进行一个**有界、无生产副作用的可行性研究**，而非立刻大改 Mica：

1. 在本地隔离页面/公开安全样本中证明浏览器扩展能够读取一个冻结的公开 GitHub 源文，按正确版本原样呈现必要中文技术说明，且不通过生成模型再次改写；要有精确文本对比；
2. 技术方案提交变化、审查缺失、旧全文/新全文不匹配时，明显显示“未审/过期”，不能继续显示“已批准”或提供已批准的执行提示词；
3. 确认私有仓库资料如何经用户授权读取；不在扩展中存放 GitHub 密钥，不把对话原文/令牌上传到第三方；
4. 不破坏 ChatGPT 原生流式输出、输入、工具、授权和登录状态；不假装在未安装 Mica 的设备、ChatGPT Desktop、移动端自动覆盖；
5. 只有上述效果和 Mica 自身 P0 限制都允许，才能把它作为候选受控显示入口冻结执行设计。若不可行，回 Planner 比较其它**实际可控制**的呈现表面，不能退回“在 Prompt 里多写两句”并宣布完整需求解决。

这项研究目前属于跨仓库候选，**不在本轮获得 Mica 产品修改授权的范围内**。旧 v0.9 的“不得修改 Mica”保持有效，除非新的独立 Critic 设计审查与用户后续批准明确改变范围。

## 7. 保留当前 1.8 的正确部分

- Prompt 与中央角色合同冲突检查；
- 一次性 execution-ready PASS，准确批准定位与短 `COPY TO CODEX`；
- PASS 后解释、新矛盾与新增要求分类；
- 关键执行接口的直接证据/条件性验证、实现前无副作用探针、失败恢复；
- 非终态唯一下一负责人和实际可复制交接；
- 同一候选版本、真实 Web 产物验收、实现后独立审查、正常合入 main 与回读；
- 不让用户每轮重复提醒，“需要修谁”由现有 Planner/Critic 职责处理；
- 语义与读者正文质量仍需真实完整审查，历史 PASS 不等于新 PASS。

## 8. 分阶段真实验证，不把测试当保证

**验证一：用户说明质量（模型审查）**。用真实 Slurm 重要选择/替代方案与曾被用户否定的三条 Critic 回复、Bridge 通知配置、Clear Writing Phase C 停止交接，要求生成线程在不被喂答案的正常任务输入下披露具体机制、因果和边界。独立 Critic 阅读完整用户文本和真实方案，不是字段检测。修复期间使用这些已见负例不能声称未见泛化。

**验证二：版本与过期说明（可执行机械检查）**。同一任务连续 `REVISE → 新 Proposal → 新 Critic`，人工删除说明、保留旧审查、改变技术包身份、交换执行任务身份；验证实际核对工具会拒绝。正例必须让完全相同的提交/审查/说明通过。只通过此项不能声称人话合格。

**验证三：用户界面真实显示（当前待可行性证据）**。在隔离浏览器先做实际文本一致性/过期拒绝，再决定是否进入真实已登录 ChatGPT Web 的明确授权验收。不能把合成 DOM 视为正式 Web 成功。

**验证四：正式正常入口跨轮持续性**。真正 role contracts 合入 main 后，在未给特殊“说人话”提示的真实任务，持续观察初次设计、返修、独立审查、最终交付；审定说明不正确、不展示或交接失效，不能宣布“默认正常使用可靠”。

用户实际认同不是固定必需的每轮批准签字表，但用户指出实际不满意时不能用内部 PASS 推翻。

## 9. 本轮阶段与授权边界

当前只形成 v1.0 架构设计和必要评审材料，**不修改**两份正式角色合同、Project setting、Capability Gate Policy、Clear Writing 产品、Bridge Kit、Slurm、Plugin Creator、Mica、生产代码或全局浏览器设置。

此次建议比 v0.9 更有工程含义，也带来新增受控显示入口研究范围。它需要独立 Critic 在设计阶段判断现实可行性、复杂度、与用户要求的匹配程度；不允许把未验证的跨仓库能力留给 Codex 私下决定。

在正式执行就绪前必须选定的关键事项：哪些入口属于正式交付；具体机器校验点/当前正常入口能否自动消费；如果需要浏览器扩展，必须先拿到独立可行性证据与用户对跨仓库设计/权限边界的批准。未闭合时 `REVISE`，不能借最终 PASS 让 Codex“边做边猜”。

外部核查：GitHub 官方说明 required checks 只有实际配置分支保护/规则集后才阻止合并，当前 main 并未验证启用此保护，不可把新增 CI 说成发布强制保证。Chrome 扩展 content scripts 的独立执行环境和 DOM 能力可作可行性依据，不能代替实际 Mica 端验证。
