# 科研组会报告写作复盘 — 2026-08-29

本文记录一次中文科研组会报告的实际返修意见，并把可复用问题整理为 writing plugin 的后续规则。它对应的是科研报告写作，不是 CAT-TRACE 的幻灯片视觉规则；CAT-TRACE 的逐页复盘只作为“把用户反馈沉淀成长期规则”的组织方式参考。

## 1. 本轮触发复盘的材料

目标材料是 `Distributed_Imaging_Inference` 中面向导师组会的阶段性科研报告。报告需要同时满足两个用途：

1. 前半部分可以直接给导师看，用来说明科学问题、已有证据和下一步研究判断；
2. 后半部分可以保留作者自己需要的限制、候选路线、停止标准和证据位置。

用户明确指出，上一版报告虽然事实基本完整，但仍有明显的 AI / 模板写作痕迹。

## 2. 用户明确指出的三类问题

### 2.1 把内部验收状态写进导师面对的正文

原文示例：

> `最终 audit：PASS。`

问题：这只说明内部执行流程通过了机器验收，对导师理解科学问题、实验设计或结论没有帮助。它把内部质量控制语言提升成了科研叙事的一部分。

规则：`PASS`、audit token、commit、branch、job id、文件存在性检查等默认只属于证据附录或内部记录。除非它改变科学可信度且必须解释，否则不能进入导师面对的主叙事。

### 2.2 把一次 minor correction 写成独立章节

原文示例：

> `为什么又做了一轮 correction + stability？`

问题：whole-myocardium 定义修正、optimizer state 持久化等确实关系到结果有效性，但导师需要知道的是“最终实验到底怎么定义”，而不是执行过程中先错了什么、后来第几轮修了什么。把小的返修过程单独成章，会把报告写成开发日志。

规则：如果修正后的版本已经成为最终分析合同，面向导师时应直接把修正后的定义并入“实验设计 / 评价方法”。只有当历史错误本身改变对旧结果的解释、形成方法学教训，或导师明确问到，才单独说明。

### 2.3 人为制造不存在的时间限制和讲稿模式

原文示例：

> `如果明天只有 3 分钟，可以这样讲`

问题：用户并没有要求 3 分钟汇报。自动生成“30 秒版”“3 分钟版”“可以这样讲”等模板，会让正常科研材料像演讲教练模板，而不是研究者准备的组会内容。

规则：除非用户明确给出时间限制或要求口头讲稿，不得自动添加 `30 秒版本`、`3 分钟版本`、`elevator pitch`、`可以这样讲` 等章节。组会材料的默认目标是把科学逻辑讲清楚，而不是虚构时间约束。

## 3. 继续审查后发现的其他问题

### A. 按执行时间线组织，而不是按科学问题组织

“第一步做了 A → 第二步做了 B → 第三步又修了 C”只有在这些阶段对应不同科学问题时才有价值。否则听众需要自己从项目流水账里提炼研究逻辑。

导师面对的报告应优先回答：

- 老师原来让我们解决什么问题；
- 那篇方法论文提供了什么关键思想；
- 为什么这个思想不能直接搬到当前医学影像任务；
- 我们设计了什么比较来识别真正的障碍；
- 结果支持什么、不支持什么；
- 下一步哪个动作最能减少当前不确定性。

### B. 把工程动作当成科学节点

`preflight`、`audit`、`pipeline 跑通`、`push 成功`、`allocation 仍在运行` 等可以决定任务是否完成，但通常不决定科学解释。它们应留在证据和复现区域，不能和方法、结果、结论占同一叙事层级。

### C. 同一个结论重复三到四次

上一版存在“主表已经给数字 → 小标题再次写结论 → 正文重复同样数字 → 后面总结再说一次”的情况。科研报告需要必要的重复，但不能机械复述。

建议：

- 表格负责精确数值；
- 紧接表格的文字负责解释最重要的差异；
- 后续不再逐项复述整张表；
- 最后只保留对下一步决策真正必要的结论。

### D. 小标题过度模板化

连续使用 `结果 1 / 结果 2 / 结果 3 / 结果 4 / 结果 5`、`第一步 / 第二步 / 第三步`、`为什么又……` 会产生自动生成报告的节奏。

小标题应直接说明内容，例如：

- `集中式微调稳定改善原始 checkpoint`
- `Decoder 下，一次通信仍有小幅 pooled gap`
- `增加到 5 轮通信没有稳定收益`

但也不能每两句话就起一个标题；标题只用于真正改变论证层级的地方。

### E. 过度使用“不是 X，而是 Y”“真正”“最值得”“核心”

这些结构偶尔有用，频繁出现会形成明显模型腔，也容易人为抬高某个判断。

改法是直接陈述事实和逻辑。例如：

- 不写：`最有价值的结果不是某方法赢了，而是……`
- 写：`这轮首先确认了真实 CARE 分割的 one-shot 比较能够运行；方法优劣还没有定论。`

### F. 普通流程词保留了太多英文

`correction`、`stability`、`audit`、`setting`、`scope`、`candidate`、`objective information` 等在正文中大量出现，会让中文读起来像把内部 prompt 直接翻成报告。

专名和必须定位的技术词保留英文；普通流程词优先改成自然中文。`FedAvg`、`ODAL`、`Hessian`、`Dice`、`nnU-Net` 属于可以保留的技术名词；`audit PASS`、`correction round` 等不属于。

### G. 过度强调“报告本身”

类似“这份报告把……串起来”“这一部分可以直接讲”“下面给出可以汇报的版本”等元叙述，对真正阅读内容的人帮助很小。

成稿默认直接进入科学问题。只有文档确实有两个不同读者层级时，才需要一句话解释“前半部导师可读，后半部为内部判断”。

### H. 把有限证据写成过强的叙事转折

例如单个 CARE fold、短程 adaptation、3 个 seed 的结果，不宜写成“推翻了高维假设”“证明高维不是问题”。更合适的是：

> `当前结果没有支持“参数越多，one-shot 必然越差”这一简单假设。`

科研报告应保留数据范围和条件，不用戏剧化转折制造故事。

### I. 实现修复应进入最终方法定义，而不是故事正文

如果 optimizer state 的修复是为了让 R=1 和 R=5 的比较有效，那么最终正文应写：

> `多轮 FedAvg 中每个 client 保留自己的 AdamW optimizer state。`

而不是详细叙述“上一轮 reset 了，所以我们又 correction 一轮”。前者是科学合同，后者是开发历史。

### J. 给导师的问题必须是真的需要导师决定

`Questions for discussion` 不能为了“有讨论页”而制造。导师面对的报告可以在最后提出少数真实决策，例如：

- 是否认可把工作定位为 ODAL / surrogate-likelihood-inspired one-shot segmentation；
- 是否先在受控 adaptation space 中研究 objective summary；
- CARE 是否先作为方法开发数据、后续再独立复现。

如果一个问题已经由数据直接回答，就不要包装成“请老师讨论”。

## 4. 推荐的导师组会报告结构

默认顺序：

1. **科学问题和来源**：老师最初要求什么；相关论文给了什么思想。
2. **为什么现有方法不能直接解决**：一到两个真正障碍，不写泛泛 literature gap。
3. **最终实验设计**：数据、比较方法、训练预算、评价定义；直接写最终版本，不写返修历史。
4. **主结果**：一张可比较的表或图先给关键数字。
5. **解释**：哪些观察稳定、哪些仍不确定、哪些原假设没有得到支持。
6. **研究问题如何收缩**：基于当前证据，把下一步限制到一个可证伪问题。
7. **需要导师确认的决策**：只写真实需要拍板的事项。
8. **内部附录 / 给自己看的部分**：停止标准、候选方法、未解决技术风险、证据路径、复现信息。

这个结构不是固定模板。真正原则是按研究决策组织，而不是按执行日志组织。

## 5. 面向 writing plugin 的硬规则

以后生成“组会报告 / 导师汇报 / 给老板看的科研 Markdown/PDF”时：

- 不自动生成 30 秒、3 分钟或任何时间限制版本；只有用户明确要求才做。
- 不自动生成“可以这样讲”的逐字稿；除非用户要求讲稿。
- 主文禁止出现 `audit: PASS`、commit hash、branch、job id、validator token 等内部状态。
- minor correction、preflight、rerun、debug 不单独成章；若它改变最终科学定义，合并进最终方法。
- 不按 round / iteration / thread 顺序机械写流水账，除非阶段本身就是科学设计的一部分。
- 表格给数值，正文做解释；不得逐行复述整张表。
- 至少做一次去重检查：相同结论是否在标题、表格、段落和总结中重复三次以上。
- 至少做一次“导师相关性”检查：如果删除某段后导师对科学问题、证据和下一步判断完全不受影响，这段应移到内部附录或删除。
- 至少做一次英文密度检查，删除非必要的内部流程英文。
- 限制“真正 / 核心 / 最值得 / 不是 X 而是 Y / 首先其次最后”等自动生成节奏。
- 证据不足时写条件化结论，不使用“推翻、证明、显著优于”等戏剧化语言。
- 导师面对部分与作者内部部分可以分开；不要把 stop criteria、repo path、运行状态强塞进主讲内容。

## 6. 验收问题

一份导师组会报告在完成前至少要能回答：

1. 不知道仓库内部状态的导师，能否直接看懂我们为什么开始做这件事？
2. 是否清楚那篇论文 / 老师给的方法思想与当前工作有什么关系？
3. 是否一眼看得出最终用了什么数据、比较了什么、预算是否公平？
4. 主表之后是否给了判断，而不是重新抄一遍主表？
5. 是否把 `audit / correction / rerun / commit` 等内部过程误写成了科学内容？
6. 是否人为制造了“30 秒版 / 3 分钟版 / 可以这样讲”？
7. 下一步是否是一个能减少当前不确定性的动作，而不是“继续优化 / 继续实验”？
8. 需要导师确认的问题是否真的需要导师拍板？
9. 主文能否独立成立，而内部证据路径只作为后置支持？

如果以上任一关键问题失败，导师面对的报告不应视为定稿。
