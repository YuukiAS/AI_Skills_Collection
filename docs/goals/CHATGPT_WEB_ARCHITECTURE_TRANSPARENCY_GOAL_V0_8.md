# 目标草案 v0.8：用户在实现前看清并能反对架构

日期：2026-10-22。任务：`chatgpt-web--pass-integrity`。
状态：待设计审查；本文件不是执行授权，旧 v0.7 Goal 不再是当前方案。

## 用户结果

以后设计插件、Skill、Profile 或 Bridge 方案，用户在投入实现之前就能知道：实际选择的技术机制、必要的精确名称、为什么选择它、代表性任务怎样运行、保证在何处成立、失败如何处理，以及哪些事实仍未验证。用户不需要重读技术执行包，也不需要追问三轮才发现使用了自己不接受的 Wrapper 或其他方案。

正文保留会改变决定的技术深度；证据路径、提交、状态、测试流水放入仓库与机器交接。用户可以只复制后者，但前者必须足以支持判断与否决。

## 采用的具体办法

在原 Proposal/Plan 前部形成同版的“给用户的方案说明”。它不是另一个架构来源，而是同一方案中准备展示给用户的部分。Planner 同时提交说明和直接依据，原独立 Critic对照真实来源审查准确性、遗漏、机制选择、适用范围与关键失败链。

通过时交付被核对过的说明，附 Critic 自己的批准依据与边界；不在最后换成审计摘要。技术正确、说明忠实、用户能理解三项同时成立，才可完成该阶段的用户交付。

原来的唯一最终 PASS、完整执行包审查、短 Codex 交接、批准不代授权、普通实现错误同任务修复、实质语义改变回 Planner、接口真实性检查、候选冻结与 main 回读全部保留。

## 当前必须实际做

当前 Planner 正文直接展示本版提案的机制说明，并指出它对应的计划章节。下一位 Critic 阅读真实内容并作独立判断，不能只承诺未来实施时遵守。当前试用不冒充正式 1.8 部署，也不提前宣布用户满意。

## 正式实施完成标准

后续经设计认可、执行就绪批准及用户发送入口后，完成两份角色合同 1.8 的最小修改；同一候选通过本地与独立检查，原有真实案例验证不喂答案、不强迫 PASS、不换样本；正式 main 合入后回读版本与内容。

整体默认行为还须由一次提前冻结的真实正常任务证实：用户没有额外提醒读取规则或列出应讲要点，线程自行读取合同、解释关键机制并完成交接。没有证据就保持该项未验证，不能把读过技能、文件存在、字段齐全或一次示例顺畅等同于长期可靠。

## 不做什么

不增加第三人工角色、常驻审查服务、数据库、状态机、提示词编译器、强制发布网关或新的付费接口。不修改项目设置、能力验收政策、Clear Writing 产品、Slurm、Bridge Kit、Mica 或 Plugin Creator。

本方案仍是双线程与版本文件支持的工作合同。能约束批准对象与审查责任，但不冒充所有 Web 输出都被程序强制拦截。
