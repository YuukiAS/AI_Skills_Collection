# Goal 草案 v1.0：真正可审、可验、可向用户展示的架构决策

任务：`chatgpt-web--pass-integrity`；日期：2026-10-22。
状态：当前只做 Planner 方案和独立 Critic 设计审查；**不是** Codex 可执行 Goal。

## 用户成果

每次正式设计插件、Skill 或 Bridge Kit，用户在实现前直接知道：为什么选择具体机制、真正的技术名称、真实请求怎样经过它、为什么拒绝关键替代、保证与恢复边界、哪些尚未验证。用户不需阅读机器日志或每轮重申“说人话”。重大方案返修后，不再把旧审查批准和旧说明冒充新版本。

要让这个成果可信，必须区分：
1. 原独立 Critic 对照源码/用户要求审说明的**专业质量**；
2. 非模型校验工具对**已审说明、技术包、批准结果、执行提示词的版本一致性**；
3. 用户实际阅读表面对**受审原文的真实呈现**。

任何一项未实现，都不可宣称三项能力全部成立。

## 设计上的具体变化

保留 v0.9 在原 Proposal 提前写机制说明的方案，但**撤回 v0.9“角色合同与同版说明足以长期确保说人话”的过度主张**。

新引入：
- 受审用户说明作为正式交付源；
- 正常启动/交付路径上的最小可执行核对，阻止已审/实际用文本或技术包版本不一致；
- 对 ChatGPT Web 的正式呈现做明确技术入口核查，不把模型最后生成的一段话当成受控显示；
- 受控 UI 候选优先评价现有 Mica 的隔离可行性，未证明、未授权则不能修改它或声称支持。

原 1.8 重要能力全部保留：任务 prompt 兼容、关键接口现实证据、非终态唯一接收方、唯一 execution-ready PASS、同一候选验证及 main 集成回读、所有权限和真实失败边界。

## 最低可接受证据

1. 真实源码/方案与用户说明由独立 Critic 整体对照审查。隐藏 Wrapper 或错误解释 `PreToolUse` 必须被识别；
2. 同一任务跨轮替换技术方案/用户说明后，旧版审查或错误身份不能通过正常校验入口；
3. 没有经过审查的机器输出不得获得“已核准”展示或完整 Codex 正式交付状态；
4. 要声称 Web 端真实展示被审原文，必须通过一个已验证的受控显示入口，直接读取精确版本并按相同文本显示；若没有，则只声明合同层改进，整体用户目标未完成；
5. 新的正常插件/Bridge 任务不靠用户重复特殊提示即可持续应用角色合同；模型仍可能漏做，因此正式界面和启动核对是必要的独立约束，不是装饰。

## 边界

当前 v1.0 只提出上述架构，不实施任何工具、扩展或正式 1.8。不得修改 main、Project setting、Mica、Bridge、任何正式 Plugin、Capability Gate Policy 或系统权限；跨仓库受控呈现/启动须在有界可行性核对和独立审查后另获授权。

原生自由 ChatGPT Web 输出仍不受本项目掌控；设计不得谎称所有平台或模型输出永远没有错误。若需要真正确保看到同版已审文本，必须把正式呈现放到被本项目实际控制且验收过的入口，而不是在 Prompt 里重复“要说人话”。
