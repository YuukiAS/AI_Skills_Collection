# Full Source, Reviewed Candidate, Actual Delivery

This reference belongs to Writing Fidelity. It preserves meaning and artifact
identity across generation and delivery; it does not own natural Chinese
style, ordinary-answer content selection, domain decisions, or tool authority.
Use the chosen writing route for quality and the host's existing tools for
access. A pure Skill is not a transaction service or send-time hook.

## Establish The Operation And Complete Source

For each requested document, identify its audience, use, requested language,
protected content, and authorized operation. Distinguish local polishing,
structural rewriting, summarization, and new writing. A polish preserves the
agreed structure but examines changes in the whole document's context; a
structural rewrite preserves the content/evidence graph with the heavy route;
a summary may narrow scope only when authorized and labeled. New writing
needs sufficient verified content, not facts invented to fill a document.

Read the complete source and required supporting material. Follow pagination
or truncation to obtain all content. An excerpt, diff, stale chat, or cached
summary is not the full source. If the source or a required route/support
file/helper cannot be consumed, preserve the draft and precise gap but do not
substitute shallow sentence replacement for the requested full route. Withhold
the write when complete required source or full-candidate checks are missing.

Keep each requested chat, inline document, external document, interface text,
and exact machine payload distinct. Their success is not interchangeable.
The supported external-finalization claim for this version is GitHub UTF-8
text through an already connected host tool; other surfaces need their own
evidence. Nothing here creates account access or write authorization.

## Produce And Check The Actual Whole Candidate

Generate one complete readable candidate with the selected professional
route, not just a patch, outline, review report, or chat explanation. Heavy
Chinese scientific/technical rewriting retains Meaning Map, Reader Plan,
realization, assembly, semantic/exact fidelity, targeted repair and the
required mechanical helper. Its realization input isolation remains intact;
source-to-final fidelity and the reader pass remain separate operations.

Compare the whole candidate to the original request and complete source for
claims, numbers, formulas, citations, comparisons, conditions, negations,
uncertainty, responsibility, permissions, and unfinished work. Explicit user
waivers are not evidence that the waived behavior was tested. Use the heavy
route's source anchors/meaning ownership when that route applies.

Then have the selected style route re-read the actual complete candidate for
its reader purpose. Chinese prose owns the Chinese document pass; Response
Clarity owns a separate accompanying ordinary answer. If either pass exposes
a concrete defect, actually repair it and reassemble the full candidate.
Recheck affected source coverage and the whole reader context. These are two
different editing tasks by the same host model, not independent reviewers.

Bind the accepted candidate to its exact UTF-8 bytes and SHA-256. Substantive
repairs invalidate previous candidate review and bound receipts; regenerate
and revalidate applicable receipts, including heavy-route final hashes.
Never generate a different, unchecked body inside a tool's content argument.
Hashes establish identity, not prose quality or scientific correctness.

## GitHub Existing File

1. Fetch full UTF-8 source and its current blob SHA from the exact repository,
   authorized writable branch, and path. Bind that target identity; an
   immutable source commit does not authorize choosing a writable branch.
2. Prepare and review the complete candidate as above. Immediately before
   writing, fetch the same branch/path again. If its blob SHA differs from
   the bound source SHA, stop without writing; do not overwrite or silently
   rebase a stale candidate.
3. Use the existing update operation with the complete reviewed content and
   that blob SHA as the expected source version. Do not fall back to an
   unconditional overwrite or a different target. Record the returned commit
   and content/blob SHA.
4. Fetch the same target's entire written content. Verify repository, branch,
   path, returned content/blob identity and exact byte equality with the
   reviewed candidate; retain the returned commit and evidence for inspection.

## GitHub New File

Confirm creation is authorized for the exact repository, writable branch and
path, verify the target does not exist, and bind the branch's prewrite head.
Obtain complete authorized content grounds and review the full candidate.
Use the host's non-overwriting create operation with that candidate, never an
update/overwrite fallback. Read back the returned commit, parent and created
path: verify the parent matches the bound branch head and the change is the
intended file creation. A mismatch is an unverified delivery, not permission
to reset other work or silently retry. These post-action observations are not
a strict concurrent-transaction lock. Fetch the full created file and check
the same identity and byte equality as for updates.

## Local Files And Publication

Codex writes the reviewed candidate to the authorized local path and actually
reads the complete saved file back for byte identity and reader quality.
Local success is not GitHub success. When remote publication was explicitly
authorized, follow the repository's normal commit/publish rules and read the
target at the exact remote commit back. Preserve unrelated work and verify
remote content equals the reviewed candidate. Do not invent a branch, bypass
a bounded publisher, or grant yourself external write permission.

## Re-read The Saved Artifact And Report Truthfully

After identity checks, read the entire saved text as a reader, not only the
tool receipt. If its quality or source coverage is still deficient, matching
bytes do not make it a final document. Within the original authority and safe
version conditions, form a repaired complete candidate and repeat its checks
and write/readback sequence. Otherwise explain that the file was written but
has not reached final quality. Never erase a real formal Gate failure by
rerolling; formal evaluation obeys its frozen attempt/recovery contract.

Use existing per-object statuses without creating a persistent state machine:

- `TARGET_SOURCE_INCOMPLETE`: required complete source is unavailable; no write.
- `TARGET_IDENTITY_DRIFT`: prewrite target version changed; no write.
- `ARTIFACT_NOT_WRITTEN`: write unavailable or rejected without a successful write.
- `ARTIFACT_FINALIZATION_UNVERIFIED`: write may have happened but full readback,
  identity, fidelity, or final reader quality is not established.
- `ARTIFACT_FINALIZED`: the required whole-candidate checks, authorized write,
  exact full readback and actual saved-artifact review all succeeded.

Report the actual outcome and location for each object. A clear chat reply
cannot finalize the document, and a good document cannot excuse a misleading
chat completion claim. Keep complete question/source/candidate/final artifacts
available to the task's independent artifact reviewer; self-reports and hashes
alone do not satisfy release-quality acceptance.
